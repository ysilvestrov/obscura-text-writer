# Стабільна пам’ять твору на дешевих моделях: wire-формат v3

Дата: 2026-11-07
Статус: затверджено 2026-11-07

## Для власника

**Мета.** Етап пам’яті перестає падати через механічні порушення формату на дешевих швидких моделях (Venice Gemma, Qwen, GLM). Менше ручних повторів, менше часу на кожну сцену, а журнал пам’яті й історія не змінюються.

**Що зміниться для тебе.**
- Стандартний промпт пам’яті переходить на новий формат відповіді. Обирати нічого не треба: власні промпти старого формату працюють як раніше, доки ти сам їх не перепризначиш.
- Якщо для ролі пам’яті вибрати режим відповіді `json_schema`, Venice сама не дозволить моделі перевищити ліміт `add` у категорії, вигадати ID фрагмента чи змінити факт. Загальний ліміт у 12 операцій і повторну зміну одного claim схема не примушує, їх і далі ловить лише сервер. Чи вмикати цей режим автоматично, вирішуєш ти (питання 1).
- Невдала спроба показує всі знайдені порушення одразу, а не лише перше. Повідомлення помилки називає кількість і перші три, а повний список (до 50) видно в деталях спроби.
- З’являється локальна команда, що проганяє вже збережені відповіді через новий парсер і рахує результат без жодного виклику моделі.
- Незворотного: нові записи пам’яті можуть містити додаткові цитати-докази, і старіші версії застосунку такий журнал не прочитають (див. «Що стане гірше»).

**На чому стоїть рішення.**
- Головна причина відмов — механічні порушення контракту, а не мережа: із 42 відповідей, що зараз не проходять перевірку, усі мають порушення формату чи правил операцій. `[проба]` П1
- 37 операцій містять кілька наявних ID фрагментів в одному полі `evidence_id`, і саме це найчастіша помилка. Моделі природно потрібно кілька доказів, бо фрагмент — це один рядок прози. `[проба]` П1, П3
- Часто модель намагається оновити або закрити факт чи подію хронології (9 відповідей). Причина: каталог віддає їй `claim_id` цих незмінних категорій. `[проба]` П1, П4
- Venice для Gemma 4 і Qwen 3.8 справді примушує `maxItems` і `enum` у `json_schema` навіть тоді, коли промпт прямо вимагає порушити ліміт. `[проба]` П2
- Журнал v2, цитати, атомарна публікація й історія спроб лишаються джерелом правди; змінюється лише те, що повертає модель. `[вимога власника]` (AGENTS.md, SPEC.MD MEMORY-001…004)
- Вибір дешевих і швидких моделей має пріоритет. `[вимога власника]`
- Перехід на wire v3 у режимі `prompt_json` без схеми теж зменшить кількість помилок, бо ліміт стає видимою довжиною масиву, а категорія — структурою. Наскільки саме, проба не доводить. `[виведення]`
- Гіпотеза, а не встановлений факт: семантична якість тверджень (повнота, правильність висновків) від нового формату не погіршиться. Жодна проба семантику не вимірювала. Межа у 3 докази може змусити модель звузити підтвердження твердження, якому потрібно 4 фрагменти (6 із 37 операцій у П3). `[виведення]` Гіпотезу перевіряє огляд власником на кроці приймання 2. Якщо якість погіршиться, це стоп-сигнал для злиття.

**Ключові рішення.**
1. **Окремий wire-формат v3 для моделі; журнал v2 без змін.** Модель повертає операції, згруповані за категоріями. Сервер перекладає їх у чинні події журналу. Відкинуто: змінювати сам журнал (дорога міграція, ризик для історії) або лише посилювати промпт (бріф показав: правила вже були в промпті, а порушення лишилися).
2. **Кілька доказів зберігаються додатковим полем `supporting_quotes` (0–2) у події журналу.** Основна цитата лишається в `quote`. Відкинуто: зберігати тільки перший доказ (губиться підтвердження, на яке посилалася модель) і цитувати суцільний проміжок прози від першого до останнього ID (у 19 із 37 випадків ID стоять на відстані 10+ рядків, і цитата роздулася б до абзаців).
3. **Категорію й scope для `update`/`retire` сервер бере з каталогу, а не з відповіді моделі.** Каталог показує ID лише для змінних категорій. Відкинуто: залишити копіювання й перевірку (6 відповідей ламаються саме на ньому).
4. **Повна діагностика замість першої помилки.** Відкинуто: зберегти Pydantic first-error (неможливо порахувати причини й виправити відповідь за один раз).
5. **Автоматичний раунд виправлення в цю зміну не входить.** Після v3 і схеми з’ясується, скільки помилок лишилося. Якщо потрібно, раунд виправлення піде окремою спекою разом з рішенням про вартість. Відкинуто: робити його зараз (зачіпає чергу, білінг і згоду на витрати R-08, а це вже розмір L).
- Розглянуто стандартне: function calling / tools замість `response_format` — відкинуто, бо та сама JSON Schema вже примушується через `response_format` (П2), а tool calls Venice для цих моделей ніхто не перевіряв.
- Розглянуто стандартне: бібліотеки примусового декодування (Outlines, guidance) — відкинуто, бо працюють лише з локальними моделями, а не через API Venice.

**Що стане гірше.**
- Журнал із `supporting_quotes` не прочитає жодна старіша збірка застосунку (`extra=forbid`). Відкат на старий коміт після першої такої сцени потребуватиме відновлення з резервної копії.
- У застосунку буде два wire-протоколи пам’яті (v2 для власних промптів і v3 стандартний) і більше тестів сумісності.
- Динамічна схема (enum усіх ID фрагментів і змінних claim) збільшує запит у режимі `json_schema` приблизно на 10–15 символів на фрагмент. Сцена на 200 рядків — це близько 3 тис. символів, менше 1 тис. токенів.
- У режимі `prompt_json` модель і далі може порушити ліміти: їх ловить лише сервер. У `json_schema` поза схемою лишаються загальний ліміт 12 операцій і повторна зміна claim.
- Для тверджень, яким потрібно 4 і більше фрагментів, модель муситиме обрати 3 найсильніші докази. Підтвердження стає вужчим.
- Семантичних помилок нові обмеження не усувають.

**Оцінка.**
Власник: M. Автор: M.
Розбивка: wire v3, переклад у журнал і динамічна схема — 30%; промпт v3, каталог і контракт промпту — 15%; повна діагностика — 15%; команда офлайн-повтору — 10%; SPEC.MD, traceability, тести сумісності, інструкції UA/EN — 30%.
Дешевший варіант (S): лишити плаский v2, дозволити `evidence_ids` і брати категорію/scope з каталогу. Він закриває 9 із 42 відмов, але не закриває найбільший залишок — ліміт `add` (17 відповідей) і оновлення незмінних claim (9). Для плаского списку `maxItems` на категорію в схемі не задається.

**Питання до власника.**
1. Чи вмикати для ролі пам’яті `json_schema` автоматично, якщо модель у каталозі має `supportsResponseSchema=true`? Альтернатива — лишити `prompt_json` за замовчуванням і лише рекомендувати схему в інструкції та налаштуваннях. Пропоную друге: налаштування ролі не змінюються без тебе.
2. Чи погоджуєшся, що перший журнал із `supporting_quotes` робить відкат на старі збірки можливим лише через резервну копію?

Рішення (07.11.2026): власник затвердив спеку без правок, тож запропоновані варіанти стають чинними. 1 — `json_schema` автоматично не вмикається; налаштування й інструкції лише рекомендують його для моделей зі `supportsResponseSchema=true`. 2 — обмеження відкату прийнято.

## Технічний опис

### Проби

**П1. Офлайн-повтор збережених відповідей.** Скрипт у scratchpad, read-only (`mode=ro`), виводить лише лічильники без текстів. Він проганяє `partial` кожної завершеної або невдалої спроби `evidence_delta` через чинний `parse_memory_result` із тим самим `previous_memory`, прозою й дозволеними персонажами, а потім класифікує всі незалежні порушення кожної відповіді.

```
attempts (completed/failed, evidence_delta): 114
current validator now: pass 60, fail 42, json 7, no_expected 5
independent issues: evidence_missing 42 (ops), evidence_multi_valid 37 (ops), add_over_3 20,
  target_immutable 9, target_meta_changed 6, target_twice 4, scope_on_nonstate 1
issue types per failing response: 1 → 31, 2 → 9, 3 → 2
fully fixed by wire (multi-evidence + server-side meta): 9
residual types after wire: add_over_3 17, evidence_missing 10, target_immutable 9, target_twice 4
sanity: passing-now responses with classifier issues: 0
```

Повторний прогін того самого скрипта 07.11 (база поповнилася трьома спробами): 117 спроб; pass 61, fail 44, json 7, no_expected 5. Wire без схеми повністю виправляє 10 із 44. У режимі `json_schema` невалідними лишаються 5 відповідей, усі через `target_twice` (у двох це єдина причина), тобто охоплено 39 із 44. Висновки спеки не змінюються.

Із 7 відмов JSON шість — порожні відповіді (обрив у провайдера або старий ліміт виходу), одна — обгортка, яку `unwrap_model_json` не зняв. Із 114 спроб база вже містить більше, ніж 91 у бріфі, бо спроби тривали й після нього.

Залишок після v3 у режимі `json_schema` (виведення з П2): `add_over_3` неможливий (`maxItems`), `evidence_missing` неможливий (`required`, `minItems: 1`), `target_immutable` неможливий (у схемі немає `update`/`retire` для `facts`/`timeline`, а `claim_id` має `enum`). Лишається `target_twice` (4): масив не може примусити унікальність полів об’єктів, тож це ловить сервер. Так само лишається `ops_limit`: схема не має обмеження на суму довжин кількох масивів (наприклад, 4×3 `add` і одна `update` дають 13 операцій). У збережених відповідях такого випадку не траплялося, але сервер відхиляє його кодом `ops_limit`.

**П2. Примус схеми у Venice.** Синтетичний нейтральний текст, по два запити до `gemma-4-uncensored` і `qwen-3-8-27b`, `temperature=0.7`. Промпт вимагав рівно шість фактів, неіснуючий `f000009` і кілька ID в одному рядку; схема мала `maxItems: 3` і `evidence_ids.items.enum` з трьох ID.

```
gemma-4-uncensored 0 items 3 bad_ids [] usage 112 116
gemma-4-uncensored 1 items 3 bad_ids [] usage 112 120
qwen-3-8-27b       0 items 3 bad_ids [] usage 109 81
qwen-3-8-27b       1 items 3 bad_ids [] usage 109 81
```

Каталог Venice (`/models?type=text`, uncensored) показує `supportsResponseSchema=true` для `gemma-4-uncensored` (вхід $0,1625/M, вихід $0,50/M, ліміт виходу 8192), `qwen-3-8-27b`, `olafangensan-glm-4.7-flash-heretic` ($0,07/$0,40) та інших. Для GLM примус окремо не перевірявся.

**П3. Розкид кількох доказів.** Серед операцій із кількома ID: 2 ID — 12, 3 ID — 19, 4 ID — 6. Відстань між першим і останнім: 1–5 рядків — 10, 7–9 — 8, 10+ — 19. Межа «до 3 доказів» покриває 31 з 37 операцій; решту схема змусить звузити.

**П4. Каталог.** `memory_catalog` (`memory/projection.py`) серіалізує всі активні claim із `claim_id` і `category`, включно з `facts` і `timeline`. Валідатор (`replay_memory`) дозволяє `update`/`retire` тільки для `character_states`/`open_threads`.

### Wire v3

Контракт промпту `memory/evidence_delta/3`. Відповідь моделі:

```json
{"schema_version":3,
 "facts":{"add":[{"text":"…","evidence_ids":["f000012"]}]},
 "timeline":{"add":[]},
 "character_states":{
   "add":[{"text":"…","character_ids":["<id>"],"evidence_ids":["f000031","f000044"]}],
   "update":[{"claim_id":"mc_…","text":"…","evidence_ids":["f000040"]}],
   "retire":[]},
 "open_threads":{"add":[],"update":[],"retire":[]}}
```

- Усі ключі обов’язкові, а порожні масиви дозволені. `add` має до 3 елементів у кожній категорії, а всіх операцій разом — до 12, як у MEMORY-002.
- `evidence_ids` — від 1 до 3 унікальних ID фрагментів поточної прози. Перший стає `quote`, решта йдуть у `supporting_quotes` у порядку переліку.
- `character_ids` є тільки в `character_states.add`. В `update`/`retire` їх немає, бо scope і категорію сервер бере з активного claim.
- Переклад детермінований: порядок подій — категорії в порядку `CATEGORIES`, усередині категорії йдуть `add`, потім `update`, потім `retire`, а в масиві зберігається порядок відповіді. `event_id`/`claim_id` рахуються чинними `stable_id`. Якщо `supporting_quotes` порожній, значення й хеші ідентичні v2-операції з тим самим першим доказом, а непорожні `supporting_quotes` входять у хеш.
- Після перекладу виконуються всі чинні перевірки `replay_memory`, CAS і атомарна публікація.

**Динамічна схема** (лише `response_mode=json_schema`, будується на кожен запит із captured даних спроби):
- `evidence_ids.items.enum` — ID фрагментів поточної прози; `minItems: 1`, `maxItems: 3`. Поправка 07.11: `uniqueItems` не використовується, бо Venice його відхиляє (Qwen — `400 Grammar error: Unimplemented keys: ["uniqueItems"]`, Gemma — `500`). Унікальність доказів перевіряє сервер (`evidence_count`).
- `claim_id.enum` для `update`/`retire` кожної змінної категорії — активні claim цієї категорії. Якщо їх немає, масив має `maxItems: 0` без `enum`.
- `character_ids.items.enum` — дозволені персонажі сцени (`memory_allowed_character_ids`). Якщо їх немає, `maxItems: 0`.
- Схема зберігається в exact request спроби, як і зараз, і входить в оцінку токенів (R-07).

**Каталог v3** (`projection_version=memory-catalog-v3`): два розділи. Змінні (`character_states`, `open_threads`) — з `claim_id`, текстом і scope. Незмінні (`facts`, `timeline`) — лише текст, щоб модель не дублювала. Для v2-контракту лишається чинний каталог.

**Сумісність.**
- Промпт із `memory/evidence_delta/2` і далі отримує v2-каталог і v2-схему та розбирається чинним parser. Автоматичного перепризначення немає (PROMPT-CONTRACT).
- Стандартний промпт стає `memory_delta_uk_v3.txt`. Збережені налаштування, що посилаються на стандартний промпт, отримують v3.
- Відповідь v3 на промпт v2 і навпаки відхиляється конкретною помилкою, без прихованого переходу між parser (MEMORY-003-S02).
- `MemoryEvent.supporting_quotes: list[str]` — від 0 до 2 елементів, за замовчуванням порожній. Кожен елемент — непорожній дослівний фрагмент того самого `source_version_id`. `schema_version` журналу лишається 2: поле адитивне, старі журнали валідні без змін. `validate_memory_journal`, fsck і ручне збереження перевіряють `supporting_quotes` так само, як `quote`. Бекап і відновлення переносять bytes без конвертації.
- Ручне редагування пам’яті показує й зберігає `supporting_quotes`. Ручний JSON без поля лишається валідним.
- `legacy_view` і проєкція для письменника цитат не показують, тож для них нічого не змінюється.

### Повна діагностика

Перевірка моделі збирає всі незалежні порушення в список `{operation: <категорія>.<дія>[<індекс>], code: <код>}`. Коди: `evidence_unknown`, `evidence_count`, `add_limit`, `ops_limit`, `target_unknown`, `target_twice`, `scope_unknown`, `schema`; також `target_meta` (лише v2: змінено категорію чи scope claim) і `wire_version` (відповідь іншої версії wire, ніж у контракту промпту). Поправка 07.11 під час планування, розділ власника не змінює. Список (до 50 записів, без текстів і значень моделі) зберігається в `attempt.context.memory_violations`. Повідомлення помилки показує кількість і перші три. Деталі спроби в UI (історія спроб) показують увесь збережений список, і він доступний через чинний API спроби. Якщо порушень більше 50, видно лише лічильник решти. JSON decode і конверт перевіряються першими: якщо JSON не розібрався, далі перевірка не йде. Для v2-відповідей працює та сама колекція з індексами `operations[i]`. Межі безпеки MEMORY-004 (без відлуння model input) чинні.

### Команда офлайн-повтору

`python scripts/memory_replay.py [--db <path>] [--story <id>]` відкриває базу read-only (`mode=ro`), бере збережені `partial` спроб пам’яті й проганяє їх через чинний і v3-сумісний валідатор. Друкує лише лічильники: pass/fail, коди порушень, кількість спроб без сирої відповіді. Тексти, ID персонажів і claim не виводяться, мережі немає. Збережені v2-відповіді команда оцінює двічі: «як є» і «v2 з серверною категорією/scope та розщепленими доказами». Повноцінна оцінка v3 можлива лише на нових відповідях. Команда — засіб розробки, в UI не входить.

### Зміни SPEC.MD і traceability

## Заявка → доказ

| Заявка | Де записується | Що доводить | Сила |
|---|---|---|---|
| Подія пам’яті має дослівний доказ | `MemoryEvent.quote`, `supporting_quotes` у журналі | `validate_memory_journal`: кожна цитата — підрядок тексту `source_version_id` при збереженні, fsck і ручному збереженні | сильна |
