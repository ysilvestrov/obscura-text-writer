# R-21 — Налаштування: розділи й форми без обов’язкового JSON

Дата: 23.10.2026. Статус: дизайн погоджено власником («Так, виглядає ОК»); реалізацію завершено за планом 2026-10-23-r21-settings-workspace.md; межі перевірок — у журналі виконання.

## Мета та погоджені рішення

Автор має швидко знайти модель, контекст, reasoning чи оцінювач для поточного твору, змінити потрібне й повернутися до сцени. Нинішні послідовні форми чотирьох ролей, оцінювач у JSON та окремий JSON класифікатора перевантажують сторінку.

Власник обрав меню розділів ліворуч, одну відкриту форму та компактний вибір розділу на мобільному. Збереження — поточний розділ або роль. Незбережені буфери зберігаються при перемиканні, позначені в навігації; вихід зі сторінки потребує рішення.

## Розглянуті підходи

1. Меню ліворуч і одна форма: зрозуміла адреса налаштування, достатня ширина для полів. Обрано власником.
2. Верхні вкладки розділів: компактніші на широкому екрані, але довгі назви й вкладені ролі створюють дві смуги навігації. Не обрано.
3. Нинішня сторінка зі згорнутими картками: менша зміна, але залишає довгий документ і пошук потрібного блоку. Не рекомендується.

## Погоджений склад сторінки

П’ять розділів: Письмо, Моделі, Оцінювач, Бюджет, Комплекти. Заголовок «Налаштування» з назвою твору та одним поверненням до сцени. Чинні пергамент/винний акцент/шрифти DESIGN.md зберігаються; це зміна композиції, не бренду.

### Письмо

Жанр, тональність, точка зору, граматичний час, авторські правила й орієнтир фіналу. Завершення попередньої сцени — у додаткових параметрах. Короткі підказки, без повторення великих технічних пояснень у кожній формі.

### Моделі

Перемикач ролі: Планувальник, Письменник, Редактор, Пам’ять. Короткий підпис поточної моделі допомагає бачити призначення, але повна форма завжди одна.

Основне: провайдер, модель із явним завантаженням каталогу, контекст, резерв відповіді, температура; поведінка конкретної ролі (режим редактора/пам’яті й доступ до майбутніх планів). На одному екрані видно, скільки контексту лишається для входу, без обіцянки точного токенізатора. Reasoning Venice показаний зрозумілим станом; поля effort і disable_thinking лишаються взаємовиключними. Каталог не встановлює ліміти й не викликається автоматично.

Додатково: адреса локального API, timeout, ліміт символів, формат структурованої відповіді, usage, stop-послідовності, провайдерські параметри й назва env-змінної ключа. Секретні значення не показуються й не вводяться тут. Промпти — окрема згортка з чинними контрактами та поверненням стандартного промпту. Власний промпт не перепризначається новому режиму мовчки.

Чинна дія застосування підключення до всіх чотирьох ролей лишається явною, з поясненням меж (provider/model, а не чужі промпти/ліміти/режими). Якщо вона зачіпає незбережені налаштування підключення інших ролей, показати їх список і вимагати рішення; не стирати решту буферів.

Необов’язковий класифікатор редактора отримує власні звичайні поля під згорткою, з вимкненням і поясненням окремого виклику лише за кнопкою. JSON не потрібний для його налаштування. Це вкладені налаштування ролі редактора й зберігаються разом із нею.

### Оцінювач

Звичайна форма: provider (local/OpenRouter/Venice/Codex CLI), model, context_tokens, max_output_tokens, max_input_chars, temperature, timeout_seconds, response_mode. Поля й підказки залежать від provider; Codex може мати model=null, а адреса cloud фіксована офіційним endpoint. Venice — include_system_prompt і disable_thinking; не додавати непідтримуваний EvaluatorConfig параметр reasoning_effort.

Угорі — поточний стан: вимкнений/лише звіт/пауза при проблемі, candidate чи перевірене калібрування, а також refusal block з реальною причиною. Немає кнопки самостійно «зняти блокування» чи галочки «калібрований». Пауза недоступна без чинного server-verified калібрування з поясненням поруч. Вибір іншої моделі не виконує оцінку й не скасовує історичні блокування.

Критерії й пороги — додатковий блок із назвами критеріїв, цілими порогами 0–4, блокувальними рівнями й мінімумом цитати. Fingerprints і допуск калібрування read-only. Зміни порогів у каліброваному профілі потребують явного створення candidate-профілю; вони не підтверджують нове калібрування. Зміна конфігурації зберігає чинну серверну перевірку fingerprint/допуску й пояснює втрату допуску до збереження.

Якщо збережена policy=pause_on_failure, а чернетка змінює fingerprint або створює candidate, форма показує несумісність біля policy та блокує Save, доки автор явно не вибере report або off. Політика не змінюється автоматично; попередня збережена конфігурація діє до успішного збереження. Це рішення погоджене разом із макетом після builder-check.

Негайне вимкнення оцінювача лишається доступним через чинний policy API, незалежно від валідності незбережених полів. Воно зберігає решту чернетки форми та узгоджує policy, не перезаписуючи весь JSON. Увімкнення зберігає чинну семантику explicit policy API; без збереженої конфігурації UI пояснює використання чинного серверного fallback, перш ніж виконувати цю дію. Повна конфігурація зберігається окремою кнопкою.

Необов’язковий технічний JSON зберігає експертну сумісність. Він має єдину чернетку даних зі звичайними полями: явне застосування валідного JSON оновлює поля; невалідний JSON не підмінює останній валідний об’єкт. Імпорт/експорт не містить ключів, а лише env-назви. Готові приклади не оголошуються каліброваними.

Незастосований raw JSON — окремий dirty буфер цієї ж форми. Він переживає перемикання й негайний off. Повне збереження та зміни звичайних полів заблоковані до «Застосувати JSON» або «Відкинути правки JSON»; вхід у JSON не стирає звичайну чернетку. Останній валідний об’єкт та введений raw текст не синхронізуються через мовчазне перетирання. Конкретний вигляд цих двох дій лишається builder choice.

### Бюджет та Комплекти

Бюджет: ліміт твору/типовий запуск, поточний облік, останній виклик; тарифи та звірка у згортках. Відсутні ціни/usage відрізняються від нуля. Чинні окремі збереження політики/тарифу/звірки зберігають власні API-ревізії.

Комплекти: вибір/preview/застосування, збереження поточної конфігурації як версії, import/export. Застосування не знищує незбережені буфери без явного рішення. Результат preview та чинні правила походження/калібрування збережені.

## Збереження та навігація

Закріплений рядок над відкритою формою: статус і «Зберегти [розділ/роль]». Немає глобального прихованого Save all. Збереження охоплює й приховані додаткові поля цієї форми. Помилка лишає введення, показує конкретну причину й переводить до першого проблемного поля; успіх не перебудовує чужі буфери. Повернення до збереженого стану — явна дія поточної форми.

Реєстр буферів відділяє серверні дані, редаговані значення, dirty/busy/error та baseline кожної області. Власне успішне збереження оновлює відомі ревізії без очищення інших чернеток. Чинні CAS-конфлікти не приховуються автоматичним перезаписом. Зовнішні зміни показуються явно. Складнішу паралельність і серверну модель оцінювача без CAS не оголошувати вирішеною редизайном; R-15 відкладена.

Deep links із R-20 (role/scene/material і #role-...) відкривають правильний розділ та роль перед фокусом на полі; повернення зберігає сцену/матеріал. Section/role з URL — allowlist, без довільних redirect. Перемикання розділів не запускає API збереження, discovery або inference.

На мобільному меню замінює select, форми одноколонкові; keyboard focus/labels/summary доступні. Dirty позначається текстом/доступною назвою, не лише кольором. Loading/error окремих блоків не видається за успішно завантажені default-налаштування.

## Архітектура та межі

Jinja/ES modules/CSS без нового UI-фреймворку. Спільна форма підключення — з окремими адаптерами ProviderSettings, ClassificationSettings та EvaluatorConfig (у них різні поля й default/null-семантика). Серверні моделі/валідація/відмови/профілі/бюджети залишаються авторитетними. Відомі збережені поля, які не редагували, мають пережити round-trip без скидання; legacy профілі не перетворюються на нові defaults.

Не входять: калібрувальні платні прогони, нові моделі/тарифи, зміна генераційного workflow, R-22/R-23, автоматичне reasoning або context tuning. Жодного модельного виклику від перегляду чи збереження форми. Якщо реалізація виявить потребу змінити API/CAS, оформити це явно в плані/SPEC, не видавати за наявний контракт.

## Приймання

- Нова/наявна конфігурація кожного provider, форми evaluator/classifier без JSON, точний round-trip null/default/advanced/profile.
- Dirty буфери при зміні розділу/ролі, успіх/помилка/конфлікт збереження, shared provider та profile apply за інших незбережених форм.
- Негайний off навіть із невалідною чернеткою; refusal block не обходиться; candidate не дозволяє pause; fingerprints не редагуються як доказ калібрування.
- Контекст/reasoning та prompt contracts зберігають чинну перевірку; deep-link із помилки R-20 і повернення до сцени.
- Desktop/mobile/keyboard/error/focus, тести буферів і API; платні моделі не потрібні для реалізації UI.

Власник погодив повний дизайн і макет 23.10.2026. Чинний контракт реалізації відображено у SPEC.MD (R21-SETTINGS, R21-EVALUATOR-FORM).

## Перевірка можливості реалізації та макет

Незалежний builder-check 23.10.2026 виявив два суттєві пропуски: policy після втрати калібрування та незастосований raw JSON. Для першого запропоновано явний вибір report/off до Save, для другого — dirty буфер і Apply/Discard без автоматичного перетирання. Інші питання реалізації належать до builder choices у наведених межах.

Клікабельний throwaway-макет: `.superpowers/brainstorm/r21-20261023/content/index.html`; loopback сервер захищений ключем доступу, startup URL у `state/server-info`. Демонструє розділи, перемикання ролей, збереження незбережених значень між формами, звичайні поля оцінювача та згорнуті технічні параметри. Значення синтетичні; збереження лише в пам’яті сторінки, API/реальні моделі не підключені. Макет не є реалізацією валідації/калібрування/відмов, не повний перелік форм і не підтвердження працездатності продуктового контракту.
