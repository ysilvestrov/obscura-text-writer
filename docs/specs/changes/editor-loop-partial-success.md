# Цикл редактури: перегляд успішних проходів після помилки

Рішення власника 22.10.2026: якщо після успішних проходів наступний виклик вичерпав вихідний ліміт, зупинити цикл, виключити невдалий текст та показати результати успішних проходів. Реалізація в поточній сесії без додаткового підтвердження.

Наявний flow зберігає незмінні робочі draft, але після failed StageAttempt переводить весь Run у failed без сумарної пропозиції. Замість цього завершений невдалий модельний прохід після успішних змін фіксує stop_reason=pass_failed, failed_attempt_id та справжню причину, припиняє виклики й локально створює звичайний summary між початковою копією та останнім успішним неповтореним кандидатом. Run переходить у needs_review, причина показується як warning. Невдала StageAttempt лишається failed, її partial/usage/accounting не видаляються; вона рахується в ліміт і не входить у текст результату. Правила однакові для patches/diff/prose та окремого/scene/remaining workflow. Модельного повтору, нового автоматичного memory/evaluation або autoaccept немає.

Перша невдала спроба без успішних змін лишається failed. Явне скасування лишається cancelled, source/CAS/ревізії/ліміти сумарного diff перевіряються перед створенням та прийняттям; некоректне джерело не відновлюється автоматично. Несподівані винятки storage/checkpoint не маскуються як модельна зупинка. Перед завершенням зберігається checkpoint; recovery використовує stop_reason без нового виклику. Старі failed-цикли не перетворюються автоматично під час читання. Для конкретного останнього збою можна явно сформувати локальний summary лише після перевірки збережених проходів і джерел, без повтору API.

План: (1) RED tests успішні→output_limit/timeout/guard→summary, перша failure/cancel/source/recovery, workflow; (2) мінімальна зміна editor_loop finish/checkpoint, без нових таблиць/ролей/UI-кнопок; (3) SPEC/traceability, регресія та повний verify, локальний коміт. Існуючі Run.warning та edit_loop_summary показують причину й історію. У checkpoint/summary додаються optional поля; старі payload читаються без міграції.

Уточнення recovery після незалежного review: лише нові failed-спроби з edit_loop_failure_origin=model_response допускають локальний fallback. Винятки checkpoint/stream/storage та старі невизначені failures без маркера не маскуються; explicit retry лишається потрібним. Вікно між failed StageAttempt і stop checkpoint теж впізнається без API, readiness calls=0. Окремі RED→GREEN тести перевіряють storage exception, справжній open_partial failure і обидва crash windows.
