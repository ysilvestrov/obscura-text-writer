# R-16 — Формати публікації FB2, EPUB і PDF

Дата: 22.10.2026. Статус: технічна специфікація після brainstorm; R-16a/b/c/d реалізовані; фактичне приймання й межі — у журналі. Продуктові рішення нижче узгоджені власником. Технічний дизайн і критерії перевірки підготовлені для реалізації; цей документ не замінює чинну SPEC.MD і не оголошує заплановані можливості наявними.

## Мета й межі

Локальний експорт авторського твору у FB2, EPUB і PDF зі спільними метаданими та одним узгодженим знімком активних версій. MD/TXT зберігаються. Чинні правила кошика, відсутніх/застарілих матеріалів, неповного експорту та manifest не послаблюються. Конвертація форматів не викликає модель і не переписує авторську прозу. Окрема, явна операція пропозиції метаданих може викликати налаштовану модель.

Не входить: публікація в книгарнях, DRM, хостинг, генерація обкладинок.

## Узгоджені продуктові рішення

### Спільна картка публікації твору

| Поле | Джерело / поведінка |
|---|---|
| Назва для публікації | Типово назва твору; можна змінити окремо від робочої |
| Автори / псевдоніми | Спільний список із вибором одного чи кількох для конкретного твору |
| Мова | Типово `uk` |
| Жанри | Українські підписи та зіставлення з кодами FB2; ручний вибір або модельна пропозиція |
| Анотація | Необов’язковий редагований текст для читача; ручне введення або модельна пропозиція за готовим текстом |
| Ключові слова | Необов’язкові довільні теги; ручне введення або модельна пропозиція |
| Обкладинка | Необов’язкове завантажене зображення; перегляд, заміна, видалення; експорт без обкладинки дозволений |
| Назва циклу, номер у циклі | Необов’язкові ручні поля, окремо від назви книги |
| Дата публікації | Необов’язкове ручне поле; не дорівнює автоматично даті створення файла |
| Видавець, ISBN | Необов’язкові ручні поля |
| Текст прав / ліцензії | Необов’язкове ручне поле |
| Перекладачі, мова оригіналу | Необов’язкові ручні поля |

Додаткові видавничі поля згруповано під «Додаткові відомості». Весь набір включається в початкову зміну схеми метаданих; власник обрав додати його одразу, щоб не робити окрему наступну міграцію лише заради цих полів. Деталі зберігання та сумісності ще належить спроєктувати.

Імена, псевдоніми та контакти не запозичуються з Git, системного профілю або ключів провайдерів. Наявність справжнього імені чи email не є умовою використання псевдоніма. Відомості, яких немає, не вигадуються.

Кожен публічний підпис є окремим записом спільного довідника: справжнє ім’я або псевдонім. Автор обирає потрібні записи для твору. Кілька псевдонімів не групуються в приховану картку фізичної особи; зв’язок псевдоніма зі справжнім ім’ям не зберігається автоматично.

### Одна кнопка «Запропонувати»

- Одна дія для всієї картки замість окремих кнопок анотації, жанрів і тегів.
- За готовим текстом пропонує назву, анотацію, жанри й ключові слова лише для порожніх полів. Уже заповнені значення не замінює.
- Автор переглядає пропозиції перед збереженням. Внутрішній план не копіюється в читачеву анотацію.
- Автори, цикл, видавець, ISBN, дата публікації, права, перекладачі, мова оригіналу та обкладинка моделлю не заповнюються. Дати й інші факти не виводяться з часу створення проєкту.
- Автоматичної генерації зображень або текстової обкладинки немає — власник обрав тільки upload.
- Операція використовує поточну модель і налаштування планувальника, окремим запитом за готовим текстом зі звичайним обліком бюджету. Окрема роль/конфігурація моделі не додається. Технічний контракт виклику, контекстного ліміту й захисту від конкурентного заповнення наведений нижче.
- Якщо повний готовий текст разом з інструкцією, схемою відповіді й резервом виходу не вміщується в налаштований контекст/символьний ліміт, операція зупиняється до модельного виклику. Показуються оцінка потрібного контексту, доступний бюджет входу й символьний ліміт, що спрацював. Обрізання, частковий аналіз, поетапне узагальнення, збільшення ліміту чи заміна моделі автоматично не виконуються.

### Розділи й технічні метадані

- Одна активна сцена — один розділ у збереженому порядку сцен.
- Використовуються поточні назви сцен; окреме поле «Назва для публікації» сцени та автоматичні «Розділ N» не додаються. За потреби автор перейменовує сцену.
- Технічні ідентифікатори, час формування файла, відомості про експортер і навігація/зміст за розділами формуються системою.
- Незавершену картку можна зберегти. Відсутні обов’язкові дані перевіряються перед експортом конкретного формату, без вигаданого автора чи жанру.

### Оформлення PDF

За вибором власника перша версія має один книжковий профіль A5: титульна сторінка, зміст, нумерація сторінок. Профіль A4 для вичитування та вибір між кількома профілями не додаються. Точні поля, шрифт із підтримкою української та ліцензією, правила розривів і розміщення завантаженої обкладинки визначаються технічною специфікацією в межах цього профілю.

## Технічний дизайн

### Межі компонентів

Рішення цього розділу — інженерна пропозиція в межах погодженого продуктового набору.

- `publication_models.py` — типізовані дані картки, публічного підпису, обкладинки, знімка й пропозиції. Без імпорту web, generation чи storage.
- `storage/publication_store.py` — довідник підписів, картки, CAS, активність твору, посилання на обкладинку та спільний SQL-знімок експорту. Доступ лише через публічний Repository.
- `publication/` — спільне складання знімка/абзаців і незалежні локальні рендерери FB2, EPUB, PDF. Не імпортує generation і не має доступу до ключів/мережі.
- `application/exports.py` — сумісний фасад наявного `export_story`, розширений форматами. Наявні виклики MD/TXT не вимагають нових аргументів.
- `generation/publication_metadata.py` — контекст і валідація окремої модельної пропозиції; не зберігає картку без явного авторського збереження.
- `web/routes_publication.py`, шаблон і ES module картки — HTTP/форми/перегляд. Спільний довідник доступний із картки; новий глобальний профіль фізичної особи не створюється.

### Дані та одна міграція

Міграція `003_publication.sql` піднімає SQLite user_version з 2 до 3 в одній транзакції, додає:

- `publication_signatures(id PRIMARY KEY, revision, archived_at, payload)` — `display_name` довжиною 1–300, UUID, ревізія, час створення/зміни. Один запис — один публічний підпис. Прихованих legal_name, email, owner і зв’язків між псевдонімами немає.
- `story_publications(story_id PRIMARY KEY REFERENCES stories, revision, payload)` — усі погоджені поля картки разом, упорядковані `author_ids` і `translator_ids`, optional cover ref. Не використовує загальну story.revision як єдиний лічильник картки.
- `publication_assets(id PRIMARY KEY, story_id REFERENCES stories, sha256, relative_path, mime_type, width, height, payload)` — незмінні нормалізовані обкладинки, незалежні від історії прози.

Назва для публікації: optional override; порожній override означає чинну назву твору. Інтерфейс показує успадковану назву як уже наявне ефективне значення, тому «Запропонувати» його не переписує. Автор може вручну задати іншу назву. Для опційних scalar-полів whitespace-only означає порожнє значення; для списків — порожній список.

Ліміти: title 300; annotation 12000; до 10 унікальних genre codes з комплектного FB2-каталогу; до 30 keywords по 100 символів; до 20 author/translator IDs без повторів; cycle_title 300; cycle_number — optional ціле 1…1000000, потребує назви циклу; publisher 300; rights 4000. ISBN — optional ISBN-10/13 з перевіркою контрольної суми після нормалізації пробілів/дефісів. Дата публікації — optional календарна YYYY-MM-DD. Мови — BCP 47 з початковим `uk`, оригінальна мова optional; мови документа/оригіналу не вгадуються з модельної відповіді. Неповні картки дозволені, але некоректні непорожні значення відхиляються.

Картка для старого твору читається з defaults без запису/масового backfill; створюється при першому збереженні з expected_revision=0. Наявні Story/Scene/Version/Run payload не переписуються; story_id лишається рядком за чинним доменним контрактом, включно з legacy ID. Нові власні signature/asset IDs — UUID hex. Reader/механізми backup, restore і fsck підтримують схеми 2 та 3 відповідно до чинного розділення read-only перевірки та міграції при відкритті Repository. Невідомі новіші версії відхиляються. Весь набір колонок/полів додається цією міграцією; наступні рендерери не додають окремих міграцій лише заради відкладених полів.

Редагування підпису — CAS за його revision. Майбутні перегляди карток та експорти розв’язують актуальний підпис; вже сформовані файли та manifest незмінні. Архівація приховує запис з нового вибору, але зберігає наявні посилання творів і дозволяє його відновити. Картка може прибрати вибраний підпис без архівації довідника. Масового перейменування/інвалідації прозових heads немає. Сам експорт фіксує значення й revision підписів у своєму знімку.

### Обкладинка

Приймаються тільки PNG і JPEG, до 10 MiB та 20 мільйонів пікселів, одна статична картинка. MIME/розширення не замінюють фактичне декодування. Pillow перевіряє формат, dimensions і decompression-bomb; багатокадрові файли, SVG, помилкові та надмірні зображення відхиляються. EXIF orientation застосовується, зайві EXIF/GPS-метадані не копіюються; нормалізовані bytes зберігаються в межах FileStore під системним ID, без довіри до шляху клієнта. Картка зберігає id/hash нормалізованого ресурсу. Заміна/видалення змінює ref з CAS, старий blob не стирається й лишається доступним старому знімку/резервуванню. Прозорість PNG підтримується в EPUB/FB2; PDF відтворює її на білому папері. Кадрування не виконується.

### Єдиний знімок публікації

Нова публічна Repository-операція `publication_snapshot(story_id)` в одному read transaction фіксує активний Story, ефективну картку, усі використані підписи/revisions, cover ref та активні сцени з prose refs у порядку position/id. Спільний контекст не збирається послідовністю незалежних GET.

Файли прози й обкладинка читаються за незмінними refs із перевіркою SHA-256 після закриття SQL-транзакції. Зміни/архівація після знімка не перемішують ревізії знімка. Повторний експорт — новий UUID. Чинні warnings неповноти/застарілості та allow_incomplete збережені, включно з явними позначками в кожному форматі. Відсутні обов’язкові метадані/помилковий ресурс не обходяться allow_incomplete.

Manifest зберігає чинні поля й додає `schema_version=2`, export UUID, точні resolved metadata/signatures/cover ref, exporter/schema/font versions і SHA-256 bytes вихідного файла. Внутрішні story/version IDs лишаються в manifest, а до EPUB/FB2 не додаються як читачеві метадані. UUID видання стабільний для твору: UUIDv5 із фіксованим namespace застосунку й story ID, тому читання defaults не створює випадковий новий ідентифікатор і не потребує запису. Це технічний ID, не гарантія анонімності; export UUID й modified timestamp розрізняють файли. Старі manifest без schema_version залишаються читабельними. Нова міграція не переписує старі exports.

Новий файл і manifest збираються в тимчасові файли, перевіряються, остаточний manifest публікується останнім. Посилання повертається лише після успіху обох. Download для нового manifest перевіряє формат/наявність/хеш; конвертаційна помилка не видає частковий файл за готовий. Залишки невдалого експорту не видаляють попередню успішну публікацію. Файли — локальні, конвертери не завантажують зовнішніх ресурсів.

### Операція «Запропонувати»

Новий RunRequest.mode=`publication_suggest`, без scene_id, з одним task stage=`publication_suggest`. Використовує існуючу чергу, request_id/idempotency, cancel/recovery, збереження StageAttempt/partial/events і accounting. Не входить до автоматичних «Уся сцена»/«Пройти решту», не запускає Evaluator, не змінює сценові heads чи пам’ять.

На старті етапу фіксується поточний provider/model/context/output/temperature/timeout/JSON режим планувальника. Системний промпт цієї окремої операції — комплектний версійований ресурс, а не промпт структурування сцен. Фіксуються точний запит, версія промпту й схема `PublicationSuggestions` з лише title/annotation/genres/keywords. API strict schema використовується, якщо ввімкнений у планувальника; локальна валідація відповіді обов’язкова завжди. Невідомі поля/genre codes, обрізана, порожня чи невалідна відповідь відхиляються, partial зберігається. Немає прихованого повтору чи зміни моделі.

Вхід — весь текст чинної повної прози всіх активних сцен, їхні назви/порядок і маска порожніх полів з того самого знімка. Плани, пам’ять, описи персонажів і промпти попередніх генерацій не передаються. Відсутні/stale/incomplete/needs_review матеріали блокують операцію: для пропозиції читачевої анотації немає прихованого allow_incomplete.

До резервування грошей і dispatch спільний token estimator перевіряє повний фактичний запит разом зі схемою, reasoning/output reserve та max_input_chars. Недостатній контекст дає типізовану помилку з оцінками, без платного виклику, обрізання чи поетапної обробки. Якщо немає порожніх придатних полів, кнопка disabled, прямий запит завершується без провайдера. Для платного запиту діє чинний явний ліміт/тариф/резерв; local не отримує вигаданої доларової ціни.

Валідована пропозиція зберігається в `StageAttempt.context.publication_proposal` зі snapshot refs/fingerprint, без нового VersionKind і без автоматичної публікації картки. Інтерфейс показує результат і заповнює лише ті поля, які були порожні на старті та досі порожні в поточній формі. Dirty значення/асинхронний текст не перезаписуються; потрібне звичайне «Зберегти». Збереження містить expected publication revision та fingerprint пропозиції; сервер повторно перевіряє належність твору, знімок джерел, придатні поля й поточні непорожні значення. Конфлікт повертає 409 із поясненням, зберігаючи форму/пропозицію для перегляду. Після зміни джерел стара пропозиція позначається неактуальною; новий виклик тільки за окремою дією автора.

### FB2

FB2 з namespace `http://www.gribuser.ru/xml/fictionbook/2.0`; комплектні XSD FictionBook/Genres/Links/Lang із ліцензією автора, зафіксованими upstream commit і SHA-256 у ресурсному manifest. Конкретні bytes/commit фіксуються під час додавання ресурсів; змінювати схему для прийняття некоректного документа заборонено. XML будується бібліотекою, текст не конкатенується в markup. Валідація XSD — локально, без DTD/entities/network.

`title-info`: genre+, author+, book-title, optional annotation/keywords/date/coverpage, lang, optional src-lang/translator/sequence у порядку XSD. Публічний `display_name` цілком записується в дозволений schema author.nickname, без вгадування first/last names. Це технічне представлення довільного публічного підпису, не твердження, що справжнє ім’я є псевдонімом. Немає автора чи жанру — FB2 експорт блокується з конкретним полем.

`document-info` відділяє укладача файла від авторів твору: exporter name, дата файла, document UUID, version. Обкладинка embedded binary із content-type та xlink ref. Видавець/ISBN електронної публікації й текст прав передаються в позначені `custom-info` та manifest; `publish-info` не створює вигадане джерельне друковане видання. Публікаційна дата й дата файла розрізняються.

Одна scene → section/title/p, абзаци/порожні рядки зберігаються. Діалогові тире, лапки та українські символи не нормалізуються літературним редактором. Довільний текст є plain text; Markdown/HTML у прозі не виконується. Namespace, refs і schema перевіряються перед видаванням файла.

### EPUB

EPUB 3.3 з package version=`3.0`, UTF-8 XHTML, обов’язковими title/identifier/language/modified, manifest/spine і nav.xhtml. `mimetype` — перший ZIP entry, без стискання, точні bytes `application/epub+zip`. Одна сцена — один XHTML chapter; порядок spine і навігації відповідає знімку. UUID видання є ідентифікатором, ISBN — додатковим, коли наданий.

Автори → dc:creator у вибраному порядку; перекладачі → dc:contributor з роллю trl; annotation → dc:description; жанри/ключові слова → dc:subject з однозначним позначенням типу в додаткових метаданих; права → dc:rights; видавець → dc:publisher; публікаційна дата → dc:date. Цикл → EPUB collection/series metadata. Лише фактично задані опційні поля; автор не вигадується, якщо не обраний.

Завантажена обкладинка входить у пакет, позначається cover-image і має окрему читачеву сторінку. EPUB не містить мережевих зображень/скриптів/вбудованих сторонніх шрифтів. Мінімальний CSS із відносними розмірами й serif fallback не нав’язує кольори застосунку, фіксовані сторінки чи розмір шрифту читача. Генерація — stdlib zipfile/XML, локальні структурні перевірки при експорті; приймання — офіційний EPUBCheck 5.4.0 для EPUB 3.3 з pinned release/checksum. Java/EPUBCheck — інструменти перевірки розробки, не прихована залежність запуску сервера.

### PDF

ReportLab 4.x (BSD), локальна генерація через Platypus. A5 148×210 мм; поля 17 мм, нижнє 18 мм; основний Noto Serif 11 pt / 15 pt, абзацний відступ 4 мм. Постачаються статичні Regular/Italic/Bold/BoldItalic TTF та OFL-1.1, upstream commit/hash фіксується в ресурсному manifest. Шрифти вбудовані, перевіряються українські Ґ/Є/І/Ї й типографічні символи. Системна Georgia чи мережеве завантаження не є залежністю PDF.

За наявності cover — перша окрема сторінка зі збереженням пропорцій, без обрізання; далі титул (назва, автори, optional цикл/видавець/дата), зміст із чинними назвами й номерами сторінок, розділи. Обкладинка/титул не мають видимого номера; сторінки рахуються послідовно, видимі номери починаються зі змісту. Немає навмисних парних/порожніх сторінок, тому короткі твори не роздуваються. Заголовок не лишається окремо внизу; обмеження висячих рядків, довгі слова/назви переносяться. Непідтримуваний шрифтом символ дає пояснену помилку замість мовчазного квадрата. Unicode/проза не спрощуються до ASCII.

Зміст складається багатопрохідним layout із межею 10 проходів; невстановлення стабільних номерів — явна помилка. Текст виділяється/шукається; випадкові XML-like символи в plain prose екрануються для Paragraph. Валідація приймання включає render сторінок і текстову екстракцію, не лише успішний виклик ReportLab.

### HTTP та інтерфейс

- GET `/api/publication-signatures?include_archived=false`, POST `/api/publication-signatures`; PATCH `/api/publication-signatures/{id}` з expected_revision і явною зміною display_name/archived стану.
- GET/PUT `/api/stories/{id}/publication`: картка, effective title, resolved signatures і revision; PUT має expected_revision та expected signature revisions.
- POST `/api/stories/{id}/publication/cover`: обмежений upload; призначення обкладинки через CAS картки. GET ресурсів перевіряє активний твір і власність asset ID, не приймає довільного шляху; видалення ref — PUT картки.
- POST чинного `/api/runs` із mode=publication_suggest запускає окрему операцію; GET `/api/stories/{id}/publication/suggestions` повертає валідовані пропозиції та їхню актуальність, без секретів/сирого контексту. Стандартні run/events/cancel лишаються доступними.
- Чинний POST `/api/stories/{id}/export` приймає md/txt/fb2/epub/pdf, зберігає allow_incomplete. Download allowlist розширюється точно цими суфіксами, встановлює application/x-fictionbook+xml, application/epub+zip, application/pdf; md/txt — UTF-8. Manifest → application/json.

Кнопка «Опублікувати» відкриває явний вибір формату/картки/неповного експорту замість циклу prompt/confirm. Незаповнені поля й помилки показуються поруч із форматом; повернення зі скасування не є дозволом неповного експорту. Після повторної публікації посилання замінюються лише при успіху; помилка лишає попередні посилання доступними. Подвійний клік не створює два паралельні запити з однієї форми. Dirty редактор/картка блокують публікацію, UI не має прихованої залежності від вибраної сцени.

### Залежності та сумісність

Рендерери FB2/EPUB — XML і ZIP stdlib; XSD — lxml з BSD ліцензією; PDF — ReportLab BSD; перевірка/нормалізація cover — Pillow з HPND ліцензією. Залежності оформлюються як web/publication extra з lazy imports, щоб CLI оцінювання не вимагав PDF/графічних пакетів. Точні встановлені версії й хеші відображаються у звіті приймання. Відсутній optional пакет дає зрозуміле повідомлення, не ламає MD/TXT або весь сервер.

Нові засоби fsck перевіряють FK/власність/ревізії, payload усіх таблиць, cover blob/hash/mime/dimensions, наявні archived signatures як допустимі посилання. Backup/restore включають таблиці й cover blobs; fsck не вважає відсутню незаповнену картку пошкодженням. Зміна метаданих не робить prose/memory/evaluation застарілими, а зміни прози роблять модельні пропозиції метаданих неактуальними. Role profiles лишаються чотирма ролями плюс optional Evaluator.

## OpenSpec — критерії приймання запланованого розширення

Наведені ID належать специфікації зміни; до кореневої SPEC.MD і матриці додаються разом із реалізацією та фактичними тестами, без завчасної заяви проходження.

### Requirement: R16-META — Картка й довідник

Система SHALL зберігати повний погоджений набір полів, частково заповнені картки й окремі публічні підписи без вигаданих відомостей.

#### Scenario: R16-META-S01 — Міграція та старий твір

- GIVEN база схеми 2 з творами/версіями й без метаданих публікації
- WHEN застосовано міграцію 003 та відкрито старий твір
- THEN схема 3, стара проза/налаштування незмінні, ефективна назва успадкована, решта defaults; MD/TXT доступні.

#### Scenario: R16-META-S02 — CAS і публічний підпис

- GIVEN підпис обраний у двох творах і є готовий export manifest
- WHEN підпис перейменовано/архівовано, а паралельна форма зберігає стару revision
- THEN нові перегляди бачать актуальний підпис, архівація не руйнує refs, старий export незмінний, конкурентне збереження дає 409 без втрати форми.

### Requirement: R16-SUGGEST — Лише порожні поля

Операція SHALL використовувати весь готовий текст і поточні налаштування планувальника, створюючи лише переглядну пропозицію допустимих порожніх полів.

#### Scenario: R16-SUGGEST-S01 — Один запит і захист заповненого

- GIVEN повний твір, заповнена анотація та порожні жанри/теги
- WHEN автор натискає «Запропонувати», а під час запиту вручну вводить ключове слово
- THEN один planner-запит, анотація і введене слово не перезаписані, запропоновані жанри доступні для перегляду, картка не збережена автоматично.

#### Scenario: R16-SUGGEST-S02 — Недостатній контекст

- GIVEN повний запит перевищує input budget або max_input_chars
- WHEN натиснуто «Запропонувати»
- THEN пояснено оцінку/ліміт, нуль модельних dispatch і грошових резервів; немає обрізання, частин чи повтору.

#### Scenario: R16-SUGGEST-S03 — Помилка, cancel і зміна джерел

- GIVEN чергова операція та збережені refs прози
- WHEN отримано refusal/technical/empty/invalid JSON, cancel, restart або джерела змінено до прийняття
- THEN причина відрізняється, partial/accounting збережені, картка не опублікована, автоматичного повтору немає; змінений snapshot не приймається мовчки.

### Requirement: R16-EXPORT — Узгоджений локальний файл

Усі формати SHALL використовувати один snapshot, відповідні метадані, дозволений набір ресурсів і manifest з хешем вихідного файла.

#### Scenario: R16-EXPORT-S01 — Сім сцен і паралельні зміни

- GIVEN сім активних сцен та archived сцена, обкладинка й підписи
- WHEN snapshot взято й потім змінено прозу/назву/підпис/порядок
- THEN кожен файл відтворює саме зафіксовані сім сцен і метадані, без кошика/суміші ревізій; manifest відповідає bytes.

#### Scenario: R16-EXPORT-S02 — Неповнота та зламана обкладинка

- GIVEN відсутня/stale проза або пошкоджений cover blob
- WHEN запитано export з/без allow_incomplete
- THEN чинні правила неповної прози збережені з видимим маркуванням; помилка cover/hash чи обов’язкових метаданих не обходиться allow_incomplete, попередній успішний export доступний.

#### Scenario: R16-EXPORT-S03 — Формати та довільний текст

- GIVEN текст до 15000 слів із Ґ/Є/І/Ї, діалогами, порожніми рядками, довгими словами, XML/HTML-подібними символами, завантаженою обкладинкою та всім набором метаданих
- WHEN створено FB2/EPUB/PDF
- THEN FB2 проходить комплектну XSD, EPUB проходить EPUBCheck, PDF має A5/вбудовані шрифти/стабільний зміст і не має обрізання чи випадкових порожніх сторінок; текст і порядок розділів збережені без виконання markup.

#### Scenario: R16-EXPORT-S04 — Межі файлів і резервування

- GIVEN надмірне/хибне зображення, чужий asset ID, підроблений download path або стара/нова база
- WHEN виконано upload/download/fsck/backup/restore
- THEN небезпечний запит відхилений, refs з перевіреною власністю, старі та нові резерви читаються відповідно до схеми; невідомі схеми не мігруються навмання.

## Перевірка та поділ реалізації

1. R-16a: міграція, моделі/довідник/обкладинка, CAS, fsck/backup, snapshot і картка без модельного виклику.
2. R-16b: queued publication_suggest, budget/context/error/proposal contracts та одна кнопка; fake gateways для тестів, без платних проб.
3. R-16c: FB2/EPUB, XSD/EPUBCheck, нові MIME/download/manifest і регресія MD/TXT.
4. R-16d: PDF A5/шрифти/зміст, render/екстракція та спільне UI/семисценове/15000-слів приймання.

Для кожної частини — окремі тести й коміт із актуальною кореневою SPEC.MD; завершення всієї надзадачі лише після всіх чотирьох. Нові Scenario при перенесенні в SPEC.MD отримують traceability з конкретними тестами/явною ручною процедурою, а не лише посиланням на намір. Кінцевий повний прогін — scripts/verify.py, docs/STATUS.md; документація — scripts/check_docs.py. Обмеження фактичного відкриття в читачі/рендеру/модельної якості зазначаються чесно. Ресурси/ліцензії/версії валідаторів фіксуються перед відповідними комітами; відсутність інструмента валідації не оголошується успішною перевіркою.
