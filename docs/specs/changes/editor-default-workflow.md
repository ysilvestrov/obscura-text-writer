# Єдиний стандартний редактор у workflow

## Requirement: EDIT-WORKFLOW — Однакова редактура

Workspace SHALL запускати edit_loop через єдину кнопку «Редагувати», а scene/remaining — з edit_workflow=loop та спільним edit_pass_limit 1..10 (типово 5). Кожна сцена має окремий checkpoint у Run.editor_loops за індексом завдання; бюджет і run_id залишаються спільними. Старі запити без edit_workflow та збережені завдання без editor_loop marker зберігають одиночну поведінку.

### Scenario: Продовження після спільного перегляду
- GIVEN комплексний запуск створив чернетку
- WHEN редактор завершив до N проходів на окремих копіях цієї чернетки
- THEN запуск чекає одного спільного diff для поточної сцени
- AND прийняття публікує прозу, але не просуває cursor комплексного запуску
- AND явне «Продовжити після прийнятого етапу» переходить до пам’яті без повтору редактора

## Requirement: EDIT-WORKFLOW-SOURCE — Джерела та сумісність

Комплексний редактор SHALL починати з актуальної поточної чернетки, незалежно від попередньої прози. Окремий edit_loop використовує поточну прозу, і лише за її відсутності — чернетку. Patches, diff і prose SHALL використовувати чинні власні промпти/контекст та guards; prose отримує повний літературний контекст з робочою копією замість draft-head. Усі результати циклу публікуються лише через спільний перегляд.

Якщо перший прохід не дав змін, окремий цикл завершується без прийняття. Комплексний workflow SHALL зупинитися без пам’яті й без пропозиції прийняття, якщо немає вже вибраної актуальної прози з точно таким текстом. Інакше він може продовжити з наявною прозою. Автоматичного створення прози з no-op немає.

Checkpoint SHALL розділяти індекс завдання та індекс проходу; відновлення не повторює завершені виклики й не змішує результати різних сцен. Кожна невдала спроба витрачає ліміт своєї сцени. Readiness і підтвердження SHALL враховувати максимальні виклики всіх редакторських фаз.

Локальне продовження no-op з уже вибраною ідентичною прозою SHALL поважати запитану паузу та pause_after=edit і зупинятися перед пам’яттю.

## Журнал виконання

Початкова перевірка: 4 нові тести RED через відсутнє edit_workflow. Реалізовано per-task checkpoints, три протоколи, publication/continuation і спільний UI. Комплексні тести двох сцен, ліміт 1, source preference, пауза, recovery збереженого проходу та локального фіналу, prose full context пройшли.

Final review: незалежний reviewer знайшов Important — no-op з ідентичною прозою скидав паузу. Виправлено в одному проході: два сценарії pause_after та паузи під час stream RED→GREEN; повний suite **682 passed, 1 skipped, 94.08s**, artifacts/default-editor-final.log. Інших Critical/Important або minor немає.

Синтетичний browser: одна кнопка, N=1, підтвердження 8 викликів для двох сцен, окремий diff кожної, прийняття й continuation через пам’ять. Детектор UI: []. Платні API й робочі авторські дані не використовувалися.

## План і перевірки

1. RED: комплексний запуск двох сцен, окремі checkpoints, прийняття/продовження, no-op та prose.
2. Generalize editor_loop, storage publication і worker dispatch; зберегти старі API/завдання.
3. Єдині UI налаштування й підрахунок викликів; оновити SPEC.MD та інструкцію.
4. Цільові й повні тести, браузер на синтетичних даних, незалежне рев’ю, локальний коміт.

Ruling: сумісність старих API зберігається явним edit_workflow=loop з UI — це не змінить вже поставлені в чергу завдання; клієнтам API для нової поведінки потрібен цей прапорець.

Після браузерної перевірки уточнено коротке повідомлення прийняття для комплексного запуску, щоб воно не вимагало продовження після completed; цільові storage/workflow/API перевірки: 14 passed, 6.57s.
