# R-11 — Профілі моделей і налаштувань ролей

Дата: 22.10.2026. Статус: реалізовано; перевірки в docs/STATUS.md і журналі плану. Власник обрав комплект чотирьох ролей із необов’язковим Evaluator. Реалізація після підготовки плану — у поточному чаті за раніше наданою вказівкою, без додаткового погодження плану.

## Мета

Переносити перевірені моделі, параметри й промпти між оповіданнями без повторного ручного введення. Збережений профіль — шаблон для явного копіювання, а не жива глобальна конфігурація всіх творів.

## Досліджена поточна поведінка

- Чотири основні ролі: planner, writer, editor, memory. `RoleSettings` містить режими редактора/пам’яті, допоміжний classification і посилання на версії промптів конкретного твору.
- `storage/settings_store.py::write_role_settings` перевіряє story revision, власність промптів і їхні контракти в write-транзакції; підвищує config_revision.
- Evaluator має окрему конфігурацію, політику, перевірку калібрування та блокування відмов за твором. Чинне збереження Evaluator не має аргументу expected_revision; для атомарного застосування комплекту недостатньо послідовно викликати два поточні writer-методи.
- app_settings уже зберігає глобальні службові записи; окрема SQL-міграція не потрібна лише за збереження профілів у цій таблиці.
- Спроба фіксує ефективні параметри й точний API request. Наступний етап читає оновлені параметри; активний виклик не змінюється.

## Обране рішення та інтерфейси

Один профіль містить рівно planner/writer/editor/memory. Необов’язковий Evaluator додається лише явним прапорцем при збереженні. Без нього застосування залишає Evaluator твору незмінним. Профіль не включає авторський стиль. Для редагування збереженого комплекту автор налаштовує його в творі та зберігає нову версію вибраного профілю.

- JSON schema `format=obscura-role-profile`, `schema_version=1`, `name` (1–100 непорожніх символів), `roles`, `evaluator` (null або налаштування). Ліміт імпорту/експорту 2 MiB UTF-8; власний промпт до 100000 символів. ID/version/timestamps — серверна обгортка, не переносимий документ.
- `GET /api/role-profiles` — версії з ID/назвою/номером; `GET /api/role-profiles/{id}/versions/{version}` — конкретна версія; export додає `/export` і віддає JSON-вкладення.
- `POST /api/stories/{id}/role-profiles/capture` — name/include_evaluator/expected_revision; optional profile_id/expected_version для нової версії.
- `POST /api/role-profiles/import` — сирий JSON; створює окремий новий профіль, не перезаписує наявний за назвою.
- `POST /api/stories/{id}/role-profiles/preview` та `/apply` — profile_id/version/expected_revision. Preview повертає склад цільових ролей, Evaluator та warnings; apply повторює серверні перевірки і повертає story. Невалідне калібрування/pause_on_failure блокує обидві дії. Імпортований Evaluator завжди candidate; calibration metadata відхиляється, а не надає допуск.
- `app_settings`: незмінні записи `role_profile:{id}:{version}` і CAS-голова `role_profile_head:{id}`; походження останнього застосування — `role_profile_applied:{story_id}`. Профіль не містить ID вихідного твору.
- UI у налаштуваннях: зберегти новий/нову версію, вибрати конкретну версію, переглянути склад, застосувати, імпортувати/експортувати JSON. Застосування потребує попереднього preview; зміна вибору скидає preview. Застосування перезавантажує сторінку лише після успіху й попередження про незбережені правки форм.
- Вбудований промпт має `text=null` та очікуваний контракт; власний — непорожній text і той самий контракт. Відсутній prepare-промпт для непланувальних ролей — null. Сирі prompt UUID відхиляються. Нові prompt blobs/версії можуть бути підготовлені до CAS і лишитися неопублікованими при конфлікті; чинні налаштування залишаються атомарними.

## Запропоновані інваріанти

### Requirement: незмінні версії та явне застосування

Профіль SHALL мати стабільний ID, назву та незмінні пронумеровані версії. Редагування SHALL створювати наступну версію із перевіркою ревізії профілю. Застосування SHALL копіювати обрану конкретну версію після перегляду складу змін і перевірки ревізії твору. Зміна профілю SHALL не оновлювати вже налаштовані твори автоматично.

#### Scenario: оновлення шаблону

- GIVEN два твори використовують копію версії 1
- WHEN збережено версію 2 профілю
- THEN обидва твори зберігають попередні параметри до явного застосування.

### Requirement: переносимі промпти

Профіль SHALL не переносити чужі prompt_version_id. Вбудовані промпти представляються посиланням на підтримуваний контракт; власні — текстом і контрактом етапу/режиму/схеми. Застосування SHALL створювати власні версії промптів цільового твору та перевіряти сумісність до публікації налаштувань. Legacy-промпт без призначеного контракту SHALL вимагати виправлення, а не автоматичного перепризначення.

#### Scenario: перенесення власного промпту

- GIVEN профіль збережено з твору A
- WHEN його застосовано до B
- THEN налаштування B посилаються на власні prompt-версії, без refs твору A.

### Requirement: експорт без секретів та сторонніх повноважень

Імпорт/експорт SHALL використовувати версійований JSON із суворою схемою, обмеженням розміру та без значень API-ключів. Дозволене ім’я key_env не є значенням секрету. Дані твору, бюджетні ліміти, тарифи, token-профілі, звіти й блокування відмов SHALL не переноситися як частина налаштувань ролей.

Evaluator переноситься лише як candidate: calibrated/fingerprints прибираються при capture та відхиляються при імпорті. Автоматичного відновлення локального допуску профіль не виконує; pause_on_failure без допуску SHALL відхилятися явно, без мовчазного переходу в report. Для переносимого комплекту автор зберігає report/off, а калібрування налаштовує окремо. Застосування SHALL не обходити блокування відмов цільового твору.

#### Scenario: імпорт некоректного профілю

- GIVEN JSON із секретом у невідомому полі, чужим UUID промпту або непідтримуваним контрактом
- WHEN виконується імпорт
- THEN помилка не містить значень секретів; часткової зміни налаштувань немає.

### Requirement: атомарність і наступний етап

Застосування SHALL виконувати публікацію всіх обраних налаштувань однією storage-транзакцією з CAS твору та відстежуваним походженням profile ID/version. Читання й перевірка незмінних промптів можуть передувати транзакції; помилка SHALL не лишати частково застосований комплект. Активна спроба SHALL зберігати зафіксовані параметри, наступний етап — читати нові. Готовий текст не стає outdated лише через зміну моделі.

#### Scenario: конфлікт ревізії

- GIVEN автор переглянув профіль, після чого налаштування твору змінилися
- WHEN застосовується попередній expected_revision
- THEN повертається конфлікт без часткового оновлення.

## Межі та приймання

Не входять платні перевірки моделей, автоматичний вибір найкращої моделі, перенос авторського стилю/матеріалів, калібрування Evaluator або глобальне перепризначення активних викликів. Перевірки — offline: незмінність версій, CAS, round-trip JSON, відсутність чужих refs, атомарний rollback, сумісність промптів, незмінність поточних спроб, UI preview та явне застосування. Під час реалізації чинний контракт і сталі Scenario ID інтегруються в SPEC.MD та матрицю перевірок.
