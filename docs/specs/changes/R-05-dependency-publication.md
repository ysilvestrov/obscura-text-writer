# R-05 — Залежності, публікація й авторське прийняття

Дата: 20.10.2026. Статус: погоджено власником; R-05a/b/c реалізовані й перевірені.
Чинні реалізовані контракти — у кореневій SPEC.MD; цей документ фіксує погоджений контракт трьох послідовних частин R-05.
Приймання: a — 341 passed/1 skipped, b — 366/1, c — 397/1; реальні моделі не викликалися.

## Мета та рішення власника

Готовий результат не повинен відхилятися через нерелевантну зміну твору.
Водночас заміна фактично використаного матеріалу або поточного результату
не повинна проходити непоміченою. Автор має бачити причини застарілості й
усвідомлено приймати придатний текст зі збереженням історії.

Погоджено власником у цій сесії:

1. Явне прийняття застарілих **чернетки та прози** дозволено з новою базою
   залежностей; пам’ять і оцінювання автоматично не підтверджуються.
2. Для нових версій із повним перевіреним знімком точне повернення всіх
   залежностей до початкового стану автоматично відновлює актуальність.
   Legacy stale без доказового знімка автоматично актуальним не стає.
3. Активна спроба використовує зафіксовані налаштування; нові налаштування
   застосовуються з наступного етапу. Зміна ролі сама не відхиляє готовий текст.

Обрано B+: перевірка релевантного dependency snapshot і target CAS в одній
write-транзакції. Перебудова промпту всередині write-lock не потрібна;
fingerprint залишається доказом точного запиту, а не заміною контракту залежностей.

## Порядок і межі реалізації

**R-05a — Межі сховища.** Перенесення SQL та транзакцій у storage без зміни
поведінки актуальності/прийняття. Публічні предметні операції замість
зовнішнього доступу до repo.db/приватних методів. Прибрати імпорти generation
зі storage, винести спільні моделі run/event у незалежний модуль. Окремий коміт.

**R-05b — Точні залежності.** Версійований snapshot, окрема ревізія
налаштувань, target CAS, похідна актуальність і пояснення. Legacy-консерватизм
та сумісність чинних API. Окремий коміт після приймання R-05a.

**R-05c — Авторське прийняття.** Записи прийняття, baseline, API/UI й
продовження alternative без повтору прийнятого етапу. Завершує залежну
частину 3 R-03. Окремий коміт після приймання R-05b.

Без реальних моделей, нових витрат, публікації в мережу або автоматичного
резервування приватного каталогу. Перевірений холодний backup потрібен перед
міграцією наявних авторських даних; випробування сумісності виконуються на
синтетичних копіях. Якщо формат можна розширити сумісно без SQL-міграції,
нова версія SQLite не вводиться заради нумерації.

## Requirement: R05-STORAGE — Предметна транзакційна межа

Зовнішні шари SHALL не виконувати SQL через repo.db і не викликати приватні
методи Repository. Виняток — тести інваріантів та інструменти всередині storage.
Немає універсального execute_sql або callback, що просто переносить зовнішній
SQL усередину чужої транзакції. Транзакції належать предметним операціям.

Публічні групи: авторські матеріали/плани/порядок/кошик; рольові та evaluator
налаштування; імпорт метаданих джерела; run/event/recovery; публікація evaluation;
реєстрація калібрування й відмовних блокувань. Валідація прози, модельних схем
і літературних правил залишається у відповідних сервісах.

### Scenario: R05-STORAGE-ROLLBACK
- GIVEN CAS або валідація власності відхилили зміну
- WHEN предметна транзакція завершується
- THEN голови, порядок, залежності й налаштування не змінюються частково.

### Scenario: R05-STORAGE-BOUNDARY
- GIVEN production-модулі поза storage
- WHEN виконується перевірка залежностей коду
- THEN немає прямого SQL/repo.db/приватних Repository API
- AND storage не імпортує generation навіть для run/event-моделей.

## Requirement: R05-SNAPSHOT — Повний релевантний знімок

Перед модельним викликом SHALL фіксуватися версія формату snapshot, фактичні
вхідні refs/хеші, релевантні mutable selectors і metadata, потрібна
послідовність сцен та очікувана голова публікації. Відсутнє джерело — явне
значення, а не пропущений запис. Знімок фіксується узгоджено; неперевірений
набір послідовних читань не видається за один атомарний стан.

| Етап | Динамічні залежності |
|---|---|
| prepare | Активні source_plan/source_characters, включно з відсутністю |
| brief/draft/prose-edit | Фактично використані стиль/канон/персонажі/промпт, плани та метадані, попередня пам’ять/проза й релевантний порядок |
| patches | Обрана чернетка й зафіксований промпт/параметри; без сторонніх планів/налаштувань |
| memory | Поточна проза, попередня пам’ять та її джерела, порядок префікса до поточної сцени; без майбутніх планів/стилю |
| evaluation | Документи й selectors фактичного case/window; явно непокриті зв’язки залишаються непокритими |

Зафіксована конфігурація поточної спроби є її походженням. Зміна настройки
ролі не підміняє промпт уже активної спроби й не робить її результат
альтернативним сама по собі. Для збереження налаштувань SHALL зберігатися CAS
і окремий config revision; legacy-клієнт не втрачає захист від lost update.
Повторне використання спроби SHALL усе ще вимагати відповідного fingerprint.

### Дані й спосіб зберігання

- `DependencySnapshot` має `schema_version=1`, предметний scope, selectors
  expected/current (включно з null), refs із SHA-256, metadata та впорядковані
  scene IDs. Селектори описують лише прочитані джерела або релевантну відсутність;
  це не довільний SQL/код для виконання. Невідомий scope/формат відхиляється.
- `ContextBundle` і збережений attempt містять snapshot та окремий target CAS.
  VersionRef нового матеріалу зберігає початковий dependency snapshot як
  походження. Старі VersionRef без поля читаються як legacy.
- `Scene.head_revisions` — окремі лічильники вибору кожної голови, типово
  порожній словник зі значенням 0 для відсутнього ключа. Target CAS порівнює
  ID та цей лічильник, щоб вибір A→B→A під час inference не обійшов захист
  авторського рішення. Ці лічильники не входять до content freshness:
  точне повернення залежностей A→B→A може відновити актуальність старого тексту.
- `Story.config_revision`, типово 0, збільшується при зміні налаштувань.
  Story.revision також лишається legacy CAS для авторських/settings API;
  нова публікація моделі не використовує глобальну ревізію як заміну snapshot.
- Журнал прийняття — append-only записи `app_settings` з ключем
  `acceptance:<story_id>:<acceptance_id>` і типізованим payload. Запис містить
  version ID, дату, дію, optional note, новий snapshot та попередній baseline ID.
  Чинним є останній запис для цієї версії за порядком вставлення; старі записи
  не переписуються. Це журнал рішень, а не новий модельний input_ref.
- Для авторського тексту/прийняття scope `author_text` прив’язує його до
  поточних авторитетних матеріалів твору/плану/метаданих і релевантного порядку,
  не стверджуючи, що модель їх читала. Старі model input_refs лишаються історією.
  Прийняття тексту не засвідчує актуальність проміжних brief/пам’яті/evaluation.
- Додаткові поля JSON сумісні через defaults; таблиці SQLite та user_version=2
  не змінюються. Файли текстів, ID й історичні хеші не переписуються. Fsck
  перевіряє формат/власність refs snapshot та acceptance, не виконує їх repair.

### Scenario: R05-SNAPSHOT-IRRELEVANT
- GIVEN memory сцени 2 уже генерується
- WHEN автор змінює план сцени 6 або нерелевантну роль
- THEN готовий результат може публікуватися, якщо його власні залежності й target CAS не змінилися.

### Scenario: R05-SNAPSHOT-RELEVANT
- GIVEN memory сцени 2 генерується
- WHEN її вхідну прозу/попередню пам’ять замінено або порядок попередніх сцен змінено
- THEN результат зберігається альтернативою й не переписує голову автоматично.

### Scenario: R05-SNAPSHOT-ABSENT
- GIVEN при генерації не було релевантного канону/стилю/джерела
- WHEN це джерело з’явилося до публікації
- THEN зміна виявляється навіть без старого input_ref.

## Requirement: R05-FRESHNESS — Актуальність і пояснення

Для нових версій актуальність SHALL визначатися відповідністю перевіреного
baseline поточним релевантним залежностям, цілісністю й complete. Публічні
списки/голови/контекст/readiness/експорт SHALL використовувати одне визначення.
Причини містять тип зміни, джерело та expected/current IDs або значення;
окремо позначається legacy stale без достатнього доказу.

Історичні input_refs, вихідний fingerprint і точний запит SHALL залишатися
походженням моделі; нова актуальність не переписує історію так, ніби модель
читала нові джерела. Зворотні dependency_edges зберігають свою роль походження;
перевірка selector/baseline не покладається лише на ребра старих refs.

### Scenario: R05-FRESHNESS-RETURN
- GIVEN нова версія мала всі залежності A і стала застарілою після зміни на B
- WHEN усі релевантні залежності знову точно A
- THEN її актуальність відновлюється без нового inference
- AND legacy stale без snapshot не стає fresh за припущенням.

## Requirement: R05-ACCEPT — Явне авторське прийняття

Перед прийняттям stale draft/edited/manual UI SHALL показувати сам текст,
перелік змінених залежностей і попередження про необхідність оновлення
похідних матеріалів. Окрема явна дія автора записує acceptance ID, original
version ID, timestamp, дію/необов’язкову авторську примітку та новий baseline.
Новий модельний виклик і ручне повторне вставлення тексту не потрібні.

Прийняття й вибір голови SHALL виконуватися транзакційно з перевіркою
expected scene revision, незмінності показаного diff/baseline, власності,
дозволеного kind, complete і SHA-256. Зміна джерел після попереднього
перегляду дає конфлікт і потребує нового перегляду. Відсутній/пошкоджений/
чужий/незавершений файл прийняти не можна. Звичайний вибір свіжої версії
залишається доступним без нового acceptance.

Прийнятий текст стає авторським рішенням на новому baseline, але старі
спроби й відхилені результати не перейменовуються на автоматично completed.
Нова база не підтверджує стару пам’ять або оцінку. Для першої реалізації
немає універсального прийняття stale brief, memory або evaluation; пам’ять
потребує перебудови/валідації, evaluation — нового актуального оцінювання.

### Scenario: R05-ACCEPT-PROSE
- GIVEN автор переглянув stale prose та змінені джерела
- WHEN явно приймає її за незмінного показаного стану
- THEN голова й acceptance збережені разом, текст та походження незмінні
- AND похідна пам’ять/оцінка не стає актуальною автоматично.

## Requirement: R05-RESUME — Альтернатива без прихованого повтору

Після прийняття результату зупиненого workflow автор SHALL мати явне
продовження після прийнятого етапу. Воно атомарно перевіряє run/task/cursor,
прийняту версію й baseline; лише тоді просуває cursor. Звичайна зміна голови
або сам факт наявності acceptance не запускає роботу у фоні.
Можна обрати нову генерацію або скасування натомість; платний повтор не
маскується як продовження. R-04 block/off та R-03 recovery/cancel зберігаються.

### Scenario: R05-RESUME-ACCEPTED
- GIVEN remaining зупинився на alternative й автор прийняв саме цей результат
- WHEN обирає продовження після прийнятого етапу
- THEN прийнятий етап не викликає модель знову, наступний будується з актуальних входів.

## Сумісність, дані та перевірки

- R-05a не змінює SQL-схему й доменні значення; старі імпорти Run/RunRequest/
  RunEvent залишаються сумісними через re-export.
- Новий snapshot має явну версію; його відсутність означає legacy-публікацію
  з консервативним story/scene revision CAS, а не дозвіл спрощеної перевірки.
- Стан старих stale/needs_review зберігається; сервер не «лікує» legacy
  автоматично. Розширення домену й журналу прийняття не переписує файли текстів.
- R-02 fsck/backup/restore SHALL читати нові метадані; невідома версія snapshot
  не сприймається як чинна. Якщо потрібна міграція, потрібні round-trip backup
  та legacy fixture до її приймання.
- Окремі commit/check для a→b→c, RED/GREEN для CAS/rollback, відсутнього→наявного
  джерела, релевантного/нерелевантного оновлення, повернення A→B→A, stale
  прийняття, пошкоджень, конкурентної правки після diff та resume без inference.
- Після кожної частини — повний послідовний offline pytest з коротким окремим
  basetemp, незалежне рев’ю й одночасне оновлення кореневої SPEC.MD.

Реальні авторські дані, моделі та бюджети для цього пакета не потрібні.
