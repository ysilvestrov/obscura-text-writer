# R-01 — Експорт лише активних матеріалів

Дата: 20.10.2026. Статус: реалізовано; уточнює чинний контракт DATA-006/EXPORT-001. Сфокусовані тести: 18 passed; повний offline pytest: 221 passed. Реалізована архітектура відображена в кореневій SPEC.MD.

Джерела: [коренева SPEC.MD](../../../SPEC.MD), [беклог](../../superpowers/plans/2026-10-20-remediation-backlog.md). Специфікація зміни не підміняє кореневий опис реалізованої архітектури.

## Мета й межі

Усунути потрапляння сцен із кошика до експорту й можливість створювати експорт архівного твору. Не змінювати формат MD/TXT/manifest, правила попереджень, кошик/відновлення або збереження версій.

### Requirement: R01-001 — Активні матеріали

Експорт SHALL відхиляти твір із кошика й SHALL включати лише активні сцени. `allow_incomplete` SHALL не дозволяти обхід кошика.

#### Scenario: Архівна сцена
- GIVEN активний твір містить активну й архівну сцени
- WHEN створюється MD або TXT, з дозволом неповноти або без нього
- THEN архівна сцена відсутня в тексті, warnings, manifest і підрахунку слів.

#### Scenario: Архівний твір
- GIVEN твір переміщено до кошика
- WHEN запитується експорт із будь-яким значенням `allow_incomplete`
- THEN репозиторій повертає KeyError, HTTP API — 404
- AND нові файли експорту не створюються.

### Requirement: R01-002 — Узгоджений знімок

Repository SHALL повертати твір, упорядковані активні сцени та метадані вибраних prose-head з однієї read-транзакції. Експортер SHALL використовувати тільки цей знімок для складання manifest і тексту.

#### Scenario: Конкурентна архівація після початку читання
- GIVEN read-транзакція вже прочитала твір
- WHEN інша транзакція архівує сцену або змінює її голову
- THEN решта SQL snapshot бачить той самий початковий стан
- AND експорт не змішує нові голови/порядок зі старою ревізією твору.

### Requirement: R01-003 — Перевірена проза

Читання зафіксованого файла SHALL перевіряти SHA-256. Відсутня, застаріла, неповна проза та needs_review активної сцени SHALL зберігати чинні правила блокування або явного неповного експорту.

#### Scenario: Пошкоджений файл
- GIVEN prose-head зафіксовано, але файл має інший хеш
- WHEN формується експорт
- THEN операція завершується помилкою цілісності, а не мовчазно експортує змінений текст.

## Технічний контракт

`Repository.export_snapshot(story_id: str) -> tuple[Story, list[tuple[Scene, VersionRef | None]]]`:

1. Відкриває read-транзакцію `BEGIN` і перевіряє активний твір.
2. Читає сцени в порядку `position,id`, виключає `trashed_at`.
3. У тій самій транзакції читає метадані prose-head кожної включеної сцени; відсутня голова — `None`.
4. Повертає відокремлені доменні об’єкти, закриваючи транзакцію перед складанням і записом файлів.

Експортер не звертається до `repo.db` або приватних методів Repository. Незмінні файли читаються через `repo.files.read(path, sha256)` за refs знімка; не через новий lookup голови. Видалення тут зворотне, файли версій не прибираються. Архівація після фіксації знімка не змінює його; якщо сам твір згодом архівовано, download-route відхиляє завантаження за чинним правилом.

## Сумісність і приймання

- Міграція БД не потрібна; API-запит і структура manifest не змінюються.
- Архівний твір більше не створює експорт; це виправлення дефекту, не новий підтримуваний режим.
- Тести: обидва формати/обидва `allow_incomplete`, HTTP 404, конкурентна зміна під час SQL snapshot, зміна голови після snapshot, відсутня проза та SHA-256.
- До завершення: GREEN сфокусованих перевірок і повного pytest, DATA-006/EXPORT-001/A8 й Known limitations оновлені в кореневій SPEC.MD.
