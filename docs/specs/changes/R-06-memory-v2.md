# R-06 — Пам’ять твору v2 і компактний контекст

Дата: 21.10.2026. Статус: погоджено власником; реалізацію плану в цій сесії дозволено без додаткового підтвердження.
Чинна реалізована архітектура залишається в кореневій SPEC.MD. Цей документ
описує запропоновану зміну; до її реалізації нові контракти не вважаються чинними.

## Мета та рішення власника

Зменшити запити генерації, усунувши з них повторювані докази пам’яті, та
представляти стан персонажа актуальним твердженням замість накопичення
суперечливих станів. Зберегти перевірку походження, історію, незмінні версії,
R-05 dependency snapshots/target CAS і явне повідомлення про overflow.

Власник обрав 21.10.2026:

1. Модель автоматично пропонує update/retire для станів персонажів і відкритих
   ліній; застосунок застосовує їх лише після перевірки доказу та протоколу.
   Окремого підтвердження кожного коректного оновлення не потрібно.
2. Факти й хронологічні події залишаються незмінними; історія зберігається.
3. Письменник отримує стани персонажів поточної сцени та загальні стани.
4. Пам’ять будується лише вперед за порядком сцен: M[n] = apply(M[n−1],
   підтверджені операції з прози n). Жодне джерело зі сцен після n не дозволене.
5. Для відомостей персонажів потрібні часові мітки доступності; відомості
   майбутніх сцен виключаються, для непозначених описів показується попередження.

Рекомендований підхід — повний доказовий журнал і дві детерміновані проєкції:
літературний контекст та каталог для наступного оновлення пам’яті. Лише
проєкція поверх старого append-only snapshot зменшила б запит, але залишила б
суперечливі чинні стани. Модельний summary не обрано: це додатковий inference
та новий ризик втрати фактів/походження.

## Межі та порядок

**R-06a — Компактна проєкція.** Єдине читання legacy/v2 через memory-сервіс;
проєкція для brief/draft/prose-edit без технічних UUID і цитат. Попередній
доказовий snapshot зберігається сервером і перевіряється повністю. Окремий коміт.

**R-06b — Журнал і операції.** v2, add/update/retire, чинний каталог для ролі
пам’яті, scope станів, сумісні адаптери, ручне збереження, діагностика та
регресії масштабу. Окремий коміт після приймання R-06a.

**R-06c — Часова доступність відомостей персонажів.** Авторська розмітка,
сумісне читання старих карток, сценова проєкція та видимі попередження.
Додано прямим рішенням власника 21.10.2026. Окремий коміт після R-06b;
підбір Venice-оцінювача виконується після всіх трьох частин.

У R-06 немає нового tokenizer, модельного summary, embeddings/retrieval,
зміни горизонту майбутнього плану, зміни рубрики чи протоколу Evaluator.
R-07 зберігає окремий обсяг робіт із точністю оцінки токенів.

Після R-06 за прямим запитом власника виконується окремий підбір і перевірка
Venice-оцінювача до повернення до решти беклогу. Зараз evaluator не читає
пам’яті: його документи — план, канон/стиль/персонажі, brief, проза, а для
edit_pair також чернетка. Тому R-06 не обіцяє усунути його overflow.

## Requirement: R06-PREFIX — Пам’ять лише від початку до поточної сцени

M[0] SHALL бути порожньою. M[n] SHALL створюватися з перевіреної M[n−1]
та операцій, підтверджених виключно вибраною прозою сцени n. M[n−1] уже
містить журнал усіх попередніх сцен: конкатенація M[1]…M[n−1] заборонена,
оскільки повторює ті самі події. Update/retire змінюють чинну проєкцію,
зберігаючи попередні події в журналі.

Перед brief/draft/prose-edit сцени n SHALL використовуватися M[n−1], навіть
якщо вже існують пам’ять n або готові наступні сцени. M[n] будується після
прози n; план n не є джерелом доказових фактів. Немає вибору «найновішої
пам’яті твору» за датою або пам’яті останньої готової сцени незалежно від n.

source_prose_ids M[n] SHALL точно дорівнювати вибраній прозі активних сцен
1…n у їхньому поточному порядку; кожний event посилається на свій елемент
цього префікса. Цитата з майбутньої сцени не стає допустимим доказом лише
через її точний збіг. Вимога однакова для генерації, ручного збереження,
legacy loader, rebuild і fsck.

Заміна попередньої прози або перестановка/кошик сцени всередині префікса
SHALL перевірятися R-05 snapshots/freshness. Перебудова починається з
найранішої зміненої сцени й рухається вперед; нерелевантна зміна сцени після
n не змінює M[n]. Читання пам’яті для ранньої сцени SHALL не реконструювати
її з пізнішого стану шляхом приблизного віднімання фактів.

Хронологія тут — авторський порядок подання сцен. Дати у прозі, спогади й
флешбеки не є підставою автоматично переставляти сцени чи джерела; згадка
минулого стає доступною контексту з тієї сцени, де вона була представлена.
Це не модель окремих знань кожного POV-персонажа.

### Scenario: Повернення до ранньої сцени
- GIVEN усі сім сцен мають прозу й пам’ять
- WHEN автор повторно запускає письменника для сцени 2
- THEN використовується лише M[1], без фактів або станів із M[2]…M[7].

### Scenario: Доказ із майбутнього
- GIVEN джерелом запису M[2] заявлено прозу сцени 5 з точною цитатою
- WHEN сервер перевіряє згенеровану або ручну пам’ять
- THEN збереження/публікація відхиляються як порушення префікса.

### Scenario: Зміна сцени після префікса
- GIVEN M[2] залежить від вибраної прози сцен 1 і 2
- WHEN змінено план, прозу або пам’ять сцени 5
- THEN ця зміна сама по собі не додає даних до M[2] і не робить її застарілою.

## Requirement: R06-CHARACTER-TIME — Доступність відомостей персонажів

Відомості картки SHALL мати окремі авторські записи зі стабільним ID, text,
походженням і availability: unclassified, timeless або from_scene. Для
from_scene обов’язковий available_from_scene_id активної сцени цього твору;
для інших режимів це поле порожнє. Стабільний scene ID, а не зафіксований
номер, зберігає прив’язку при перестановці сцен.

Картки v2 зберігаються як список об’єктів schema_version=2/id/name/entries.
Запис entries містить id/text/availability/available_from_scene_id/origin/sources.
Origin imported вимагає непорожніх SourceCitation з перевіреними належністю
й дослівним quote; origin author явно позначає авторське твердження і допускає
відсутність цитат. Наявні посилання завжди перевіряються, а авторська мітка
не є доказом семантичної правильності тексту. Нові IDs призначає сервер,
редагування зберігає ID, дублікати відхиляються. Legacy-конвертація ID
детермінована й не переписує джерельного файла.

Мітка означає «цей текст можна передати письменнику починаючи з цієї сцени».
Вона не означає, що подія вже відбулася до початку цієї сцени. Запис може
описувати намір/ціль поточної сцени; новий здійснений факт потрапляє в пам’ять
лише через її прозу. Timeless означає явну авторську перевірку доступності
від самого початку, а не автоматичний висновок моделі.

Для brief/draft/prose-edit сцени n SHALL будуватися однакова проєкція карток:
timeless включається, from_scene включається лише при позиції початкової
сцени ≤ n. Майбутній запис SHALL не передаватися як факт, примітка,
пояснення виключення або повна прихована копія початкової картки.
Якщо всі записи виключено, вихідний повний опис не підставляється як fallback.
Недоступний/чужий/архівний available_from_scene_id SHALL давати явну помилку
до inference, а не трактуватися як timeless. Зміна порядку сцен змінює
проєкцію за стабільною прив’язкою й входить у snapshot/fingerprint.

Unclassified SHALL включатися лише з видимим неблокувальним попередженням:
«Часову доступність опису не перевірено; він може містити відомості з майбутніх
сцен». Попередження показується в readiness/підтвердженні запуску, стані
запуску та зберігається у зафіксованому контексті. У запиті це окрема
секція неперевірених авторських відомостей, не підтверджена пам’ять.
Попередження не оголошує конкретний фрагмент спойлером без доказів.
Readiness додає неблокувальний warnings, ContextBundle — context_warnings
із порожнім default для старих спроб. Worker зберігає context_warning подію
та додає повідомлення до Run.warning, не стираючи наявних попереджень,
зокрема Evaluator. Reload має показувати його з persisted стану, а не лише toast.

Старий CharacterCard.description SHALL читатися як один unclassified запис
із тим самим текстом та джерелами. Вихідний source_characters без карток
також має неперевірену часову доступність. Автоматичне розбиття довільного
опису, встановлення дат доступності або позначення всього legacy-опису
timeless не виконується. Створена старим blueprint картка лишається
unclassified до авторської розмітки; протокол prepare не вимагає нових
модельних полів заради цієї задачі.

У контексті твору SHALL бути доступний редактор відомостей персонажів:
розбити/редагувати записи, вибрати timeless/unclassified або першу сцену
доступності, переглянути результат для вибраної сцени. Збереження окремою
авторською дією створює нову immutable character_cards версію з CAS ревізії
твору; старі bytes збережені. Перегляд проєкції не змінює буфер сцени.
API GET/PUT /api/stories/{story_id}/characters SHALL повертати/приймати
сумісно нормалізовані картки; PUT містить expected_revision. Формат запису
карток v2 версійований, legacy loader не переписує наявні файли.

Ця фільтрація SHALL стосуватися карток і вихідних описів персонажів; вона
не є гарантією відсутності будь-якого спойлера в каноні, авторському промпті,
brief або глобальних інструкціях. Readiness SHALL повідомляти цю межу, якщо
використовуються нерозмічені джерела. Майбутні плани залишаються явно
позначеними намірами за чинним CONTEXT-002; налаштування їхнього горизонту
залишається окремим R-12. Додатковий модельний аудит джерел тут не запускається.

### Scenario: Майбутнє знайомство
- GIVEN запис «A уже знайомий із B» доступний зі сцени 4
- WHEN готується письменник для сцени 2
- THEN цього тексту немає в character-контексті
- AND для сцени 4 він може бути авторською вказівкою, а не доказом із M[3].

### Scenario: Старий опис без міток
- GIVEN legacy description містить невідомо які за часом відомості
- WHEN готується рання сцена
- THEN автор бачить попередження і може розмітити опис
- AND система не стверджує, що автоматично перевірила його хронологію.

### Scenario: Перестановка або кошик опорної сцени
- GIVEN відомість прив’язана до scene ID X
- WHEN X переміщено або архівовано
- THEN доступність перераховується за новою позицією або inference блокується
- AND система не підміняє X іншою сценою зі старим номером.

## Requirement: R06-PROJECTION — Літературний контекст

Brief, draft і повна prose-редактура SHALL отримувати детермінований текст
пам’яті з чотирма секціями: факти, поточні стани, відкриті лінії, хронологія.
Технічні claim/event/version IDs, source_prose_ids та доказові quote SHALL
не додаватися до цієї секції запиту. Власний текст твердження не редагується
заради видалення звичайних лапок, номерів або ідентифікаторів із сюжету.

Проєкція SHALL містити всі факти й події хронології, всі активні відкриті
лінії та вибрані активні стани. Update замінює видиме формулювання стану;
retire прибирає його з чинної проєкції, зберігаючи повну історію на сервері.
Пояснення retire відкритої лінії SHALL додаватися до хронологічної секції
як її завершення; закриття не видається за досі відкриту проблему. Промпт
не вимагає вдруге додавати той самий запис операцією timeline/add.
Порядок секцій і записів фіксований, хронологія прив’язана до номера джерельної
сцени. Сортування за текстом або семантична дедуплікація не застосовуються.

### Scenario: Докази лишаються на сервері
- GIVEN попередня пам’ять містить твердження, source ID й довгу цитату
- WHEN формується контекст письменника
- THEN він містить текст твердження без технічного походження
- AND input_refs, dependency snapshot і зафіксований серверний контекст зберігають походження.

### Scenario: Детермінованість
- GIVEN ті самі пам’ять, склад сцени та версія проєкції
- WHEN контекст будується повторно
- THEN секція пам’яті має ідентичні байти й однакові метрики.

## Requirement: R06-SCOPE — Стани персонажів сцени

Новий стан SHALL мати character_ids: порожній список означає загальний стан,
непорожній — явну прив’язку до персонажів. Якщо scene.character_ids заданий,
проєкція SHALL включати загальні стани та стани з непорожнім перетином ID.
Якщо список персонажів сцени порожній, SHALL включатися всі чинні стани:
система не вгадує склад сцени з тексту.

Legacy-стани без character_ids SHALL трактуватися як загальні. Вони не
отримують вигаданих тегів під час міграції. Для точнішого відбору потрібне
нове доказове оновлення/перебудова або явна коректна авторська версія.

Memory-запит SHALL показувати allowed character IDs поточної сцени й scope
вже наявних станів. Новий scope дозволяється лише з character_ids сцени;
якщо модель не може однозначно співвіднести ID з прозою, вона використовує
загальний стан. Картки, майбутні плани та їхні залежності не вводяться в
memory-запит заради вгадування scope. Прив’язка є модельним твердженням,
а не доведеною семантичною істинністю лише через збіг цитати.

Зміна scene.character_ids SHALL входити в dependency snapshot нового memory
етапу, якщо цей список передано як allowed scope. Зміна майбутнього плану або стилю SHALL не створювати конфлікту
memory-публікації. Scope незмінний для claim; щоб замінити прив’язку,
потрібні retire старого й add нового з доказами.

### Scenario: Вибрані персонажі
- GIVEN активні стани персонажів A/B і загальний стан, а сцена має ID A
- WHEN формується її літературна проєкція
- THEN включаються A і загальний стан, а B залишається в журналі
- AND метрики фіксують кількість виключених за scope станів.

### Scenario: Невідомий склад сцени
- GIVEN scene.character_ids порожній
- WHEN формується проєкція
- THEN жоден чинний стан не виключається через scope.

## Requirement: R06-JOURNAL — Версійований журнал

Канонічний v2 snapshot SHALL містити schema_version=2, впорядковані
source_prose_ids і впорядкований журнал events. Подія містить event_id,
claim_id, operation, category, text, character_ids, source_version_id і quote.
Види category: facts/character_states/open_threads/timeline.

Claim ID SHALL призначатися сервером при add детерміновано з зафіксованого
джерела й операції та залишатися незмінним для update/retire. Event ID
ідентифікує конкретну операцію. Повтор ID, невідомий target, зміна category
або scope і неправильна послідовність операцій SHALL відхилятися.

Add створює активний claim. Update дозволений лише для активного
character_states/open_threads й створює нове формулювання того самого claim.
Retire дозволений лише для цих активних категорій і фіксує пояснення
закриття; попередній стан і докази лишаються в журналі. Retired claim
повторно не оновлюється: повторне відкриття — окремий add із новим ID.
Facts/timeline мають лише add. Зміна помилкової минулої події потребує
виправлення джерельної сцени/пам’яті та перебудови залежного префікса.
Промпт SHALL відрізняти встановлені незмінні обставини й здійснені події
від змінного стану. Місцезнаходження, володіння предметом, стан дверей або
поточна домовленість належать до станів; загальні стани можуть мати порожній
character_ids. Семантично перевірити правильність категорії лише схемою не можна.

Кожний новий event SHALL посилатися на поточну прозу й непорожній дослівний
фрагмент; старі events SHALL перевірятися проти власних джерел. Точний збіг
цитати перевіряє походження, але не доводить логічну правильність висновку.

### Scenario: Послідовні стани
- GIVEN claim «A перебуває у студії» активний
- WHEN поточна проза підтверджує від’їзд і модель повертає коректний update
- THEN проєкція показує новий стан, а журнал зберігає обидві версії з доказами.

### Scenario: Закрита лінія
- GIVEN активна лінія пошуку ключа
- WHEN проза підтверджує її завершення і прийнято retire
- THEN лінія відсутня серед відкритих, але її історія відновлюється з events.

### Scenario: Неправомірна операція
- GIVEN модель намагається update факту, повторно змінити retired claim або використати невідомий ID
- WHEN перевіряється весь набір операцій
- THEN жодна його операція не публікується; partial залишається для діагностики.

## Requirement: R06-DELTA — Компактний протокол ролі пам’яті

Новий evidence_delta SHALL використовувати schema_version=2 і operations.
Операція має action add/update/retire, category, nullable claim_id,
непорожній text, character_ids та evidence_id поточної прози. Add вимагає
claim_id=null; інші операції — точний активний claim ID. Для категорій, крім
character_states, character_ids порожній. Один target не можна змінювати
двічі в межах однієї відповіді. Допускається до 12 операцій загалом і до
трьох add на категорію, порожній набір дозволений.

Memory-модель SHALL отримувати всі потрібні чинні claims як компактний
каталог ID/category/text/scope та пронумеровану поточну прозу. Минулі цитати,
version IDs, retired/superseded події й список усіх джерел не передаються
для дослівного переписування. Повний previous snapshot, mapping фрагментів
і походження SHALL зберігатися в контексті спроби на сервері.

Операції SHALL перевірятися й застосовуватися атомарно в пам’яті до створення
незмінної версії. Модель не передає власні source IDs/quote для v2 operations;
їх додає сервер. Результат зберігається повним snapshot v2, partial — сирою
відповіддю. Нові ролі типово використовують evidence_delta; раніше збережені
налаштування й авторські промпти не переписуються автоматично.
Для збереженого legacy payload без memory_mode loader SHALL використовувати
старе значення snapshot; зміна default нових налаштувань не змінює читання старих.

### Scenario: Один некоректний доказ
- GIVEN відповідь має кілька коректних операцій і одну з невідомим evidence_id
- WHEN сервер перевіряє відповідь
- THEN весь результат відхилено, поточна пам’ять і попередній журнал не змінені.

## Requirement: R06-COMPAT — Сумісність і ручні правки

Єдиний loader SHALL розрізняти legacy v1 без schema_version і v2 з явним
schema_version=2. Невідома версія або змішаний невалідний формат відхиляється.
Читання v1 будує детерміновані add-events із тих самих text/source/quote,
без семантичного об’єднання, прихованого retire або переписування старого файла.
Порядок конвертації — source_prose_ids, категорія, вихідний індекс; ідентифікатор
враховує джерело, категорію, вміст і номер однакового запису. Копіювання того
самого префікса до наступного snapshot не змінює його claim/event IDs.
Legacy-суперечності не оголошуються виправленими самою конвертацією.

Snapshot-режим SHALL залишатися доступним як застарілий add-only протокол.
Модель бачить сумісне представлення чинних записів із доказами; відповідь
має зберегти всі ці записи. Сервер переносить лише нові доповнення до
попереднього повного v2-журналу, тому старі retired/superseded events не
втрачаються. Валідний старий evidence_delta з чотирма масивами підтримується
як add-only адаптер для авторських legacy-промптів; це не fallback після
невалідного v2. JSON Schema нового evidence_delta описує саме operations v2.

Нове збереження SHALL створювати snapshot v2. Наявні immutable v1 bytes,
SHA-256, heads, snapshots і stale-ознаки не мігрують на старті сервера;
SQL schema_version лишається 2. Сумісність перевіряється на синтетичних
копіях, а не переписуванням авторського каталогу.

Ручний API SHALL приймати v1/v2, перевіряти ревізію, точний список джерел,
цитати й канонічний незмінений журнал попередніх сцен. Поточні операції
сцени можна виправляти в новій версії з власним доказом; події попередніх
сцен не видаляються й не переприв’язуються. Для виправлення попередньої
сцени потрібна її власна нова пам’ять і явна перебудова наступних.

### Scenario: Стара пам’ять
- GIVEN v1 snapshot із доказами й чинними залежностями
- WHEN його читає нова версія або він використовується перед наступною сценою
- THEN текст, джерела й цитати збережені без модельного виклику
- AND історичні bytes/хеші/freshness не змінені.

### Scenario: Legacy-протокол після v2
- GIVEN журнал містить retired та оновлені claims
- WHEN snapshot-протокол додає новий коректний запис
- THEN новий snapshot v2 зберігає весь попередній журнал, а не лише активний зріз.

### Scenario: Ручне стирання минулої події
- GIVEN JSON змінив або видалив event із попередньої сцени
- WHEN автор зберігає поточну пам’ять
- THEN API повертає пояснення без зміни голови чи редакторського буфера.

## Requirement: R06-LINEAGE — Публікація та цілісність

Loader/validator/projection SHALL бути спільними для generation, ручного API,
memory_before, rebuild і fsck. ContextView SHALL залишатися джерелом
узгодженого читання. Дані для валідації результату беруться з captured
previous memory/prose/scope, а не з конкурентно змінених голів.

Усі старі джерела, попередня memory-версія, поточна проза та scope metadata
SHALL залишатися в релевантному dependency snapshot. target CAS, acceptance
baseline IDs, відмова від автоматичного retry і правила R-05 не змінюються.
Зміна релевантного входу під час запиту дає alternative, а не частковий commit.

Fsck SHALL перевіряти форму v1/v2, унікальність і послідовність IDs/операцій,
джерела, хронологічний префікс, цитати та відтворюваність поточного стану.
Для історичної версії префікс перевіряється за її captured snapshot, а не
новими головами/порядком після авторських змін. Неперевірюваний історичний
порядок legacy без snapshot фіксується як обмеження перевірки; це не доводить
пошкодження. Споживання поточної пам’яті завжди перевіряє актуальний префікс.
Backup/restore SHALL зберігати обидві версії формату без нормалізації bytes.

## Requirement: R06-BUDGET — Вимірювання й явний overflow

ContextBundle SHALL фіксувати версію проєкції та метрики: розмір повного
журналу, кількість подій/чинних claims, розмір і склад проєкції, кількість
виключених за scope станів. Memory-запит окремо фіксує розмір каталогу.
Fingerprint SHALL враховувати фактичні system/user bytes і frozen-параметри.

Чинні context_tokens/max_output_tokens/max_input_chars SHALL перевірятися
після побудови компактного запиту. Overflow SHALL повідомляти оцінку входу,
доступний бюджет і внесок пам’яті; до провайдера запит не надсилається.
Стиснення моделлю, мовчазне обрізання чи відкидання фактів для fit заборонені.
Повний timeline і кількість незалежних активних ліній можуть рости;
сталий розмір проєкції або гарантований fit 15 сцен у 8k не обіцяється.

## Перевірки та приймання

Уточнення реалізації: POST `/api/stories/{id}/characters/preview` проєктує
незбережений набір cards/scene_id без запису; GET preview залишається для
збережених карток. Це забезпечує перегляд до збереження. Story publication
допускає лише перевірені пари style/style_version_id і character_cards/characters_version_id.

- Unit: add/update/retire, immutable category/scope, невідомий/retired target,
  дубль ID/операції, неправильний evidence, точний source order, legacy loader.
- Context: відсутність технічних полів/цитат у секції пам’яті, чинний стан
  без superseded версій, cast/global/empty-cast, незмінні facts/timeline,
  детермінованість, metadata й явний overflow до gateway.
- Префікс: повтор сцени 2 при готових 7/15 сценах, відхилення майбутнього
  source ID навіть із правильною цитатою, M[n−1] замість M[n] для письменника,
  одноразове включення кожної події та порядок подання при флешбеках.
- Персонажі: timeless/from_scene/unclassified, межі n−1/n/n+1, empty
  проєкція без raw fallback, reorder/trash/foreign anchor, legacy warnings,
  source quotes, авторські записи, CAS і збереження буфера при preview.
- Інтеграція: 7 і 15 синтетичних сцен, повторні зміни тих самих станів і
  закриття ліній, журнал/проєкція/повний запит вимірюються окремо. Для fixture
  з довгими доказами компактна секція пам’яті має бути щонайменше вдвічі
  меншою за legacy JSON; fixture не використовується як універсальна оцінка.
- Конкуренція: заміна прози/попередньої пам’яті/cast під час запиту,
  нерелевантний майбутній план, повернення A→B→A, target CAS й acceptance IDs.
- API/UI: ручні v1/v2, коректна 409, dirty/history buffer, позначення
  застарілого snapshot-режиму та новий default лише для нових налаштувань.
- Maintenance: fsck валідного й зіпсованого журналу; холодний backup/restore
  змішаного каталогу v1/v2; старі immutable файли лишаються ідентичними.
- Повний offline regression suite після кожної з трьох частин. Зовнішні моделі не
  потрібні для приймання протоколу; семантична якість пам’яті оцінюється окремо.

Реалізація SHALL оновити MEMORY-001/002, додати контракти журналу/scope,
оновити CONTEXT-002, контракти карток/попереджень, A2/A5/A6/A8 і матрицю
перевірок SPEC.MD у тих самих комітах.
Чинні недоліки append-only станів і сирого JSON у запиті SHALL бути зазначені
як усунені відхилення після фактичної реалізації, а не оголошені усуненими тут.
