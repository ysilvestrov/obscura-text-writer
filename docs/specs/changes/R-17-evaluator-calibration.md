# R-17 — Калібрування профілю Venice Evaluator

Дата: 21.10.2026. Статус: прогін завершено, кандидат не допущений.
Власник погодив повний синтетичний набір і новий окремий бюджет до $0.90,
без повторів і зі зупинкою після відмови.
Результат: [звіт R-17](../../r17-calibration-2026-10-21.md).

## Мета та межі

Перевірити придатність конкретного кандидата для оцінювання української прози
за чинним контрактом SPEC.MD та R-04. Використати штатні CLI, протокол,
рубрику, evidence verification і реєстрацію профілю. Нового механізму
калібрування, змін порогів чи автоматичного fallback немає.

Кандидат: `config/evaluator.venice.example.json`, Venice `qwen-3-8-27b`,
prompt_json, temperature=0.1, thinking off, Venice system prompt off,
max_output_tokens=3000, max_input_chars=100000, timeout=180 с.
Контекст із каталогу: 262144; політика застосунку залишається report.

## Requirement R17-001: Відтворюваний повний прогін

Система SHALL перевірити всі 16 випадків `calibration_suite_v2.json`
версії `adult-v2-neutral-1` тричі, зафіксувавши конфігурацію, fingerprint,
канонічний hash набору, рубрику, промпт і незалежні run IDs.
Синтетичні дорослі приклади входять до набору; приватний твір не надсилається.
Exact requests/responses, usage, резерви й результати MUST залишатися поза Git.

### Scenario: Незмінна конфігурація
- GIVEN зафіксований кандидат і повний набір
- WHEN виконуються 48 незалежних викликів
- THEN кожний результат має походження й перевірені докази, а revision-пари
  використовують штатне чергування порядку між повторами.

## Requirement R17-002: Бюджет та зупинка

Перед платними викликами MUST бути погоджено новий окремий бюджет.
Перед кожним викликом резервується консервативна верхня оцінка, записана
на диск; навіть error/timeout не звільняє її як нібито безкоштовну.
Резерв входу: UTF-8 bytes усіх messages + bytes схеми + 4096 overhead;
резерв виходу: 3000 токенів. Тариф перевіряється перед запуском;
невідома або збільшена ціна вимагає перерахунку до відправлення.
Жодних прихованих retries, паралельних викликів або додаткових моделей.

### Scenario: Відмова
- GIVEN модель явно відмовилась у контрольному випадку
- WHEN відповідь класифікована refused
- THEN наступні виклики прогону не виконуються, звіт зберігає відмову
  окремо від технічної помилки; допуск не надається.

### Scenario: Незавершений запуск
- GIVEN процес перервався після запису резерву
- WHEN досліджується стан прогону
- THEN невизначений виклик не повторюється автоматично й не рахується
  успішним або безкоштовним; продовження потребує явного рішення.

## Requirement R17-003: Чесний допуск

Допуск SHALL визначатися штатним calibrate: recall≥0.8,
false positive rate≤0.2, availability≥0.9, refusal_count=0,
без пропущених critical, невідомих доказів і нестабільних доступних вердиктів.
Precision відображається без вигаданого додаткового порогу.

### Scenario: Успішний кандидат
- GIVEN повний звіт задовольняє всі чинні критерії
- WHEN профіль реєструється штатною операцією з перевіркою артефактів
- THEN допуск прив’язаний до точного fingerprint і зберігається після reopen;
  зміна моделі, response_mode, промпту, рубрики чи набору його скасовує.
  report не змінюється на pause_on_failure без рішення автора.

### Scenario: Недостатня якість
- GIVEN хоча б один обов’язковий критерій не виконано
- WHEN підбивається результат
- THEN профіль залишається candidate; звіт пояснює конкретні причини,
  а пороги й очікування не змінюються задля успіху.

## Реалізація та перевірка

1. Read-only preflight каталогу, бюджету й точних request sizes.
2. Штатний CLI dry-run та offline-перевірка набору й артефактів.
3. Після погодження бюджету — послідовний bounded runner зі стійким ledger
   навколо штатного evaluate/calibrate, без модифікації приватного твору.
4. Аналіз усіх результатів; реєстрація лише за успіху, перевірки reopen та
   інвалідації в ізольованому каталозі перед зміною налаштувань застосунку.
5. Український підсумковий звіт без exact текстів/секретів у Git,
   оновлення журналу й інструкції Evaluator.

SQL-міграції та зміни UI/API не плануються. Якщо прогін виявить дефект коду,
виправлення отримує регресійний тест і відповідну зміну SPEC.MD.
