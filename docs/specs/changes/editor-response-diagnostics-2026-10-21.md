# Редактор: JSON-обгортка та діагностика reasoning

Дата: 21.10.2026. Виправлення після R-09, без нових автоматичних викликів.

## Докази

Реальна невдала відповідь містила чотири допустимі правки в одній Markdown-обгортці json. Після вилучення лише зовнішньої обгортки всі guards проходять. Інша спроба вичерпала вихідний ліміт 32000 повністю на reasoning за входу 2705 токенів і порожнього content. Це не переповнення входу.

## Requirement: EDIT-RESPONSE — Обмежене розпізнавання формату

Редактор patches SHALL приймати JSON без обгортки або одну зовнішню обгортку з трьох backticks, необов’язковою міткою json і без стороннього тексту. Сирий partial не змінюється; зняття обгортки фіксується попередженням у спробі й run. Текст навколо, кілька блоків, дублікати ключів і нечислові JSON-константи не виправляються. Схема та всі guards правок застосовуються після розпізнавання; немає витягування довільного JSON або автоматичного повтору.

### Scenario: Валідні правки в обгортці
- GIVEN повна відповідь stop містить лише один json-блок
- WHEN виконано розпізнавання та всі перевірки
- THEN пропозиція зберігається за чинним auto/review контрактом із попередженням і незмінним partial.

## Requirement: EDIT-DIAGNOSTICS — Причина відмови в збереженні

Помилка редактора SHALL розрізняти синтаксис JSON, схему, однозначність якоря, перетини, числа/заперечення, розмір правок і невідоме порушення публікації. Позиція/поле/номер правки та пояснення — тільки з довіреного словника, без копіювання модельних значень, довільного exception чи секретів. Структурна причина зберігається у спробі та відображається в run.error.

Надмірна глибина JSON є помилкою протоколу: RecursionError не виходить із парсера, спроба зберігається failed.

### Scenario: Reasoning вичерпав вихід
- GIVEN finish_reason=length, порожній content і usage вказує витрату всього completion на reasoning
- WHEN формується помилка
- THEN вона називає вихідний ліміт і reasoning, радить вимкнути/зменшити reasoning для сумісної моделі, не видає це за брак вхідного контексту й не повторює запит.

## Провайдер і налаштування

Для Venice наявний `venice_disable_thinking=true` SHALL додатково передавати рекомендоване офіційною документацією top-level `reasoning:{enabled:false}` через спільний exact request builder та SDK extra_body; legacy disable_thinking зберігається. Те саме правило діє для Evaluator; його fingerprint за активного вимкнення враховує новий wire-контракт, старий допуск не переноситься мовчки. Значення false не змінює звичайний запит.

Власник окремо погодив змінити лише редактора поточного твору: JSON Schema, disable thinking, max_output_tokens=8192; модель/контекст/інші ролі зберегти. Застосування через штатний API з CAS після тестів. Генерацію не запускати. Каталог Venice безкоштовно перевірено: qwen-3-8-27b supportsResponseSchema=true, reasoning options none/low/medium/xhigh, default=xhigh.

Промпт точкової редактури уточнює суцільну перевірку всіх фрагментів, не задає мінімум правок і не оголошує мало правок доказом якості. Нова інструкція не є доказом фактичної повноти редактури.

## План і приймання

1. RED→GREEN: точна зовнішня обгортка, недопустимі обгортки/дублікати, незмінний raw та guards; безпечні конкретні помилки.
2. RED→GREEN: length із reasoning-only usage; exact Venice body/SDK без зміни значення false; fingerprint Evaluator.
3. Прогін збереженої реальної відповіді офлайн без зміни авторської історії, повний pytest, SPEC й інструкція.
4. CAS-налаштування лише редактора через API, без paid inference; локальний коміт. Раніше невдалі спроби не переписуються й автоматично не приймаються.

Джерела: [Reasoning Models](https://docs.venice.ai/guides/features/reasoning-models), [Structured Responses](https://docs.venice.ai/guides/features/structured-responses). SQL2 та схеми CopyEdits не змінюються.
