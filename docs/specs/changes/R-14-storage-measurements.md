# R-14a — Вимірювання сховища перед рішенням про оптимізацію

Дата: 23.10.2026. Погоджений обсяг: прямий запит власника; реалізація оптимізацій не погоджена цим етапом.

## Мета й межі

Дати вимірювану відповідь, чи потрібно зараз змінювати SQL/індекси. Це дослідницький етап, а не зміна архітектури. Runtime, SPEC.MD, схема 3, авторські дані, моделі та сервер залишаються незмінними. Тимчасовий probe і бази зберігаються в ігнорованому artifacts; висновки — у docs/storage-measurements-2026-10-23.md.

## Протокол

- Синтетичні набори: 1 твір × 7 сцен × 20 версій; 10 × 15 × 30; 50 × 15 × 40. Поточна проза — 1000 слів на сцену, історичні версії коротші. Останній набір — запас масштабу, а не поточна потреба користувача.
- Створення через чинні доменні моделі та bulk SQL лише в нових синтетичних БД з чинними міграціями; валідні FK та реальні blob/hash. Голови draft/prose мають dependency snapshots із джерелами плану. Історія запусків і спроб масштабується разом із базою.
- Вимірювати list_stories, list_scenes, get_scene, context_view, list_versions для однієї сцени, list_attempts, list_runs і export_snapshot. Початковий виклик показувати окремо; після прогріву 20 повторів, median/p95/max. Це не вимір холодного диска.
- Для реальних SELECT із trace зафіксувати EXPLAIN QUERY PLAN та окремий час execute+fetchall без доменної десеріалізації. cProfile важких операцій відділяє SQL від Pydantic/файлів/перевірки залежностей. Інструментування не включати до основного API timing.
- Фіксувати версії Python/SQLite/ОС, HEAD, dirty paths, параметри SQLite, кількість рядків, обсяг БД, метрику результату й відсутність мутацій даних під час вимірів.

## Критерій рішення

Орієнтир для обговорення: p95 окремого читання >100 мс на типовому наборі або >250 мс на stress; це запропонований діагностичний поріг, не затверджений SLA. Повне сканування саме по собі не є доказом потрібності індексу. Зіставити вартість SQL з вартістю Python/повного знімка й описати обмеження. Не робити міграцію/додавання індексів без наступного рішення власника.

## Перевірка

У probe: FK check, відповідність обсягів, наявність/хеші blobs, перевірка кількості результатів та незмінності logical database dump до/після читань. Окрема ручна процедура: запустити probe, переглянути JSON timings/plans/profile та відтворити висновки у звіті. Нових продуктових Scenario/API цей етап не вводить; матриця traceability не змінюється.
