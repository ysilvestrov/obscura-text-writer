# R-04 — Evaluator для дорослого художнього тексту

Дата: 20.10.2026. Статус: реалізовано й прийнято offline (331 passed, 1 skipped). Реальний модельний допуск не виконано.
Чинна архітектура визначена кореневою SPEC.MD; цей документ деталізує пакет R-04.
Джерела: R-04 активного беклогу, F-14/T-20 та рішення власника нижче.

## Мета й погоджене рішення

Оцінювач перевіряє українську мову, літературну якість і відповідність задуму,
зокрема для дорослого художнього матеріалу. Наявність оголеності, інтимної теми
або насильства сама по собі не є літературним дефектом. Відмова сервісу не є
низьким балом твору; позначка uncensored у каталозі не доводить якості моделі.

Власник обрав 20.10.2026: у політиці `report` відмова або технічна помилка
оцінювача дає попередження й не блокує наступні сцени. У `pause_on_failure`
workflow зупиняється на паузі. Повтор, заміна моделі й fallback не автоматичні. Уточнення власника: відмова через контент назавжди блокує автоматичне використання цієї моделі оцінювача для цього оповідання; технічна помилка має показувати реальну надану причину, а не маскуватися як відмова.

## Межі та складові

1. Розширення чинного evaluation gateway/config для Venice; local, OpenRouter
   і Codex CLI залишаються доступними. Загальна уніфікація провайдерів — R-08.
2. Явне розрізнення відмови, технічної помилки, неповного покриття та
   літературного негативного висновку в runner, звітах, API/CLI й UI.
3. Версійований контрольний набір і реєстрація придатності конкретного профілю.
4. Узгодження цих результатів зі спільною чергою, checkpoints та політикою off.
5. Постійне блокування оцінювача для конкретного твору після контентної відмови.

Немає нової схеми SQLite, міграції авторських текстів, модераційного фільтра,
автоматичного очищення або переписування матеріалу. Зміна renderer, пам’яті,
редактора й грошовий ledger не входять у пакет.

## Requirement: R04-PROVIDER — Явний вибір backend

EvaluatorConfig SHALL підтримувати `venice` з офіційною адресою
`https://api.venice.ai/api/v1`, точним model ID і `VENICE_API_KEY` за замовчуванням.
Для решти провайдерів чинні адреси й умови ключів зберігаються. Ключі читаються
лише на сервері й не потрапляють у конфігурацію, fingerprints або звіти.

Перед надсиланням авторського тексту Venice gateway SHALL перевіряти каталог
текстових моделей: обраний ID має бути доступним, `uncensored=true`, не offline;
у режимі json_schema потрібен `supportsResponseSchema=true`. Використовується
наявний `providers/venice.py`, без другої суперечливої політики каталогу.
Перевірка не встановлює придатність local/OpenRouter/Codex за назвою моделі.

Venice-запит SHALL явно вимикати web search/scraping/X search. Параметри
`venice_include_system_prompt` і `venice_disable_thinking` конфігуруються та
входять до fingerprint; типово false, як у генераційних ролях. Чужі системні
промпти не додаються неявно. SDK max_retries=0; fallback відсутній.

### Scenario: R04-PROVIDER-UNAVAILABLE
- GIVEN модель відсутня, offline або не має uncensored=true
- WHEN починається оцінювання через Venice
- THEN авторські документи не надсилаються до chat/completions
- AND звіт містить технічну причину capability/model unavailable.

### Scenario: R04-PROVIDER-SCHEMA
- GIVEN модель не підтримує JSON Schema
- WHEN налаштовано json_schema
- THEN запит відхиляється до inference
- AND prompt_json не підставляється автоматично.

## Requirement: R04-OUTCOME — Відмова відокремлена від оцінки

EvaluationOutcome.status SHALL мати п’ять значень:

| Статус | Значення |
|---|---|
| passed | Повне каліброване оцінювання без блокувальних дефектів |
| failed | Літературні дефекти за чинними правилами scoring |
| incomplete | Оцінювання неповне або профіль некалібрований |
| refused | Оцінювач явно відмовився оцінювати |
| error | Технічна помилка, невалідна відповідь або несумісна capability |

Refused SHALL не мати літературних балів, findings чи preliminary_verdict.
Сирий текст відмови, usage, finish reason і структурована причина зберігаються,
коли провайдер їх надав. Наявність ціни не припускається.

Підтримуються три джерела відмови:

- Явне поле API refusal або finish_reason=content_filter; помилки авторизації,
  rate limit і довільні HTTP 403 не прирівнюються до цензурної відмови.
- Структурована відповідь: сумісне nullable поле `refusal` у JudgeReport;
  непорожнє значення допускає лише порожні assessments/findings/checked_document_ids у валідному звіті. Навіть якщо модель порушила цю умову, явна непорожня refusal обробляється перед scoring для захисту від повторного виклику.
- Неструктурована текстова відмова: вузькі перевірені початкові формулювання
  українською/англійською, лише коли відповідь не є коректним звітом. Шаблони
  застосовуються до відповіді оцінювача, а не документів чи їхніх цитат.

Нерозпізнаний невалідний текст лишається error; евристика не обіцяє визначення
кожної можливої відмови. Явна непорожня структурована refusal має пріоритет навіть за суперечливих балів: runner відкидає бали, формує refused і записує блокування; такий payload не стає JudgeReport для літературного scoring. Суб’єктивні чи моральні зауваження всередині формально валідного звіту
не виправляються прихованою моделлю; їх перевіряє контрольний набір.

Помилка SHALL містити окремі поля категорії, безпечного повідомлення, HTTP status,
provider code/type та request ID, якщо вони надані. Технічні категорії:
відсутній ключ, authentication/permission, quota, rate_limit, timeout, connection,
capability/schema, invalid_response і невідома помилка провайдера. Ці категорії
не стають контентною відмовою за одним лише HTTP status. Відомий SDK exception
не підміняє точніший структурований provider code. Вивід не містить ключів,
Authorization, повних HTTP bodies або відлуння авторського запиту. Безпечне
пояснення SHALL відповідати фактам відповіді; якщо її недостатньо, показати
«Провайдер не повідомив точну причину» з наявними кодами, а не вигадувати її.

### Scenario: R04-ERROR-CAUSE
- GIVEN провайдер повідомляє про quota/rate limit/невірний ключ або timeout
- WHEN формується error-звіт і UI-повідомлення
- THEN користувач бачить відповідну причину та доступні коди
- AND це не refused і не блокує модель за контентом.

### Scenario: R04-REFUSAL-NO-SCORE
- GIVEN API або текстова відповідь явно відмовляє в оцінюванні
- WHEN runner формує результат
- THEN status=refused, report відсутній і literary failed не створюється
- AND сирий результат та доступний usage збережені.

### Scenario: R04-REFUSAL-QUOTATION
- GIVEN художній текст або цитата у валідному звіті містить слова відмови
- WHEN runner аналізує відповідь
- THEN сама ця фраза не змінює результат на refused.

## Requirement: R04-WORKFLOW — Наслідки політик

| Результат оцінювача | report | pause_on_failure |
|---|---|---|
| passed | Продовжити | Продовжити |
| failed | Продовжити зі звітом | Пауза |
| incomplete | Продовжити з попередженням | Пауза |
| refused/error | Продовжити з попередженням про неоцінений текст | Пауза |

`off` SHALL не створювати gateway й не надсилати дані, включно з наступними
вікнами активного запуску. Технічна помилка саме сервісу оцінювання може стати
error-звітом; пошкодження сховища або неможливість зберегти результат SHALL
зупиняти запуск як failed і не маскуватися політикою report.

Для багатовіконного оцінювання report SHALL продовжувати наступні вікна після
технічної error, якщо gateway може виконати незалежний наступний виклик; retry
того самого виклику немає. Після контентної відмови наступні вікна не
надсилаються взагалі через блокування нижче. Pause_on_failure після такої
відмови відразу зупиняє workflow; report продовжує генерацію наступних сцен,
але пропускає заблокованого оцінювача з явним попередженням.

Для решти непозитивних оцінок пауза діє на чинній межі завдання оцінювання.
Checkpoint наступного явного resume пропускає вже записаний результат,
а не повторює inference приховано. Невідома/перервана спроба без збереженого
результату зберігає вимогу repeat_interrupted. Жоден resume/retry не обходить
блокування моделі; автор має явно обрати іншу модель або вимкнути оцінювача.

Записаний refused/error — завершений факт спроби оцінювання, а не успішний
літературний вердикт. StageAttempt SHALL фіксувати збережений outcome, а Run
відображати наслідок обраної політики; розбіжність входів, як раніше, дає
alternative й не обходиться через report.

### Scenario: R04-WORKFLOW-REPORT
- GIVEN remaining workflow з політикою report
- WHEN оцінювач відмовився або сервіс повернув технічну помилку
- THEN звіт і попередження збережені, наступна сцена може виконуватися
- AND текст не позначений як літературно перевірений.

### Scenario: R04-WORKFLOW-PAUSE
- GIVEN pause_on_failure і збережений refused/error
- WHEN етап оцінювання завершується
- THEN запуск paused, збережений виклик не повторюється при простому resume
- AND заблокована модель не викликається навіть з repeat_interrupted=true.

## Requirement: R04-BLOCK — Постійний захист від повторної контентної відмови

Перед кожним модельним викликом SHALL перевірятися блокування за парою:
story ID + identity(provider, нормалізований base_url, точний model ID).
Loopback localhost/127.0.0.1/::1 нормалізуються разом з портом і шляхом; Codex identity не включає неактивний base_url. Промпт, temperature, response_mode, профіль калібрування й налаштування ролей
не входять до identity блокування. Для Codex без явного model ID використовується
окрема identity «модель CLI за замовчуванням»; конкретний backend не вигадується.
Модельні aliases різних ID не ототожнюються без доказів; це обмеження відображається
в документації, а не використовується як автоматичний спосіб обходу.

Підтверджена відмова через контент SHALL записувати стійке блокування ДО
наступного виклику та події продовження workflow. Зберігаються причина, timestamp,
identity, story/attempt/run IDs. Блокування зберігається в app_settings
під окремим ключем без міграції SQLite; backup/restore включає цей стан.
Неможливість зберегти блокування зупиняє workflow як failed, без нових запитів.

Блокування SHALL діяти для ручних оцінок, автоматичних оцінок наступних сцен,
багатовіконного story-evaluation, раніше поставлених у чергу запусків, resume,
retry та після рестарту. Воно не видаляється після off/on, успішного запиту
іншої моделі або зміни промпту. Інша явно обрана модель проходить власні
перевірки; автоматичного переключення немає. Автоматичного чи прихованого
розблокування немає; UI ручного зняття захисту не входить у R-04.

Запити, які не можуть виконувати оцінювання через блокування, SHALL показувати
«Оцінювач заблоковано для цього оповідання після відмови» та первісну причину.
Жодного нового inference/catalog-запиту заблокованого оцінювача не робиться.
У report автоматичні оцінки пропускаються з warning/evaluation_skipped,
проза генерується далі; у pause_on_failure виконання потребує рішення автора.
Readiness, enqueue і повторна перевірка перед API SHALL узгоджувати цей контракт.
Відсутність оцінки не представляється як passed.

### Scenario: R04-BLOCK-NEXT-WINDOW
- GIVEN перше вікно отримало підтверджену контентну відмову
- WHEN workflow доходить до наступного вікна або сцени
- THEN нових викликів цього оцінювача для твору немає
- AND користувач бачить первісну причину блокування.

### Scenario: R04-BLOCK-RESTART
- GIVEN модель заблокована для твору
- WHEN застосунок перезапущено, змінено промпт або натиснуто retry
- THEN блокування лишається чинним і модель не викликається.

### Scenario: R04-BLOCK-SCOPE
- GIVEN модель заблокована для твору A
- WHEN автор явно вибрав іншу модель для A або оцінює твір B
- THEN блокування A/попередньої identity не переноситься автоматично
- AND жоден новий оцінювач не обирається без рішення автора.

### Рішення власника: відмова без поясненої причини

Власник обрав: явна відмова з невідомою причиною також блокує модель для
оповідання. UI прямо відрізняє «відмова через контент» від «відмова, причина
не встановлена». Технічні error не створюють контентного блокування.

## Requirement: R04-CALIBRATION — Контроль придатності

Канонічний набір v2 SHALL містити чинні 10 нейтральних прикладів та 6 нових
синтетичних прикладів українською: три пари «чистий / з відомим дефектом»:

1. Нееротична фотосесія ню повнолітньої моделі за її згодою.
2. Доросла взаємна романтична близькість без графічного опису сексу.
3. Сцена помірного неграфічного насильства з ясною причинністю.

У дефектних варіантах закладено конкретні мовні, сюжетні або редакторські
помилки з точними anchors; сама доросла тема не є дефектом. Усі персонажі
інтимних прикладів явно повнолітні. Приватні авторські файли не копіюються в
пакет. Цей набір перевіряє лише наведений діапазон, а не довільну відвертість.

Для допуску SHALL виконуватися чинні критерії калібрування (recall≥0,8,
false-positive rate≤0,2, availability≥0,9, без пропущених/неперевірених
критичних дефектів і нестабільного вердикту), щонайменше три незалежні повтори
кожного з 16 прикладів та **нуль refused на всьому наборі**. Мінімум — 48
оцінювань одного профілю; dry-run не є калібруванням.

Звіт придатності SHALL містити suite version/hash, відбиток evaluator,
prompt/rubric/config, точний model ID, кількість повторів, refusal/error counts,
покриття категорій, якісні метрики й run IDs. Придатність не видається за
абсолютну uncensored-гарантію або ручне літературне приймання.

Зміна config/model/параметрів Venice/prompt/rubric/контрольного набору SHALL
інвалідовувати допуск. Частковий набір і старі v1-звіти залишаються читабельними,
але не можуть зареєструвати v2-придатність. Наявний реєстр калібрування
в app_settings і файли provenance використовуються без міграції SQL.

### Scenario: R04-CALIBRATION-REFUSAL
- GIVEN решта літературних метрик достатні, але є хоча б одна відмова
- WHEN реєструється профіль v2
- THEN допуск не встановлюється.

### Scenario: R04-CALIBRATION-STALE
- GIVEN профіль пройшов попередній набір або іншу конфігурацію
- WHEN перевіряється поточний допуск
- THEN старий звіт не успадковує статус придатності автоматично.

## API, UI, CLI та сумісність

Чинні settings/evaluations/calibration endpoints зберігаються. JSON
конфігурація Evaluator приймає Venice та названі параметри без секретів;
нова продуктова форма вибору всіх моделей не входить у R-04. Поточний стан блокування та первісна причина доступні через evaluator settings/readiness; клієнт не може видалити блокування звичайним PUT налаштувань; read-only поле block приймається для GET→PUT сумісності, але ігнорується сервером.
UI й Markdown-звіти SHALL розрізняти українськими підписами «Відмова
оцінювача», «Помилка оцінювання», «Неповне оцінювання» та літературні результати.
Run.warning зберігається в payload без міграції; UI показує попередження і після reload, не понижуючи наступний failed до warning. Попередження workflow не повинно виглядати як успішне оцінювання. Відображаються категорія, фактичне безпечне пояснення і наявні provider codes; blanket-повідомлення «провайдер недоступний» не замінює відому причину.

Чинні CLI exit codes збережено: passed=0, failed=1, incomplete=2, error=3;
нове refused=4. Старі збережені outcome читаються, відсутнє JudgeReport.refusal
трактується як null. Оновлена JSON Schema явно повідомляє про нове поле.
Старі читачі мають оновитися для нового status; автоматичного переписування
історичних результатів немає. Зміна промпту/схеми інвалідовує калібрування.

## План перевірки та критерії завершення

1. RED/GREEN gateway: mock HTTP каталогу/ключа/endpoint/schema, uncensored і
   offline guards, capability mismatch, timeout/429/відмова без retry/fallback;
   перевірка незмінених авторських документів у запиті.
2. Runner: API/structured/plain-text refusal, відмова в цитаті, неоднозначний
   невалідний JSON, finish_reason, raw/usage, відсутність літературного штрафу.
3. Workflow: off/report/pause_on_failure, блокування після контентної відмови до наступного вікна, restart/retry/prompt changes, ізоляція між творами й моделями, багатовіконний resume без повтору,
   збереження alternative/cancel/recovery, окремо failure сховища.
4. Калібрування: всі anchors існують; чисті/дефектні приклади всіх категорій;
   три повтори, нуль відмов, відхилення змішаних/старих fingerprints.
5. HTTP/CLI/UI: новий status відображається без падіння або хибного success.
6. Повний offline pytest з коротким унікальним basetemp, незалежне рев’ю;
   актуальні SPEC.MD, runbook і журнал в тому самому наборі змін.

не включені автоматично:** перед ними окремо погоджуються модель, передані

## Межі захисту та простежуваність

Блокування інтегрованих творів записується callback runner перед raw/partial і
report IO. Жорстка зупинка процесу до отримання/класифікації відповіді не може
гарантувати відоме рішення провайдера; чинний interrupted вимагає явного повтору.
Standalone CLI cases не пов’язані зі story_id і не реєструють story-block;
calibrate перериває свій набір після першої відмови. Приклад без ключа:
`config/evaluator.venice.example.json`; exact model ID обирається явно.
