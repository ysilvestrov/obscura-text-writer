# R-22/R-23 — Візуальний редактор і переписування за коментарями

Дата: 24.10.2026. Статус: зведений UX-дизайн погоджено власником 24.10.2026 («Ок»). Технічний план підготовлено окремо; runtime не змінено.

## Спільна мета

Автор читає й вручну править чернетку, накопичує загальний коментар і коментарі до незмінених фрагментів, одним викликом письменника отримує новий варіант усього тексту та приймає/відхиляє зміни. Початкова чернетка й усі вказівки залишаються в історії.

R-22 і R-23 проєктуються як одна надзадача з двома окремими специфікаціями: [редактор R-22](R-22-markdown-editing.md) і [AI-assisted R-23](R-23-ai-assisted-writing.md). Спільні межі — текст/виділення/версії; R-23 використовує редактор R-22. Коренева SPEC.MD описує лише чинну реалізацію, до неї ці пропозиції ще не інтегровані.

## Погоджено власником

1. Основний редактор візуальний, перемикача сирого Markdown немає. Markdown залишається внутрішнім джерелом тексту.
2. Загальний коментар розміщено під редактором. Права панель лишається для контексту, статусу й витрат.
3. Фрагмент виділяється мишкою; кнопка з іконкою коментаря на панелі інструментів відкриває редаговане спливне вікно. Коментований текст підсвічується фоном; натискання відкриває те саме вікно для редагування.
4. Коментовані фрагменти не перетинаються. Вкладені коментарі теж заборонені. Підсвічування й коментарі не є частиною рукопису або його Markdown.
5. Автор може вручну правити текст під час накопичення коментарів. Правки поза коментованим фрагментом зберігають його прив’язку. Зміна самого фрагмента позначає коментар як «Потрібно перевірити прив’язку» й блокує модельний виклик до переприв’язки або видалення.
6. Якщо текст dirty, перед викликом запитується збереження: «Зберегти й переписати» / «Скасувати». Виклик завжди спирається на конкретну збережену версію. Помилка Save не запускає модель, коментарі не губляться.
7. Усі коментарі надсилаються одним викликом налаштованої моделі письменника з окремим промптом. Окрема модель можлива пізніше; нова п’ята роль зараз не додається.
8. Модель може переписувати весь текст; виділення не обмежують дозволені місця змін. У diff показано зміни всередині коментованого фрагмента, поза фрагментами та через межу фрагмента. Це розташування, а не твердження про причину/якість зміни.
9. Diff порівнюється зі збереженою версією, що пішла у виклик; попередні ручні правки не видаються за модельні.
10. Перегляд і прийняття/відхилення модельних змін — окремий етап без змішування з ручним редагуванням. Після застосування автор може редагувати знову вручну або через AI-assisted, або перейти до прози. Для першої версії об’єкт AI-assisted — чернетка; завдання та проза — подальше розширення.

## Запропоновані деталі для остаточного погодження

- Мінімальна панель форматування: жирний і курсив; абзаци та переноси. Обсяг інших Markdown-конструкцій визначити в технічному плані з перевіркою на наявних текстах; непідтриманий вміст не можна мовчки втратити або виконати як HTML.
- Спливне вікно: поле вказівки, «Зберегти», «Скасувати», «Видалити». Іконка має назву для a11y; коментар доступний також із клавіатури й на touch.
- Порожнє виділення не створює фрагментного коментаря. Вибір, що перекриває інший коментар, пояснює конфлікт; наявний коментар не затирається. Сусідні фрагменти можуть торкатися межами.
- Коментарі зберігаються як окремий стан сцени/матеріалу з ревізією та точними прив’язками до тексту; не лише в пам’яті вкладки. Стан потребує зрозумілих dirty/save/error ознак. Подробиці збереження визначить технічний план.
- Застарілі прив’язки доступні в компактному переліку під редактором для виправлення; немає додаткової постійної бічної панелі.
- Результат переписування не замінює current draft до явного застосування. Порівняння показано всередині роботи над чернеткою, не як завершення етапу мовної редактури/прози.
- Коментарі є вхідними авторськими вказівками, правки — пропозиціями моделі. Коментарі попередньої спроби зберігаються в історії; не пересилаються автоматично на новий, уже змінений текст. Повторна спроба потребує явного рішення автора.
- Порожній/невдалий/відхилений результат лишає початковий текст і набір коментарів доступними. Без автоматичних повторів, класифікатора або другого модельного виклику.

## Прийняття змін — як у чинного редактора

Власник обрав консистентність із редакторськими правками. Для AI-assisted використовується чинна поведінка режиму переписування з програмним diff (protocol_version=2): нова пропозиція починається без вибраних правок, автор вибирає потрібні, переглядає зібраний результат і явно застосовує вибір. Зміни в одному реченні групуються так само, як у редактора. Повторне відкриття тієї самої пропозиції відновлює рішення за чинними правилами; без автоматичного застосування. Старий patches-протокол із вибраними за замовчуванням правками не задає default для нового AI-assisted сценарію.

Перевірено за src/storygen/generation/copyedit_review.py і static/copyedits.js. Додаткові позначки inside/outside/cross-boundary не змінюють механізм вибору/застосування. Відкритих продуктових питань у поточному переліку немає; зведений дизайн погоджено власником.

## Межі й подальше проєктування

Технічний план після погодження визначить бібліотеку редактора, спосіб поставки її ресурсів, зворотне перетворення Markdown без зайвого Save, точне зіставлення координат виділення з джерелом, схему коментарів і транзакційний API, queue/task/attempt контракти, відображення Markdown у diff та книгах. Інваріанти: no-op Save, immutable версії, точні цитати пам’яті, CAS, відсутність переписування при конкурентній зміні, бюджет/cancel/refusal guards, UA/EN. Не переносити браузерні DOM-координати як доказ у модельні/серверні контракти.

Після повного погодження — деталізований план реалізації, RED/GREEN, інтеграція Requirement/Scenario в SPEC.MD і traceability, нейтральні desktop/mobile/keyboard перевірки. Реальні модельні прогони потребують визначених даних і бюджету.
