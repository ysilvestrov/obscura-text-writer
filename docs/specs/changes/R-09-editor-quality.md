# R-09 — Контракт промптів і якість редактури

Дата: 21.10.2026. Статус: погоджений напрям, реалізація в поточній сесії за дорученням власника.

## Мета та рішення

Сумісність завдання з відповіддю перевіряється до API, точкові пропозиції зберігаються для вибіркового прийняття, а мовні евристики дають перевірні попередження. Це не доказ нормативності всієї прози чи незмінності художнього голосу.

Власник обрав: `edit_review=auto` типово; додатковий режим `review` чекає вибору автора. Виконання — у цьому чаті після підготовки плану без повторного погодження. Чинний режим `prose` не перетворюється на patches і зберігає поведінку.

## Requirement: PROMPT-CONTRACT — Типізоване призначення промпту

Версія власного промпту SHALL містити незмінний контракт `stage`, `mode`, `schema_version`. Вбудовані промпти SHALL мати еквівалентний контракт. Очікувані пари: prepare/blueprint/1, brief/brief/1, draft/prose/1, edit/prose/1, edit/patches/1, memory/snapshot/1 та memory/evidence_delta/2.

Перед викликом SHALL перевірятися власник, тип, завершеність, актуальність і точний контракт промпту; перевірка всіх запланованих ролей SHALL відбуватися також у preflight. Контракт не доводить змістовної правильності інструкцій усередині промпту.

### Scenario: Зміна режиму редактора
- GIVEN власний промпт призначений edit/prose/1
- WHEN обрано patches без нового призначення
- THEN виклик заблоковано до API з поясненням очікуваного й фактичного контракту.

### Scenario: Старий власний промпт
- GIVEN стара версія не має контракту
- WHEN автор явно підтверджує призначення для вибраного етапу й режиму в налаштуваннях
- THEN створюється нова версія з тим самим текстом і контрактом; стара не переписується.
- AND без підтвердження запуск із legacy-промптом заблоковано; можна повернути стандартний промпт.

Збереження нового або зміненого тексту є явним призначенням до поточного етапу/режиму. Звичайна зміна моделі не переозначує старий контракт. Підготовка має окремий контракт від брифу планувальника. Налаштування наступного етапу читаються за чинним контрактом R-05.

## Requirement: EDIT-REVIEW — Збережені пропозиції та вибір правок

Після перевірки повного `CopyEdits` спроба SHALL зберігати пропозиції, ID вихідної чернетки та версію протоколу. Сирий partial зберігається дослівно. Неприпустимий повний набір не стає припустимим через вибір підмножини.

У `auto` чинні перевірки та атомарна публікація зберігаються, записується автоматичний вибір усіх правок. У `review` спроба SHALL зупинитися в `needs_review` без зміни поточної прози й без доступної для обходу неопрацьованої edited-версії. Навіть порожній набір потребує явного прийняття у цьому режимі.

GET `/api/scenes/{scene_id}/copyedits/{attempt_id}` SHALL повертати оригінал, пропозиції, повний preview, fingerprint пропозиції, ревізію сцени, попередні рішення та можливість застосування з причиною блокування. UI показує кожну пару original/replacement із категорією та прапорцем. POST за тим самим шляхом приймає `expected_revision`, `proposal_fingerprint`, `selected_indices` (унікальні цілі індекси, включно з порожнім списком).

### Scenario: Прийняття частини правок
- GIVEN валідна пропозиція для чинної чернетки й незмінної цілі публікації
- WHEN автор вибирає частину або жодної правки
- THEN створюється нова edited-версія з точно зібраним текстом та початковим знімком залежностей
- AND атомарно оновлюється prose, інвалідуються залежні матеріали, зберігається рішення з індексами, часом і result_version_id
- AND історія оригіналу, пропозицій і попередніх рішень зберігається.

### Scenario: Конкурентна або застаріла зміна
- GIVEN змінився fingerprint, ревізія, залежності, чернетка або поточна проза поза рішеннями цієї пропозиції
- WHEN автор застосовує вибір
- THEN сервер відхиляє публікацію без зміни голови чи історії рішень.

Повторний вибір дозволено, лише поки поточною прозою є останній результат цієї пропозиції з тією самою ревізією голови; це дозволяє переглянути автоматичне застосування. Вихідна ціль із CAS використовується до першого рішення. Вибір не запускає inference й не робить пам’ять/оцінку актуальними. Завершені/cancelled/failed спроби не перетворюються на needs_review; ручне рішення дозволене для збереженої валідної пропозиції, але невдала/перервана відповідь не є пропозицією.

Після прийняття `needs_review` спроба стає completed із новим result_version_id. Run залишається зупиненим до чинної явної дії «Продовжити після прийняття»; cursor перевіряється без повтору редактора.

Скасування run з пропозицією не дозволяє звичайному resume повторно викликати редактор: для cancelled потрібний `repeat_interrupted=true` як свідома нова спроба згідно з R-03. Нескасований needs_review чекає прийняття навіть за цього прапорця. UI блокує Apply відразу після зміни пропозиції до отримання її preview.

## Requirement: LANGUAGE-WARNINGS — Обмежені мовні евристики

Детермінований локальний аналіз SHALL повертати коди, точні позиції/цитати й пояснення без переписування тексту, негативного бала або блокування workflow. Початкові правила: літери ы/э/ъ/ё, змішані латинські/кириличні літери в одному слові, повтор сусідніх слів, дефіс/коротке тире на початку репліки й точні контекстні регресії з підтверджених прикладів («ваші провина», «що відбиваючи аритмічний пульс», «торкалається»).

### Scenario: Чистий контрприклад
- GIVEN нормативне «Вона йшла, відбиваючи ритм кроками» або авторська доросла тема без мовної ознаки
- WHEN виконується аналіз
- THEN сама тема чи нормативне «відбиваючи» не створюють попередження.

GET `/api/versions/{id}/language-warnings` SHALL аналізувати збережену draft/edited/manual версію. UI запускає перевірку явно й позначає її обмеження. Спроба редактора також зберігає попередження для зібраного результату. Автоматична перевірка відмінюваних імен та часу оповіді не вводиться як достовірна: без мовного розбору це дає хибні висновки; перевірка не підміняє Evaluator.

Регресійний набір SHALL мати версію, hash, підтверджені дефекти та чисті контрприклади. Його hash SHALL входити у fingerprint калібрування Evaluator разом із чинним suite, щоб зміна контрольних прикладів скасовувала старий допуск. Це не калібрує нову модель без фактичного прогону та бюджету.

## Дані, межі та сумісність

- Optional `VersionRef.prompt_contract`; старі JSON читаються без міграції blobs. Контракт дозволений лише для kind=prompt. SQL-схема не змінюється.
- `RoleSettings.edit_review` типово auto; `StageAttempt.context` зберігає валідовану пропозицію, попередження й журнал рішень (із попередженнями для кожного обраного результату). Транзакції публікації належать storage; HTTP і генератор не виконують SQL. Спільні контракти винесені в незалежні `prompt_contracts.py` і `copyediting.py`; storage не імпортує generation.
- Часткова публікація зберігає всі guards `CopyEdits`, snapshot refs та CAS. Жодного silent rebase, автоматичного повтору чи підміни моделі.
- Мова UI/документації українська; вміст моделі в UI виводиться через textContent. Зміна не потребує нових зовнішніх залежностей, мережевих або платних викликів.
- Сторонні/кошикові сцени, чужі спроби/промпти, дублікати й вихід за межі індексів відхиляються. UI не перезаписує dirty-буфер після фонового refresh.

## Приймання

Контракт блокується до API, legacy явно перепризначається новою версією; auto/review, порожній набір, підмножина, повторний вибір, CAS/застарілість/чужі дані та продовження cursor мають offline-регресії. Мовні fixtures мають чисті контрприклади, зміна їх hash інвалідовує calibration. API, поведінка UI та повний pytest перевіряються окремо; реальна літературна якість і допуск моделі не оголошуються доведеними offline-тестами. SPEC.MD оновлюється разом із кодом.
