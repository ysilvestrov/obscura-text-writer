# R-10 — Перевірна специфікація та стан перевірок

Погоджене рішення: відсутність тесту або явної процедури ручної перевірки для сценарію є помилкою команди перевірки документації. Робочий застосунок не залежить від цієї команди.

## Requirement: DOCS-TRACE — Простежуваність сценаріїв

SPEC.MD SHALL лишатися головним архітектурним контрактом і мати зміст, унікальні сталі Requirement/Scenario ID. Зміна заголовка не змінює ID; видалений ID не перепризначається іншому сценарію. Наявні ID зберігаються; сценарії без ID отримують суфікс S01, S02 у межах вимоги.

`docs/verification/traceability.json` SHALL перелічувати кожен сценарій: його вимогу, конкретні Python test node IDs без wildcard та/або процедуру ручної перевірки з причиною її необхідності. Матриця не є доказом повноти тесту. Процесні та літературні вимоги не отримують фіктивного автоматичного допуску. Ручна процедура не означає, що її виконали.

Read-only `scripts/check_docs.py` SHALL перевіряти структуру SPEC, повноту й унікальність матриці, існування конкретних тестів через AST, локальні Markdown-посилання й anchors в актуальних документах та точкові pytest req markers. Невідомий ID, missing mapping, файл/тест/anchor, пустий опис ручної перевірки або зайвий запис SHALL завершувати команду ненульовим кодом. Загальний marker на модуль/клас не вважається покриттям. Зареєстрований `req` допускається на функціях і звіряється з матрицею; матриця не вимагає масового додавання маркерів до старих тестів.

## Requirement: DOCS-STATUS — Результат виконання відокремлений від collection

`scripts/verify.py` SHALL запускати pytest поточним Python, створювати свіжий JUnit XML у новому окремому artifact-каталозі та формувати docs/STATUS.md із датою UTC, commit, ознакою незакомічених змін, SHA-256 поточних вихідних файлів, точною командою, exit code, passed/failed/errors/skipped та тривалістю. Статус SHALL не стверджувати успіх без exit=0, валідного XML та хоча б одного виконаного тесту. Collection-only не створює звіт виконання. Відсутній/пошкоджений XML, переривання чи ненульовий exit SHALL відображатися як непідтверджена/невдала перевірка, без повторного використання старого XML. Частковий запуск явно лишається частковим за командою; успіх не підтверджує літературної якості або реальних моделей.

Hash/commit перевіряються до та після pytest; зміна під час виконання дає unconfirmed. STATUS — свідчення конкретного знімка, не обіцянка для майбутніх змін. Власні generated STATUS/artifacts не входять у hash знімка. Документ у тому самому коміті може посилатися на базовий commit із dirty=true та hash перевірених файлів; циклічне переписування commit не потрібне.

## Документація та сумісність

ADR пояснюють мотиви вже реалізованих рішень (локальний запуск, evidence memory, відсутність fallback, редакторський diff); не замінюють SPEC. Датовані звіти й старі плани позначаються історичними; їхні числа не переписуються. README/CONTRIBUTING посилаються на актуальний STATUS і команду документаційної перевірки.

SQL, API, промпти, моделі та авторські дані незмінні. Нових залежностей/платних API/CI-хостингу немає. Валідатор працює на стандартній бібліотеці; pytest уже є dev-залежністю. Відомі протиріччя SPEC (зокрема застаріла відсутність бюджетного обмежувача) виправляються за кодом і погодженими контрактами, не шляхом зміни поведінки.

## Критерії приймання

RED→GREEN: missing/duplicate ID, пропущена/зайва mapping, невідомий test, path traversal, зламаний anchor, marker невідомої вимоги, заборона module marker, ручна процедура без причини; corrupt/missing JUnit, exit failure з XML без failures, collection-only, no tests, частковий запуск. Після цього актуальна матриця проходить перевірку, всі тести виконані послідовно, незалежне рев’ю й локальний коміт включають SPEC.
