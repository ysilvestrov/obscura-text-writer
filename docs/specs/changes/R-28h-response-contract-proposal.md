# R-28h — Альтернативна схема відповідей аналізу впливу

Статус: ПРОПОЗИЦІЯ, нейтральний локальний spike погоджено й виконано27.10.2026; до інтеграції не допущено, не чинний контракт. Реалізацію, SPEC.MD, активні запуски та модельні налаштування не змінено.

## Проблема

Спостереження26.10: delta повернула1325символів JSON, summary близько620символів та E1…E100. Код розкрив references у canonical26527символів приcap5939. Спільна схема змішує дельту, перевірку й синтез; no_impact у delta означає завершення пакета, а в check — відсутність знайденої проблеми. Обов’язковий вільний summary стимулює переказ і декоративне обґрунтування. Модель дублює coverage/цитати, які вже відомі коду.

## Основне рішення

Три окремі response schema за phase; жодного модельного verdict. Код обчислює кінцевий стан із findings, uncertainty, complete, валідності proof DAG/coverage та live source/target CAS. Змістова коректність висновків залишається відповідальністю моделі й автора; структурна валідація не доводить відсутності суперечностей.

Модельні відповіді не містять загальних evidence_ids/target_evidence_ids, covered_ids, довгих внутрішніх ID або обов’язкового summary. References залишаються короткими task-local aliases, але прив’язані до конкретного твердження або правки. Пропозиція НЕ замінює перелік E1…E100 діапазоном: це відтворило б зайве розкриття.

## 1. delta/reduce_delta — зміни передумов

```json
{
  "complete": true,
  "changes": [
    {
      "source": "C1",
      "before": "Зустріч призначена на вечір.",
      "after": "Зустріч перенесена на ранок.",
      "before_ref": "E4",
      "after_ref": "E7"
    }
  ],
  "uncertainties": []
}
```

C1 — адреса порівнюваного джерела, E4/E7 — відомі коду exact evidence references потрібної old/new сторони. before/after — короткі змістові формулювання, не обов’язково дослівні; proof references — завжди exact. Для появи/зникнення твердження відповідна сторона і reference можуть бути null. Відсутність не доводиться відсутністю одного уривка: коли old/new розбиті, leaf передає побачене та сумнів, а фінальний delta reducer встановлює зміну лише після повного зіставлення. Зміни джерела, пунктуації й переміщення фрагмента самі не є фактичною зміною подій. Зміни голосу/стилю включаються, лише якщо вони змінюють вимоги до залежного тексту.

Для частини без значущої зміни: complete=true, changes=[], uncertainties=[]. Це не verdict щодо сцени. Не переносити в changes переказ усіх прочитаних фактів. reduce_delta повертає новий компактний змістовий перелік змін, а зв’язки з дитячими записами зберігає код; не дозволяється непомітно втратити окрему зміну. Якщо перелік неможливо повно звести в бюджет, complete=false з причиною, а не мовчазне відкидання.

## 2. check — проблеми цільового тексту та опорні твердження

```json
{
  "complete": true,
  "new_findings": [
    {
      "change": "D1",
      "target_ref": "T3",
      "source_ref": "E7",
      "problem": "Сцена називає цю зустріч вечірньою, хоча її перенесено на ранок.",
      "required_change": "Узгодити час цієї зустрічі з ранком."
    }
  ],
  "carry": [],
  "uncertainties": []
}
```

D1 — короткий alias конкретного delta item, призначений кодом після прийняття дельти; T3 та E7 — цільовий і джерельний доказ. Для складного finding дозволити малий список source_refs замість одного source_ref; остаточний ліміт та schema визначити за бюджетом реальних цитат. Модель не генерує precise offsets чи ID. required_change — інструкція автору, не автоматичне переписування прози.

Для чистої частини new_findings=[]; немає обов’язкового обґрунтування «усе добре». Але не можна повертати тільки порожній масив: наступному синтезу можуть знадобитися твердження target, пов’язані з дельтою. Для цього carry:

```json
{
  "complete": true,
  "new_findings": [],
  "carry": [
    {
      "change": "D1",
      "claim": "Марія ще не знає про перенесення зустрічі.",
      "target_ref": "T8"
    }
  ],
  "uncertainties": []
}
```

carry — не загальний конспект сцени, а лише твердження, важливі для перевірюваних змін або зв’язків між частинами. Воно передається наступній моделі й має exact target reference. Його семантична повнота не перевіряється детерміновано: це відоме обмеження отбора моделлю. Якщо важливий зв’язок не вміщується або незрозумілий, модель має вказати uncertainties/complete=false. Результат не дає автоматичного очищення. Повне покриття вхідних діапазонів лишається обов’язковим, але не видається за доказ повного модельного розуміння.

## 3. reduce_check/reduce_memory — нові міжфрагментні проблеми

Та сама компактна форма complete/new_findings/carry/uncertainties. Нові findings можуть спиратися тільки на реально передані child claims та доступні exact proofs. Уже знайдені findings код успадковує по DAG: модель їх не копіює й не може видалити. Для наступного рівня модель зберігає необхідні carry, не додаючи декоративного summary. Повне зведення не заменюється правилом «усі leaf чисті — root чистий»: reducer обов’язково шукає взаємодію між пакетами. Потенційний конфлікт без доказів — uncertainty, не finding.

На фінальному root carry далі нікому не передається й не потрібний у фінальному модельному виході; окрема root schema залишає complete/new_findings/uncertainties. Проміжні carry зберігаються в журналі для відтворення proof. Загальні й конкретні невизначеності переносяться кодом; модель не знімає їх без окремого доказового механізму, який не входить у цю пропозицію.

## 4. Результат автора та UI

Не виявлено впливу: усі обов’язкові частини complete, proofs/coverage/CAS валідні, успадкованих і нових findings немає, uncertainties порожній. Код показує «Потрібних змін не виявлено. Перевірено N частин»; N рахує код. Це не гарантія літературної якості.

Є findings: показати точні цільові й source quotes, problem та required_change. Якщо також є невизначеність або неповний аналіз — показати окремо; наявність правок не означає завершену перевірку.

Є uncertainty, complete=false або технічна/структурна помилка: автоматично не знімати ознаку перегляду, зберегти успішні частини й конкретну причину. У UI не називати stop-відповідь з неповним аналізом технічним завершенням без застереження. Нових автоматичних повторів немає.

## 5. References, розміри та збереження

- Immutable task/coverage, source hashes, exact passages і evidence registry — дані коду. Модель не повертає їх як receipt.
- Proofs зберігаються reference-зв’язками, а не повторним копіюванням цитат у кожному canonical parent. Саме збереження registry поза модельною відповіддю не робить цитати безкоштовними для наступного input.
- Кожний фактичний запит вимірюється разом із потрібними розкритими доказами/claim/schema. UI може розкрити source/target quote на вимогу без inference.
- Резерв виходу охоплює фактичний модельний JSON. Резерв наступного входу окремо охоплює реально передані claims та proofs. Загальний внутрішній граф не повинен помилково рахуватися як модельний output.
- Кількість references на твердження мала й обмежена schema. Сукупна кількість і довжина дозволених доказів обмежуються ще при packing; обмеження лише maxItems=100 непридатне. Конкретні числа — предмет контрольного виміру, не довільна гарантія достатності2–4цитат.
- Якщо повний необхідний зміст/набір findings не вміщується — явний incomplete або новий план частин, не обрізання, не втрата findings і не позитивне очищення. Цей дизайн не обіцяє менше викликів на кожному творі.
- Old/new pairing через частини, невизначеність, міжфрагментні links, findings inheritance, chronology та CAS перевіряються окремо. No inference після cancel/refusal/technical failure без чинного авторського рішення.

## 6. Сумісність і перевірки перед реалізацією

Потрібен новий versioned wire-контракт (кандидат wire3), version-aware schemas/normalizer/packing/replay/UI report adapter. Старі wire1/2 manifests, system prompts, API bodies і докази відтворюються без переписування. Новий prompt/tokenizer binding кваліфікується окремо; SQL migration визначити лише після проектування формату збереження, а не припускати її відсутність.

Контрольні випадки: зміна лише пунктуації; реальний час/знання/стосунки; стикування old/new в різних пакетах; суперечність помітна тільки на synthesis; no-impact leaf із важливим carry; багато незалежних змін; багато inherited findings; нечіткі/неправильні references; змішаний partial+findings; неможливість вмістити важливі claims; legacy replay/cancel/resume/CAS. Порівняти actual bytes/tokens/calls/local latency зі старим контрактом на нейтральних прикладах. Реальні авторські тексти й повний book run не запускати як наслідок погодження самого дизайну.


## Результат spike27.10.2026

[Звіт](../../research/2026-10-27-r28h-response-probe.md):16локальних викликів,3варіанти input/prompt, всі response JSON/refs структурно валідні, компактний output98…991символів. Повного семантичного допуску немає: false positives на коректних окремих подіях, root не дає належного нового finding у двох уточнених серіях. Runtime не змінено.

Два корисні уточнення дизайну для наступного випробування: carry без вільного claim (лише change/target_ref, код підставляє точний уривок); check/root бачать чинні delta.current, а old/before залишається у delta/provenance. Це пропозиції, не затверджений production wire3. Перший варіант прибирає вигаданий переказ у carry; другий усунув помилку простої пари часу, але не false positives загалом. Потрібна окрема перевірка логічної надійності моделі до реалізації production contract.
