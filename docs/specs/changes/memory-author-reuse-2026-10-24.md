# Авторське використання попередньої пам’яті

Рішення власника 24.10.2026: дозволити використання застарілої пам’яті після підтвердження, включно зі справді зміненою прозою; зберігати історичні джерела й позначати ризик.

## Контракт

- Оновлення сцени n використовує журнал n−1 та лише вибрану прозу n; майбутні сцени не додаються.
- Якщо попередній журнал stale або його історичні джерела відрізняються від поточних heads, preflight пропонує явне підтвердження. Воно показує кількість нових версій і справді змінених текстів. Відмова не створює запуску/платного виклику.
- Підтвердження прив’язане до fingerprint конкретного журналу, поточних джерел, порядку сцен і цільової сцени. Зміна цих даних потребує нового підтвердження; згода не є глобальним вимкненням перевірок.
- Джерела та цитати старих подій не переприв’язуються. Перевіряються їхні історичні тексти, SHA, schema, complete, належність цьому твору/відповідній попередній сцені й порядок. Пошкоджені дані, сторонній твір, майбутнє або пропущена сцена не мають обходу через підтвердження.
- Авторське рішення зберігається в спробі та dependency snapshot нової пам’яті. Успадкована provenance зберігається в наступних журналах; ризик видимий у попередженнях, а старий журнал/його stale-позначка не переписуються.
- Чинний похідний журнал із зафіксованою provenance можна використовувати далі без повторного питання до зміни його залежностей. Звичайна неавторизована застаріла пам’ять лишається заблокованою.
- Перша версія підтвердження — окремий етап memory; автоматичний workflow не отримує дозволу на всі майбутні сцени. Промпти/схеми модельного результату/бюджетні правила не змінюються.

## Реалізація й сумісність

Read-only memory/reuse.py готує перевірений історичний префікс і fingerprint. RunRequest має optional memory_approval; readiness повертає can_confirm/memory_review лише після інших перевірок. UI використовує звичайне підтвердження запуску з додатковим поясненням. DependencySnapshot отримує сумісні порожні за замовчуванням accepted_stale_memory_ids і memory_provenance. Транзакційні publication/CAS/hash guards залишаються чинними. SQL-міграція відсутня.

Перевірки: однакові тексти/нові ID; справжня зміна з ризиком; відсутня/несвіжа згода; пошкодження/майбутнє/чужі джерела; незмінні цитати; publication і наступна сцена; UI decline/confirm та UA/EN. Реальні моделі й авторські тексти в тестах не використовуються.

Уточнення реалізації: ручні правки свіжої нової пам’яті використовують її зафіксоване підтвердження без зміни старих джерел. Перевірка цілісності приймає лише конкретні пари old/current з provenance; загального обходу через наявність будь-якого запису provenance немає.
