# R-28i — Reasoning та пошук→суддя,27.10.2026

Статус: локальний spike завершено; жодного production допуску чи перемикання ролей.

## Фактичне reasoning

Huihui-Qwen3.5-9B-abliterated Q4_K_M, loaded context131072, batch512. Локальний каталог повідомив allowed_options off/on, default on. Не використовували непідтверджені low/medium. На capability-контролі effort був відсутній, на off-парі — none; додатково перевірено actual reasoning usage. Обидва запити мають той самий neutral input/system/schema/temp0.1/max_tokens4096. Цей capability-контроль використовує стару experimental GroundedCheck форму, не змішується зі свіжою Single формою нижче.

On витратив приблизно18,26×часу і не повернув кінцевої відповіді. Це не input overflow. Не можна оцінити якість ненаданої відповіді чи зробити висновок, що reasoning взагалі не допомагає. На цій default-on конфігурації budget4096 недостатній. Решту чотири paired-on проб явно пропущено після цього дорогого невдалого контролю; без прихованих retries/збільшення output або глобального reasoning budget. Наступне reasoning-випробування потребує перевіреного керованого thinking budget або свідомо більшого ліміту й часу.

[Офіційний опис каталогу reasoning](https://lmstudio.ai/docs/developer/rest/list) пояснює allowed_options/default; у досліді конкретні значення отримано з локального Bionic API. Сам прийнятий HTTP-запит не вважався доказом увімкненого reasoning.

## Однопрохідний та двопрохідний контроль

Чотири фіксовані нейтральні входи. Current rules + original passages, без скасованих правил, вигаданих child findings чи gold labels у запитах. max_tokens4096, temperature0.1, reasoning none у всіх наведених далі викликах. Нова проста Single форма без carry у відповіді; тому це не прямий повтор R-28h і не повна інтеграція chunk DAG.

Пошук повертає hypotheses. Код надає H-IDs, перевіряє source/target references та передає судді повні оригінали. Суддя зобов’язаний оцінити кожен H-ID рівно один раз: accept/reject/uncertain. Запити stateless, але та сама модель/ваги — це різні ролі, не незалежні джерела істини.

| Контроль | Очікування | Single off: категорія / час | Пошук+суддя v1: рішення / сумарний час | Суддя v2 на тих самих гіпотезах |
|---|---|---|---|---|
| Правильний час | сумісно | clean / 6.84с | uncertain / 63.91с | accept |
| Старий час після перенесення | проблема | issue / 15.19с | uncertain / 44.85с | accept |
| Одне використання коду | сумісно | clean / 3.36с | uncertain / 43.29с | accept |
| Два використання коду | проблема | issue / 21.59с | uncertain / 45.97с | accept |

У single всі4контролі класифіковані очікувано (2clean/2issue). Це не4/4повністю правильних літературних звітів: у double-use пропозиція виправлення радить послабити чинне правило, а не лише виправити сцену. Підтримувальна перша подія T1 також потрібна для висновку про повторне використання, але пошук вибрав для target_refs лише T2; Single вибрав лише T1. Правильний ID не гарантує достатній набір доказів.

Пошук знайшов по одній гіпотезі в кожному випадку, включно з двома хибними на чистих контролях. У кожному також згенерував uncertainties. Суддя v1 повернув uncertain у всіх4випадках, не відхиливши зайві й не підтвердивши реальні проблеми. Уточнений промпт судді v2 на тих самих originals/hypotheses прийняв усі4: зокрема дві хибні гіпотези. У wrong-time його причина неправильно приписує T1 час09:00, хоч actual target містить18:00. Отже правильна категорія рішення не дорівнює правильності пояснення.

## Що довів код, а що ні

Код детерміновано:
- перевіряє, що selected reference існує в original input;
- призначає H-IDs та відхиляє missing/duplicate/foreign judgement IDs;
- підставляє exact original text за references, не дозволяє судді генерувати посилання чи довільні offsets;
- відокремлює hypotheses від підтверджених для UI кандидатів;
- не видає uncertainty/невалідну відповідь за clean і не запускає автоматичну редактуру.

Це не доводить, що обраний уривок достатній для конкретного твердження або що модель правильно його зрозуміла. Semantic validity, пропуски пошуку й корельовані помилки не зникають від правильного URL чи двох ролей.

Наявний обережний pipeline не знімає review state після uncertainties. Тому навіть accept судді v2 не дає автоматичного очищення: search uncertainties залишаються. Їх потрібно типізувати/прив’язувати до конкретних гіпотез, щоб суддя міг явно їх вирішувати; не можна просто видалити всі сумніви після reject. У досліді цього механізму не реалізовано.

## Висновок для наступного дизайну

Пошук→суддя є обґрунтованою окремою гіпотезою для кращого балансу пропусків/зайвих правок, але цей pilot не показав переваги на поточній9B. Поки не переносити в production.

Перевірити наступним окремим дизайном: пошук повертає коротке атомарне твердження/контекстні refs, не багатослівне переконування й готову редактуру; суддя встановлює факти за оригіналом перед перевіркою гіпотези та повертає достатні підтримувальні refs. Код формує посилання й окремі стани candidate/accepted/rejected/unresolved. Спосіб переписування — окремий наступний етап після підтвердження проблеми. Для оцінки потрібні нові негативні/позитивні holdout-контролі й повтори; однакові ваги не оголошувати незалежним консенсусом. Суддя не відновить гіпотезу, яку пошук пропустив; можливий окремий багатопрохідний пошук не входить у вже виміряну ціну.
