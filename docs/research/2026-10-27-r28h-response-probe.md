## Висновки

1. Структурно всі16реальних викликів дали stop та валідні за pilot-схемою відповіді з допустимими посиланнями; reasoning_tokens=0. Ще2рядки дельти в таблиці — явне повторне використання першого контролю, не нові виклики. Компактний output98…991символів. Дані не розгорталися в повторні canonical quotes: це властивість spike, а не вже реалізований storage/proof граф.
2. Початкова схема: модель помилково застосувала старий час до узгодженої сцени; вільний carry.claim містив непідтверджені перекази. Уточнення напряму old→new не усунуло false positive.
3. Carry лише change/target_ref прибирає вільно вигаданий текст із цього поля: точний уривок підставляє код. Вибір правильного уривка все ще є модельною задачею. У root передано реальні child outputs та точні уривки за їхніми посиланнями; їх змістову правильність код не виправляв.
4. Передача лише delta.current виправила просту пару: коректний час не отримав правок, старий час отримав finding. Але обидві окремо допустимі події про одноразовий код знову отримали зайві findings. У root модель не дала очікуваного нового finding про два використання, а повернула необґрунтовану невизначеність. Повний pipeline не пройдено.
5. Головний бар’єр тепер — false positives і логічна перевірка, а не розмір JSON. Підвищувати резерв за цими результатами не потрібно. Не переносити схему в production лише на підставі компактності. Наступний окремий експеримент може порівняти контрольований reasoning або іншу локальну модель на тому самому незмінному наборі; не підлаштовувати приклади, щоб приховати помилки.

Не переносити поточний summary/evidence output у новий контракт заднім числом; wire1/2 replay та runtime SPEC лишаються чинними. Для майбутньої wire3 інтеграції потрібні production schema/packing/full coverage/proof DAG/CAS/recovery/legacy тести. Pilot-валідатор перевіряє лише JSON/типи/відомі reference та old/new owner/side, не весь чинний proof pipeline.
