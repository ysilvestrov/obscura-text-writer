# Звичайна й модифікована Qwen для планувальника

## Питання та межі

Власник запропонував перевірити, чи придатна звичайна модель для аналізу дорослого тексту, навіть якщо вона не підходить для його генерації. Це правдоподібна гіпотеза, не встановлений факт. 27.10 погоджено завантаження звичайної Qwen3.5-9B Q4_K_M, тимчасове перемикання GPU й синтетичні локальні проби без платного API та рукопису. Робочий профіль не змінюється за результатом автоматично.

## Як трактувати поради Venice

Наданий `model-advices.txt` — стороння консультація. Вбудовані промпти не є інструкціями застосунку. Списки моделей, оцінки української, припущення про відмови та «копійчану» ціну не замінюють каталог, тариф і вимір. Твердження «1–2 тисячі слів = 2–3 тисячі токенів» не використовується для бюджетування української; потрібен tokenizer/usage. Розбіжність двох коректорів також не доводить, яка правка правильна.

Офіційні джерела, перевірені 27.10:

- [Базова Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B) — відповідна базова родина для порівняння із встановленою Huihui9B. Заява про придатність саме нашому планувальнику потребує досліду.
- [Unsloth GGUF](https://huggingface.co/unsloth/Qwen3.5-9B-GGUF): revision `3885219b6810b007914f3a7950a8d1b469d598a5`, файл `Qwen3.5-9B-Q4_K_M.gguf`,5680522464bytes, SHA256 `03b74727a860a56338e042c4420bb3f04b2fec5734175f4cb9fa853daf52b7e8`. Download перевірено, локальний Bionic key `qwen3.5-9b`.
- [Venice model catalog](https://github.com/veniceai/api-docs/blob/main/models/text.mdx) містить IDs/контекст/ціни/ознаки; він не є порівняльним тестом якості української чи гарантованої відсутності відмов на конкретній задачі.
- [Venice privacy](https://venice.ai/privacy): Anonymous приховує особу, але сторонній провайдер бачить текст і може зберігати його. Private спирається на договірні обіцянки; TEE/E2EE мають інші гарантії й обмеження. Приватність, uncensored та якість виконання — різні критерії. Локальна проба не надсилає текст до Venice.

## Протокол

`r28k-base-model-probe.py` створює8коротких синтетичних check-запитів чинного protocol3: нейтральна пара, ню-пара з повнолітніми учасницями, романтична пара з повнолітніми та пара про наслідки насильства. У кожній парі clean та однозначна суперечність. Production system prompt, current-consistency payload, native JSON Schema, code-owned refs і production validator; temperature0,1, thinkingoff, output4096, context131072. Жодного дописування сцени.

Однакові дані для Huihui та базової Qwen, по одному проходу. Фіксуємо finish_reason, refusal/помилку, валідність JSON/refs, знайдені й вигадані issues/questions, usage та wall time. Native grammar може приховувати відмову як порожній список, тому відсутність refusal-поля не є самостійним доказом. Контрольні очікування перевіряються окремо. Це вузький feasibility smoke, не статистична калібровка й не доказ роботи на довгому романі або будь-якому дорослому контенті.

Артефакти — `artifacts/base-model-comparison/<model>/`, не частина Git. Модель завантажується з131072контекстом, після проб повертається попередня Huihui з її початковими налаштуваннями. Профілі токенів прив’язані до моделі: чинний Huihui counter не активується для базової Qwen.

## Стан

Проведено16локальних викликів — по8на модель. В обох серіях stop,0reasoning, JSON синтаксично коректний8/8; явних content refusals немає. Це не підтверджує відсутність відмов на всіх дорослих текстах.

| Метрика | Huihui9B | Базова Qwen9B |
|---|---:|---:|
| Повний production validator |8/8|5/8|
| Хибні issues серед4clean прикладів |4/4|2/4|
| Контрольні суперечності, помічені в raw |4/4|4/4|
| Відповіді з помилковим complete=false |0|3|
| Повністю прийнятий правильний результат |4/8|3/8|
| Wall time серії |131,99с|104,71с|

Базова Qwen краще відрізнила нейтральний і романтичний clean текст. Обидві моделі вигадали проблеми в ню-clean та violence-clean: відсутність деталі в передумові трактували як суперечність. Базова правильно описала planted проблеми листа/часу/опіку, але повернула complete=false, тому ці3відповіді валідатор справедливо не прийняв. Це технічна/семантична помилка виконання контракту, не content refusal. Boolean не виправлявся кодом; автоповторів не було.

Raw messages перевірено вручну як контроль синтетичних очікувань: Huihui має4явні false positives; усі4planted суперечності позначено обома моделями, хоча пояснення Huihui про медовий місяць містить зайве припущення. Лічильник found_issue сам по собі не доводить точності пояснення.

При native load131072 контексту базова Qwen зайняла7744MiB із8151MiB VRAM. Це load/короткий-inference вимір, не доказ обробки повного128K input. Wall time отримано паралельно з CPU-регресією застосунку; він не є ізольованим benchmark. Квантизатори різні (Unsloth проти mradermacher), тому різницю не можна причинно приписати лише abliteration.

Після проб базову модель вивантажено; Huihui повернуто з context131072, batch512, flash_attention=true, KV GPU=true. Порівняння всіх вихідних полів native load config не знайшло різниці. Обидва GGUF залишаються на диску. Ролі оповідань, активні tokenizer bindings, книга й БД не змінені; cloudcalls0.

Висновок: гіпотеза щодо відсутності content refusal на вузькій задачі аналізу підтримана цим smoke. Прямо замінювати production planner зарано через3непридатні відповіді та2false positives. Наступний окремий дослід: уточнити complete/coverage і різницю між новою деталлю та суперечністю на інших контрольних прикладах; потім перевірити delta/synthesis, довгий input та кваліфікувати власний tokenizer binding. Немає автоматичного перемикання моделі.
