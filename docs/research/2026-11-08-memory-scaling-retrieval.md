# Масштабування пам'яті й відбір контексту для романів і серій (#25)

Дата: 08.11.2026. Задача: [#25](https://github.com/ysilvestrov/obscura-text-writer/issues/25). Дизайн: [2026-11-08-memory-scaling-retrieval-design.md](../superpowers/specs/2026-11-08-memory-scaling-retrieval-design.md). Скрипт: `scripts/memory_retrieval_bench.py` (пакет `scripts/memory_bench/`, тести `tests/retrieval_bench/`).

Код продукту, SPEC.MD і робоча база не змінювалися. Викликів моделі й платних запитів не було. Нижче лише агрегати, без текстів твору та ID записів.

## Коротко

1. **Повна пам'ять не масштабується, і стискання хронології (А) цього не виправляє.** Повна секція росте на ≈ 660 символів за сцену, стискання знімає 10–22 % (10 % у середньому на реальному творі, 17 % на найбільшій сцені, 22 % на синтетиці 300 сцен). На 300 сценах це ≈ 195 тис. символів (≈ 97 тис. токенів Qwen3), на 3000 — ≈ 1,9 млн. Разом із рештою запиту (≈ 20 тис. токенів зараз, і вона теж росте з планами майбутніх сцен) і резервом відповіді роман на 300 сцен упирається в межу 131 тис.
2. **Етап memory переповниться першим.** Його каталог уже зараз більший за літературну секцію: у середньому 32 тис. символів, максимум 64 тис. проти 19/37 тис. Звужений каталог дає −37 % без втрати жодної цілі на реальних даних.
3. **Структурний відбір за іменами (Б) мало що відсіює**, коли протагоністка є в 98 % сцен і їй належать 127 зі 130 станів. Без обмеження бюджетом Б вибирає ≈ 410 символів на сцену, В — ≈ 450, проти 657 у повної пам'яті. «Ядро = всі стани протагоністки» росте лінійно (≈ 300 записів на 300 сценах, ≈ 3000 на 3000).
4. **Масштабується лише ядро зі строком дії** (нижня межа: стани, змінені за останні 3 сцени, — 7–11 записів, сталий розмір). Але без справжнього розділення «ядро / атмосфера» і без закриття застарілих станів воно губить частину записів, які сцена змінює. На синтетиці recall змінних цілей падає до 0,49–0,62 на 300 сценах і до 0,24–0,27 на 3000.
5. **Рекомендація:** архітектура В + А (детермінований відбір + лексичний добір + стискання хронології) лише разом зі змінами моделі даних: тип запису (ядро / атмосфера), строк дії ядра в часі історії, закриття застарілих станів, знайомства, явні сутності. Без них жоден відбір не дасть одночасно сталого розміру й повного покриття. Векторний пошук (Г) зараз не потрібен.
6. **Консервативна оцінка токенів сама блокує роботу.** За нею решта запиту чернетки (без пам'яті) займає в медіані 68 тис. токенів, тоді як за реальною fertility токенізатора Qwen3 — ≈ 20 тис. Отже, з продуктовою оцінкою 64 тис. контексту не вистачає вже зараз незалежно від стратегії пам'яті, а з реалістичною — вистачає з запасом. Це окрема від пам'яті проблема, але вона визначає, скільки бюджету пам'яті взагалі лишається.

## Дані й методика

**Дані.** Копія робочої бази 08.11.2026, знята через `readonly_database` і `sqlite3.backup`. Робоча тека лише читалася (розмір і час зміни бази ті самі). Два твори:

- **основний — 68 сцен.** 59 проаналізовано, 9 пропущено: у 6 попередня сцена не має пам'яті, у 3 її пам'ять чекає підтвердження автора. Протагоністка в 98 % сцен; останній знімок має 400 активних записів (130 станів, 107 фактів, 39 відкритих ліній, 124 записи хронології). 21 перша зустріч на 59 сцен;
- **малий — 11 сцен.** 5 проаналізовано, 6 пропущено: пам'ять попередньої сцени чекає підтвердження.

**Для кожної сцени** відтворюється пам'ять до неї: `journal_for_read`, `hidden_before`, номери сцен — як у `generation/context.py`. **Цілі сцени** — записи, які етап memory цієї сцени оновив або закрив подіями з прози саме цієї сцени. Це рішальна метрика: чи бачила модель запис, який сцена змінює. На основному творі таких цілей 45.

**Стратегії:**

| Ключ | Що це |
|---|---|
| `full` | поточна `project_memory` (стани поза складом сцени відкидаються) |
| `all_active` | усі активні записи |
| `full_a` | А: `full` + хронологія старше 20 сцен замінена умовним підсумком (600 символів на 10 сцен) |
| `structural[core=upper/lower]` | Б: ядро протагоністки → стани присутніх → стани без scope → лінії й факти зі згадкою присутніх → хронологія → атмосфера (10 % бюджету, детерміноване чергування) |
| `structural_fts[…]` | В: Б + добір залишку бюджету FTS5/BM25 (`trigram`) за планом сцени |

**Дві межі ядра.** Типу запису й часу історії в даних немає, тому ядро виміряне з двох боків:

- **upper** — усі стани протагоністки;
- **lower** — лише стани, змінені за останні 3 сцени. Старші стани й факти лише про протагоністку переходять в атмосферу.

**Дві міри токенів:**

- **консервативна** — як продукт вирішує `ContextOverflow`: UTF-8 байти JSON + 256, тобто ≈ 2 токени на кириличний символ;
- **реалістична** — символи на токен = 6,78 символу на слово ÷ fertility токенізатора. Fertility (токени на слово українською) взято з [ukrqualbench](https://github.com/grayodesa/ukrqualbench); його корпус UA-GEC має 238 096 символів на 35 122 слова. За замовчуванням береться Qwen3 (fertility 3,38 → 2,0 символу на токен), бо локальні моделі проєкту — Qwen; це й найпесимістичніший варіант. Для порівняння: Claude 2,96 → 2,29, GPT 2,38 → 2,85, Gemma 2,26 → 3,0. Скрипт приймає `--tokenizer`.

**Бюджет пам'яті** = контекст − резерв відповіді 8192 − решта запиту. Решта запиту — з `context_breakdown` останньої спроби чернетки цієї сцени: вона є для всіх 59 сцен.

**«Вміщається» означає різне для різних стратегій:**
- `full`, `all_active`, `full_a` нічого не обрізають, тому «вміщається» = уся секція в межах бюджету;
- Б і В заповнюють шари, доки є бюджет, а решту відкидають і рахують (`dropped_by_budget`). Для них «не вміщається» означає лише одне: не вмістилося саме ядро. Тоді продукт відмовив би запиту (`ContextOverflow`).

Тому recall наводиться двома цифрами: по всіх сценах і по сценах, де вибір вміщається (`target_recall_fitting`). Таблиці синтетики побудовані на вибірці ≈ 60 сцен (кожна N/60-та сцена і остання), а не на кожній сцені.

**Наближення:**

- зв'язок фактів і ліній із персонажами — через згадку основи імені. Відмінювання враховано, локацій і предметів у даних немає;
- стискання хронології моделюється розміром, а не якістю підсумку;
- синтетичні твори на 300 і 3000 сцен згенеровані за частотами основного твору: приріст записів, частка оновлень, давність оновлених записів (медіана 1 сцена, 16 % старші за 10 сцен), розмір складу, частка сцен із протагоністкою. Синтетика показує форму росту, а не якість;
- контрольних випадків від автора поки немає. Скрипт приймає `--control-cases`, коли вони з'являться.

## Результати на реальних даних (68 сцен)

Розмір секції пам'яті (символи, середнє / максимум) і recall змінних цілей. Без обмеження бюджетом (контекст 131 072, реалістична міра Qwen3 — усе вміщається):

| Стратегія | Символи | Токени Qwen3 | Recall цілей | Сцен із пропуском |
|---|---|---|---|---|
| `all_active` | 19 273 / 37 630 | 9 610 / 18 762 | 0,956 | 2 |
| `full` | 19 097 / 37 364 | 9 522 / 18 630 | 0,956 | 2 |
| `full_a` | 17 125 / 31 071 | 8 539 / 15 492 | 0,956 | 2 |
| `structural` (upper/lower) | 13 418 / 24 660 | 6 691 / 12 296 | 0,933 | 3 |
| `structural_fts` (upper/lower) | 14 791 / 26 763 | 7 375 / 13 344 | 0,956 | 2 |

- Дві цілі не досяжні для жодної стратегії, навіть `all_active`: автор вимкнув перенесення цих записів (`hidden_before`), а етап memory однаково їх оновив. Це питання узгодження вимкнених записів із каталогом етапу memory, а не відбору. Записів, яких просто немає в пам'яті, серед цілей не знайшлося.
- На цьому обсязі В досягає recall повної пам'яті з −23 % символів. Б губить одну ціль, бо не має лексичного добору.

**Із консервативною мірою (як працює продукт):**

| Контекст | `full` вміщається | `structural_fts` upper: вміщається / recall у сценах, що вміщаються / відкинуто записів (середнє) | lower: те саме |
|---|---|---|---|
| 32 768 | 0 % сцен | 0 % / — / 102 | 0 % / — / 158 |
| 65 536 | 0 % | 19 % / 0,67 / 96 | 41 % / 0,60 / 114 |
| 131 072 | 100 % | 100 % / 0,956 / 0 | 100 % / 0,956 / 45 |

Причина: решта запиту чернетки за консервативною мірою займає в медіані 67 903 токени (максимум 110 457), за Qwen3 — 19 596 (максимум 31 861). З продуктовою оцінкою на 64 тис. пам'яті просто не лишається місця.

**З реалістичною мірою Qwen3** на 64 тис. і 131 тис. вміщаються всі стратегії в усіх сценах (recall 0,956). На 32 тис. повна пам'ять не вміщається в жодній сцені, А — у 20 %, а В — у 63 % сцен (ядро upper, recall у них 0,96) і 75 % (ядро lower, recall 0,94). Тобто вже на 68 сценах 32 тис. вимагають відбору.

**Малий твір (11 сцен):** секція ≈ 0,9 / 1,7 тис. символів, бюджет не обмежує. Повчальна деталь: `full` має recall 0,5, а `all_active` — 0,8 (10 цілей; 2 з них немає в пам'яті до сцени). Фільтр `project_memory` за складом сцени ховає стани персонажів, яких немає в сцені, а етап memory саме ці стани потім оновлює. Етап memory бачить свій каталог, тож для нього це не проблема. Але письменник у такій сцені не бачить стану відсутнього персонажа, який сцена змінює.

Каталог змінних і незмінних записів (`memory_catalog_v3`) на основному творі:

| Каталог | Символи | Токени Qwen3 | Recall цілей |
|---|---|---|---|
| повний | 32 475 / 63 953 | 16 192 / 31 887 | 0,956 |
| звужений (ядро + присутні + без scope + пов'язані лінії + FTS top-20 за прозою) | 20 300 / 40 865 | 10 122 / 20 375 | 0,956 |

Каталог росте швидше за літературну секцію, бо містить ID, scope і всі незмінні записи. Звуження не втратило жодної цілі. Реплей збережених відповідей (`scripts/memory_replay.py`, 153 спроби) дає `target_unknown` 22 і `target_twice` 7 як є; у переводі на v3 лишається 9 і 7. Чи зменшить звужений каталог ці порушення, офлайн не виміряти: для цього потрібні нові виклики моделі.

## Прогноз росту

Лінійна регресія розміру за номером сцени (основний твір, бюджет не обмежений — показано, скільки кожна стратегія вибирає, а не скільки вміщається):

| Стратегія | Символів за сцену | 300 сцен | 3000 сцен |
|---|---|---|---|
| `full` | 657 | ≈ 195 тис. | ≈ 1,97 млн |
| `full_a` (А) | 535 | ≈ 160 тис. | ≈ 1,60 млн |
| `structural` (upper і lower) | 410 | ≈ 123 тис. | ≈ 1,23 млн |
| `structural_fts` (upper і lower) | 450 | ≈ 135 тис. | ≈ 1,35 млн |

Без бюджету нижня межа ядра не зменшує розміру: старші стани переходять в атмосферу, а квота атмосфери пропорційна бюджету. Сталий розмір нижньої межі виникає лише під бюджетом, коли атмосфера чергується.

Синтетика (контекст 131 072, консервативна міра, бюджет після медіанної решти запиту):

| | 300 сцен | 3000 сцен |
|---|---|---|
| `full`: вміщається | 18 % сцен (лише ранні) | 3 % |
| `full_a`: вміщається | 23 % | 3 % |
| `structural_fts` upper: ядро (записів) / вміщається / recall (усі сцени; ті, що вміщаються) | 302 / 57 % / 0,87; 0,95 | 3057 / 7 % / 0,76; 1,0 (лише ранні сцени) |
| `structural_fts` lower: ядро / вміщається / recall | 7 / 100 % / 0,62 | 8 / 100 % / 0,27 |
| `structural` lower: recall | 0,49 | 0,24 |

Висновок із прогнозу: стала величина контексту можлива лише з ядром, обмеженим у часі. Повнота ж тримається лише доти, доки сцени змінюють записи, які вже є в ядрі чи в присутніх. Синтетика дещо песимістична: вона не закриває застарілі стани, тому ядро upper там росте без меж. Але в реальних даних стани протагоністки теж здебільшого не закриваються (127 активних), тож це не штучний ефект.

## Рекомендація

**Основна архітектура — В + А, з такими змінами моделі даних:**

1. **Тип запису: ядро / атмосфера** (визначення власника). Ядро — те, порушення чого ламає сюжет. Атмосфера — вподобання, звички, улюблені слова, спогади. Тип пише етап memory, автор може виправити.
2. **Строк дії ядра в часі історії** з маркерами днів у хронології. Одяг — ядро протягом дня, потім переходить в атмосферу. Перехід детермінований, за маркерами часу, а не за кількістю сцен. Нижня межа бенчмарку (3 сцени) — лише грубе наближення.
3. **Закриття й заміщення станів.** Новий стан того самого виду (одяг, місце, предмет у руках) заміщує старий, а не додається поруч. Це прямо пов'язано з [#41](https://github.com/ysilvestrov/obscura-text-writer/issues/41): без цього ядро росте, а халат «повертається».
4. **Знайомства для планувальника.** Таблиця «хто з ким знайомий і з якої сцени». Перша зустріч визначається детерміновано з історії складу сцен (21 на 59 сцен основного твору, тобто приблизно кожна третя сцена). Планувальник отримує позначку «перша зустріч — не називати на ім'я до представлення». Це найдешевший і окремий виграш, нові виклики моделі для нього не потрібні.
5. **Явні сутності** (персонажі, локації, предмети) у записах замість згадки імені. Без них зв'язок «запис ↔ сцена» лишається лексичним.
6. **Звужений каталог етапу memory:** ядро + присутні + записи, змінені недавно, + лексичний добір за прозою сцени. Тут цілі — жорстка вимога, тому каталог завжди містить усе ядро й стани присутніх.
7. **Стискання хронології (А)** з підсумками розділів і книг, кожен із власним походженням: які сцени й версії прози він підсумовує. Підсумок інвалідується як stale, щойно змінюється проза будь-якої сцени, що в ньому підсумована (CONTEXT-003). Перебудова — окремий виклик моделі за явним рішенням автора.

**Як це зберігає гарантії:**

- **MEMORY-001, MEMORY-002.** Відбір не змінює записів і доказів, лише вирішує, які з них показати.
- **CONTEXT-001.** Шари з явними лімітами й лічильниками відкинутого (`dropped_by_budget`), ядро ніколи не обрізається: його переповнення — явна помилка.
- **Відтворюваність `ContextBundle`.** Відбір детермінований (порядок шарів, хеш-чергування атмосфери, BM25 з вирішенням рівних оцінок за ID), тож точні ID вибраних записів визначаються знімком даних і фіксуються в контексті.
- **CONTEXT-003.** Індекс FTS будується з того самого знімка, кешу між запитами немає.

**Дешевший варіант — А + ядро з вікном у кілька сцен, без лексичного добору і без нових типів записів.**
- **Що дає:** сталий розмір, мінімум змін.
- **Що втрачає:** записи, які сцена змінює після довгої паузи (16 % оновлень стосуються записів, старших за 10 сцен), і всю атмосферу поза вікном. На синтетиці recall змінних цілей ≈ 0,5 на 300 сценах. Для оповідань і коротких романів прийнятно, для серій — ні.

**Векторний пошук (Г) — кабінетна оцінка.**
- **Що вимагає:** локальну модель ембедингів (сотні МБ ваг, окреме середовище виконання, нова залежність), індекс, прив'язаний до версії моделі, і перебудову після кожної правки прози.
- **Чим гірший за детермінований відбір:** пропуск запису не пояснити («схожість 0,41 < порога» — це не причина, яку автор може виправити). Відтворюваність залежить від версії моделі й чисел із рухомою комою. Для локальних моделей з обмеженим контекстом це ще один процес поруч із генерацією.
- **Що дав би:** лише неявні тематичні зв'язки. Для пам'яті з прози їх частково закриває лексичний пошук.
- **Де доречний:** у біблії світу й довідкових документах ([#31](https://github.com/ysilvestrov/obscura-text-writer/issues/31)), де пошук іде по великих авторських текстах, а не по коротких записах.
- **Вимірювання 24–25.11.2026** (розділ нижче) кабінетну оцінку для поточного відбору підтвердило: на реальному контексті й з ядром upper вектори не дали жодної цілі чи закладеної пари проти BM25. Але як рангувальник вектори на змінних цілях основного твору кращі за BM25, а з ядром, обмеженим у часі (lower), забирають 1–3 цілі на середніх бюджетах. Тож питання варто повернути разом зі зміною моделі даних.

## Векторний пошук (Г): вимірювання 24.11.2026

**Що порівнювалося.** Векторний добір і гібрид BM25 + вектори замість BM25 у залишковому бюджеті стратегії В (`structural_fts`). Шари до добору ті самі, той самий пул (без хронології) і той самий бюджет.

- `structural_vec[<модель>]` — косинусна схожість між планом сцени й записом, без порогу.
- `structural_hybrid[<модель>]` — злиття рангів BM25 і векторів (RRF, k = 60).
- Рівні оцінки вирішуються за ID запису. Векторні оцінки округлюються до 1e-6.

**Моделі.** Обидві локальні, CPU, один потік.

| Ключ | Модель | Ревізія | Вимір | Межа токенів |
|---|---|---|---|---|
| `e5-base` | `intfloat/multilingual-e5-base` | `d1287505` | 768 | 512 (префікси `query:` / `passage:`) |
| `bge-m3` | `BAAI/bge-m3`, лише щільні вектори | `5617a9f6` | 1024 | 8192 |

Хмарна модель (`text-embedding-3-large`, Azure) підготовлена за прапорцем, але не викликалася: квота й згода власника на конкретні твори ще попереду.

**Дані.**
- Копія робочої бази 24.11.2026, знята через `readonly_database` і `sqlite3.backup`. Розмір і час зміни робочої бази ті самі.
- **Основний твір:** 65 сцен з пам'яттю (3 сцени чекають підтвердження).
- **Тестовий текст А:** 12 сцен за спільним планом. У нього вплетено 10 закладених пар і 3 контрольні пари.
  - **Пара** — деталь, яку сцена N описує одними словами, а сцена M — іншими (умовний приклад: «кросівки» → «бігове взуття»). План сцени-повтору містить нове формулювання, а не старе. Отже, BM25 не може знайти запис за самою деталлю. Це і є випадок, де вектори мали б виграти.
  - **Контрольна пара** повторює деталь тими самими словами.
  - **Розмітка.** Записи пам'яті, що несуть деталь, розмічено вручну (лише ID, `docs/research/data/2026-11-24-rag-pairs-annotation.json`).
  - Текст Б (автор пише вручну) додається пізніше тією самою командою.

### Тестовий текст А: пари й щаблі бюджету

**Діагностика ранжування без шарів.** Пул сцени-повтору — 30–40 записів пам'яті без хронології. Запит — план сцени. Пари P04, P06, P07 і P10 збереглися в пам'яті лише записами хронології, тому тут рахуються 6 пар і 2 контрольні.

| Рангувальник | Пари у топ-5 / 10 / 20 (з 6) | Медіанний ранг | Контрольні у топ-5 / 10 / 20 (з 2) |
|---|---|---|---|
| BM25 | 4 / 5 / 6 | 3 | 1 / 2 / 2 |
| `vec[e5-base]` | 0 / 1 / 5 | 15 | 1 / 1 / 2 |
| `vec[bge-m3]` | 2 / 2 / 6 | 11,5 | 1 / 1 / 2 |
| `hybrid[e5-base]` | 1 / 5 / 6 | 8 | 1 / 2 / 2 |
| `hybrid[bge-m3]` | 4 / 4 / 6 | 5 | 1 / 2 / 2 |

- BM25 знаходить записи пар, хоча саму деталь перефразовано. План сцени-повтору ділить із записом інші слова: імена, місця, предмети.
- Вектори ставлять ті самі записи нижче. Порівнюється короткий запис із довгим планом, де деталь — лише одна з багатьох думок.
- Гібрид у кращому разі дорівнює BM25.
- Пул малий, тому recall@20 майже не розрізняє рангувальники. Сигнал дає recall@5.

**Хто бере записи пар у відборі** (найбільший контекст, рахунок записів, а не пар):
- хронологія — 9;
- добір — 4;
- upper: шар фактів — 4;
- lower: атмосфера — 3, факти — 1.

Це однаково для BM25, `vec` і `hybrid`: добір лише заміняє рангувальник.

**Щаблі бюджету** (частка від `tokens_realistic` повної пам'яті сцени). Скільки з 10 пар потрапило в контекст, у дужках — скільки з них узяв добір.

| Щабель | `structural` | `structural_fts` | `structural_vec` (e5 / bge) | `structural_hybrid` (e5 / bge) |
|---|---|---|---|---|
| 1,0 | 8–9 | 10 (3–4) | 10 (3–4) | 10 (3–4) |
| 0,75 | 8 | 8–9 (0–2) | 8–9 (0–2) | 8–9 (0–2) |
| 0,5 | 5–6 | 5–6 (0) | 5–6 (0) | 5–6 (0) |
| 0,35 | 5 | 5 (0) | 5 (0) | 5 (0) |
| 0,25 | 3–5 | 3–5 (0) | 3–5 (0) | 3–5 (0) |

- Діапазон — це варіанти ядра lower / upper.
- Контрольні пари: 2–3 з 3 на всіх щаблях, однаково для всіх варіантів.
- **Змінні цілі (39) різняться на 1–2 цілі в обидва боки:**
  - щабель 1,0 lower: `structural_fts` 37, `vec` 39, гібриди 38;

**Що це означає.** Нижче половини бюджету шари забирають весь бюджет, і рангувальник добору ні на що не впливає. Вище половини всі рангувальники беруть ті самі пари.

### Відтворюваність і вартість

- **Відтворюваність.** Повторний прогін з порожнім кешем і новим екземпляром моделі дав ідентичні набори ID у 100 % пар «сцена × варіант», для обох моделей, на обох творах.
- **Обрізання.** `e5-base` обрізав один текст основного твору, довший за 512 токенів. Це план сцени, тобто запит, який за прогін подавався 22 рази. `bge-m3` не обрізав нічого.

| | `e5-base` | `bge-m3` |
|---|---|---|
| Ваги на диску | 1,16 ГБ | 2,32 ГБ |
| Завантаження моделі | 6,6 с | 1,4 с |
| Ембединги основного твору з завантаженням моделі (374 унікальні тексти, CPU, 1 потік) | 40 с | 112 с |
| Кеш ембедингів на диску (основний твір і текст А, 445 векторів) | 1,6 МБ | 2,0 МБ |

- Час завантаження включає кеш ОС: модель, прочитану вдруге, вантажиться швидше.
- Розмір ваг — верхня межа: рахується вся тека моделі в кеші Hugging Face (там одна ревізія).

### Офлайн-перевірки 25.11.2026: чому рангувальники збігаються

Повний конвеєр дав однакові результати, а чисте ранжування на тексті А — перевагу BM25. Щоб відрізнити «методи рівні» від «тест цього не міряє», зроблено чотири перевірки на тій самій копії бази й тому самому кеші ембедингів. Скрипти: `scripts/memory_bench/adhoc_2026_11_25/`. Вони друкують лише агрегати, без текстів і ID записів.

**Контрольний варіант `fts+fill`.** BM25 повертає лише записи зі спільними словами, а векторний ранг впорядковує весь пул. Тому порівняння йде також із BM25, який після своїх збігів дозаповнює решту пулу за ID.

**1. Оракул: скільки взагалі може дати рангувальник.** Оракул ставить цільові записи першими, далі — порядок `fts+fill`. Цілі — змінні цілі сцени, бюджет — щаблі від повної пам'яті, міра реалістична.

- **Текст А:** оракул не кращий за `fts+fill` на щаблях 1,0 і 0,5; на 0,75 — на 1–2 цілі. Різниця 37 → 39 на щаблі 1,0 lower із попередньої таблиці — ефект дозаповнення, а не ранжування.
- **Основний твір, ядро upper:** оракул = BM25 = вектори на всіх щаблях від 1,0 до 0,35. 44 з 45 цілей, які лежать у пулі, і так беруть структурні шари.
- **Основний твір, ядро lower:** запас є, і вектори забирають його частину. Розмір секцій різниться лише на кілька символів (до 0,1 %), тож це не дозаповнення.

| Щабель (lower) | BM25 і `fts+fill` | `vec[e5-base]` | `vec[bge-m3]` | Оракул |
|---|---|---|---|---|
| 0,75 | 43 | 44 | 44 | 45 |
| 0,6 | 42 | 43 | 42 | 45 |
| 0,5 | 37 | 40 | 40 | 42 |
| 0,42 | 36 | 37 | 37 | 39 |
| 0,35 | 36 | 37 | 36 | 37 |

Гібриди на 0,5 lower дають 38, max-sim (перевірка 3) — 39–40. На реальному контексті 32 тис. (таблиця вище) виграшу немає. Але прогноз розділу «Синтетика» каже, що стала величина контексту на сотнях сцен можлива лише з ядром, обмеженим у часі, тобто з lower. Саме там рангувальник починає важити.

**2. Ранг проти розміру пулу (основний твір).** Ранг кожної змінної цілі в чистому ранжуванні пулу без хронології, запит — план сцени. 45 цілей у 23 сценах; BM25 повертає всі 45. Пул включає записи, які шари беруть і без добору, тож це міра якості ранжування, а не виграшу в контексті.

| Пул (записів) | Цілей | BM25: топ-5 / медіанний ранг | `vec[e5-base]` | `vec[bge-m3]` |
|---|---|---|---|---|
| 9–75 | 15 | 4 / 12 | 7 / 6 | 8 / 3 |
| 113–161 | 15 | 2 / 36 | 2 / 29 | 4 / 9 |
| 167–297 | 15 | 3 / 38 | 6 / 13 | 6 / 10 |

- Знаковий тест за сценами (середній відносний ранг сцени): `vec[e5-base]` кращий у 19 сценах із 23, гірший у 4 (p = 0,003); `vec[bge-m3]` — 16 проти 6 (p = 0,05). Середній відносний ранг: BM25 0,29, e5 0,19, bge 0,16.
- Перевага є вже в найменших пулах, і розрив не росте монотонно. Пули тексту А (30–37 записів) лежать у тому самому діапазоні з протилежним результатом. Отже, різниця між творами — у типі цілей і походженні тексту, а не в обсязі.

**3. Лексичний місток на парах тексту А.**
- План сцени-повтору ділить із записом пари 5–9 основ слів (перші 5 літер), а з іншими записами пулу — у середньому 1–3. Виняток — P09 (1 основа): там BM25 ставить запис на 14-те місце, `vec[bge-m3]` — на 5-те.
- Місток іде не через імена: спільних основ імен 0–1, і маскування імен у запиті не міняє рангів.
- **Запит — лише формулювання повтору з файлу пар**, позитивний контроль — перше формулювання:

| Рангувальник | Пари у топ-5 (з 6) | Ранги P01, P02, P03, P05, P08, P09 |
|---|---|---|
| BM25 (`fts+fill`) | 2 | 18, 1, 15, 31, 20, 5 |
| `vec[e5-base]` | 4 | 1, 1, 16, 4, 18, 2 |
| `vec[bge-m3]` | 6 | 1, 1, 4, 4, 5, 1 |

  Ранг випадкового вгадування (найкращий із розмічених записів) — 10–19. Перше формулювання всі рангувальники ставлять на 1–2 місце.

Вектори долають перефраз, коли запит зосереджено на деталі. У повному плані деталь — одна думка з 13–15 речень, і BM25 знаходить запис через інші спільні слова.

**4. Запит по реченнях (max-sim).** Ранг за найкращим реченням плану не допомагає. `vec[e5-base]` на тексті А покращується (топ-5 пар 0 → 3), `vec[bge-m3]` — ні. На основному творі max-sim гірший за звичайний вектор, а різниця з BM25 стає статистично незначущою. Max-sim піднімає все, що схоже на будь-яке речення плану, а не саме деталь. Варіант «BM25 по реченнях» на тексті А гірший за звичайний BM25, на основному творі рівний.

### Висновок

**Г зараз не вводиться в відбір пам'яті, але й не закрита.** Це перший із трьох можливих висновків дизайну, з поправкою після офлайн-перевірок.
- На реальному контексті (32–131 тис.) і з ядром upper вектори й гібрид не дають жодної цілі чи закладеної пари проти BM25: шари беруть майже все, і запасу для рангувальника немає.
- Як рангувальник вектори не гірші за BM25 загалом. На змінних цілях основного твору вони кращі (p = 0,003 для e5 за сценами). Перевага BM25 у діагностиці тексту А виникає через повний план у запиті й лексичний місток пар.
- З ядром lower на бюджетах 0,42–0,75 повної пам'яті вектори забирають 1–3 цілі з 2–5 можливих. Якщо модель даних перейде на ядро, обмежене в часі (рекомендація розділу «Синтетика»), питання Г варто повернути з вимірюванням саме цього режиму.
- Ціна — нова залежність на 1–2 ГБ, індекс, прив'язаний до ревізії моделі, і обрізання довгих запитів у меншої моделі.
- Рекомендація «В + А» лишається без змін.

**Що лишається відкритим:**
- **Підказки атмосфери з прози** (частина 2 брифу) — інша задача: пошук по прозі, а не по коротких записах. Їй потрібен окремий дизайн.
- **Біблія світу** ([#31](https://github.com/ysilvestrov/obscura-text-writer/issues/31)) — так само.

### Обмеження вимірювання

- **Мало даних.** Текст А — 12 сцен і 10 пар; ранжувати вдалося лише 6, бо 4 пари живуть тільки в хронології. Висновок про пари спирається на малу вибірку.
- **Записи пар і контрольних частково збігаються.** У двох із шести ранжованих пар (P02, P05) запис пари водночас є записом контрольної пари з тими самими словами. Це частково пояснює, чому BM25 їх знаходить.
- **Один автор пар.** Текст А написано з чату за планом, у який пари вплітав той самий автор. Текст Б (рука автора) додасть незалежну перевірку.
- **Хмарна модель не вимірювалася.**
- **Тільки щільні вектори.** Розріджені й багатовекторні режими `bge-m3` не пробувалися.
- **Запит — увесь план сцени.** Розбиття плану на речення (max-sim) не допомогло. Зосереджений запит (лише формулювання деталі) векторам допомагає, але в продукті такого запиту немає: його треба було б будувати окремо.
- **Офлайн-перевірки мають малу вибірку.** 45 цілей у 23 сценах і 6 пар; знакові тести за сценами й за цілями без поправки на множинні порівняння. Цілі однієї сцени ділять запит, тому p-значення за цілями оптимістичні, за сценами — чесніші.
- **Оракул для тексту А побудовано за змінними цілями, не за парами.** Пари в конвеєрі всі рангувальники беруть однаково (10/10 на щаблі 1,0).
- **Щабель 1,0 не вміщує всієї пам'яті** для структурних стратегій: базова вартість секції й резерв віднімаються. Щаблі не враховують решти запиту.

## Жанрові вимоги до моделі даних (огляд)

- **Детектив.** Три шари знання: правда світу, знання кожного персонажа, знання читача. Підказки — записи з моментом появи й розкриття. «Знайомства» з рекомендації — окремий випадок «хто що знає». Відбір має показувати письменнику правду, але позначати, чого не знає точка зору сцени.
- **LitRPG.** Типізований числовий стан (рівні, характеристики, ресурси), інвентар і навички як структуровані записи з детермінованою перевіркою змін (сума, межі, одиниці). Це ядро за визначенням: порушення ламає сюжет. Текстова пам'ять тут непридатна як джерело істини.
- **Фентезі й фантастика.** Правила світу й лор-біблія — авторський канон, окремий від пам'яті з прози. Канон не видобувається з прози і не інвалідується правками сцен. Пошук по ньому — шматками довідкових документів; саме тут має сенс векторний пошук або гібрид із лексичним (#31).

## Обмеження дослідження

- 9 сцен основного твору (6 без пам'яті попередньої сцени, 3 чекають підтвердження) і 6 сцен малого пропущено. Висновки спираються на 59 і 5 сцен.
- Recall рахується за проксі «записи, які сцена змінила». Записів, які сцені потрібні лише для узгодженості (факт зі сцени 12 на сцені 250), він не бачить. Контрольні випадки автора закриють це, коли з'являться.
- Зв'язок через згадку імені частково «підігрує» лексичному добору. Різниця між Б і В на реальних даних — одна ціль із 45.
- «Перші зустрічі» — перша поява персонажа у складі сцен твору, а не перша зустріч саме з протагоністкою.
- Каталог етапу memory у бенчмарку не містить вимкнених автором записів, а в продукті містить. Тому повний каталог тут трохи менший за реальний.
- Синтетика відтворює частоти, а не зміст. Її recall показує тенденцію, а не очікувану якість.
- Реалістична міра бере fertility з ukrqualbench, виміряну на корпусі есеїв UA-GEC. Для художньої прози з діалогами й іменами вона може дещо відрізнятися. Решта запиту рахується за символами частин запиту, а JSON-обгортка — за байтами.

## Наступні кроки

1. **Знайомства для планувальника** — окремий невеликий пакет, корисний одразу. Потребує окремої специфікації.
2. **Design spec моделі даних** (тип запису, строк дії, заміщення станів, сутності, звужений каталог memory) з грою оцінок перед реалізацією. Узгодити з [#41](https://github.com/ysilvestrov/obscura-text-writer/issues/41) (повнота запису) і [#39](https://github.com/ysilvestrov/obscura-text-writer/issues/39) (швидкість).
3. **Консервативна оцінка токенів** блокує 64 тис. контексту вже зараз. Варто окремо переглянути, які ролі мають калібрований профіль токенізатора і чи можна його поширити.
4. **Повторити бенчмарк** після того, як пропущені сцени отримають і підтвердять пам'ять, і з контрольними випадками автора.

## Відтворення

```bash
python scripts/memory_retrieval_bench.py --data <копія теки даних> --story <префікс ID> --synthetic 300,3000
```

Робоча тека `data/` відхиляється (`live_data`). Вивід — JSON з агрегатами; у ньому немає текстів, імен і ID записів.

**Векторний пошук (Г).** Окреме середовище з `requirements-lock.txt` і `scripts/memory_bench/requirements-vector.txt`. Кеш ембедингів лежить поза репозиторієм.

```bash
python scripts/memory_retrieval_bench.py --data <копія> --story <префікс> --synthetic "" \
  --vector-models e5-base,bge-m3 --cache-dir C:/tmp/rag-bench/cache --repro \
  --pairs docs/superpowers/notes/2026-11-24-rag-test-pairs.json \
  --pairs-annotation docs/research/data/2026-11-24-rag-pairs-annotation.json \
  --budget-steps 1.0,0.75,0.5,0.35,0.25
```

Офлайн-перевірки 25.11.2026 — у тому самому середовищі, по черзі `offline_checks.py`, `main_pipe.py`, `blocking.py` з `scripts/memory_bench/adhoc_2026_11_25/`. Копію даних і кеш задають змінні `RAG_BENCH_DATA` і `RAG_BENCH_CACHE`.

Розмітку пар готує `scripts/rag_annotate_pairs.py propose` / `confirm`. Файл кандидатів містить тексти, тому лежить поза репозиторієм. Хмарна модель (`azure-3-large`) вмикається лише прапорцем `--cloud` для творів з `--cloud-stories`, з межею `--cloud-max-usd`.
