# R-14a — Вимірювання читання сховища

Дата: 23.10.2026. Базовий HEAD: `18bcd59`. Обсяг погоджений власником: лише виміри, потім рішення щодо оптимізації.

## Висновок для рішення

**У перевіреному синтетичному навантаженні термінової потреби в оптимізації не виявлено.** Рекомендація — відкласти зміни SQL/схеми та перейти до дизайну сторінки редагування (R-20), якщо власник погодиться. Це рекомендація, а не автоматичне закриття R-14b або доказ швидкості будь-якого реального твору.

У наборі з 10 творами найбільший p95 окремої операції — 43,46 мс; у stress з 50 творами — 58,59 мс. Діагностичні орієнтири 100/250 мс зі специфікації не перевищено. Пороги не є затвердженим SLA, а повне сканування не є достатньою причиною міграції.

## Що й як вимірювали

Python 3.12.14, SQLite 3.53.1, Windows 11 build 26300. Чинна схема 3, WAL, synchronous=2, page_size=4096, cache_size=-2000. Runtime, індекси, авторські дані та сервер не змінювалися; зовнішніх викликів немає.

Використано чинні `Repository`/доменні моделі. Seed через bulk SQL лише в нових synthetic БД; усі FK перевірено, кожен version blob реально створений і прочитаний із перевіркою SHA-256. Поточна проза — 1000 слів/сцену; історичні blobs короткі. Версії, крім плану, містять snapshot із посиланням на план; це простий граф без міжсценових залежностей.

| Набір | Творів | Сцен загалом | Версій загалом | Версій у вибраному творі | Запусків / спроб | SQLite, MiB |
|---|---:|---:|---:|---:|---:|---:|
| small | 1 | 7 | 140 | 140 | 70 / 70 | 0,29 |
| typical | 10 | 150 | 4500 | 450 | 1500 / 1500 | 5,45 |
| stress | 50 | 750 | 30000 | 600 | 7500 / 7500 | 33,82 |

`typical` — назва умовного набору, не вимір реальної робочої бази. У кожному з останніх двох наборів твір має 15 сцен / 15000 слів поточної прози. Історія — 20/30/40 версій на сцену відповідно, запусків — 10 на сцену.

Перший виклик збережено окремо, потім 20 повторів у детерміновано перемішаному порядку. p95 — 19-те значення з 20 відсортованих. Перед timings уже створено й перевірено blobs, тому навіть перший виклик не є холодним диском. Для кожного Repository-виклику відкривається звичайне нове DB connection. Trace, EXPLAIN та cProfile виконували окремо від timings.

## Що показали SQL-плани й профілі

1. `scenes WHERE story_id=? ORDER BY position,id` використовує чинний UNIQUE-індекс `(story_id,position)`; доступ за story/scene ID також індексований. Причини змінювати ці індекси не знайдено.
2. `versions WHERE story_id=? ORDER BY rowid` має `SCAN versions`. На stress сканується таблиця з 30000 рядків, повертаються 600. Окремий SQL execute+fetchall: median 12,63 мс, p95 14,28 мс. Це конкретний кандидат для майбутнього індексу по story_id, якщо масштаб або фактичні затримки виростуть; індекс не створювали й ефект не вимірювали.
3. `list_runs(story_id)` читає **всі** запуски та десеріалізує їх перед Python-фільтрацією. На stress: SQL повертає 7500, API — 150. SQL median 6,30 мс, p95 9,34 мс. Окремий cProfile підтверджує 7500 валідацій Run. Тут майбутня оптимізація потребувала б SQL-фільтра, а не лише нового індексу до чинного запиту.
4. `stage_attempts WHERE story_id=?` теж сканується, але SQL median лише 1,49 мс, p95 1,81 мс на stress. Терміновості не виявлено.
5. ContextView завантажує всі версії вибраного твору. Історія однієї сцени додатково перевіряє актуальність/hash і копіює доменні об’єкти. У профілі typical для історії 30 версій помітні читання/resolve paths, snapshots і deepcopy, а не лише SQLite. Не варто знімати перевірки цілісності заради швидкості.

SQL microtimings отримані на одному вже відкритому прогрітому connection. Їх не можна напряму віднімати від Repository timing і називати залишок витратами Pydantic: різняться connection lifecycle, транзакції, порядок читання та кеші. cProfile додає накладні витрати; його абсолютний час не замінює таблицю вище.

## Перевірки та межі висновків

- Усі три набори пройшли FK check, контроль кількості рядків і відповідності SHA-256 усіх version blobs. Кількості результатів перевірено для списків творів/сцен/версій/запусків/спроб та export snapshot. Logical SQL dump до й після всіх читань/профілів ідентичний у кожному наборі.
- Це in-process Repository latency, не HTTP, мережа, браузерний рендер, побудова модельного промпту чи повний FB2/EPUB/PDF. `export_snapshot` вибирає метадані й перевіряє вибрані джерела; не вимірює серіалізацію книги або читання всього тексту для рендеру.
- Немає конкурентних writers, cold-cache/повільного диска, повноцінної накопиченої пам’яті, персонажів, source_files, acceptance records, калібрувань, оцінювань та редакторських журналів. Runs мають порожні tasks, спроби — порожній context; великі збережені prompts можуть змінити результат.
- Кількість версій усередині одного твору не перевищує 600; stress переважно перевіряє вплив **інших** творів на глобальні сканування. Глибоку історію одного твору або довгі prefix dependency chains цей прогін не перевіряє.
- Продуктові код і схема не змінювалися, тому повний pytest не перезапускався; попередній suite не оголошується новим прийманням цих вимірів. Поточні перевірки документації записані в журналі.

Наступне рішення власника: відкласти R-14b та перейти до R-20 або розширити конкретний сценарій вимірів. R-15 відкладена за прямим рішенням власника незалежно від цих результатів.
