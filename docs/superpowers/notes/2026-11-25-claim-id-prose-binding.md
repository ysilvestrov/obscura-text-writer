# ID твердження прив'язаний до версії прози: розбіжність із VALID-LINKS / VALID-MEMORY

25.11.2026. Дослідження для власника. **Рішення власника (25.11.2026): реалізувати варіанти 1 і 4** — зроблено в тому самому PR (SPEC: MEMORY-003-S09, VALID-MEMORY-S09). Привід: проба скіла `revise` (R-40), `docs/superpowers/specs/2026-11/2026-11-25-revise-skill-probe/results.md`, розділи B і C.

## Коротко

- **Висновок: дефект.** Це не навмисне рішення і не регресія. R-44 побудував П₀ й перенос пам'яті на хибному припущенні, що ID тверджень стабільні. У SPEC наслідок записано як відоме обмеження, а не як бажану поведінку.
- **Рекомендація: варіант 1.** Брати в `claim_id` ID сцени замість ID версії прози. Міграції немає: старі ID зберігаються в журналах і не перераховуються. Зміна виправляє обидва симптоми, але лише для випадку «прозу змінено, твердження ті самі».
- **Окремо й дешевше:** дати чату дію «Залишити попередню пам'ять» через MCP. Для `revise` (правка одного слова) це вже передбачений шлях, і він не створює нових ID взагалі.

## Факт

`memory/journal.py:221-226` (`_add_event`) рахує `claim_id = stable_id('mc_', [category, text, prose_id, quote, occurrence, …])`. `storage/links.py:45-56` (`memory_digest`) виключає `event_id`, `source_version_id` і `evidence_version_id`, але `claim_id` лишає.

Мінімальна проба на чистих функціях (скрипт поза репозиторієм):

- проза сцени 1 змінилася лише поза цитованим фрагментом;
- текст твердження й цитата ті самі (`quote same True`);
- `claim_id` різні: `mc_8acb…` → `mc_7795…`;
- `carry_journal` для сцени 2, яка робить `update` цього твердження, падає з `CarryFailed` («Записи сцени посилаються на твердження, яких немає в новій пам'яті попередньої сцени»).

Два симптоми:

1. Змінюється `memory_digest` сцени k, тож змінюється П₀ сцени k+1, і її З1/З2 стають `unchecked`.
2. `update`, `retire` і `resolves_claim_id` пізніших сцен посилаються на зниклі ID. Тоді перенос дає `carry_failed`, а всі наступні сцени блокуються.

Є й третій, тихий наслідок. На `claim_id` ключовані:

- вибір перенесення автора (`Scene.memory_forwarding`);
- позначки типу запису (`Story.memory_kind_overrides`);
- рішення ядра пам'яті (`threads.<claim_id>`).

З новими ID ці рішення автора без попередження перестають діяти.

## Чи це навмисно

- **Звідки `prose_id` у формулі.** Він там з `a5500495` (21.10.2026, пам'ять v2), за місяць до R-44. Тоді він робив ID детермінованими й унікальними в межах журналу: `validate_memory_journal` відхиляє «Повтор claim ID». Без розрізнювача однакові (категорія, текст, цитата) у двох сценах зіткнулися б. Стабільності між версіями прози ніхто не вимагав, бо `memory_digest` і переносу ще не було.
- **Що припускав R-44.** Дизайн `2026-11-23-book-validation-design.md:163` відносить до дайджесту «стабільні ID тверджень і ті, на які вони посилаються, … крім ID версій прози й доказів». План PR 2a (`2026-11-23-r44-pr2a-validity-core.md:83`): «`claim_id`/`resolves_claim_id` входять (стабільні ID тверджень)». Код `memory_digest` виконує букву цього правила: виключає саме ID версій. Але намір, тобто незалежність П₀ від версії прози, не виконується, бо `claim_id` сам похідний від ID прози.
- **Що каже SPEC.** VALID-LINKS: «нова пам'ять із тими самими власними записами не змінює П₀ наступної сцени». VALID-MEMORY / «Відомі обмеження» (`b0c5e5b0`): «ID твердження хешує ID прози», для стартів зі сцен 1–3 до кінця книги доходить 5 переносів із 24. Тобто наслідок помічено в пробі R-44 і записано як обмеження, але не погоджено як бажану поведінку.
- **Тести.** VALID-LINKS-S04 (`test_same_own_events_keep_next_scene_valid`) зберігає ту саму пам'ять на **тій самій** прозі. Випадку нової версії прози з тими самими записами тест не перевіряє, тож розбіжність пройшла непоміченою.

## Варіанти

| | Що лікує | Наявні книги | Ризик і ціна |
|---|---|---|---|
| **1. `claim_id` від ID сцени замість ID прози** (рекомендовано) | Обидва симптоми й тихий наслідок, коли твердження не змінилося (категорія, текст, цитата, порядок і додаткові поля ті самі) | Міграції немає: ID у журналах збережені, `load_memory`, `validate` і fsck їх не перераховують. Дайджести старих пам'ятей і відбитки рішень автора чи Ревізора не змінюються | Одноразово: перша нова пам'ять сцени k після оновлення дає ID нової форми, і перенос на k+1 ще раз не зійдеться, як і сьогодні. Далі все стабільно. ID сцени треба передати в усі виклики `_add_event`: `apply_operations`, `wire_v3`, `wire_v4`, `core_review`, `merge.py` (там джерело — злиття), `normalize_manual_memory`. `journal_from_legacy` не чіпати: він рахує ID під час читання legacy. Змінюється контракт MEMORY-003-S05 («ID збігаються з v2-формою»): це навмисна зміна, її треба описати в SPEC разом із кодом |
| **2. Виключити `claim_id` з `memory_digest` з нормалізацією посилань** (ID → зміст цільового твердження) | Лише симптом 1 (`unchecked` у k+1). `carry_failed` лишається, бо перенос шукає ID. Щоб прибрати й його, переносу потрібна перемапа старих ID на нові за змістом, а це порушує інваріант «власні події без змін». Тихий наслідок лишається | Змінюються дайджести всіх пам'ятей, тож давні рішення автора й висновки Ревізора для З1/З2 перестають збігатися з відбитком. Прецедент — `plan_identity` у R-44 PR 2b. Побудова переживе: записана й поточна П₀ рахуються однаково | Складніше й лікує менше, ніж варіант 1 |
| **3. Лишити код, уточнити SPEC** | Нічого | — | Не узаконює регресію, бо регресії немає. Але це скасовує записаний намір R-44 («нова пам'ять із тими самими записами не змінює П₀») і лишає 5 із 24 переносів. Прийнятно лише як свідоме рішення власника |
| **4. MCP-дія «Залишити попередню пам'ять»** (рішення З3 + `ProseEquivalence`) | Сценарій `revise`: правка прози без нової пам'яті. Нових ID немає, тож немає й обох симптомів | Без змін даних | Сервер має цю дію лише в HTTP (`POST /api/scenes/{id}/links/memory/decision`), у MCP її немає. Чат не може сказати «пам'ять лишається чинною» замість перебудови. Незалежний від варіантів 1–3 |

## Межі варіанта 1 (чесно)

- Регенерація пам'яті моделлю зазвичай формулює твердження інакше, і ID все одно новий. Тож цифру 5 із 24 з проби R-44 (регенерація етапу) варіант 1 майже не змінить.
- Правка слова, що стоїть у цитаті чи в тексті твердження (наприклад, назва міста), теж дає новий ID. Так і має бути: твердження змінилося. Проба B змінила текст твердження, тож упала б і після варіанта 1.
- Допомагає він там, де твердження відтворено дослівно: правка поза цитатами, ручне чи чатове повторне збереження тих самих записів, `revise`, який перебудовує пам'ять і свідомо зберігає незмінені записи.
- Для змістових змін справжнє рішення інше: пам'ять сцени k має видавати `update` наявних тверджень, а не нові `add`, або перенос має перемапляти посилання. Це окрема робота, вона не входить до цієї розбіжності.

## Питання власнику

1. Виправляти сервер (варіант 1) чи свідомо лишити обмеження (варіант 3, з уточненням SPEC)?
2. Додати MCP-дію «Залишити попередню пам'ять» (варіант 4) для скіла `revise` окремим пакетом?
3. Якщо варіант 1, чи прийнятний одноразовий `carry_failed` на першій перебудові пам'яті кожної книги після оновлення? Його можна уникнути, якщо перенос тимчасово зіставлятиме ID старої форми, але це ускладнення без явної потреби.

Якщо виправляти, у тому самому PR: оновити MEMORY-003 (формула ID, S05), VALID-LINKS (речення про `memory_digest`), прибрати пункт «ID твердження хешує ID прози» з відомих обмежень VALID-MEMORY як усунене відхилення. Також додати сценарій із тестом «нова проза, ті самі записи → П₀ і перенос незмінні».
