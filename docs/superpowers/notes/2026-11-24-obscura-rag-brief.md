# Векторний пошук по прозі: бенчмарк стратегії Г і підказки атмосфери

Запит власника 24.11.2026. Продовження [#25](https://github.com/ysilvestrov/obscura-text-writer/issues/25) (масштабування пам'яті й відбір контексту). Пов'язано з [#31](https://github.com/ysilvestrov/obscura-text-writer/issues/31) і [#41](https://github.com/ysilvestrov/obscura-text-writer/issues/41).

Дві частини. Друга спирається на індекс і висновки першої, тож їх можна завести двома задачами.

## Мета

1. **Закрити відкрите питання #25 цифрами.** Векторний пошук (стратегія Г) у дослідженні `docs/research/2026-11-08-memory-scaling-retrieval.md` оцінено лише кабінетно, без запуску. Треба виміряти його на тих самих даних і метриках, що й А/Б/В, і підтвердити або переглянути рекомендацію «В + А».
2. **Підказки атмосфери.** Детермінована пам'ять добра для верифікації, але свідомо обмежена: вона не пов'язує кросівки з бігової доріжки (сцена 6) з кросівками на полігоні (сцена 12), інакше записів було б забагато. Векторний пошук по прозі попередніх сцен може підкинути схожі фрагменти, з яких можна перевикористати деталі (той самий опис кросівок). Результат недетермінований за змістом, але час від часу додає деталі, з яких складається атмосфера.

## Поточний стан

- Пам'ять детермінована. Відбір: шари ядро / присутні / лінії / атмосфера плюс FTS5/BM25 (`trigram`) за планом сцени (`structural_fts`). Recall змінних цілей на основному творі (68 сцен) — 0,956, як у повної пам'яті, при −23 % символів.
- Ембедингів, векторного індексу й моделі ембедингів у продукті немає. #25 прямо забороняв завантаження моделі без окремої згоди власника. Ця задача й є такою згодою, але лише в межах, описаних нижче.
- Кабінетні аргументи проти Г з #25: пропуск запису неможливо пояснити автору; відтворюваність залежить від версії моделі й чисел із рухомою комою; нова залежність і окремий процес поруч із генерацією. Там же сказано, що вектори доречні для великих текстів, а не для коротких записів. Підказки атмосфери шукають саме по прозі.

## Частина 1. Бенчмарк Г: локально проти хмари

Дослідницька гілка, **не мерджиться в main**. Продукт лишається локальним; хмарні варіанти — лише для порівняння.

- **Стратегії, які додаються** до наявних у скрипті бенчмарку:
  - `vector_local` — локальна модель ембедингів і векторний індекс поруч із SQLite;
  - `vector_cloud` — хмарні ембединги (Azure OpenAI); бажано також Azure AI Search з його вбудованим гібридним пошуком;
  - `hybrid_*` — BM25 + вектори для кожного з двох варіантів.
- **Дані й метрики ті самі, що в #25:** копія бази через `readonly_database`, основний твір плюс синтетика; recall ядра й атмосфери окремо (не одна підсумкова цифра); розмір контексту; частка сцен, що вміщаються в 32 / 64 / 128 тис.
- **Чесне порівняння.** Однакові слова (кросівки → кросівки) знаходить і BM25 з триграмами. Вектори можуть виграти лише там, де слова різні: «кросівки» / «бігове взуття» / «стоптані підошви». У тестовий набір свідомо додати такі пари, інакше висновок буде про лексику, а не про вектори.
- **Відтворюваність:** зафіксувати назву й версію моделі ембедингів, розмірність, параметри чанкування; перевірити, чи дає повторний прогін ті самі ID.
- **Вартість:** час індексації локально, ціна й латентність хмари на обсяг твору, розмір індексу на диску.

**Результат:** новий розділ у research-документі #25 з таблицями поруч із наявними і перегляд рекомендації: Г лишається поза пам'яттю, входить як добір у гібрид чи потрібен лише для підказок.

## Частина 2. Прототип підказок атмосфери

На моделі ембедингів, яка виграє в частині 1 (у продукті — лише локальна).

- **Що шукаємо:** фрагменти прози попередніх сцен, схожі на план і склад поточної сцени.
- **Кому:** моделі, що пише чернетку (цей прототип), і письменнику як підказка в інтерфейсі (пізніше, окрема задача).
- **Окремий шар, не заміна пам'яті.** Пам'ять — для верифікації й фактів; підказки — для стилю й деталей. Підказки не створюють і не змінюють записів пам'яті (MEMORY-001, MEMORY-002).
- **Маркування для моделі:** фрагменти подаються як «матеріал для стилю й деталей, не поточний стан». Ядро завжди переважає: якщо за ядром героїня боса, кросівки зі сцени 6 у чернетку не потрапляють.
- **Бюджет:** окрема явна частка контексту з лічильником відкинутого (CONTEXT-001); ядро ніколи не обрізається на користь підказок.
- **Відтворюваність:** ID фрагментів, версія моделі ембедингів і знімок індексу фіксуються в `ContextBundle`; при тому самому стані даних і моделі контекст відтворюється.
- **Stale:** індекс сцени перебудовується після правки її прози (CONTEXT-003); підказка зі старої версії прози не подається.

**Оцінка:** recall тут не підходить, бо «правильної» підказки немає.
- Ручна оцінка на 10–15 сценах: кожен фрагмент «корисний / нейтральний / шум».
- Лічильник суперечностей: скільки разів чернетка з підказками порушила ядро порівняно з чернеткою без них.

## Відкриті рішення

- Модель ембедингів для локального варіанта: розмір ваг, середовище виконання, якість на українській прозі.
- Векторний індекс: розширення SQLite (наприклад, sqlite-vec) чи окремий файл.
- Одиниця пошуку: сцена, абзац чи вікно речень.
- Скільки підказок і яка частка бюджету за замовчуванням; чи вимикаються вони для локальних моделей з малим контекстом.
- Чи хмарні ембединги колись стають опцією для автора, явно й за згодою (за замовчуванням — ні).

## Межі

- Частина 1: робоча база лише на читання; хмарні виклики — тільки на творах власника й за його згодою, не в main і не в збірці Store.
- У виводі скрипта, звітах і документах — лише ID, коди й агрегати, без текстів твору й моделі (як у #25).
- Частина 2: прототип за прапорцем, вимкнений за замовчуванням; без змін у SPEC.MD. Якщо прототип себе виправдає — окремий design spec для продукту, з грою оцінок.
- Підказка в інтерфейсі для письменника — поза цією задачею.
