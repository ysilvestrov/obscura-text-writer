# Явні локації в пам'яті (#67)

Дата: 2026-11-22
Статус: затверджено (22.11.2026)
Spec-review: agy/gemini-4-argon @ 62304f7 (author: claude) — 5 findings: 5 fixed, 0 rejected (fallback: codex — usage limit)

## Для власника

### Мета

Пам'ять знає, де відбувається сцена: локації з рядка «Локація:» плану стають картками твору, записи пам'яті посилаються на них, а відбір пам'яті для сцени бере записи про це місце й місця, що його містять чи в ньому лежать, — навіть коли в плані й записі місце назване однаково, але без збігу інших слів.

### Що зміниться для тебе

- Рядок «Локація:» плану починає працювати: «Квартира Джорджа / вітальня, потім двір» дає три картки — «Квартира Джорджа», «Квартира Джорджа / вітальня», «двір». Картки створюються самі, коли зберігається план; для наявних творів — один раз під час оновлення застосунку.
- У контексті твору з'являється панель «Локації»: список карток зі сценами, підказки «схоже на…» і кнопки «Злити» / «Не схожі» / «Розділити». Без твого рішення нічого не зливається. Злиття чи розділення позначає застарілими лише версії сцен, чиї локації (з предками й нащадками) воно зачепило: у них змінюється відбір пам'яті.
- Зміна рядка «Локація:» позначає завдання, чернетку, пам'ять і оцінку сцени застарілими — так само, як зараз зміна «Хто бере участь:».
- Етап memory може позначати факти, стани, лінії й події локаціями сцени; промпт memory трохи довшає. Наявна пам'ять не стає застарілою й не переписується: старі записи просто без локацій.
- Картка локації має необов'язковий опис, який ти пишеш у панелі «Локації». Його бачать планувальник (етап brief) і письменник (чернетка й переписування), щоб використати під час написання; модель пам'яті опису не отримує.
- Предмети й пошук по прозі («кросівки») — поза цією зміною.

### На чому стоїть рішення

- Локації беруться з рядка «Локація:» плану; кілька — через кому або «смислові» слова; вкладеність — через `/`; тотожність — за точним текстом назви; картки створюються автоматично; злиття схожих — лише рішенням людини; починаємо з локацій, предмети — наступна задача `[вимога власника]` (22.11.2026).
- Картка локації має необов'язковий опис, що йде планувальнику й письменнику (чернетка) і може бути використаний під час написання `[вимога власника]` (22.11.2026).
- Картки персонажів уже йдуть у контекст етапів brief і письма з `build_context` (`generation/context.py`), тож опис локації лягає поруч `[проба]` (П5).
- Рядок «Хто бере участь:» уже розбирається під час збереження плану в склад сцени (`apply_description`), а зміна складу позначає залежні версії застарілими `[проба]` (П1).
- Формат відповіді memory (wire v4) має динамічну схему з дозволеними `character_ids` сцени; поле можна додати необов'язковим, не змінюючи версію контракту `[проба]` (П2).
- Актуальність версій не залежить від тексту вбудованого промпту, тож довший промпт memory не робить наявну пам'ять застарілою `[проба]` (П3).
- Відбір пам'яті вже має шари за збігом ID персонажів; шар локацій лягає поруч `[проба]` (П4).
- Роздільники «і», «та», «and» трапляються всередині назв («Сад і город»), тому роздільниками не є `[виведення]`.

### Ключові рішення

1. ID локації детермінований: `loc_` + 16 hex SHA-256 від (ID твору, нормалізований шлях). Таблиця `story_locations` зберігає шлях для показу, батька, час появи, `merged_into` і відхилені підказки. Відкинуто: картки локацій як файл-версія, як у персонажів, — злиття й автостворення в транзакції збереження плану простіші в SQLite, а ID не залежить від порядку появи.
2. Роздільники в рядку: кома, крапка з комою, `→` і окремі слова «потім», «далі», «згодом», «then», «later»; «і», «та», «and» — ні. Шлях `А / Б` дає картки `А` і `А / Б` (батько — `А`); тотожність — за нормалізованим повним шляхом (регістр, пробіли, лапки й кінцева розділова), показ — першим написанням.
3. Злиття — псевдонім: `merged_into` перенаправляє і сцени з цією назвою, і записи пам'яті; текст планів не змінюється; «Розділити» знімає злиття. Злиття змінює відбір пам'яті, тож версії сцен, чия околиця локацій (див. «Обсяг») змінилася, стають застарілими через знімок залежностей; злиття двох локацій поза околицею сцени її не зачіпає. Відкинуто: переписування рядків планів — змінює авторський текст і робить план застарілим; злиття без інвалідації — версії перестали б відповідати поточному стану.
4. Підказки схожості детерміновані, без моделі: однакова остання частина шляху, одна назва повністю міститься в іншій як слова, або відстань редагування ≤ 20 % довжини. Відкинуто: підказки планувальника — платний виклик на кожен план і невідтворюваний результат; можна додати пізніше.
5. Пам'ять: необов'язкове `location_ids` у записах журналу й у додаваннях wire v4 для всіх чотирьох категорій; дозволені — локації сцени та їхні предки; ID поза дозволеними — порушення `location_unknown`, що відхиляє відповідь, як `scope_unknown` для персонажів. Відбір: шар `place` після `present` — стани, лінії й факти, чиї локації (після злиттів) лежать в околиці сцени. Відкинуто: wire v5 — несумісний із власними промптами memory з контрактом `/4`.
6. Опис локації: необов'язкове поле картки (до 2000 знаків), редагується лише автором у панелі. Розділ контексту «Локації сцени» — шляхи локацій сцени та їхніх предків з описами, де вони є, — додається в етапи brief, draft, rewrite і edit повним переписуванням (і в контекст чату `get_scene_context`, що повторює draft). Описи — матеріал автора, а не факти пам'яті: у журнал вони не потрапляють, у memory не йдуть. Зміна опису робить застарілими завдання, чернетку й переписування сцен, які його показують. Злита локація показує опис цільової; опис злитої зберігається й повертається після «Розділити». Відкинуто: опис у файлі-версії, як картки персонажів, — локації живуть у таблиці твору, а версія на кожну правку одного опису роздула б історію.

Розглянуто стандартне: векторний пошук місць і моделі виділення сутностей — відкинуто дослідженням #25 і рішенням власника: шумно, дорожче, непояснювано.

### Що стане гірше

- Помилка в назві місця дає нову картку: «Квартира Джоржа» ≠ «Квартира Джорджа», доки ти не зіллєш їх за підказкою.
- Зміна рядка «Локація:» робить завдання, чернетку, пам'ять і оцінку сцени застарілими; злиття — версії зачеплених сцен.
- Відповідь моделі, що назвала чужу локацію, відхиляється (етап memory треба повторити), як зараз із чужим персонажем.
- Промпт memory довший на інструкцію й перелік дозволених локацій — трохи більше токенів на етап memory.
- Описи локацій додають токенів у brief і чернетку; правка опису робить застарілими завдання й чернетки всіх сцен у цій локації та вкладених у неї.
- Записи пам'яті, створені до зміни, без локацій: шар `place` працює лише для нової пам'яті (поки сцени не перебудуються).
- Назва з «і»/«та» в рядку не розділяється: «двір і сад» — одна локація.

### Оцінка

- Власник: L або XL залежно від підходу (для повного варіанту з предметами). Автор: усе разом — XL; ця специфікація (лише локації) — L, 2 PR.
- Розподіл: таблиця й ID локацій, розбір рядка, автостворення, міграція всіх сцен ≈ 20 %; пам'ять (журнал і перенесення поля, wire v4, схема, промпт, проєкція, відбір, звужений каталог) ≈ 30 %; знімок залежностей і завантаження локацій у `ContextView` ≈ 10 %; панель «Локації» зі злиттям і підказками, показ локацій у таблиці пам'яті ≈ 20 %; SPEC, traceability, сайт uk/en ≈ 20 %. Опис локації додає ≈ 10 % (поле, розділ контексту, селектор, поле в панелі). Після рев'ю й опису — межа L/XL; оцінка автора — XL.
- Дешевший варіант — без панелі злиття (≈ −20 %): дублікати назв лишаються різними локаціями без способу їх поєднати.
- Фактично: L, 2 PR (#257, #261), 10 задач (6 + 4). #67 закрито 22.11.2026; предмети винесено в окрему задачу #262 за рішенням власника.

## Обсяг

**PR 1 — ядро:**
- `src/storygen/locations.py` (новий, без IO): `parse_locations(line) -> list[list[str]]` (шляхи), `normalize(path) -> str`, `location_id(story_id, key) -> str`, `similar(a, b) -> bool`.
- `storage/locations.py` (новий): таблиця `story_locations(story_id, id, path, parent_id, created_at, merged_into, payload)` і `location_dismissals(story_id, a, b)`; `ensure_locations(db, story_id, paths)`, `canonical(map, id)` (з урахуванням `merged_into`), `ancestors`/`descendants`.
- **Околиця сцени** — канонічні ID її локацій, їхніх предків і нащадків разом з усіма ID, злитими в них. Одна функція `scene_neighbourhood(locations, scene)` обчислює її для відбору, проєкції та знімка залежностей.
- `Scene.location_ids: list[str] = []`; `apply_description` читає рядок «Локація:»/«Location:» (мітки `scene_plan_template.READ['location']`), створює картки, записує `location_ids`; зміна `location_ids` дає ту саму пряму застарілість legacy-версій без знімка і `invalidate_in_transaction`, що й зміна складу.
- Знімок залежностей (`storage/snapshots.py`): селектор `scene.location_ids` поруч із `character_ids` для тих самих скоупів (memory, brief, draft, prose_edit, author_rewrite, author_text, evaluation) і селектор `story.location_neighbourhood` (відсортована околиця сцени) для скоупів, що відбирають пам'ять. `ContextView` і спільний знімок завантажують `story_locations` твору, щоб `compare_snapshot` бачив злиття.
- Міграція бази: таблиці й одноразовий прохід **усіх** сцен, також у кошику (`scene.beats`), з тим самим розбором; сцени без рядка — без локацій. Ревізій сцен міграція не збільшує й версій застарілими не позначає; знімки, створені до міграції, без нових селекторів вважаються актуальними щодо локацій.
- Журнал: `MemoryEvent.location_ids: list[str] = []` — поле запису (claim): `update`, `retire`, закриття лінії й перехід слота в `unknown` успадковують `location_ids` запису, а `replay_memory` перевіряє їхню незмінність, як `character_ids`. Поле входить у серіалізацію v3 з `omit_defaults` (порожнє не пишеться, старий журнал читається), у `_extras`/`_change_event`/`_add_event`/`_nonstandard`, `normalize_manual_memory`, `memory/merge.py::_author_events` і `series_start.prequel_split`; у `duplicate_key` не входить (той самий факт з іншою локацією — дублікат).
- wire v4: необов'язкове `location_ids` лише в додаваннях усіх категорій; `schema_bounds_v4` отримує дозволені ID (канонічні локації сцени й предки); фрагмент контексту `memory_allowed_location_ids` з назвами для моделі; інструкція у вбудованому промпті memory. ID поза дозволеними чи дубль — `Violation(label, 'location_unknown')`, відповідь відхиляється (як `scope_unknown`). Ручне редагування пам'яті й legacy wire v2/v3 поля не задають.
- Проєкція (`memory/projection.py::memory_items`): стан персонажа поза складом сцени не відкидається, якщо його локації в околиці сцени.
- Відбір (`memory/selection.py::classify`): шар `place` у `LAYERS` після `present`. Правило: `core`/`atmosphere`-kind і стани `hero_recent`/`present` зберігають свої шари; інакше стан, лінія чи факт із локацією в околиці сцени йде в `place` замість `atmosphere`, `general`, `threads`, `facts` чи `fts`. Події хронології лишаються в `timeline` (вона показується за порядком сцен). `narrow_catalog` додає стани з локаціями околиці.

- Опис локації: поле `description` у `payload` картки; розділ контексту `scene_locations` (мітки uk/en у `context_labels`) в етапах brief, draft, rewrite, edit повним переписуванням і в `get_scene_context`; селектор знімка `scene.location_descriptions` (шляхи й описи, що показуються сцені) для тих самих етапів. Сцена без локацій чи без описів — розділ лише зі шляхами або відсутній, якщо локацій немає.

### Новий Requirement і Scenarios

`MEMORY-LOCATIONS` — картки локацій із плану, злиття й шар відбору. Scenarios:

- `MEMORY-LOCATIONS-S01` — розбір рядка: кома, `;`, `→`, «потім»/«далі»/«згодом»/«then»/«later» розділяють; «і»/«та»/«and» — ні; `А / Б` дає `А` і `А / Б`; однаковий нормалізований шлях — та сама картка, інший текст — інша.
- `MEMORY-LOCATIONS-S02` — збереження плану створює картки й `Scene.location_ids`; зміна рядка робить застарілими (через знімок залежностей) пам'ять, завдання, чернетку й оцінку сцени; міграція заповнює всі сцени, також у кошику, без зміни ревізій і без застарілості.
- `MEMORY-LOCATIONS-S03` — злиття перенаправляє сцени й записи пам'яті, «Розділити» повертає; текст планів не змінюється; версії сцени, чию околицю зачепило злиття, застарілі, інших — ні; підказки схожості детерміновані, відхилена пара більше не пропонується.
- `MEMORY-LOCATIONS-S04` — memory: дозволені в схемі лише локації сцени та їхні предки; ID поза ними дає `location_unknown` і відхиляє відповідь; `update`/`retire`/закриття/`unknown` зберігають `location_ids` запису; ручне збереження, злиття арок і розділ передісторії їх не гублять; старий журнал без поля читається.
- `MEMORY-LOCATIONS-S05` — відбір: запис про `А` потрапляє в шар `place` сцени в `А / Б`, запис про `А / Б` — у сцену в `А`; запис зі злитої локації — як про цільову; стан відсутнього персонажа в околиці сцени не відкидається проєкцією; стани героя й присутніх лишаються у своїх шарах, хронологія — у `timeline`.
- `MEMORY-LOCATIONS-S06` — опис локації: розділ «Локації сцени» з описами локацій сцени й предків є в контексті brief, draft, rewrite, повного edit і `get_scene_context`, немає в memory й edit патчами; зміна опису робить застарілими завдання й чернетку сцен, які його показують, інших — ні; злита локація показує опис цільової.

## План

PR 1 — ядро (розбір, таблиця, міграція, сцена, журнал і wire, відбір) з тестами й SPEC; PR 2 — API, панель «Локації», таблиця пам'яті, сайт uk/en. Предмети й пошук по прозі — окремі issue.

## Поправки під час реалізації (PR 1)

- Селектор `scene.location_ids` пишеться лише для етапу memory: brief, draft і author_text уже залежать від голови плану сцени, тож зміну рядка бачать без нього.
- Інструкція моделі пам'яті — у розділі «ДОЗВОЛЕНІ LOCATION_IDS…», а не у вбудованому промпті: її отримують і власні промпти з контрактом `/4`, вбудовані промпти не змінюються.
- `location_ids` не входить у `_extras` (ID запису й ключ дубліката лишаються тими самими); `_add_event`/`_change_event` приймають поле окремим параметром.
- `series_start.prequel_split`: майбутні записи — текст для іншої книги, де ID локацій твору не мають сенсу; збережена частина журналу несе події як є.

## Поправки під час реалізації (PR 2)

- Панель «Локації» — розділ рівня твору в панелі пам'яті сцени, після «Підсумків хронології»: права панель за WORKSPACE-TOOLS містить лише розділи сцени.
- Підказки схожості не пропонують пари предок–нащадок: «Маєток» і «Маєток / вітальня» ділять слова за побудовою — це вкладеність, а не дублікат (дефект PR 1).
- Перелік сцен картки — сцени, що називають її прямо (після злиттів); сцени вкладених карток показуються у своїх картках.
- Локації рядків таблиці пам'яті не додаються до MCP `get_scene_text(material=memory)`.
- Після запису локацій, типу запису чи підсумку сторінка перечитує стан твору, а чиста таблиця пам'яті — свої дані, щоб наступний запис іншої панелі чи дії робочого простору не був хибним конфліктом, а локації й актуальність у таблиці були поточними.
