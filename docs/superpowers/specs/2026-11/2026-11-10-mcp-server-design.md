# MCP-сервер для Claude/Codex: перший набір інструментів (R-32, #84)

Дата: 2026-11-10
Статус: чекає на затвердження
Spec-review: codex/gpt-6.1-sol @ df995f3 (author: claude) — 3 findings: 3 fixed, 0 rejected

## Для власника

### Мета

Автор обговорює ідею, план і персонажів у Claude чи Codex, якими вже користується, і передає результат в Obscura однією командою в чаті. Чат-модель може прочитати завдання сцени, картки й пам'ять і записати чернетку. Автор потім переписує її в Ghost Mode. Для звичайної прози власний API-ключ не потрібен: модель оплачує підписка автора в його клієнті.

### Що зміниться для тебе

- **Нова команда `storygen-mcp`.** Автор реєструє її в Claude Desktop, Claude Code або Codex (ChatGPT desktop читає ту саму конфігурацію, що й Codex). Вона працює лише поки запущено Obscura на цьому комп'ютері й розмовляє з ним через локальну адресу.
- **Шість інструментів у першому наборі**: список творів; огляд твору (сцени й стани); контекст сцени для письма (завдання, картки учасників, пам'ять попередніх сцен, віковий рівень, мова); імпорт плану й персонажів (той самий додавальний імпорт, що й у формі); запис чернетки сцени; і для автора — короткий опис, що робити далі в Obscura.
- **Модельних викликів з боку Obscura немає.** Інструменти лише читають і записують, бюджет не витрачається.
- **Чернетка з чату позначена.** Версія має позначку «Написано в зовнішньому клієнті (Claude / Codex…)». Позначка видна в історії версій і рядку стану (#89). Чернетка стає поточною, як і чернетка, збережена вручну. Попередня лишається в історії.
- **Чернетка з чату фіксує мову твору**, так само як чернетка, створена моделлю в Obscura (#32).
- **Нічого не видаляється й не публікується через MCP.** Немає інструментів для видалення, публікації, запуску конвеєра чи зміни налаштувань і ключів.
- **Одна твоя дія поза репозиторієм**: приймання з реальним клієнтом. Ти реєструєш `storygen-mcp` у своєму Claude або Codex і проходиш сценарій «план → імпорт → чернетка» на нейтральному прикладі. Модельних викликів Obscura це не потребує. Підписка використовується твоя, у межах звичайного чату.
- Конвеєр Obscura через CLI підписки (модель викликає Obscura) — не тут, окреме рішення після перевірки умов провайдерів.

### На чому стоїть рішення

1. Мета й межі задано в #84: без хмарного розгортання й автентифікації; Obscura модель не викликає; конвеєр через CLI підписки окремо; реальні модельні виклики для перевірки — лише за згодою. `[вимога власника]`
2. Перший набір: імпорт плану й персонажів, читання пам'яті, запис чернетки. Пропозиція з #84, розширена двома інструментами лише для читання (список творів, огляд), без яких клієнт не знає ідентифікаторів. `[вимога власника]` + `[виведення]`
3. PIPE-002: один виконавець на каталог даних. SECURITY-001: сервер обслуговує лише loopback і відхиляє змінювальні запити з чужим `Origin`. `[проба]` (П1)
4. Claude Desktop, Claude Code і Codex CLI підтримують локальні MCP-сервери через stdio; ChatGPT desktop ділить конфігурацію з Codex. Веб-ChatGPT і веб-Claude приймають лише віддалені HTTPS-сервери, тобто для локального застосунку непридатні. `[проба]` (П2); дані про ChatGPT desktop із вторинних джерел, перевіряються під час приймання
5. Імпорт (`POST /api/stories/{id}/sources`), картки й ручна чернетка (`POST /api/scenes/{id}/draft` з оптимістичною ревізією) вже є в HTTP API. Немає двох операцій: JSON-списку творів (`/api/stories` приймає лише POST) і контексту письма сцени — `memory-view` показує власну пам'ять сцени, а не проєкцію пам'яті попередніх сцен, яку бачить етап `draft`. Їх додаємо як два нові ендпоінти лише для читання. `[проба]` (П3, П6)
6. Ручна чернетка стає поточною (`set_head`) з `author_lineage` на попередню; знімок залежностей береться в момент збереження. Тому чернетка з чату, записана після зміни карток, виглядала б свіжою щодо карток, яких модель не бачила; потрібен відбиток контексту, перевірений під час запису. Фіксація мови твору дивиться лише на `source_run_id`. `[проба]` (П4) + `[виведення]` (рев'ю)
7. Офіційний Python SDK `mcp` існує (2.3.0) і не встановлений у проєкті. `[проба]` (П5)
8. Звичайні чат-клієнти відмовляють у відвертих сценах. Тому контекст сцени передає віковий рівень явно, а інструмент запису не обходить відмову клієнта. Маршрутизації за рейтингом у першому наборі немає. `[виведення]`
9. Без контролю моделі й промпту клієнта обов'язковими лишаються серверні перевірки, що не залежать від моделі: ревізії, мова, порожній текст, розмір, застарілість залежностей. Модельні перевірки (оцінювач, редактура) автор запускає в Obscura сам. `[виведення]`

### Ключові рішення

1. **Тонкий stdio-клієнт до запущеного сервера Obscura, а не другий процес над даними й не HTTP-ендпоінт у сервері.** `storygen-mcp --url http://127.0.0.1:8765` перекладає виклики інструментів у HTTP-запити: наявні плюс два нові ендпоінти лише для читання (список творів і контекст письма сцени). Якщо Obscura не запущено, інструмент повертає зрозумілу помилку. Відкинуто доступ до каталогу даних напряму: порушує PIPE-002. Відкинуто Streamable HTTP-ендпоінт `/mcp` у самому сервері: stdio підтримують усі цільові клієнти, а HTTP-ендпоінт розширює поверхню SECURITY-001 без потреби.
2. **Перший набір — шість інструментів, жодного руйнівного й жодного платного.** Відкинуто запуск конвеєра й прийняття матеріалів через MCP: це платні або незворотні дії, які в першому наборі має робити автор в інтерфейсі.
3. **Чернетка з чату прив'язана до прочитаного контексту.** `get_scene_context` повертає `context_fingerprint` — відбиток знімка залежностей етапу `draft` на момент читання. `save_draft` передає його назад; якщо поточний знімок відрізняється (змінено картки, пам'ять, бриф чи план), сервер відхиляє запис 409 «Контекст сцени змінився — прочитайте його знову». Відкинуто лише перевірку ревізії сцени: зміна карток не змінює ревізії сцени, і чернетка виглядала б свіжою щодо входів, яких модель не бачила.
4. **Походження чернетки — нове поле версії `external_origin {client, model?}`**, задане клієнтом і непідтверджене. Сервер записує його як «так заявив клієнт». Фіксація мови твору зважає на `source_run_id` або `external_origin`. Відкинуто запис чернетки як звичайної ручної: автор і майбутні перевірки (#55 Ghost Mode) не відрізнили б текст моделі від власного. Відкинуто фіктивний `source_run_id`: запуск у черзі не існує, а слід виконання й бюджет посилалися б на неіснуючий запис.
5. **Пам'ять через MCP лише читається.** Відкинуто запис пам'яті клієнтом: цитати-докази й роль memory — механізм перевірки, який варто відкривати окремим рішенням.
6. **Залежність — офіційний SDK `mcp` як опційна extra `[mcp]`.** Відкинуто власну реалізацію JSON-RPC і узгодження версій протоколу: протокол змінюється, а SDK — стандарт.

- Розглянуто стандартне: офіційний Python SDK `mcp` (FastMCP, stdio) — прийнято (рішення 6).
- Розглянуто стандартне: Streamable HTTP як рекомендований віддалений транспорт MCP — відкинуто для першого набору (рішення 1); можна додати пізніше без зміни інструментів.

### Що стане гірше

- Нова залежність (`mcp` і її транзитивні пакети) у збірці з extra `[mcp]`. Це збільшує інсталятор #30, якщо extra туди ввійде.
- Чернетку з чату Obscura не оцінює автоматично й не рахує в бюджеті. Модель і промпт клієнта невідомі, а `external_origin` — лише заява клієнта.
- Інструмент запису чернетки може замінити поточну чернетку, яку автор ще не переписав. Попередня лишається в історії, а запис вимагає `expected_revision`, тож одночасна зміна в інтерфейсі не перезаписується мовчки.
- Відверті сцени чат-клієнт може відмовитися писати. Obscura цього не обходить.
- Підтримку ChatGPT desktop підтверджено лише вторинними джерелами.

## Обсяг

### PR 1 — ядро

- **Домен.** `VersionRef.external_origin: ExternalOrigin | None`, де `ExternalOrigin(client: str (1..64, [A-Za-z0-9 ._-]), model: str | None (≤128))`. Старі записи без поля — `None`.
- **Нові ендпоінти лише для читання.** `GET /api/stories` → `[{id, title, language, rating, scene_count}]` для неархівованих творів. `GET /api/scenes/{id}/writing-context` → план сцени, бриф (якщо є), картки учасників і проєкція пам'яті попередніх сцен такі самі, як у контексті етапу `draft` (через ту саму збірку контексту: `journal_before` + `project_memory` і проєкцію карток, без промптів Obscura), віковий рівень, мова прози, цільова кількість слів, `revision` і `context_fingerprint` — SHA-256 канонічного JSON знімка залежностей `draft` (`_manual_snapshot(repo, scene, 'draft')`). Обидва — GET, тож SECURITY-001 щодо змінювальних запитів не зачіпається.
- **API.** `DraftChange` приймає необов'язкові `external_origin` і `expected_context_fingerprint`. Якщо передано відбиток, сервер обчислює поточний і при розбіжності відхиляє запис 409 «Контекст сцени змінився — прочитайте його знову». Для `external_origin` відбиток обов'язковий (400 без нього). `POST /api/scenes/{id}/draft` передає його в `save_manual_draft(..., external_origin=...)`. Чернетка з `external_origin` завжди створює нову версію (без «unchanged» скорочення, як Ghost Mode), щоб походження не втратилося. Фіксація мови (`storage/authoring.py`, перевірка наявності модельного матеріалу) зважає на `source_run_id IS NOT NULL OR external_origin IS NOT NULL`.
- **Клієнт `storygen-mcp`** (`src/storygen/mcp/`): console script; аргументи `--url` (типово `http://127.0.0.1:8765`) і `--client-name` (типово з `clientInfo.name` під час initialize). Транспорт stdio через `mcp` SDK. HTTP через `httpx` без заголовка `Origin`. Таймаут 30 с. Помилки сервера (409, 400, 403) повертаються як `isError` з текстом сервера; недоступний сервер → «Obscura не запущено за адресою …».
- **Інструменти** (назви англійською, описи мовою, що повертає `localization` за замовчуванням):
  - `list_stories()` → відповідь `GET /api/stories`;
  - `get_story(story_id)` → сцени з позицією, назвою, станом (той самий словник, що UI-FEEDBACK), `revision`;
  - `get_scene_context(scene_id)` → відповідь `GET /api/scenes/{id}/writing-context` як є, зокрема `revision` і `context_fingerprint`. Без промптів Obscura й без ключів;
  - `import_plan_and_characters(story_id, plan_markdown?, characters_markdown?)` → результат додавального імпорту як є (`files`, `partial`). Немає автоматичного повтору (контракт імпорту: безномерні сцени додалися б удруге);
  - `save_draft(scene_id, text, expected_revision, context_fingerprint, content_format='markdown')` → нова версія й ревізія. `external_origin = {client: --client-name, model: None}`. Модель клієнт MAY передати параметром `model`;
  - `next_steps(scene_id)` → короткий текст для автора: відкрити сцену в Obscura, переписати в Ghost Mode, запустити пам'ять.
- **Безпека.** Немає інструментів видалення, публікації, запуску, налаштувань і ключів. Клієнт звертається лише до loopback-адреси: `--url` з не-loopback хостом відхиляється на старті. SECURITY-001 без змін.

## SPEC.MD

Новий Requirement **MCP-BRIDGE** — «Локальний MCP-клієнт до сервера Obscura» (компонент, межі, контракт інструментів, безпека). Scenario:

- MCP-BRIDGE-S01 «Сервер не запущено» → інструмент повертає помилку з адресою; жодного доступу до каталогу даних.
- MCP-BRIDGE-S02 «Імпорт через MCP» → результат той самий, що в формі; повтору немає.
- MCP-BRIDGE-S03 «Запис чернетки зі застарілою ревізією» → 409 повертається клієнту як помилка; поточна чернетка не змінюється.
- MCP-BRIDGE-S08 «Картки змінено між читанням контексту й записом» → ревізія сцени та сама, але відбиток інший; запис відхиляється 409, чернетка не змінюється.
- MCP-BRIDGE-S09 «Контекст письма сцени без власної пам'яті» → `writing-context` сцени B повертає проєкцію пам'яті сцени A таку саму, як у контексті етапу `draft`.
- MCP-BRIDGE-S04 «Чернетка з чату» → нова версія з `external_origin`, поточна; попередня в історії.
- MCP-BRIDGE-S05 «Не-loopback адреса» → клієнт не стартує.
- MCP-BRIDGE-S06 «Набір інструментів» → `tools/list` повертає рівно шість інструментів; немає руйнівних.
- MCP-BRIDGE-S07 «Приймання з реальним клієнтом» → ручна процедура з причиною (потрібен обліковий запис власника).

Оновити STORY-LANGUAGE: фіксація зважає на `external_origin`. Розділ походження версій: `external_origin` — заява клієнта, не підтверджена сервером, не входить у бюджет і слід виконання.

PR 1 — ядро (≤4 задачі: домен, відбиток і API чернетки з фіксацією мови; два ендпоінти читання; каркас клієнта й інструменти; SPEC/traceability). Після злиття — план PR 2.

## Проби

- **П1.** SPEC.MD PIPE-002 (≈рядок 432): «SHALL послідовно виконувати завдання… і блокувати запуск другого виконавця для цього каталогу». SECURITY-001 (≈1651) і `web/app.py:50-56`: хост ∉ {127.0.0.1, localhost, ::1} → 403; змінювальний запит з `Origin`, що не збігається з `host`, → 403; запит без `Origin` пропускається.

## Заявка → доказ

| Заявка | Де записано | Що доводить | Сила |
|---|---|---|---|
| Чернетку написав зовнішній клієнт | `external_origin` у версії | лише заява клієнта; сервер не перевіряє | слабка — так і показується («заявлено клієнтом»), не використовується як доказ якості |
| Модель клієнта | `external_origin.model` | необов'язкова заява | слабка — показується лише якщо передано |
| Чернетка з чату написана за поточним контекстом | `context_fingerprint` при записі | сервер обчислює відбиток знімка залежностей і порівнює; тест S08 | сильна (щодо входів знімка; що саме модель використала — невідомо) |
| Мову твору зафіксовано | перевірка наявності версій | SQL по `source_run_id`/`external_origin`; тест | сильна |
| MCP не обходить PIPE-002 | архітектура клієнта | клієнт не імпортує сховища; тест: клієнт без сервера не відкриває каталог даних | сильна |
| Набір інструментів без руйнівних | `tools/list` | тест на точний список | сильна |
| Цільові клієнти підтримують stdio | зовнішня документація | П2; підтверджується прийманням власника | середня |
