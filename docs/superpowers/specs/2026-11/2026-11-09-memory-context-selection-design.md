# Відбір пам'яті в контекст під бюджет і звужений каталог етапу memory (#60)

Дата: 2026-11-09
Статус: затверджено 2026-11-09
Spec-review: agy/gemini-4-argon @ 076204c (author: claude) — 8 findings: 8 fixed, 0 rejected (fallback: codex — usage limit)

## Для власника

**Мета.** Довгий роман (сотні сцен) або модель із малим контекстом більше не впиратимуться в помилку «контекст завеликий» через пам'ять. Коли повна пам'ять не вміщається, застосунок детерміновано відбирає найважливіше й показує, що саме не потрапило в запит. Етап memory отримує звужений каталог і не переповнюється першим.

**Що зміниться для тебе.**
- Поки повна пам'ять вміщається, нічого не змінюється: запити такі самі, як зараз. Для твого основного твору (контекст усіх ролей 262 тис.) відбір зараз не вмикатиметься.
- Коли не вміщається, замість помилки запит іде з відібраною пам'яттю. Ядро героя потрапляє завжди. Далі йдуть свіжі (за поточний день історії) стани героя, лінії, де згадано учасників, стани інших присутніх, загальні стани, факти про учасників, недавня хронологія, частка «атмосфери» (старші стани героя й факти лише про нього) і записи, знайдені за текстом плану й завдання.
- У статистиці сцени видно, що відбір спрацював: скільки записів вибрано з кожного шару і скільки відкинуто через бюджет. Відкинута хронологія позначена в самому запиті рядком на кшталт «Хронологія: не показано N записів (сцени 1–K)».
- Якщо не вміщається навіть ядро, лишається явна помилка, як зараз. Ядро ніколи не обрізається.
- Етап memory при переповненні отримує звужений каталог: усе ядро й усі лінії, стани присутніх, загальні стани, до 20 станів, знайдених за прозою сцени, а з незмінних записів — факти про учасників і хронологію останніх 20 сцен. Застосунок попереджає, що каталог звужено.
- У таблиці пам'яті можна позначити запис «завжди показувати» (ядро) або «атмосфера». Позначка діє лише тоді, коли спрацьовує відбір. Застарілими вона робить лише тексти, у запитах яких відбір справді працював і цей запис був серед кандидатів. Якщо відбору не було, позначка нічого не змінює.
- Нічого незворотного: схема бази не змінюється, журнали пам'яті не переписуються.

**На чому стоїть рішення.**
- Ядро — те, порушення чого ламає сюжет; атмосфера — решта; запис може переходити з ядра в атмосферу з часом `[вимога власника, #25]`.
- Підхід — В (структурний відбір + повнотекстовий пошук FTS5) з елементами А; векторний пошук не потрібен `[вимога власника, #25]`.
- Повна секція пам'яті росте ≈ 644 символи на сцену: ≈ 191 тис. на 300 сцен, ≈ 1,93 млн на 3000 `[проба: П1]`.
- На 35 сценах основного твору, які зараз можна виміряти, бенчмарк дає recall змінних цілей 0,933 для повної пам'яті. Варіант «усі стани героя в ядрі» тримає 0,933, але росте лінійно. Варіант «ядро — лише свіжі стани» на 32 тис. дає 0,867, зате вміщається в 57 % сцен проти 37 %. Запропонований відбір — проміжний між ними, тому його recall ще треба виміряти. Це критерій приймання PR 1 `[проба: П1]`.
- Каталог етапу memory більший за літературну секцію: 23 тис. символів у середньому, максимум 70 тис. Звужений каталог старого формату v3 дає −37 % без втрати цілей. Каталог v4 зі слотами ще не виміряно, це критерій приймання PR 2 `[проба: П1]`.
- Основний твір має контекст 262 тис. в усіх ролях, тож відбір там зараз не потрібен. Він потрібен для моделей на 8–80 тис., які вже налаштовано в інших творах (локальна memory на 8 тис., ролі на 24–80 тис.) `[проба: П2]`.
- За консервативною оцінкою токенів (так рахує продукт) на 64 тис. вміщається лише 14 % сцен навіть з відбором. Причина — оцінка решти запиту, а не пам'ять. За реалістичною оцінкою на 64 тис. вміщається все `[проба: П1]`. Ця проблема — поза обсягом (див. рішення 5).
- Для героя вже є заміщення станів і перехід дня, але лише в п'яти слотах ядра (#41), а знайомства зроблено в #43. Неслотові стани героя й стани інших персонажів заміщення й строку дії не мають `[проба: П3]`.

**Ключові рішення.**
1. Відбір вмикається лише тоді, коли повний запит не вміщається в бюджет (токенів або символів). Відкинуто «завжди відбирати»: він змінив би всі запити й відбитки для творів, яким нічого не загрожує, і без потреби ховав би атмосферу.
2. Відкинута хронологія замінюється в запиті рядком-лічильником, без підсумків від моделі. Відкинуто підсумки розділів у цьому пакеті: це новий модельний етап, власне походження, інвалідація й інтерфейс перебудови. Окремою задачею.
3. Тип «ядро / атмосфера» за замовчуванням визначається детерміновано з наявних даних (слоти ядра, свіжість зміни в часі історії, згадані учасники), а автор може перевизначити його для окремого запису. Відкинуто тип від етапу memory: це новий дріт v5, новий промпт і платні виклики для перевірки якості.
4. Каталог етапу memory звужується також лише при переповненні, а межі допустимих рішень (`schema_bounds_v4`) звужуються разом із ним. Відкинуто звуження без меж: модель отримувала б право оновити запис, якого не бачить.
5. Поза обсягом і окремими задачами: явні сутності (локації, предмети), строк дії для станів поза слотами, підсумки розділів, калібрування оцінки токенів для ролей без профілю. Відкинуто «все разом»: це XL, кілька специфікацій.
- Розглянуто стандартне: векторний пошук за ембедингами (RAG) — відкинуто, бо пропуск запису не пояснити автору, відтворюваність залежить від версії моделі, а нова локальна залежність — сотні МБ (#25, розділ «Векторний пошук»).
- Розглянуто стандартне: обрізання найстаріших записів (sliding window) — відкинуто, бо губить ядро й стани, змінені після довгої паузи (16 % оновлень стосуються записів, старших за 10 сцен, #25).

**Що стане гірше.**
- Під бюджетом модель не бачить частини пам'яті. Recall змінних цілей на синтетиці падає (0,62 на 300 сценах, 0,27 на 3000 за нижньої межі ядра). Це краще за помилку, але не повна пам'ять.
- Відкинута хронологія зникає з запиту без підсумку, доки не з'являться підсумки розділів.
- Звужений каталог етапу memory може не містити запису, який проза змінює. Тоді модель додасть новий запис замість оновлення, і в пам'яті з'явиться дубль. Те саме з незмінними записами: модель не бачить старих фактів про відсутніх персонажів і хронології старше 20 сцен, тож може повторно додати той самий факт чи подію.
- Позначки «ядро / атмосфера» — ще одне джерело застарілості для текстів, створених із відбором.
- Консервативна оцінка токенів і далі блокує моделі на 64 тис. незалежно від пам'яті.
- Збирання контексту при переповненні дорожче: кілька оцінок токенів повного запиту і FTS-індекс у пам'яті. Без переповнення вартість та сама.

**Оцінка.** Власник: L. Автор: L для цього обсягу; повна рекомендація #25 (з сутностями, підсумками розділів і строком дії для всіх станів) — XL. Розподіл: модуль відбору з шарами, бюджетом, FTS5 і лічильниками, підключення в збирання контексту, стратегія `product` у бенчмарку ≈ 40 % (PR 1); звужений каталог етапу memory разом із межами рішень ≈ 25 % (PR 2); перевизначення типу автором у таблиці пам'яті, selector застарілості, статистика сцени ≈ 20 % (PR 3); SPEC.MD, traceability, документація UA/EN ≈ 15 % (розподілено між PR). Три PR. Дешевший варіант — лише PR 1: відбір без звуженого каталогу й без позначок автора (M). Втрачає захист етапу memory, який переповнюється першим, і можливість виправити тип запису.

**Питання до власника.**
1. Відбір лише при переповненні (рішення 1). Згоден, чи хочеш, щоб він працював завжди, навіть коли все вміщається?
   - **Відповідь (2026-11-09):** лише при переповненні.
2. Відкинуту хронологію позначати рядком-лічильником, доки немає підсумків від моделі (рішення 2). Прийнятно?
   - **Відповідь (2026-11-09):** так.
3. Обсяг: сутності, підсумки розділів, строк дії для інших станів і калібрування оцінки токенів — окремими issue (рішення 5). Згоден? Калібрування оцінки найбільше заважає саме зараз на моделях з 64 тис.
   - **Відповідь (2026-11-09):** так, окремими issue: #67 сутності, #68 підсумки розділів, #69 строк дії інших станів, #70 калібрування оцінки токенів.

## Тіло

### Поточний стан

- `generation/context.py::build_context` для brief/draft/edit/rewrite додає секцію «ЗДІЙСНЕНІ ПОДІЇ — ПЕРЕВІРЕНА ПАМ'ЯТЬ» з `memory/projection.py::project_memory` (ядро відстежуваних, потім факти/стани/лінії/хронологія; стани фільтруються за складом сцени; MEMORY-FORWARD ховає вимкнені записи). `make_context` рахує `token_estimate`, і при `estimate > context_tokens - max_output_tokens` або `chars > max_input_chars` кидає `ContextOverflow` («Текст не обрізано»).
- `token_budget/core.py`: перевірений профіль діє лише в діапазоні `[min_bytes, max_bytes]` тіла запиту й додає фіксований резерв 256 токенів на запит; поза діапазоном — консервативна оцінка `body_bytes + 256`. Тож оцінка окремого рядка чи частини запиту не адитивна.
- Етап memory отримує `memory_catalog_v4` (ядро всіх слотів відстежуваних, усі лінії, mutable-стани, immutable факти/хронологія) і `schema_bounds_v4` з `memory/wire_v4.py`.
- Модель журналу: `open_threads` не мають `character_ids` (`journal.py`: «Scope дозволено лише для станів»); зв'язок лінії з учасником — лише через згадку імені.
- Бенчмарк `scripts/memory_bench/` (`strategies.py`, `synthetic.py`, тести `tests/retrieval_bench/`) працює на власних `Record`/`SceneInput` без журналу, слотів і `day_key`; стратегії `full/full_a/structural/structural_fts` і `catalog_narrow` (формат v3).
- `Scene.memory_forwarding` і selector `scene.memory_projection_policy` (власник — сцена, значення обчислює `selector_value`) — прецедент авторських позначок у знімку залежностей.

### Модуль відбору (PR 1)

`memory/selection.py` — чисті функції без IO.

```python
@dataclass(frozen=True)
class SelectionInput:
    journal: MemoryJournal; scene_id: str; scene_number: int; cast: list[str]; tracked: list[str]
    names: dict[str,str]; hidden: set[str]; source_scene_numbers: dict[str,int]
    query_text: str                 # beats плану сцени + brief (якщо є) — для FTS
    kinds: dict[str,Literal['core','atmosphere']]   # перевизначення автора (PR 3), інакше {}
    day_keys: dict[str,str|None]    # day_key сцени за source_version_id запису й поточної сцени

def select_memory(inp, char_budget) -> MemorySelection
```

Кандидати — активні записи після MEMORY-FORWARD. Кожен запис потрапляє рівно в один шар — перший за порядком, правило якого спрацювало. Записи з перевизначенням `core` — у шар 1, з перевизначенням `atmosphere` — у шар 8, незалежно від інших правил. Шари в порядку пріоритету, усередині шару — за порядком журналу:

1. `core` (обов'язковий): слоти відстежуваних (як у `project_memory`) + перевизначення `core`.
2. `hero_recent`: неслотові стани відстежуваних у складі сцени, чия остання зміна відбулася в поточний день історії (`day_key` джерела = `day_key` сцени, обидва не `None`); якщо в будь-якої з двох сцен `day_key=None` — змінені за останні 3 сцени.
3. `threads`: відкриті лінії, у тексті яких згадано учасника сцени (основи імен — `name_stems`).
4. `present`: стани персонажів зі складу сцени, крім відстежуваних.
5. `general`: стани без `character_ids`.
6. `facts`: факти, що згадують учасника сцени, крім відстежуваного героя (факти лише про героя йдуть у шар 8).
7. `timeline`: хронологія сцен `≥ scene_number - 20`.
8. `atmosphere` (квота 10 % бюджету пам'яті): неслотові стани відстежуваних, що не потрапили в шар 2; факти лише про героя; перевизначення `atmosphere`. Порядок — хеш `sha256(scene_id:claim_id)`.
9. `fts`: решта активних записів, крім хронології, ранжування BM25 по FTS5 trigram за `query_text`, рівні — за `claim_id`.

Бюджет у символах відрендереного тексту секції:

- Спершу резервується рядок про хронологію найбільшої можливої довжини.
- Шар 1 береться повністю; якщо він більший за бюджет → `CoreOverflow`.
- Шари 2–9 беруться записами, поки вміщаються; кожен відкинутий запис рахується в `dropped[шар]`.
- Якщо відкинуто хоч один запис хронології (стара за вікном чи недавня через бюджет), секція містить рядок «Хронологія: не показано N записів (сцени …)» із фактичними номерами сцен.

`MemorySelection{text, selected_claim_ids, layers: dict[str,int], dropped: dict[str,int], timeline_note: str | None, char_budget}`. Текст рендериться тими самими рядками, що `project_memory`, лише для вибраних записів.

**Підключення.** `build_context` будує повну проєкцію як зараз і передає в `make_context` `memory_selector` (замикання над `SelectionInput`). Якщо повний запит перевищує ліміт токенів або `max_input_chars` і секція пам'яті є:

- `max_chars = min(довжина повної секції - 1, settings.max_input_chars - (chars запиту без секції))`;
- детермінований двійковий пошук найбільшого `char_budget ∈ [0, max_chars]` (≤ 12 кроків), для якого повний запит із `select_memory(inp, char_budget)` проходить і `token_estimate` (тим самим профілем ролі, на весь запит), і `max_input_chars`;
- якщо не проходить навіть `char_budget`, рівний довжині шару 1 → `ContextOverflow` із поясненням «ядро пам'яті не вміщається».

Профіль токенів не застосовується до окремих рядків, тож межі діапазону профілю й резерв 256 не спотворюють бюджет. `memory_metrics.selection = {layers, dropped, selected_claim_ids, timeline_note, char_budget, steps}`; `projection_version` → `memory-uk-v3-selected` для запитів із відбором.

**Відтворюваність.** Відбір — функція даних знімка (`ContextView`), налаштувань ролі й перевизначень; FTS-індекс будується в `:memory:` на кожен запит без кешу (CONTEXT-003). Вибрані ID фіксуються в `ContextBundle.memory_metrics`.

**Бенчмарк.** Додається стратегія `product`, яка для реальних даних будує `SelectionInput` з журналу копії бази й викликає `select_memory`. Наявні стратегії, синтетика й тести `tests/retrieval_bench/` лишаються без змін. Критерій приймання PR 1: на реальному творі за реалістичною мірою на 32 тис. recall `product` ≥ recall `structural_fts[core=lower]`, а частка сцен, що вміщаються, ≥ частки `structural_fts[core=upper]`; результат записується в журнал виконання.

### Звужений каталог етапу memory (PR 2)

Якщо запит етапу memory переповнюється, `memory_catalog_v4` будується з `narrow=True`:

- `core` — без змін (усі слоти всіх відстежуваних у складі), `threads` — усі активні лінії (рішення для кожної обов'язкове, тож лінії не звужуються);
- `mutable` — стани присутніх, загальні стани і до 20 станів за BM25 по прозі сцени;
- `immutable` — факти, що згадують учасників, і хронологія останніх 20 сцен.

`schema_bounds_v4` отримує той самий набір mutable claim ID: оновлення запису поза каталогом відхиляється як і зараз для невідомого ID. Попередження в контексті: «Каталог пам'яті звужено: N записів не показано моделі». Якщо не вміщається навіть звужений — `ContextOverflow`. Критерій приймання PR 2: бенчмарк звуженого каталогу v4 (нова стратегія `catalog_narrow_v4`) не втрачає цілей проти повного каталогу v4 на реальному творі; результат — у журналі виконання.

### Перевизначення типу (PR 3)

- `Story.memory_kind_overrides: dict[claim_id, 'core'|'atmosphere']` у payload твору (без SQL-міграції), `PUT /api/stories/{id}/memory-kind` `{claim_id, kind | null, expected_revision}` з CAS на ревізію твору.
- Таблиця пам'яті: колонка «Тип» із перемикачем «авто / ядро / атмосфера»; для слотів ядра — лише «ядро» (неможливо понизити).
- Знімок залежностей brief/draft/edit/rewrite: selector із власником-сценою `scene.memory_kind_overrides` додається **лише тоді, коли контекст цієї версії зібрано з відбором**. Значення — перевизначення для записів, активних у журналі до сцени (обчислює `selector_value` за `owner_id` сцени, як `memory_projection_policy`). Версії без відбору й старі версії selector не мають і від позначок не залежать: їхній запит позначок не враховував. Етап memory selector не отримує: каталог позначок не використовує.
- Статистика сцени (R-18): рядок «Відбір пам'яті: вибрано X з Y, відкинуто Z (шари …)» з `memory_metrics.selection`.

### Інваріанти

- І1. Без переповнення запит байт у байт збігається з поточним (той самий текст, відбиток, `projection_version`).
- І2. Ядро ніколи не обрізається: або воно повністю в запиті, або `ContextOverflow`.
- І3. Відбір не змінює журналів, доказів, MEMORY-FORWARD і підтверджень; лише вирішує, що показати.
- І4. Той самий знімок даних і налаштування → той самий набір `selected_claim_ids`.
- І5. Межі рішень етапу memory завжди збігаються з показаним каталогом.
- І6. Кожен відкинутий запис порахований у `dropped` свого шару; будь-яка відкинута хронологія позначена в тексті запиту.
- І7. Кожен активний запис належить рівно одному шару.
- І8. Позначки типу впливають на застарілість лише версій, зібраних із відбором.

### Сумісність і міграція

Без міграції SQLite. Старі запити й версії не змінюються (І1). Нове `projection_version` лише для запитів із відбором, тож MEMORY-REUSE не плутає їх зі старими. Бенчмарк зберігає наявні стратегії й ключі виводу, додається `product` і `catalog_narrow_v4`.
