# Відбір пам'яті в контекст під бюджет і звужений каталог етапу memory (#60)

Дата: 2026-11-09
Статус: чернетка

## Для власника

**Мета.** Довгий роман (сотні сцен) або модель із малим контекстом більше не впиратимуться в помилку «контекст завеликий» через пам'ять. Коли повна пам'ять не вміщається, застосунок детерміновано відбирає найважливіше й показує, що саме не потрапило в запит. Етап memory отримує звужений каталог і не переповнюється першим.

**Що зміниться для тебе.**
- Поки повна пам'ять вміщається, нічого не змінюється: запити такі самі, як зараз. Для твого основного твору (контекст усіх ролей 262 тис.) відбір зараз не вмикатиметься.
- Коли не вміщається, замість помилки запит іде з відібраною пам'яттю. Ядро героя й відкриті лінії, пов'язані зі сценою, потрапляють завжди. Далі йдуть стани присутніх персонажів, загальні стани, факти про учасників, недавня хронологія, частка «атмосфери» і записи, знайдені за текстом плану й завдання.
- У статистиці сцени видно, що відбір спрацював: скільки записів вибрано з кожного шару і скільки відкинуто через бюджет. Старша хронологія, якої немає в запиті, позначена в самому запиті рядком «Хронологія сцен 1–K не показана (N записів)».
- Якщо не вміщається навіть ядро, лишається явна помилка, як зараз. Ядро ніколи не обрізається.
- Етап memory при переповненні отримує звужений каталог: усе ядро й усі лінії, стани присутніх, загальні стани і до 20 записів, знайдених за прозою сцени. Застосунок попереджає, що каталог звужено.
- У таблиці пам'яті можна позначити запис «завжди показувати» (ядро) або «атмосфера». Позначка впливає лише на відбір під бюджет і робить залежні тексти застарілими, як будь-яка зміна вхідних даних.
- Нічого незворотного: схема бази не змінюється, журнали пам'яті не переписуються.

**На чому стоїть рішення.**
- Ядро — те, порушення чого ламає сюжет; атмосфера — решта; запис може переходити з ядра в атмосферу з часом `[вимога власника, #25]`.
- Підхід — В (структурний відбір + повнотекстовий пошук FTS5) з елементами А; векторний пошук не потрібен `[вимога власника, #25]`.
- Повна секція пам'яті росте ≈ 644 символи на сцену: ≈ 191 тис. на 300 сцен, ≈ 1,93 млн на 3000 `[проба: П1]`.
- На 35 сценах основного твору, які зараз можна виміряти, відбір В досягає того самого recall змінних цілей, що й повна пам'ять (0,933), з меншим обсягом `[проба: П1]`.
- Каталог етапу memory більший за літературну секцію: 23 тис. символів у середньому, максимум 70 тис. Звужений каталог дає −37 % без втрати цілей `[проба: П1]`.
- Основний твір має контекст 262 тис. в усіх ролях, тож відбір там зараз не потрібен. Він потрібен для моделей на 8–80 тис., які вже налаштовано в інших творах (локальна memory на 8 тис., ролі на 24–80 тис.) `[проба: П2]`.
- За консервативною оцінкою токенів (так рахує продукт) на 64 тис. вміщається лише 14 % сцен навіть з відбором. Причина — оцінка решти запиту, а не пам'ять. За реалістичною оцінкою на 64 тис. вміщається все `[проба: П1]`. Ця проблема — поза обсягом (див. рішення 5).
- Ядро героя вже має заміщення станів і перехід дня (#41), а знайомства зроблено в #43. Тож пункти 3 і 4 рекомендації #25 уже виконано для героя `[виведення]`.

**Ключові рішення.**
1. Відбір вмикається лише тоді, коли повний запит не вміщається в бюджет. Відкинуто «завжди відбирати»: він змінив би всі запити й відбитки для творів, яким нічого не загрожує, і без потреби ховав би атмосферу.
2. Старша хронологія поза вікном (20 сцен) відкидається з явним рядком-лічильником у запиті, без підсумків від моделі. Відкинуто підсумки розділів у цьому пакеті: це новий модельний етап, власне походження, інвалідація й інтерфейс перебудови. Окремою задачею.
3. Тип «ядро / атмосфера» за замовчуванням визначається детерміновано з наявних даних (слоти ядра, лінії, свіжість зміни в часі історії), а автор може перевизначити його для окремого запису. Відкинуто тип від етапу memory: це новий дріт v5, новий промпт і платні виклики для перевірки якості.
4. Каталог етапу memory звужується також лише при переповненні, а межі допустимих рішень (`schema_bounds_v4`) звужуються разом із ним. Відкинуто звуження без меж: модель отримувала б право оновити запис, якого не бачить.
5. Поза обсягом і окремими задачами: явні сутності (локації, предмети), строк дії для станів поза слотами, підсумки розділів, калібрування оцінки токенів для ролей без профілю. Відкинуто «все разом»: це XL, кілька специфікацій.
- Розглянуто стандартне: векторний пошук за ембедингами (RAG) — відкинуто, бо пропуск запису не пояснити автору, відтворюваність залежить від версії моделі, а нова локальна залежність — сотні МБ (#25, розділ «Векторний пошук»).
- Розглянуто стандартне: обрізання найстаріших записів (sliding window) — відкинуто, бо губить ядро й стани, змінені після довгої паузи (16 % оновлень стосуються записів, старших за 10 сцен, #25).

**Що стане гірше.**
- Під бюджетом модель не бачить частини пам'яті. Recall змінних цілей на синтетиці падає (0,62 на 300 сценах, 0,27 на 3000 за нижньої межі ядра). Це краще за помилку, але не повна пам'ять.
- Відкинута стара хронологія зникає з запиту без підсумку, доки не з'являться підсумки розділів.
- Звужений каталог етапу memory може не містити запису, який проза змінює. Тоді модель додасть новий запис замість оновлення, і в пам'яті з'явиться дубль.
- Позначки «ядро / атмосфера» — ще одне джерело застарілості залежних текстів.
- Консервативна оцінка токенів і далі блокує моделі на 64 тис. незалежно від пам'яті.
- Збирання контексту при переповненні дорожче: друга оцінка токенів і FTS-індекс у пам'яті. Без переповнення вартість та сама.

**Оцінка.** Власник: L. Автор: L для цього обсягу; повна рекомендація #25 (з сутностями, підсумками розділів і строком дії для всіх станів) — XL. Розподіл: модуль відбору з шарами, бюджетом, FTS5 і лічильниками, підключення в збирання контексту, перенесення бенчмарку на модуль продукту ≈ 40 % (PR 1); звужений каталог етапу memory разом із межами рішень ≈ 25 % (PR 2); перевизначення типу автором у таблиці пам'яті, selector застарілості, статистика сцени ≈ 20 % (PR 3); SPEC.MD, traceability, документація UA/EN ≈ 15 % (розподілено між PR). Три PR. Дешевший варіант — лише PR 1: відбір без звуженого каталогу й без позначок автора (M). Втрачає захист етапу memory, який переповнюється першим, і можливість виправити тип запису.

**Питання до власника.**
1. Відбір лише при переповненні (рішення 1). Згоден, чи хочеш, щоб він працював завжди, навіть коли все вміщається?
2. Стару хронологію поза вікном відкидати з рядком-лічильником, доки немає підсумків від моделі (рішення 2). Прийнятно?
3. Обсяг: сутності, підсумки розділів, строк дії для інших станів і калібрування оцінки токенів — окремими issue (рішення 5). Згоден? Калібрування оцінки найбільше заважає саме зараз на моделях з 64 тис.

## Тіло

### Поточний стан

- `generation/context.py::build_context` для brief/draft/edit/rewrite додає секцію «ЗДІЙСНЕНІ ПОДІЇ — ПЕРЕВІРЕНА ПАМ'ЯТЬ» з `memory/projection.py::project_memory` (ядро відстежуваних, потім факти/стани/лінії/хронологія; стани фільтруються за складом сцени; MEMORY-FORWARD ховає вимкнені записи). `make_context` рахує `token_estimate`, і при `estimate > context_tokens - max_output_tokens` або `chars > max_input_chars` кидає `ContextOverflow` («Текст не обрізано»).
- Етап memory отримує `memory_catalog_v4` (ядро всіх слотів відстежуваних, усі лінії, mutable-стани, immutable факти/хронологія) і `schema_bounds_v4` з `memory/wire_v4.py`.
- Бенчмарк `scripts/memory_bench/strategies.py` уже реалізує шари `core/present/general/threads/facts/timeline/atmosphere/fts`, бюджет (`_Budget`), FTS5 trigram з BM25 і розв'язанням рівних за `claim_id`, чергування атмосфери хешем `scene_id:claim_id` і звужений каталог `catalog_narrow`. Він не знає слотів ядра v4 (`core_size` рахує всі стани героя).
- `Scene.memory_forwarding` і `memory/forwarding.py::projection_policy` — прецедент авторських позначок, що змінюють проєкцію і входять у знімок залежностей як selector `scene.memory_projection_policy`.

### Модуль відбору (PR 1)

`memory/selection.py` — чисті функції без IO; бенчмарк імпортує їх замість власних стратегій (один код для продукту й виміру).

```python
@dataclass(frozen=True)
class SelectionInput:
    journal: MemoryJournal; scene_id: str; scene_number: int; cast: list[str]; tracked: list[str]
    names: dict[str,str]; hidden: set[str]; source_scene_numbers: dict[str,int]
    query_text: str                 # beats плану сцени + brief (якщо є) — для FTS
    kinds: dict[str,Literal['core','atmosphere']]   # перевизначення автора (PR 3), інакше {}
    day_keys: dict[str,str|None]    # day_key сцен для свіжості

def select_memory(inp, budget_tokens, cost) -> MemorySelection
```

Шари в порядку пріоритету (кожен детермінований, усередині шару — за порядком журналу):

1. `core` (обов'язковий): слоти відстежуваних із `project_memory` + записи з перевизначенням `core`. Якщо не вміщається → `CoreOverflow` → `ContextOverflow` із поясненням.
2. `threads`: відкриті лінії, що згадують учасника сцени (основа імен — `name_stems`) або мають `character_ids` ∩ cast.
3. `present`: стани з `character_ids` ∩ cast (крім слотів).
4. `general`: стани без `character_ids`.
5. `facts`: факти, що згадують учасника сцени.
6. `timeline`: записи хронології сцен `≥ scene_number - 20`; для старших — рядок «Хронологія сцен 1–K не показана (N записів)» (рахується у `dropped`).
7. `atmosphere` (квота 10 % бюджету пам'яті): стани героя поза слотами, змінені до поточного дня історії (`day_key` останньої зміни ≠ `day_key` сцени) або позначені автором `atmosphere`; порядок — хеш `sha256(scene_id:claim_id)`.
8. `fts`: решта активних записів (крім хронології), ранжування BM25 по FTS5 trigram за `query_text`, рівні — за `claim_id`.

`MemorySelection{text, selected_claim_ids, layers: dict[str,int], dropped: dict[str,int], timeline_omitted: (K, N) | None}`. Текст рендериться тими самими рядками, що `project_memory` («— …», «Сцена N: …», «ЯДРО СТАНУ — …», суфікс «читачеві невідомо»), лише для вибраних записів.

**Підключення.** `build_context` будує повну проєкцію як зараз. `make_context` отримує `memory_selector`: якщо перша оцінка перевищує ліміт і секція пам'яті є, то `budget = limit - estimate(запит без секції пам'яті) - 1`; вартість рядка — тим самим `token_estimate` профілем ролі (на рядок, із запасом на роздільники, як `_line_cost`); потім друга оцінка повного запиту. Якщо й тоді перевищено → `ContextOverflow` (без обрізання). `memory_metrics` отримує `selection: {layers, dropped, selected_claim_ids, timeline_omitted, budget_tokens}`; `projection_version` → `memory-uk-v3-selected` для запитів із відбором.

**Відтворюваність.** Відбір — функція даних знімка (`ContextView`), налаштувань ролі й перевизначень; FTS-індекс будується в `:memory:` на кожен запит без кешу (CONTEXT-003). Вибрані ID фіксуються в `ContextBundle.memory_metrics`.

### Звужений каталог етапу memory (PR 2)

Якщо запит етапу memory переповнюється, `memory_catalog_v4` будується з `narrow=True`:

- `core` — без змін (усі слоти всіх відстежуваних у складі), `threads` — усі активні лінії (рішення для кожної обов'язкове, тож лінії не звужуються);
- `mutable` — стани присутніх, загальні стани і до 20 станів за BM25 по прозі сцени;
- `immutable` — факти й хронологія, що згадують учасників, і останні 20 сцен хронології.

`schema_bounds_v4` отримує той самий набір mutable claim ID: оновлення запису поза каталогом відхиляється як і зараз для невідомого ID. Попередження в контексті: «Каталог пам'яті звужено: N записів не показано моделі». Якщо не вміщається навіть звужений — `ContextOverflow`.

### Перевизначення типу (PR 3)

- `Story.memory_kind_overrides: dict[claim_id, 'core'|'atmosphere']` у payload твору (без SQL-міграції), `PUT /api/stories/{id}/memory-kind` `{claim_id, kind | null, expected_revision}` з CAS на ревізію твору.
- Таблиця пам'яті: колонка «Тип» із перемикачем «авто / ядро / атмосфера»; для слотів ядра — лише «ядро» (неможливо понизити).
- Знімок залежностей brief/draft/edit/rewrite/memory: selector `story.memory_kind_overrides` — лише записи, активні в журналі до сцени (щоб позначка пізнішого запису не робила застарілими ранні сцени).
- Статистика сцени (R-18): рядок «Відбір пам'яті: вибрано X з Y, відкинуто Z (шари …)» з `memory_metrics.selection`.

### Інваріанти

- І1. Без переповнення запит байт у байт збігається з поточним (той самий текст, відбиток, `projection_version`).
- І2. Ядро ніколи не обрізається: або воно повністю в запиті, або `ContextOverflow`.
- І3. Відбір не змінює журналів, доказів, MEMORY-FORWARD і підтверджень; лише вирішує, що показати.
- І4. Той самий знімок даних і налаштування → той самий набір `selected_claim_ids`.
- І5. Межі рішень етапу memory завжди збігаються з показаним каталогом.
- І6. Кожен відкинутий запис порахований у `dropped` свого шару; стара хронологія позначена в тексті запиту.

### Сумісність і міграція

Без міграції SQLite. Старі запити й версії не змінюються (І1). Нове `projection_version` лише для запитів із відбором, тож MEMORY-REUSE не плутає їх зі старими. Бенчмарк переходить на модуль продукту; його JSON-вивід зберігає ті самі ключі.

### SPEC.MD

- CONTEXT-001: відбір під бюджет замість помилки, ядро як обов'язковий шар, оновлене «Текст не обрізано» → «Ядро не обрізається; відкинуті записи пораховані».
- Новий Requirement MEMORY-SELECT: S01 без переповнення — без змін; S02 шари й порядок; S03 переповнення ядра — помилка; S04 FTS і рівні оцінки; S05 стара хронологія; S06 відтворюваність; S07 звужений каталог і межі; S08 перевизначення типу й застарілість.
- MEMORY-002/CONTEXT-002: посилання на шари; відомі обмеження (дублі при звуженому каталозі, консервативна оцінка токенів).
- traceability: усі S — pytest; таблиця пам'яті — Playwright.

### Тести
