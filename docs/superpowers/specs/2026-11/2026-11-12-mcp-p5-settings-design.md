# MCP, пакет 5: налаштування письма й моделей з чату

Дата: 2026-11-12
Статус: чернетка

Пакет 5 загального дизайну [MCP як пульт Obscura](2026-11-11-mcp-full-toolset-design.md). Спирається на пакети 1, 2, 7 і 4 (18 інструментів після пакета 4).

## Для власника

### Мета

Налаштовувати твір із чату так само, як на сторінці налаштувань: профіль письма (жанр, тон, оповідач, час, правила стилю, обсяг твору), моделі чотирьох ролей (планувальник, письменник, редактор, пам'ять) і застосування збереженого пресета ролей. Ключів провайдерів чат не бачить і не змінює.

### Що зміниться для тебе

- У чаті з'являються три інструменти: `get_settings`, `update_settings`, `apply_role_preset`. Разом їх стає 21.
- `get_settings` показує профіль письма, налаштування кожної ролі, чи є ключ для її провайдера (і де він: змінна середовища чи сховище ключів), список пресетів. Тексти промптів — лише на прохання (`include_prompts`).
- `update_settings` змінює один розділ (письмо або одна роль) і лише ті поля, які чат назвав. Запис іде поверх прочитаного: якщо ти змінив цей розділ після того, як чат його прочитав, запис відхиляється й нічого не змінює. Зміни сцен і назви твору запис не блокують.
- Назву змінної ключа (`key_env`) чат змінити не може: інакше він міг би підставити будь-яку змінну середовища твого комп'ютера, і Obscura надіслала б її значення провайдеру як ключ. Перемикання провайдера бере стандартний ключ нового провайдера.
- `apply_role_preset` спершу показує, що зміниться, і застосовує пресет лише з `confirm=true`. Якщо пресет містить налаштування оцінювача, вони застосовуються теж — так само, як кнопкою.
- Оцінювач і бюджет твору з чату не змінюються: ліміт бюджету — те, що стримує витрати, коли чат змінює модель.
- Відкрита сторінка налаштувань тепер помічає зміни ззовні, коли ти до неї повертаєшся: без незбережених правок вона перезавантажується, з правками — показує «Налаштування змінено ззовні». Це стосується й рейтингу та мови, які чат змінює з пакета 2.
- Ці інструменти грошей не коштують: моделі вони не викликають. Але від вибраної моделі залежить, скільки коштуватиме наступний запуск, який ти зробиш в Obscura.
- **Твої дії:** відповісти на три питання нижче й затвердити специфікацію.

### На чому стоїть рішення

1. Через MCP потрібні налаштування письма й моделей ролей і застосування профілю ролей; ключі недоступні, чат бачить лише ознаку «ключ є / немає» й назву джерела. `[вимога власника]` (загальний дизайн, пакет 5)
2. HTTP API вже є: `GET /api/stories/{id}/settings` (твір, ролі, профіль, промпти, контракти промптів), `PUT /api/stories/{id}/settings` (окремо профіль з обсягом або одна роль), `GET /api/role-profiles`, `POST …/role-profiles/preview|apply`, `GET /api/provider-keys/{name}` (стан ключа без значення). `[проба]` (П1)
3. `PUT` налаштувань перевіряє `story.revision`, а `story.revision` змінюється від будь-якої зміни твору: профілю, мови, нової сцени, назви. `config_revision` змінюється лише від запису ролей. Сторінка налаштувань тому порівнює не ревізію, а вміст розділу (`checkScope`) і надсилає свіжу ревізію. `[проба]` (П2, П3)
4. Сервер приймає в ролі будь-яку назву `key_env` за шаблоном `[A-Z][A-Z0-9_]{2,63}` (`HOME_SECRET_X` → 200), а клієнт провайдера читає значення цієї змінної середовища й надсилає його офіційному endpoint провайдера. Endpoint хмарних провайдерів зафіксований, локального — лише loopback. `[проба]` (П4)
5. Налаштування ролі зберігаються заміною (`INSERT OR REPLACE`), без історії; профіль письма — новою версією `style`. Новий твір не має жодної ролі: перший запис ролі мусить назвати провайдера й модель. `[проба]` (П3, П5)
6. Пресет застосовується через `preview` → `apply` з тією самою ревізією; пресет може містити налаштування оцінювача й тоді змінює і їх. `[проба]` (П6)
7. Сторінка налаштувань завантажує дані при відкритті й на повернення до вкладки не реагує; зміну ззовні вона виявляє лише під час збереження (`checkScope` → помилка). Незбережені правки визначає `hasUnsavedSettings()`. `[проба]` (П7)

### Ключові рішення

1. **Часткове оновлення одного розділу поверх прочитаного.** `update_settings(story_id, section, expected_fingerprint, fields)`, `section ∈ {writing, planner, writer, editor, memory}`. `get_settings` повертає для кожного розділу `fingerprint` — SHA-256 канонічного JSON його вмісту (як `checkScope` сторінки: для `writing` — профіль і обсяг, для ролі — налаштування, промпт, промпт підготовки й контракт). Клієнт перечитує налаштування, порівнює відбиток розділу (розбіжність → помилка без запису), накладає лише передані поля й надсилає повний розділ `PUT` зі свіжою `story.revision`, тож сервер ловить зміну між читанням і записом у тому самому виклику. Відкинуто `expected_revision` твору: після кожної нової сцени чи назви чат мусив би перечитувати налаштування, хоч вони не змінювались.
2. **Поля ролі — плоский перелік.** Поля провайдера (`provider`, `model`, `base_url` лише для `local`, `timeout`, `response_mode`, `include_usage`, `local_disable_thinking`, `venice_include_system_prompt`, `venice_disable_thinking`, `venice_reasoning_effort`) і ролі (`context_tokens`, `max_output_tokens`, `max_input_chars`, `temperature`, `future_plan_mode`, `future_plan_count`, `stop_sequences`, для редактора `edit_mode` і `edit_review`) передаються в одному `fields`, як на формі. Невідоме поле, порожній `fields`, `key_env`, ідентифікатори промптів, `classification` → помилка без запиту. Розділ `writing`: `target_words` і поля `StyleProfile` (`ending_goal`, `genre`, `tone`, `point_of_view`, `tense`, `rules`, `previous_tail_chars`).
3. **`key_env` поза досяжністю чату.** Клієнт ніколи не надсилає `key_env` від чату: бере збережене значення ролі, а при зміні `provider` прибирає його, і сервер ставить стандартний ключ нового провайдера (`OPENROUTER_API_KEY` / `VENICE_API_KEY`). Стан ключа чат бачить як `key: {name, source}` (`source ∈ {env, store, null}`) з `GET /api/provider-keys/{name}`; значення ключа нікуди не повертається. Відкинуто серверну заборону: сторінка дозволяє авторові власну назву змінної (SECURITY-002 зберігає в налаштуваннях саме назву), а загроза — інструмент чату.
4. **Пресет — перегляд, потім застосування.** `apply_role_preset(story_id, profile_id, version, expected_fingerprint, confirm=false)`: `expected_fingerprint` — відбиток ролей з `get_settings` (`roles_fingerprint`, усі чотири ролі); без `confirm` — лише `preview` (що зміниться в кожній ролі й чи є оцінювач), з `confirm=true` — `preview` і `apply` зі свіжою ревізією, як кнопка. Створювати, імпортувати й експортувати пресети чат не може.
5. **Відкрита сторінка налаштувань помічає зміни ззовні** (інваріант 9): на `visibilitychange`/`focus`, не частіше ніж раз на 2 с і без паралельних перевірок, вона читає `GET /api/stories/{id}/settings` і налаштування оцінювача; підпис вмісту (ролі, профіль, промпти, контракти, обсяг, мова, рейтинг, оцінювач — без `revision`) відрізняється від завантаженого → без незбережених правок і збереження сторінка перезавантажується (`location.reload()`, розділ лишається з адреси); інакше — повідомлення «Налаштування змінено ззовні — збережіть свої правки окремо або оновіть сторінку». Рішення — чиста функція з node-тестом. Відкинуто перезавантажувати за ревізією: сторінка перезавантажувалась би від кожної сцени, яку додав чат.

Розглянуто стандартне: JSON Merge Patch (RFC 7396) на сервері — відкинуто з тієї самої причини, що в пакеті 4: злиття робить клієнт поверх наявного маршруту, а новий маршрут дублював би перевірки контрактів промптів.

### Що стане гірше

- Чат може вибрати дорожчу модель для ролі; наступні запуски в Obscura коштуватимуть більше. Стримують ліміт бюджету твору, який чат не змінює, і те, що запуск робиш ти (до пакета 6).
- Налаштування ролей не мають історії (як і з інтерфейсу): попередні значення ролі після зміни з чату видно лише у відповіді інструмента (питання 3).
- Автор, що тримає ключ під власною назвою змінної, після перемикання провайдера з чату отримає стандартну назву; повернути власну можна на сторінці.
- Ще три інструменти (21 з орієнтиру 25); пакетам 3 і 6 лишається 4.

### Оцінка

- Оцінка власника: S.
- Оцінка автора: S — один PR, план із трьох задач. Розбивка: три інструменти клієнта (відбитки розділів, злиття полів, захист `key_env`, перегляд пресета) ~40%; оновлення сторінки налаштувань ззовні з node-тестом ~20%; тести через справжній сервер ~15%; `SPEC.MD`, traceability, сайт `mcp` і `models` двома мовами ~25%.
- Дешевший варіант: без оновлення сторінки налаштувань. Втрачається інваріант 9: відкрита сторінка мовчки тримала б старі значення до помилки збереження, і це вже так для рейтингу й мови з пакета 2.

### Питання до власника

1. **Промпти ролей з чату.** Моя рекомендація: чат читає промпти (`include_prompts`), а змінює їх лише автор на сторінці. Власний промпт керує платними запусками Obscura, має контракт формату відповіді й підтвердження несумісності; вказівка в тексті плану могла б через чат переписати промпт письменника. Альтернатива: дозволити `prompt_text` / `prepare_prompt_text` у `update_settings` з тими самими підтвердженнями контракту, що на сторінці (+1 задача).
2. **Список моделей провайдера.** Моя рекомендація: так, параметром `models_for_role` у `get_settings` — той самий запит, що кнопка «Отримати список моделей» (`POST /api/providers/discover`): для OpenRouter і Venice — запит до офіційного endpoint з ключем (безкоштовний), для локального — до loopback. Чат тоді бачить точні ідентифікатори, контекст і тарифи замість вгадування. Альтернатива: без списку; чат пише назву моделі зі слів автора, помилку покаже лише запуск.
3. **Слід змін з чату.** Моя рекомендація: нового механізму історії не додавати; відповідь `update_settings` і `apply_role_preset` містить попередні й нові значення змінених полів, сторінка показує зміну на поверненні, а перед великою зміною ти можеш зберегти пресет. Альтернатива: перед першим записом ролей з чату клієнт сам зберігає пресет «До змін із чату <дата>» — відкат кнопкою, але пресети накопичуються.

## Технічний опис

### Клієнт `storygen-mcp`

| Інструмент | HTTP | Примітки |
|---|---|---|
| `get_settings(story_id, include_prompts=False)` | `GET /api/stories/{id}/settings`, `GET /api/provider-keys/{key_env}` для кожної налаштованої ролі, `GET /api/role-profiles` | `writing` (`target_words` і поля профілю) з `fingerprint`; `roles` — для кожної з чотирьох ролей `configured`, поля рішення 2, `key` (`name`, `source`), `custom_prompt` (чи є власний промпт), `fingerprint`; `roles_fingerprint`; `presets` (`id`, `name`, версії); з `include_prompts` — тексти промптів налаштованих ролей і промпт підготовки |
| `update_settings(story_id, section, expected_fingerprint, fields)` | той самий `GET`, потім `PUT /api/stories/{id}/settings` | рішення 1–3; для нової ролі обов'язкові `provider` і `model`; відповідь — новий стан розділу з `fingerprint` і `changed` (`поле: [було, стало]`); загальна 422 доповнюється підказкою про допустимі значення |
| `apply_role_preset(story_id, profile_id, version, expected_fingerprint, confirm=False)` | `GET` налаштувань, `POST …/role-profiles/preview`, з `confirm` — `POST …/role-profiles/apply` | рішення 4; `profile_id` — `identifier()`; відповідь — ролі, що змінюються, наявність оцінювача, з `confirm` — `changed` |

- Відбиток розділу клієнт рахує сам із відповіді `GET` (канонічний JSON, `sort_keys`, без пробілів); серверного поля не треба.
- Описи інструментів кажуть, що вони змінюють і що моделі не викликають. `next_steps` не змінюється.

### Сторінка налаштувань

- Обробник `visibilitychange` (сторінка видима) і `focus`, з інтервалом ≥ 2 с і без паралельних запитів, читає налаштування й налаштування оцінювача. Підпис вмісту відрізняється від завантаженого: `hasUnsavedSettings()` хибне й збереження не йде → `location.reload()`; інакше — повідомлення «Налаштування змінено ззовні — збережіть свої правки окремо або оновіть сторінку» («Settings were changed elsewhere — keep a copy of your edits or reload the page»; `i18n`, `textContent`). Після власного збереження сторінка оновлює завантажений підпис, тож своє збереження не вважається зміною ззовні. Помилка мережі тиха.

### Контракт і документація

- MCP-BRIDGE: 21 інструмент; знімається заборона інструментів налаштувань письма й моделей (оцінювач, бюджет, ключі, створення пресетів — і далі ні).
- R21-SETTINGS: оновлення відкритої сторінки налаштувань після змін ззовні. SECURITY-002 не змінюється: значення ключа й далі не передається; додається лише правило, що `storygen-mcp` не передає `key_env` від чату.
- Сценарії (ID сталі):
  - `MCP-BRIDGE-S32` — читання налаштувань: розділи з відбитками, стан ключа без значення, промпти лише з `include_prompts`, пресети;
  - `MCP-BRIDGE-S33` — часткове оновлення розділу лишає інші поля; застарілий відбиток → помилка без запису; нова сцена чи назва твору запис не блокують;
  - `MCP-BRIDGE-S34` — `key_env`, ідентифікатори промптів, `classification`, невідоме поле → відмова без запиту; зміна провайдера бере стандартний ключ нового провайдера;

## Проби

- **П1.** `web/routes_settings.py`: `GET /api/stories/{id}/settings` → `story`, `roles`, `profile`, `prompts`, `prepare_prompt`, `prompt_contracts`, `prepare_prompt_contract`; `PUT` (`SettingsChange`: або `profile`/`target_words`, або `role` + `settings`). `web/routes_role_profiles.py`: `GET /api/role-profiles`, `POST …/preview|apply` (`profile_id`, `version`, `expected_revision`). `web/routes_provider_keys.py`: `GET /api/provider-keys/{name}` → `name`, `source`, `stored`, `store_available`, без значення.
- **П2.** Пробний скрипт на тимчасовому каталозі, нейтральний твір: профіль → `revision` 0→1, `config_revision` 0; мова → 2; нова сцена → 3; назва → 4; `config_revision` увесь час 0.
- **П3.** Той самий скрипт: новий твір — `roles: {}`; запис письменника з `{provider: local, model}` → 200, `config_revision` 1; сервер доповнює `base_url`, `timeout`, `key_env=OPENROUTER_API_KEY`. Промпт письменника за замовчуванням — 562 символи, промпт підготовки — 485.
- **П4.** Той самий скрипт: запис ролі з `key_env=HOME_SECRET_X` → 200. `providers/secrets.py::valid_name` — лише шаблон `[A-Z][A-Z0-9_]{2,63}`; `providers/client.py` бере значення `resolve_key(key_env)` для `openrouter`/`venice`; `ProviderSettings.endpoint` фіксує офіційні endpoint і loopback для `local`.
- **П5.** `storage/settings_store.py::write_role_settings` — `INSERT OR REPLACE INTO role_settings`, історії немає; `authoring/blueprints.py::update_story_profile` зберігає профіль версією `style`.
- **П6.** `role_profiles.py::preview_profile` перевіряє ревізію й повертає ролі, промпти й оцінювача; `apply_profile` повторює `preview` і застосовує ролі й оцінювача.
- **П7.** `static/settings.js::load()` викликається при відкритті й після збереження; `checkScope` порівнює підпис розділу перед збереженням; обробників `focus`/`visibilitychange` немає. `static/settings-workspace.js::hasUnsavedSettings()`.
