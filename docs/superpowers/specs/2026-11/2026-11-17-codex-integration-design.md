### Що зміниться для тебе
Поруч із Claude з’явиться «Підключити до Codex». Кнопка зберігає MCP-налаштування навіть за відсутнього config.toml; це не встановлює сам Codex. Вона вмикає obscura й замінює його HTTP-підключення локальним мостом, зберігши попередню конфігурацію; окрема кнопка «Встановити скіли Codex» доступна лише з робочої копії. Процеси Codex не закриваються: після зміни налаштувань інтерфейс просить відкрити нову сесію або перезапустити клієнт. Кожна фактична зміна має нову резервну копію; копії накопичуються, відновлення й очищення — вручну за інструкцією. Чужі скіли не перезаписуються. Скіли для Store залишаються наступним пакетом після R-39.

### 3. MCP: модуль і запис
Новий src/storygen/codex_connect.py, чисті функції з явно переданими коренями й файловими операціями. Не імпортує глобальний профіль під час завантаження; тестова фікстура забороняє звернення до справжніх Codex/Agents тек.

- target: CODEX_HOME/config.toml або USERPROFILE/.codex/config.toml; не .codex поточного репозиторію. Відносний чи неоднозначний CODEX_HOME відхиляється з поясненням, без вгадування шляху.
- Якщо теки або файла немає, створити їх і мінімальний TOML; резервна копія відсутнього файла не потрібна, результат має backup=null і created=true. Для наявного файла created=false. Відсутність файла — штатний стан missing у GET, не 404. Відмова доступу — помилка без успішного статусу.
- Розібрати TOML Kit; некоректний файл або не-таблиця mcp_servers/obscura — відмова без зміни.
- Команда береться тільки з bridge_command; жодних шляхів, argv, env чи адрес із тіла HTTP-запиту. Для Codex base_url передається як http://127.0.0.1:<request.app.state.settings.port> із перевіреним портом запуску, не request.base_url/Host. Запуск за localhost і 127.0.0.1 дає однаковий запис; Host та його порт не впливають на команду. Не змінювати bridge_command і потік Claude; frozen і desktop launcher зберігають вибір --data-dir.
- Бажаний запис: command, args, enabled=true. Наявні параметри політик інструментів, env, timeouts у obscura зберігаються; замінюються лише command, args і enabled. Конфліктні поля HTTP-транспорту (url, bearer_token_env_var, http_headers, env_http_headers, oauth) прибираються лише в таблиці obscura при переході на stdio. Значення секретів не читаються для відповіді, не логуються, не генеруються й не повертаються клієнту. Невідомі поля зберігаються; несумісність, яку не можна безпечно вирішити, дає відмову.
- Якщо керовані поля вже потрібні, нічого не переписувати й не створювати нову копію.
- До зміни створити унікальну резервну копію вихідних байтів поруч; наявну копію не перезаписувати. Копія містить ті самі приватні налаштування, тому їй не розширюють доступ.
- Серіалізувати й повторно розібрати результат у пам’яті, перевірити керовані поля й незмінність решти семантичних значень. Тимчасовий файл поруч; перед os.replace порівняти актуальні байти з прочитаними. Змінився файл — відмова з проханням повторити. Внутрішній замок серіалізує запити Obscura. Зовнішній редактор не зобов’язаний дотримуватися замка: вузька гонка між останньою звіркою й replace лишається обмеженням.
- Перечитати файл після replace і підтвердити запис. Немає відповідності — помилка; не перезаписувати автоматично можливу зовнішню правку резервною копією.
- Помилка запису/доступу/неправильний TOML: файл не оголошується готовим, показується пояснення й запасна команда. Не ремонтувати TOML регулярними виразами.

Прямий запис забезпечує кнопку без CLI. Можна підготувати конфігурацію до встановлення клієнта; факт файла не доводить, що Codex встановлено. Запасна команда codex mcp add obscura -- ... формується з фіксованих даних сервера з коректним PowerShell quoting (включно з апострофами), показується через textContent і копіюється, але не виконується оболонкою.

### 4. Генератор і встановлення
Новий src/storygen/codex_skills.py і тонкий CLI scripts/install_codex_skills.py. 4. Підтверджені клієнтські фрази «Claude», «Connect Claude» і AskUserQuestion адаптувати до Codex, «Підключити до Codex» та доступного засобу запитань із текстовим fallback. Не підміняти назви моделей у recipes.md: це моделі ролей Obscura, а не клієнта.

6. Секцію Model у start-story (включно з /model, Advisor і обома клієнтами Claude) та секцію Model routing з її Claude-обґрунтуванням у chat-pipeline.md замінити явними Codex-адаптерами: планування й усі етапи — поточна сесія; модель, субагентів і тариф автоматично не змінювати; не заявляти доведеної якості.
7. Для кожної структурної заміни перевірити очікувану кількість входжень/межі секції. Невідома структура, залишок CLAUDE_PLUGIN_ROOT, клієнтських команд Claude чи нерозв’язане посилання — генерація відмовляє до будь-якого встановлення. Не забороняти слово claude у рецептах провайдерів.

Підготувати всі п’ять тек у staging до зміни цілі. Staging — Roots.userprofile/.agents/obscura-staging/<operation-id>, копії скілів — Roots.userprofile/.agents/obscura-backups/<operation-id>: поза сканованим skills/, на тому самому томі. Жодних staging/backup із SKILL.md у корені ~/.agents/skills чи тестовому repo/.agents/skills, включно із залишками partial. У кожній встановленій теці — .obscura-install.json із версією генератора, хешами джерел і переліком/хешами результату; без матеріалів творів, ключів і абсолютних шляхів автора.
- Порожня ціль: установка.
- Той самий результат: unchanged, без запису.
- Попередня керована версія без локальних змін: оновити з унікальною резервною копією.
- Чужа тека, відсутній/некоректний маніфест, локальна зміна або доданий користувачем файл: відмова всього пакета до замін; назвати конфлікт, не стирати й не пропонувати автоматичний force.
- Замок установника, перевірка вмісту перед замінами, контрольовані rename. За відмови посеред установки відкотити лише власні зміни, які ще точно відповідають записаному в цій операції. Якщо це неможливо через зовнішню зміну — повернути partial, перелік установленого/відновленого й розташування копій. Не називати операцію атомарною для всіх п’яти тек.
- Повторне читання всіх установлених файлів перед станом installed. Маніфест сам по собі не є доказом.
- Видалення скілів: документована ручна дія лише для п’яти obscura-* тек; автоматичне видалення у цьому пакеті не додається.

Розглянуто стандартне: junction/symlink на згенерований вихід — відкинуто: потрібна стала друга тека, Windows reparse-переходи, а захист локальних правок і оновлення виходу лишаються. Самодостатні встановлені теки не залежать від подальшого існування checkout/worktree. Розглянуто стандартне: codex plugin add — --help підтверджує команду, живого встановлення не перевіряли. Відхилення спирається на вибір власника прямого встановлення, не на заяву, що плагіни не працюють.

### 5. UI і маршрути
Додатковий модуль маршрутів routes_codex_connect.py, підключений в app.py. Існуючі Claude endpoints, DOM-обробники й тести не переробляються.
- GET /api/connect/codex/status: наявність/відповідність керованих MCP-полів, доступність джерел скілів у checkout, версія встановлення або конфлікт, стан missing для відсутньої конфігурації; без повного TOML і env.
- POST /api/connect/codex: зберегти MCP-запис.
- POST /api/connect/codex/skills: згенерувати й установити пакет із фіксованого checkout.
- JSON-відповіді з розділеними результатами configured/unchanged/failed для MCP і installed/unchanged/conflict/partial/unsupported для скілів. Відповідні HTTP-коди: 200, конфлікт 409, некоректна конфігурація 422, помилка доступу 500, недоступні джерела 409. Внутрішні винятки не показують секретів або трасування.
- Порожнє тіло; дані запиту не впливають на файлові шляхи чи процеси. Захист /api/connect/* лишається в middleware; для codex-префікса він повертає окрему константу «Підключення до Codex виконує лише автор в Obscura», не змінюючи текст Claude. Обидва нові POST внесено в long_prose_guard.ALLOWED з причиною «налаштування застосунку, не твору»; тест повноти маршрутів їх перевіряє; перевірки 403 включають GET від моста та POST від моста/стороннього Origin до нових шляхів і доводять відсутність побічних дій.
- В одному блоці бібліотеки — самостійний Codex-підблок із власними data-атрибутами, aria-live і JS-модулем; не додавати невідомий data-connect до наявного обробника Claude.
- Після MCP: «Налаштування Codex збережено. Відкрийте нову сесію або перезапустіть Codex». Не «Codex підключено»: файл не підтверджує живого MCP.
- Після скілів: перелік п’яти встановлених назв і порада оновити сесію, якщо вони не з’явилися. Часткову відмову не приховувати загальним success.
- Store: MCP доступний; установка скілів неактивна з поясненням про майбутній пакет. Жодного пошуку текстів у пакеті R-39.
- Повні переклади uk/en; keyboard, disabled під час дії, long paths, помилки й повторний клік перевіряються на нейтральному UI.

### 6. Перевірка і майбутній контракт
У реалізації розширити STORE-MCP-001 новими стабільними сценаріями STORE-MCP-S12 (Codex-конфігурація) і STORE-MCP-S13 (захист і UI-стани) та додати CODEX-SKILLS із CODEX-SKILLS-S01…S05. Перед внесенням звірити зайняті ID у main; тут це зарезервовані пропозиції, не чинні Scenario.

| Майбутній сценарій | Запланований доказ |
|---|---|
| STORE-MCP-S12 | tests/test_codex_connect.py: новий/незмінний/змінений TOML, збереження чужих значень і коментарів, malformed, stdio замість HTTP, disabled, резервні копії, відмова доступу, конкурентна зміна, quoting |
| STORE-MCP-S13 | tests/test_codex_connect_web.py: маршрути, відмова моста й Origin до дій, відсутність даних запиту в шляхах; browser tests підблока й помилок |
| CODEX-SKILLS-S01 | tests/test_codex_skills.py: рівно п’ять переносних скілів, вбудовані правила, усі посилання існують, незмінність джерел, відсутність клієнтських залишків Claude |
| CODEX-SKILLS-S02 | той самий файл: повторна установка й оновлення, реальний вміст проти маніфесту, чужа тека/правка, backup, збої й partial |
| CODEX-SKILLS-S03 | структурна звірка інструментів/полів із MCP; адаптер усіх чотирьох етапів не називає Claude-моделі та не запускає субагентів |
| CODEX-SKILLS-S04 | ручна процедура: окремий тимчасовий CODEX_HOME, fixture repo/.agents/skills і нейтральний list_stories в обох клієнтах; окремо user-scope на одноразовому профілі; без моделі |
| CODEX-SKILLS-S05 | Store показує недоступність установки скілів, але дозволяє зберегти MCP; ні джерела, ні файли пакування не змінено |

Кожен фактично доданий Scenario отримує traceability із конкретними іменами тестів або деталізованою ручною процедурою та причиною ручної перевірки. Структурні тести не замінюють літературного виміру чи живої поведінки моделі. Без окремого дозволу не запускати codex exec, оцінювачі чи платні сценарії. Ручний виклик MCP напряму через протокол/діагностику клієнта не потребує моделі. CODEX_HOME сам по собі не ізолює користувацькі скіли: discovery перевіряти через тимчасовий fixture-репозиторій C:\tmp\...\repo/.agents/skills, а установник — з ін’єкцією Roots.userprofile у C:\tmp. Запустити обидва клієнти з тим самим тимчасовим CODEX_HOME; спершу довести, що вони використовують саме цей профіль. Якщо клієнт не дає ізоляції, не підміняти її записом у справжній профіль: зафіксувати неперевірений критерій і повернути питання власнику до злиття. Пряме user-scope discovery перевіряти окремо на одноразовому профілі ОС/тестовому хості з домашньою текою у C:\tmp. Без такого середовища не заявляти повної підтримки user-scope. Це заплановані критерії, зараз вони не виконані.

TDD для коду в ізольованому worktree C:\tmp; реальні ~/.codex і ~/.agents не використовуються навіть якщо тест запущено без параметрів: автоматична фікстура підміняє всі корені та обмежує subprocess. Старі тести Claude проходять без правок очікувань.

Після реалізації: check_site.py --rehash mcp, check_docs.py, verify.py з потрібним повним набором; фактичний прогін записується у docs/STATUS.md. Залежність TOML Kit перевіряється import, round-trip fixture, ліцензійним gate й пробним заморожуванням Store за чинною процедурою після координації з R-39, без зміни файлів пакування. Це критерій до злиття реалізації: без успішної перевірки не оголошувати кнопку Store готовою; повернути питання власнику, а не прийняти неперевірену збірку як готовий результат.

### 7. Документація, етапність і доставка
Сторінки docs/site/{uk,en}/mcp.md пояснюють: Store — obscura-mcp.exe, checkout — storygen-mcp.exe у .venv; кнопка, ручна команда, установка/оновлення скілів, відмова при локальних правках, перезапуск, джерела й обмеження Store. Пояснити створення конфігурації до встановлення Codex, ввімкнення obscura й заміну HTTP на stdio. Для скасування закрити клієнт і вручну відновити названу копію, спершу узгодивши пізніші сторонні зміни, або прибрати лише запис obscura. Для скілів назвати п’ять точних тек видалення, копії для відновлення й безпечне ручне очищення backup/staging поза сканованим коренем; автоматично нічого не видаляти. Нейтральні приклади без робочих творів. Нові знімки потрібні лише якщо чинна сторінка показує змінений блок; обидві мови перевірити разом.

До затвердження — лише цей дизайн і журнал, docs-only PR на main. Сайт, кореневу SPEC і продуктовий код не змінювати наперед.
Після затвердження — детальний план основи: (1) TOML-конфігурація; (2) генератор; (3) керована установка й ізольований CLI; (4) цілісна перевірка основи. Це межі майбутніх задач, а не дозвіл на реалізацію.
Після виконання основи й цілісного рев’ю написати окремий план периферії за реальним API основи: маршрути/UI, сайт, SPEC/traceability, повний gate й доставка. Не вигадувати зараз точні сигнатури ще не реалізованого механізму.

Результат зберігати комітом, push і PR виключно на main. Перед синхронізацією основної теки перевірити локальні зміни й перетини; зберегти авторські файли й конфігурацію. Без reset --hard/clean. Злиття PR реалізації та оновлення основної теки — після перевірок і явного дозволу на реалізацію; факт цього дизайну не є дозволом писати код.

### 8. Заявка → доказ

| Заявка | Де записується | Що доводить | Сила / межа |
|---|---|---|---|
| MCP-налаштування збережено | результат configured/status | повторний parse файла і точне порівняння command, args, enabled | сильна для файла, не для клієнта |
| Запис уже потрібний | unchanged | прочитаний актуальний файл, не кеш попереднього POST | сильна для файла |
| Наявна резервна копія | результат backup | фактичний файл із байтами попередньої конфігурації | сильна, не обіцянка відновлення чужих паралельних правок |
| Пакет скілів сформовано | staging | inventory, валідні шляхи, правила, структура й контрольні суми всіх файлів | структурна; не якість текстів |

| Локальні зміни захищені | conflict/partial | порівняння реальних файлів із останнім керованим результатом | сильна на момент звірки, зовнішні гонки можливі |

| Cross-review виконано | заголовок і таблиця нижче | звіт CLI, прив’язаний до коміту | не прирівнюється до затвердження власником |
