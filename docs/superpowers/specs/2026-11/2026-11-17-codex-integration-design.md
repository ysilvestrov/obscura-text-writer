# Підключення Obscura до Codex і встановлення скілів

Дата: 2026-11-17
Статус: чернетка
Spec-review: ще не виконано

## Для власника

### Мета
Автор підключає локальну Obscura до Codex кнопкою в бібліотеці. Із робочої копії він також встановлює п’ять скілів, які ведуть від задуму до експорту книжки, без ручного копіювання текстів.

### Що зміниться для тебе
Поруч із Claude з’явиться «Підключити до Codex». Кнопка зберігає MCP-налаштування; окрема кнопка «Встановити скіли Codex» доступна лише з робочої копії. Процеси Codex не закриваються: після зміни налаштувань інтерфейс просить відкрити нову сесію або перезапустити клієнт. Зміни конфігурації мають резервні копії; чужі скіли не перезаписуються. Скіли для Store залишаються наступним пакетом після R-39.

### На чому стоїть рішення
- [вимога власника] Бріф від 17.11.2026: обидва клієнти Codex, та сама команда моста, один комплект джерел скілів, без змін джерел Claude і файлів пакування, без викликів моделей.
- [вимога власника] У чаті 17.11.2026 обрано генератор і пряме встановлення скілів; оцінка власника M.
- [проба] П1–П2: CLI 0.166.0 працює з MCP у TOML; офіційна документація описує спільну конфігурацію локальних клієнтів. Одна дія обслуговує клієнти з тим самим профілем конфігурації.
- [проба] П3–П4: Codex підтримує SKILL.md; поточні джерела потребують адаптації шляхів, назви клієнта, запитань та інструкцій щодо моделей.
- [виведення] Без окремого виміру не можна переносити висновки про Sonnet/Opus на Codex; усі чотири етапи виконує поточна сесія.

### Ключові рішення
1. Записувати лише таблицю mcp_servers.obscura через TOML Kit; додати tomlkit>=0.13,<1 до extra web. Зберігати решту документа, коментарі та інші сервери. Розглянуто стандартне: codex mcp add — відкинуто як обов’язковий шлях кнопки, бо застосунок може бути встановлений без доступного CLI, а наявний запис команда замінює повністю (П1). Ручна команда залишається запасним способом.
2. Встановлювати самодостатні скіли у користувацьку ~/.agents/skills з назвами obscura-start-story, obscura-draft-scene, obscura-publish, obscura-series-bible, obscura-setup-models. Генерація з джерел Claude під час встановлення, без ручних копій. Розглянуто стандартне: плагін Codex — власник обрав пряме встановлення; маркетплейс і його стан не потрібні для цього пакета.
3. Спільні правила вбудовувати в кожен SKILL.md; посилання на довідкові файли робити відносними до файла, який їх містить. Відкинуто прямий symlink на джерела Claude: він залишив би інструкції Claude та змінні плагіна.
4. Перша кнопка змінює лише MCP; встановлення скілів — окрема явна дія в тому самому блоці. У Store пояснюється, що скіли ще недоступні цією кнопкою. Відкинуто автоматичну установку всього: вона приховала б ширший запис у профіль автора.
5. Модельний маршрут Codex — поточна сесія для всіх етапів, без автоматичного перемикання моделі чи субагентів. Відкинуто механічну заміну назв Claude на назви GPT: немає доказів еквівалентності якості та вартості.

### Що стане гірше
Додається невелика залежність TOML Kit. Генератор залежить від структури джерел Claude: невідома зміна має зупиняти генерацію, а не випускати неповний скіл. Пряме встановлення потребує повторної дії після оновлення джерел; немає маркетплейсного автооновлення. Проза та якість виконання скілів Codex у цьому пакеті не вимірюються. Перевірений файл конфігурації ще не доводить роботу MCP у відкритому клієнті.

### 2. Проби до специфікації

**П1 — CLI та формат конфігурації.** 17.11.2026, Windows, codex-cli 0.166.0. Виявлено CLI в LocalAppData/Programs/OpenAI/Codex/bin та resources установленого застосунку OpenAI.Codex_26.1111.2228.0. Наявність executable — не перевірка встановлення на іншому комп’ютері.

Окреме середовище CODEX_HOME=C:\tmp\obscura-codex-probe-20261117; справжній config.toml не читався й не змінювався пробою.
Команди:
- codex mcp add obscura -- "C:\Program Files\Obscura\obscura-mcp.exe" --data-dir "C:\tmp\neutral library"
- codex mcp get obscura --json
- codex mcp remove obscura
- codex mcp get obscura --json

Результати: «Added global MCP server 'obscura'.»; JSON: name=obscura, enabled=true, transport.type=stdio, command і args точно відповідають argv. TOML: [mcp_servers.obscura], command і args з коректними Windows-шляхами та пробілами. Після remove: «Removed global MCP server 'obscura'.», наступний get — помилка «No MCP server named 'obscura' found.» Міст і модель не запускалися.

Друга проба додала нейтральний model, інший сервер і старий obscura з enabled=false: add зберіг інший сервер, model і верхній коментар, замінив obscura та прибрав enabled=false. Отже для ідемпотентності недостатньо одного exit code.

Першу спробу створення C:\tmp заблокувала пісочниця; повтор із дозволом на ізольований шлях пройшов. Виклики --help без ізоляції друкували попередження про заборону службових tmp/arg0 у справжньому CODEX_HOME; реєстрацій там не виконувалось. Усі подальші прогони мають явно задавати тимчасові профілі.

**П2 — конфігурація застосунку й CLI.** Офіційна [документація MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli), перевірено 17.11.2026, описує ~/.codex/config.toml, проектний .codex/config.toml лише для довірених проєктів і спільні налаштування локальних клієнтів. Користувацьку теку визначає CODEX_HOME, якщо задано, інакше USERPROFILE/.codex. Проєктні та керовані налаштування можуть перевизначити користувацький запис; кнопка їх не змінює й не обходить. Живе перечитування конфігурації відкритим застосунком не перевірялося; потрібна ручна перевірка на нейтральному профілі.

**П3 — скіли та плагіни.** Офіційні [Build skills](https://learn.chatgpt.com/docs/build-skills) і [Package your plugin](https://developers.openai.com/plugins/build/plugins), перевірено 17.11.2026: skill — тека з SKILL.md, обов’язкові name і description; локальні теки ~/.agents/skills і .agents/skills у репозиторії; підтримуються symlink. Оновлення зазвичай підхоплюються автоматично, інакше потрібен перезапуск. Вбудований skill-installer — інструкція агенту, а не доведена команда codex skills install. Плагіни підтримуються: переносний plugin.json і skills/, або сумісний .codex-plugin/plugin.json; маркетплейс — окремий механізм. Ізольований --help поточного CLI додатково показав plugin add/remove/list і plugin marketplace add/list/upgrade/remove. Встановлення плагіна не виконувалося.

У документації плагінів PLUGIN_ROOT, PLUGIN_DATA та сумісні CLAUDE_PLUGIN_ROOT/CLAUDE_PLUGIN_DATA описані для процесів hooks. Це не доказ підстановки змінної в текст SKILL.md. Еквівалент для довільного тексту скіла не підтверджений; дизайн його не потребує.

### 3. MCP: модуль і запис
Новий src/storygen/codex_connect.py, чисті функції з явно переданими коренями й файловими операціями. Не імпортує глобальний профіль під час завантаження; тестова фікстура забороняє звернення до справжніх Codex/Agents тек.

- target: CODEX_HOME/config.toml або USERPROFILE/.codex/config.toml; не .codex поточного репозиторію. Відносний чи неоднозначний CODEX_HOME відхиляється з поясненням, без вгадування шляху.
- Розібрати TOML Kit; некоректний файл або не-таблиця mcp_servers/obscura — відмова без зміни.
- Команда береться тільки з bridge_command; жодних шляхів, argv, env чи адрес із тіла HTTP-запиту.
- Бажаний запис: command, args, enabled=true. Наявні параметри політик інструментів, env, timeouts у obscura зберігаються; замінюються лише command, args і enabled. Конфліктні поля HTTP-транспорту (url, bearer_token_env_var, http_headers, env_http_headers, oauth) прибираються лише в таблиці obscura при переході на stdio. Значення секретів не читаються для відповіді, не логуються, не генеруються й не повертаються клієнту. Невідомі поля зберігаються; несумісність, яку не можна безпечно вирішити, дає відмову.
- Якщо керовані поля вже потрібні, нічого не переписувати й не створювати нову копію.
- До зміни створити унікальну резервну копію вихідних байтів поруч; наявну копію не перезаписувати. Копія містить ті самі приватні налаштування, тому їй не розширюють доступ.
- Серіалізувати й повторно розібрати результат у пам’яті, перевірити керовані поля й незмінність решти семантичних значень. Тимчасовий файл поруч; перед os.replace порівняти актуальні байти з прочитаними. Змінився файл — відмова з проханням повторити. Внутрішній замок серіалізує запити Obscura. Зовнішній редактор не зобов’язаний дотримуватися замка: вузька гонка між останньою звіркою й replace лишається обмеженням.
- Перечитати файл після replace і підтвердити запис. Немає відповідності — помилка; не перезаписувати автоматично можливу зовнішню правку резервною копією.
- Помилка запису/доступу/неправильний TOML: файл не оголошується готовим, показується пояснення й запасна команда. Не ремонтувати TOML регулярними виразами.

Прямий запис забезпечує кнопку без CLI. Запасна команда codex mcp add obscura -- ... формується з фіксованих даних сервера з коректним PowerShell quoting (включно з апострофами), показується через textContent і копіюється, але не виконується оболонкою.

### 4. Генератор і встановлення
Новий src/storygen/codex_skills.py і тонкий CLI scripts/install_codex_skills.py. Джерело — integrations/claude/obscura, визначене сервером із кореня робочої копії; довільного source або destination у вебзапиті немає. Окремий параметр --output CLI дозволяє збирати пакет у тестову теку без встановлення; --install використовує визначений користувацький корінь. Проби й тести завжди явно вказують тимчасові корені у C:\tmp.

Перетворення детерміновані:
1. Рівно п’ять відомих скілів; усі посилання мають вести всередину джерела. Упакувати лише SKILL.md і потрібні references, без evals і виконуваних файлів.
2. Зберегти description, переносні metadata; name перетворити на obscura-<name>. Явні звернення між скілами адаптувати до цих назв.
3. Замість початкового посилання на shared/rules.md вбудувати його зміст рівно один раз у кожний SKILL.md.
4. Підтверджені клієнтські фрази «Claude», «Connect Claude» і AskUserQuestion адаптувати до Codex, «Підключити до Codex» та доступного засобу запитань із текстовим fallback. Не підміняти назви моделей у recipes.md: це моделі ролей Obscura, а не клієнта.
5. Усі CLAUDE_PLUGIN_ROOT-посилання перетворити на локальні відносні посилання з явною вказівкою рахувати від теки поточного файла. Довідкові файли копіюються з тією самою семантикою.
6. Секцію Model routing і її Claude-обґрунтування замінити невеликим Codex-адаптером: усі етапи — поточна сесія; модель, субагентів і тариф автоматично не змінювати; не заявляти доведеної якості.
7. Для кожної структурної заміни перевірити очікувану кількість входжень/межі секції. Невідома структура, залишок CLAUDE_PLUGIN_ROOT, клієнтських команд Claude чи нерозв’язане посилання — генерація відмовляє до будь-якого встановлення. Не забороняти слово claude у рецептах провайдерів.

Підготувати всі п’ять тек у staging до зміни цілі. У кожній встановленій теці — .obscura-install.json із версією генератора, хешами джерел і переліком/хешами результату; без матеріалів творів, ключів і абсолютних шляхів автора.
- Порожня ціль: установка.
- Той самий результат: unchanged, без запису.
- Попередня керована версія без локальних змін: оновити з унікальною резервною копією.
- Чужа тека, відсутній/некоректний маніфест, локальна зміна або доданий користувачем файл: відмова всього пакета до замін; назвати конфлікт, не стирати й не пропонувати автоматичний force.
- Замок установника, перевірка вмісту перед замінами, контрольовані rename. За відмови посеред установки відкотити лише власні зміни, які ще точно відповідають записаному в цій операції. Якщо це неможливо через зовнішню зміну — повернути partial, перелік установленого/відновленого й розташування копій. Не називати операцію атомарною для всіх п’яти тек.
- Повторне читання всіх установлених файлів перед станом installed. Маніфест сам по собі не є доказом.
- Видалення скілів: документована ручна дія лише для п’яти obscura-* тек; автоматичне видалення у цьому пакеті не додається.

### 5. UI і маршрути
Додатковий модуль маршрутів routes_codex_connect.py, підключений в app.py. Існуючі Claude endpoints, DOM-обробники й тести не переробляються.
- GET /api/connect/codex/status: наявність/відповідність керованих MCP-полів, доступність джерел скілів у checkout, версія встановлення або конфлікт; без повного TOML і env.
- POST /api/connect/codex: зберегти MCP-запис.
- POST /api/connect/codex/skills: згенерувати й установити пакет із фіксованого checkout.
- JSON-відповіді з розділеними результатами configured/unchanged/failed для MCP і installed/unchanged/conflict/partial/unsupported для скілів. Відповідні HTTP-коди: 200, конфлікт 409, некоректна конфігурація 422, помилка доступу 500, недоступні джерела 409. Внутрішні винятки не показують секретів або трасування.
- Порожнє тіло; дані запиту не впливають на файлові шляхи чи процеси. Захист /api/connect/* лишається в middleware; перевірки 403 включають GET від моста та POST від моста/стороннього Origin до нових шляхів і доводять відсутність побічних дій.
- В одному блоці бібліотеки — самостійний Codex-підблок із власними data-атрибутами, aria-live і JS-модулем; не додавати невідомий data-connect до наявного обробника Claude.
- Після MCP: «Налаштування Codex збережено. Відкрийте нову сесію або перезапустіть Codex». Не «Codex підключено»: файл не підтверджує живого MCP.
- Після скілів: перелік п’яти встановлених назв і порада оновити сесію, якщо вони не з’явилися. Часткову відмову не приховувати загальним success.
- Store: MCP доступний; установка скілів неактивна з поясненням про майбутній пакет. Жодного пошуку текстів у пакеті R-39.
- Повні переклади uk/en; keyboard, disabled під час дії, long paths, помилки й повторний клік перевіряються на нейтральному UI.

### 6. Перевірка і майбутній контракт
У реалізації розширити STORE-MCP-001 новими стабільними сценаріями STORE-MCP-S12 (Codex-конфігурація) і STORE-MCP-S13 (захист і UI-стани) та додати CODEX-SKILLS із CODEX-SKILLS-S01…S05. Перед внесенням звірити зайняті ID у main; тут це зарезервовані пропозиції, не чинні Scenario.

| Майбутній сценарій | Запланований доказ |
|---|---|
| STORE-MCP-S12 | tests/test_codex_connect.py: новий/незмінний/змінений TOML, збереження чужих значень і коментарів, malformed, stdio замість HTTP, disabled, резервні копії, відмова доступу, конкурентна зміна, quoting |
| STORE-MCP-S13 | tests/test_codex_connect_web.py: маршрути, відмова моста й Origin до дій, відсутність даних запиту в шляхах; browser tests підблока й помилок |
| CODEX-SKILLS-S01 | tests/test_codex_skills.py: рівно п’ять переносних скілів, вбудовані правила, усі посилання існують, незмінність джерел, відсутність клієнтських залишків Claude |
| CODEX-SKILLS-S02 | той самий файл: повторна установка й оновлення, реальний вміст проти маніфесту, чужа тека/правка, backup, збої й partial |
| CODEX-SKILLS-S03 | структурна звірка інструментів/полів із MCP; адаптер усіх чотирьох етапів не називає Claude-моделі та не запускає субагентів |
| CODEX-SKILLS-S04 | ручна процедура на ізольованому профілі: клієнти бачать п’ять скілів і list_stories нейтрального стенда; без генерації тексту моделлю |
| CODEX-SKILLS-S05 | Store показує недоступність установки скілів, але дозволяє зберегти MCP; ні джерела, ні файли пакування не змінено |

Кожен фактично доданий Scenario отримує traceability із конкретними іменами тестів або деталізованою ручною процедурою та причиною ручної перевірки. Структурні тести не замінюють літературного виміру чи живої поведінки моделі. Без окремого дозволу не запускати codex exec, оцінювачі чи платні сценарії. Ручний виклик MCP напряму через протокол/діагностику клієнта не потребує моделі.

TDD для коду в ізольованому worktree C:\tmp; реальні ~/.codex і ~/.agents не використовуються навіть якщо тест запущено без параметрів: автоматична фікстура підміняє всі корені та обмежує subprocess. Старі тести Claude проходять без правок очікувань.

Після реалізації: check_site.py --rehash mcp, check_docs.py, verify.py з потрібним повним набором; фактичний прогін записується у docs/STATUS.md. Установлена залежність TOML Kit перевіряється import і збиранням за чинною процедурою після координації з R-39, без зміни файлів пакування. Якщо Store-збірку не виконано, це явно зазначається як неперевірене обмеження.

### 7. Документація, етапність і доставка
Сторінки docs/site/{uk,en}/mcp.md пояснюють: Store — obscura-mcp.exe, checkout — storygen-mcp.exe у .venv; кнопка, ручна команда, установка/оновлення скілів, відмова при локальних правках, перезапуск, джерела й обмеження Store. Нейтральні приклади без робочих творів. Нові знімки потрібні лише якщо чинна сторінка показує змінений блок; обидві мови перевірити разом.

До затвердження — лише цей дизайн і журнал, docs-only PR на main. Сайт, кореневу SPEC і продуктовий код не змінювати наперед.
Після затвердження — детальний план основи: (1) TOML-конфігурація; (2) генератор; (3) керована установка й ізольований CLI; (4) цілісна перевірка основи. Це межі майбутніх задач, а не дозвіл на реалізацію.
Після виконання основи й цілісного рев’ю написати окремий план периферії за реальним API основи: маршрути/UI, сайт, SPEC/traceability, повний gate й доставка. Не вигадувати зараз точні сигнатури ще не реалізованого механізму.

Результат зберігати комітом, push і PR виключно на main. Перед синхронізацією основної теки перевірити локальні зміни й перетини; зберегти авторські файли й конфігурацію. Без reset --hard/clean. Злиття PR реалізації та оновлення основної теки — після перевірок і явного дозволу на реалізацію; факт цього дизайну не є дозволом писати код.

### 8. Заявка → доказ

| Заявка | Де записується | Що доводить | Сила / межа |
|---|---|---|---|
| MCP-налаштування збережено | результат configured/status | повторний parse файла і точне порівняння command, args, enabled | сильна для файла, не для клієнта |
| Запис уже потрібний | unchanged | прочитаний актуальний файл, не кеш попереднього POST | сильна для файла |
| Наявна резервна копія | результат backup | фактичний файл із байтами попередньої конфігурації | сильна, не обіцянка відновлення чужих паралельних правок |
| Пакет скілів сформовано | staging | inventory, валідні шляхи, правила, структура й контрольні суми всіх файлів | структурна; не якість текстів |
| Скіли встановлено | installed/status | перечитано п’ять цільових тек і звірено з результатом генерації | сильна для диска, не для discovery відкритої сесії |
| Локальні зміни захищені | conflict/partial | порівняння реальних файлів із останнім керованим результатом | сильна на момент звірки, зовнішні гонки можливі |
| Клієнт бачить MCP і скіли | ручна процедура | список скілів і успішний нейтральний list_stories у кожному клієнті | лише для перевірених версій/профілів |
| Перевірки пройшли | docs/STATUS.md | реальний verify.py, argv, SHA і JUnit | лише для наведеного прогону |
| Cross-review виконано | заголовок і таблиця нижче | звіт CLI, прив’язаний до коміту | не прирівнюється до затвердження власником |
