## Для власника

**Мета.** Відбір пам'яті для сцени має знаходити лінії, факти й події хронології за тим, хто в них бере участь і де вони відбуваються, а не за збігом імені в тексті. Це має працювати й для книг, пам'ять яких уже побудована, без переписування записів.

**Що зміниться для тебе.**
- Нова пам'ять записуватиме учасників ліній, фактів і хронології автоматично, нічого робити не треба.
- **Стара пам'ять** отримує учасників і локації окремою дією «Розмітити сутності пам'яті». Вона йде моделлю ролі «Пам'ять» з переглядом вартості й твоєю згодою, або з чату через MCP без оплати моделей Obscura. Тексти записів не змінюються. Результат застосовується одразу, його можна виправити в таблиці пам'яті поштучно або скасувати весь.
- Коли пам'ять не вміщається в запит, у відбір повертаються старі події хронології (старші за 20 сцен), у яких бере участь хтось зі сцени, крім головного героя, або які відбуваються в цьому місці.
- **Наслідок для вже написаного:** застосування, правка чи скасування розмітки робить застарілими брифи, чернетки й пам'ять тих сцен, чий запит був зібраний із відбором пам'яті чи звуженим каталогом і чиї кандидати отримали інші сутності, так само як позначки ядра/атмосфери. Сцени, запит яких уміщав повну пам'ять, не зачіпаються. Застарілі матеріали видно в робочому просторі; перегенерація оплачується, як звичайно.
- **Незворотно:** книгу з новими полями старіша версія Obscura не відкриє. Повернутися можна лише з резервної копії, як після локацій.

**На чому стоїть рішення.**
- Предмети (#262) не входять, це окрема специфікація. `[вимога власника]`
- Старі записи дозаповнюються моделлю й через чат, без зміни їхніх текстів. `[вимога власника]`
- Стара хронологія береться за сутностями. `[вимога власника]`
- Стани вже мають явних персонажів (162 з 163 в основному творі). Лінії, факти й хронологія не мають жодних (0 з 350), і відбір шукає їх за основами імен. `[проба]` (§1.1)
- Пам'ять основного твору побудована до локацій: 0 з 513 записів мають локацію. Без дозаповнення зміна на ньому нічого не дасть. `[проба]` (§1.1)
- Журнал відхиляє `character_ids` поза станами, тож учасникам потрібне окреме поле. `[проба]` (§1.2)
- Продуктовий відбір на 32 тис. (реалістична міра) бере 0,66 змінних цілей основного твору й відкидає в середньому 145 записів, тобто місце для кращого відбору є. `[проба]` (§1.3)
- Зв'язок «учасники, місце, час» дав значущий виграш у бенчмарку 27.11 (ядро lower, щабель 0,75). Продуктовий відбір має ядро, обмежене в часі (`hero_recent` + атмосфера), тож виграш має перенестися і на нього. Це не виміряно; вимірювання — критерій приймання PR 2. `[виведення]` (§1.3)
- Без переповнення запит не змінюється (MEMORY-SELECT І1), а запис без учасників і розмітки відбирається так само, як сьогодні. `[виведення]` з чинних інваріантів, тримається тестами плану.

**Ключові рішення.**
1. **Окреме поле `participant_ids`** для ліній, фактів і хронології. Відкинуто: дозволити `character_ids` поза станами. Там це поле означає власника стану (scope), і за ним проєкція фільтрує стани за складом сцени. Змішати власника й учасника означало б змінити чинний валідатор і сенс поля.
2. **Розмітка старих записів — накладка в payload твору за `claim_id`**, як позначки ядра/атмосфери. Відкинуто: переписати старі журнали новими подіями. Це зробило б застарілими всі версії пам'яті й залежні від них брифи та чернетки.
3. **Результат моделі застосовується одразу, без поштучного прийняття**, з поштучним виправленням і скасуванням усієї розмітки. Відкинуто: схема CHARACTER-EXTRACT з прийняттям кожної пропозиції. Записів сотні, а розмітка не змінює ні тексту, ні карток, лише порядок відбору під бюджет.
4. **Стара хронологія — окремий шар `past`** після `place`. Він бере лише записи з учасником сцени, що не є відстежуваним героєм, або з локацією в околиці, новіші першими. Відкинуто: брати будь-який старий запис із героєм. Героїня є в 98 % сцен, і шар забрав би всю стару хронологію.
5. Розглянуто стандартне: векторний пошук замість сутностей. Відкинуто, бо вимірювання 24–27.11 не дали йому виграшу в конвеєрі: виграв саме контекст «хто, де, коли» (див. документ дослідження).

**Що стане гірше.**
- **Більший запит етапу memory.** Розділ дозволених учасників (ID → ім'я всіх карток) додається до кожного запиту етапу memory у книзі з картками: на 30 картках це ≈ 1–2 тис. символів. Старі спроби етапу перестануть повторно використовуватися (MEMORY-REUSE), бо запит інший.
- **Оплачена дія.** Дозаповнення через модель — новий оплачуваний запуск. Для основного твору: ≈ 513 записів, кілька груп, оцінка в межах центів–доларів залежно від моделі ролі. Точну суму показує перегляд перед запуском.
- **Помилки моделі.** Модель може приписати хибного учасника, і запис потрапить у відбір не за ділом. Помилка видима в таблиці й виправляється поштучно.
- **Сумісність.** Новий журнал v4 і нове поле payload: даунгрейд Obscura лише з резервної копії.
- **Ще одна позначка в таблиці.** Ще один рядок під цитатою; таблиця стає щільнішою.

**Оцінка.**
- **Власника:** L чи XL, залежно від дизайну. Оцінку дано на попередній переказ, обсяг якого проби звузили: локації й персонажі станів уже є.
- **Автора:** L, три PR:
  - PR 1 ≈ 35 %: поле учасників, wire v4, відбір, шар `past`, звужений каталог, показ у таблиці;
  - PR 2 ≈ 45 %: накладка, запуск розмітки з переглядом і відбитком, API, застарілість, вимірювання;
  - PR 3 ≈ 20 %: кнопка й діалог, MCP-етап для чату, сайт uk/en.
- **Дешевший варіант (M):** без запуску розмітки. Старі книги отримують сутності лише через наявне «Перебудувати пам'ять». Що він втрачає: перебудова переписує всі записи (і позначки ядра/атмосфери, прив'язані до старих `claim_id`), коштує повного етапу memory на кожну сцену, а поки автор не перебудує пам'ять, книга нічого не виграє.
- Розбіжність оцінок менша за два розміри.

**Питання до власника.**
1. Якщо вимірювання в PR 2 не покаже виграшу продуктового відбору на основному творі, чи робимо PR 3 (кнопка, чат, сайт)? Пропоную: PR 3 лише за наявності виграшу; без нього PR 1 лишається (нова пам'ять), а запуск розмітки — лише в API та MCP. **Рішення власника 27.11.2026:** специфікацію затверджено разом із цією пропозицією.

### 1.2. Журнал не приймає персонажів поза станами

- `src/storygen/memory/journal.py:134`: `replay_memory` відхиляє подію з непорожнім `character_ids` у категорії, відмінній від `character_states` («Scope дозволено лише для станів»).

- `character_ids` і `location_ids` не входять у `claim_id` (`journal.py::_add_event`), тож накладка за `claim_id` не змінює ID записів.

Згенерований контекст там був текстом, а не ID. Перенесення на продуктовий відбір з ID не виміряне, звідси §6.

## 2. Модель даних

### 2.1. Учасники нових записів

- `MemoryEvent.participant_ids: list[str]` — ID карток персонажів, що беруть участь у лінії, факті чи події хронології.
- **Лише для `facts`, `open_threads`, `timeline`.** У `character_states` поле має бути порожнім: там власник — `character_ids`.
- Порожнє поле не серіалізується, тож старі журнали й версії лишаються байт у байт. До `claim_id` і ключа дубліката поле не входить. Непорожнє поле робить журнал `schema_version = 4`.
- **Валідація в `replay_memory`:**
  - без повторів і порожніх ID («Некоректні учасники пам’яті»);
  - непорожнє поле в стані відхиляється;
  - зміни (`update`, `retire`, закриття лінії) несуть `participant_ids` свого запису, інакше подія відхиляється, як для `location_ids`.
- **Успадкування:** факт розв'язки лінії успадковує учасників лінії, а злиття арок переносить поле.
- **Ручне збереження** бере для зміни без поля учасників її запису; явну іншу множину відхиляє.

### 2.2. Wire v4

- `schema_bounds_v4(..., participant_ids)` пише `bounds.participant_ids` лише для книги з картками: канонічні ID усіх карток твору, а не лише складу сцени, бо факт може стосуватися відсутнього.
- Тоді схема має обов'язкове `participant_ids` з enum дозволених у `add` категорій `facts`, `open_threads`, `timeline`.
- Запит отримує розділ «ДОЗВОЛЕНІ PARTICIPANT_IDS» / «ALLOWED PARTICIPANT_IDS» з інструкцією («вкажіть усіх персонажів, які діють чи про яких ідеться в записі; порожній список — якщо таких немає») і словником ID → ім'я (основне ім'я картки).
- Модель відповіді має поле необов'язковим, тож старі відповіді валідні. ID поза дозволеними чи повтор дають `participant_unknown`, і відповідь відхиляється.
- Вбудовані промпти й контракт `/4` не змінюються: інструкція — у самому розділі, як у локацій.
- Книга без карток має запит, межі й схему memory без змін.

### 2.3. Накладка розмітки старих записів

- `Story.memory_entities: dict[claim_id, MemoryEntityMark]`, де `MemoryEntityMark{participant_ids: list[str], location_ids: list[str], source: 'model'|'author'}`. До 20 000 записів; порожній словник у payload не пишеться.
- **Чинні сутності запису** (`memory/entities.py::effective`, без IO), окремо для кожного поля, перше наявне:
  - поле накладки з `source='author'` (правка автора перекриває й поле події, тож хибного учасника чи локацію, записану етапом memory, автор теж виправляє);
  - непорожнє поле самої події;
  - поле накладки з `source='model'`;
  - інакше поле порожнє.
- Для станів накладка дає лише `location_ids`; її `participant_ids` для стану ігнорується.
- ID невідомої картки персонажа (видаленої) при читанні відкидається. Локація проходить `canonical` за злиттями.
- **Накладка не змінює журналів, текстів, доказів, MEMORY-FORWARD і підтверджень.** Вона впливає лише на відбір (§3) і звужений каталог.
- `storage/memory_entities.py`:
  - `update_memory_entities(story_id, claim_id, participant_ids, location_ids | None, expected_revision)` — правка автора, `source='author'`; `None` прибирає запис накладки;
  - `apply_entity_marks(story_id, marks, expected_revision)` — пакет від запуску чи чату, `source='model'`;
  - `clear_entity_marks(story_id, expected_revision, source='model')` — скасувати всю розмітку моделі.
  - Пакет моделі не перезаписує записів із `source='author'`.
  - Усі три — CAS на ревізію твору: 409 при конфлікті; без змін ревізія не змінюється.
  - Невідомий `claim_id` (поза активними записами й хронологією книги) чи ID поза картками дає 400.

## 3. Відбір

`classify` бере сутності запису через `effective`.

- **Згадка учасника** (шари `threads`, `facts` і правило «факт лише про героя»):
  - якщо запис має чинних учасників, рішення приймається за їхнім перетином зі складом сцени;
  - лише запис без учасників (ні подія, ні накладка) перевіряється за основами імен, як зараз.
- **Шар `place`** для станів, ліній і фактів бере чинні `location_ids`: подія або накладка.
- **Фільтр проєкції за складом сцени не змінюється.** `memory_items` і далі відкидає стан відсутнього персонажа за локаціями самої події, а не накладки: інакше змінилася б повна проєкція, і запит без переповнення перестав би бути незмінним (І1). Накладка впливає лише на шари кандидатів, які вже є в проєкції.
- **Новий шар `past`**, у `LAYERS` після `place` і перед `general`. До нього потрапляє запис хронології старший за `TIMELINE_WINDOW`, якщо виконано обидві умови:
  - він має учасника зі складу сцени, що не є відстежуваним героєм, або локацію в околиці;
  - підсумок його блоку (MEMORY-SUMMARY) не відібрано.

  Порядок усередині шару — новіші сцени першими. Позначка «Не показано записів: N (сцени …)» рахує лише ті старі записи хронології, яких немає в запиті.
- **`narrow_catalog`** лишає факти з чинним учасником сцени (або згадкою, якщо учасників немає) і стани, лінії й факти з чинною локацією в околиці.
- **Метрики:** `selection.layers.past` і `selection.dropped.past`. `projection_version` для запитів із відбором стає `memory-uk-v4-selected`, тож MEMORY-REUSE не плутає їх зі старими.
- **Знімок залежностей:** версія, зібрана з відбором (`memory_metrics['selection']`) або зі звуженим каталогом етапу memory (`memory_metrics['narrow']`), пише селектор `scene/memory_entities`. Його значення — чинні сутності кандидатів відбору цієї сцени, які дала накладка. Зміна накладки робить застарілими лише версії, зібрані з відбором чи звуженим каталогом, і лише через записи, активні до сцени (як позначки типу, MEMORY-SELECT І8). Відсутній у старому знімку селектор не порівнюється.

## 4. Запуск «Розмітити сутності пам'яті»

Механіка запуску CHARACTER-EXTRACT повторюється, змінюється вміст.

- **Виконавець — роль «Пам'ять»** (`resolve_extractor`), температура 0,2. Промпт вбудований (`memory_entities_v1`, мовою твору).
- **Вхід групи:**
  - каталог карток (`c<N>: ім'я; інші імена`);
  - каталог канонічних локацій (`l<N>: шлях`);
  - записи групи (`r<N>`: категорія, текст, цитата, номер сцени).
- **Контракт відповіді:** `records[{record, participants, locations}]`. Невідомі короткі ID відкидаються, структурна помилка — збій виклику.
- **Цілі:** об'єднання кандидатів (`candidate_claim_ids`: активні записи й хронологія) останньої голови пам'яті **кожного родоводу** книги (BOOK-LINEAGE: за перемежованих арок A1, B1, A2, B2 — голови A2 і B2), без дублікатів за `claim_id`. Без перемежування арок це одна остання голова. Береться запис, якому бракує чинних учасників (лише лінії, факти й хронологія) або чинних локацій, і який не має запису накладки з `source='author'`.
- **Групи** — записи за порядком сцен, жадібно до бюджету символів ролі з резервом каталогу.
- **Перегляд:** `POST /api/stories/{id}/memory-entities/preview` → `{ready, reason, records_count, groups, calls_bound = 2 × груп + 2, cost, plan_fingerprint}`. Перегляд нічого не записує.
- **Відбиток плану** — sha256 груп, ID записів, ID версій пам'яті, `cards_digest` локацій, ID версії карток персонажів, виконавця, тарифу й ліміту бюджету.
- **Запуск:** `RunRequest.mode='memory_entities'` з `entities_plan_fingerprint`. Давній відбиток — 409, запит від моста без відбитка — 409. Дозволено в режимах `chat`, `obscura` і `author`, бо запуск не пише тексту твору.
- **Контрольна точка:** групи, що лишилися, і `calls`. Виклик зараховується до надсилання, тож запуск не робить більше `calls_bound` викликів. Один активний запуск на книгу.
- **Застосування** — після кожної групи через `apply_entity_marks` з поточною ревізією; конфлікт перечитує ревізію один раз. Збій виклику повторюється один раз, повторний ділить групу навпіл, а запис з окремої групи, що не вдалася, пропускається з причиною.
- **Вичерпаний ліміт викликів:** коли `calls` досягає `calls_bound`, запуск не робить нових викликів, записи груп, що лишилися, пропускаються з причиною «вичерпано ліміт викликів», і запуск завершується з частковим результатом (застосовані групи лишаються).
- **Підсумок запуску:** `{marked, skipped[{claim_id, reason}]}`.

**Чат (MCP).**
- `get_stage_task(stage='memory_entities', group?)` повертає інструкції, каталоги, записи групи й `task_fingerprint`.
- `save_stage_result` перевіряє відповідь тим самим контрактом і застосовує її через `apply_entity_marks`.
- Без оплати моделей Obscura; доступно в усіх режимах написання.

## 5. Інтерфейс

- **Таблиця пам'яті:** рядок `memory-view` отримує `participants` (імена) і поле `entities_source` (`event` / `model` / `author`). Під цитатою стоїть «Учасники: …» поряд із «Локації: …», а пошук враховує імена. Кнопка «Сутності…» відкриває поштучну правку; в API це `PUT /api/stories/{id}/memory-entities` `{claim_id, participant_ids, location_ids | null, expected_revision}`.
- **Меню твору:**
  - «Розмітити сутності пам'яті (записів: N)» відкриває діалог із переглядом вартості, моделлю й рядком «Модель … отримає: тексти й цитати записів пам'яті, імена карток, назви локацій»; запуск іде через рядок запуску;
  - «Скасувати розмітку моделі» — з підтвердженням.
- **MCP:** `start_run(action='memory_entities')` спершу дає перегляд, а з `confirm=true` запускає з відбитком.

## 6. Вимірювання (PR 2)

- **Стратегія бенчмарку `product_entities`.** Це продуктовий відбір із накладкою, отриманою запуском розмітки на копії бази основного твору й тексту А. Моделлю ролі «Пам'ять» копії чи Haiku через обв'язку бенчмарку, у наявних межах витрат (Anthropic ≤ $5 сукупно), лише на погоджених творах.
- **Звіт:** `target_recall`, змінні цілі й цілі перефразувань `syn`/`desc` у контексті на 32 тис. (реалістична міра), парний тест проти `product` без накладки.
- **Критерій:** виграш на перефразуваннях без втрати змінних цілей. Рішення про PR 3 — за власником (питання 1).

## 7. Сумісність і міграції

- **Без міграції SQLite.**
  - Журнали без `participant_ids` і payload без `memory_entities` читаються як раніше.
  - Журнал v4 і непорожня накладка роблять книгу нечитною для старішої Obscura (`extra="forbid"`); повернення лише з резервної копії.
- **Старі версії не стають застарілими.** Селектора `scene/memory_entities` у старих знімках немає.
- **Власні промпти memory з контрактом `/4` працюють.** Без інструкції розділу модель може не давати учасників, тоді запис відбирається за основами імен.

## 8. Інваріанти

- **І1.** Без переповнення запит, відбиток і метрики незмінні.
- **І2.** Запис без чинних учасників і локацій класифікується так само, як до зміни.
- **І3.** Накладка не змінює журналів, текстів, `claim_id` і доказів.
- **І4.** Пакет моделі ніколи не перезаписує правки автора.
- **І5.** Запуск розмітки не робить більше `calls_bound` викликів.
- **І6.** Книга без карток має запит, межі й схему memory без змін.
- **І7.** Кожен кандидат належить рівно одному шару (MEMORY-SELECT І7 зберігається з шаром `past`).

## 9. Межі й відомі обмеження

- **Предмети** — #262.
- **Строк дії неслотових станів** — #69.
- **Переповнення на консервативній мірі** — #70.
- **Учасники станів, крім власника** (наприклад, «посварилася з Петром»), не записуються: стан має лише власника.
- **Старі записи** без запуску розмітки відбираються, як раніше.
- **Розмітка моделі може помилятися.** Виправлення поштучне.
- **Накладка не повертає в проєкцію** стан відсутнього персонажа, відкинутий фільтром складу: локація з накладки діє лише для кандидатів, які вже є в проєкції.
