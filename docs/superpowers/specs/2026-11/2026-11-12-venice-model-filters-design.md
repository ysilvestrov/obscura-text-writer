## Для власника

### Мета

Автор сам вибирає модель для кожної ролі, бачачи в каталозі, наскільки вона приватна, чи вона без цензури і скільки коштує. Звичайні приватні моделі стають доступними для планування, редагування й пам'яті. Відверті сцени й надалі пише модель без цензури, а звичайні сцени можна віддати іншій моделі.

### Що зміниться для тебе

- **Каталог моделей замість поля з підказками.** Для Venice показуються всі текстові моделі, а не лише uncensored, з позначками Uncensored, TEE / Private / Anonymous, JSON Schema, контекстом і ціною. Фільтри: пошук, «лише Uncensored», мінімальна приватність (типово «Private і вище»), JSON Schema. Вигляд — затверджений прототип від 12.11.2026.
- **JSON Schema пов'язано з режимом відповіді ролі.** Якщо роль або підключення працює в режимі «JSON Schema», фільтр JSON Schema увімкнений і зафіксований, а модель без підтримки JSON Schema вибрати не можна. Пояснення пропонує або іншу модель, або режим «JSON за промптом». У режимі «JSON за промптом» фільтр звичайний і необов'язковий. Підтримка JSON Schema видна й для OpenRouter, бо його каталог її теж повідомляє.
- **Жорстку заборону замінює згода.** Хмарну модель без позначки Uncensored можна поставити в будь-яку роль. Але для творів із рейтингом вище 0 вона працює лише після твоєї явної згоди. Згода дається один раз для пари «роль + точний ID моделі», діє для всіх творів і скидається, якщо змінити модель.
- **Блокування після відмови.** Якщо модель відмовила через зміст, пара «роль + модель» отримує позначку з рейтингом тієї сцени. Наступні виклики для сцен із таким самим або вищим рейтингом блокуються з поясненням, доки ти не зміниш модель або не знімеш позначку. Автоматичного перемикання на іншу модель немає.
- **Друга модель письменника.** У налаштуваннях письменника можна додати необов'язкову «модель для сцен 0–1» з власними лімітами; промпт спільний. Сцену, де хоч одна вісь рейтингу дорівнює 2, завжди пише основна модель. Наявні налаштування продовжують працювати без змін.
- **Нічого не стає незворотним.** Згоди й позначки зберігаються в теці даних і знімаються з інтерфейсу. Формат комплектів ролей отримує нову версію; старі комплекти імпортуються як раніше.
- Оцінювач (Evaluator) поза межами зміни: для нього лишається нинішня вимога `uncensored=true`.

### На чому стоїть рішення

1. Відповідальність за вибір моделі несе автор. Застосунок лише попереджає й блокує після відмови. `[вимога власника]`
2. Згода потрібна, коли модель не локальна, не має позначки Uncensored, а рейтинг **твору** вищий за 0 хоч за однією віссю. `[вимога власника]` Рішення автора специфікації: згода потрібна також тоді, коли твір має рейтинг 0, але ефективний рейтинг сцени в запиті вищий за 0. `[виведення]`: інакше одна сцена з власним рейтингом 2 у «нульовому» творі пішла б до звичайної моделі без згоди, а це суперечить меті вимоги.
3. Згода глобальна для пари «роль + модель», а не для твору. `[вимога власника]` Налаштування ролей при цьому зберігаються **окремо для кожного твору** (таблиця `role_settings` з ключем `story_id, role`), тож згоду треба зберігати окремо від них. `[проба]` (П4)
4. Після відмови виклики блокуються без автоматичного перемикання. `[вимога власника]`
5. Письменник має основну модель (усі сцени, зокрема рівень 2) і необов'язкову модель для сцен 0–1. Навпаки не буває. Планувальнику, редактору й пам'яті досить однієї моделі. `[вимога власника]`
6. Каталог Venice дає все потрібне машиночитними полями: `privacy` (`anonymized` / `private`), `capabilities.supportsE2EE` і `supportsTeeAttestation` (завжди разом), `uncensored`, `pricing`. `[проба]` (П1)
7. Моделі `e2ee-*` відповідають на звичайний запит без шифрування в клієнті й повертають `x-venice-tee: true`. Гарантію TEE це підтверджує, а наскрізного шифрування — ні: текст до Venice іде звичайним TLS. `[проба]` (П2) Звідси висновок: позначка для них — «TEE», а не «E2EE». `[виведення]`
8. Межа «рівень 2» означає будь-яку вісь ефективного рейтингу сцени, а не лише сексуальну. `[виведення]`: детальні описи насильства звичайні моделі теж стабільно відхиляють. Ти погодив це в обговоренні.
9. Відмову можна надійно розпізнати лише за структурними ознаками: `finish_reason=content_filter` або поле `refusal` у потоці (категорії `refusal_content` / `refusal_unknown`). `[проба]` (П5) Текстову відмову («I can't help with that») зі звичайним `stop` генерація не розпізнає. `[виведення]`: евристика `is_text_refusal` є лише в оцінювачі.
10. Підтримка JSON Schema важлива для вибору моделі й має бути у фільтрі. `[вимога власника]` Обидва хмарні каталоги її повідомляють: Venice — `capabilities.supportsResponseSchema`, OpenRouter — `structured_outputs` у `supported_parameters` (392 з 468 моделей). `[проба]` (П1, П6)
11. Провайдер `local` вважається локальним, лише коли його Base URL вказує на loopback-адресу (`localhost`, `127.0.0.1`, `[::1]`). Інакше він підлягає тим самим правилам, що й хмарні провайдери. `[виведення]`: Base URL локального провайдера можна навести на чужий сервер.

### Ключові рішення

1. **Позначки й фільтри будуються з полів каталогу, а не з назв моделей.** Якщо поля немає, ставиться «приватність невідома» (так завжди для OpenRouter) і «не Uncensored». Відкинуто таблицю відомих моделей у коді: вона застаріває з кожним оновленням каталогу.
2. **Згода й позначки відмови зберігаються глобально в `app_settings`** (ключі `model_consent:<role>:<endpoint>:<model>` і `model_refusal:<role>:<endpoint>:<model>`, де `endpoint` — нормалізований Base URL). Base URL входить у ключ, тож згода, дана для одного сервера провайдера `local`, не переходить на інший сервер. Відкинуто поле в `RoleSettings`: ці налаштування належать окремому твору, а згода за твоїм рішенням глобальна.
3. **Друга модель письменника — необов'язковий підоб'єкт `RoleSettings.low_rating_variant`** (провайдер, модель, контекст, ліміти, температура; промпт спільний). Маршрутизація відбувається в одній функції за ефективним рейтингом сцени. Відкинуто п'яту роль: вона ламає контракт «чотири ролі» (MODEL-001) і роздвоює промпт письменника.
4. **MODEL-003 змінюється з «лише uncensored» на «каталожна перевірка + згода».** Перевірка ID в каталозі, `offline`, JSON Schema й лімітів лишається перед кожним викликом. Відкинуто збереження жорсткої вимоги з винятками для окремих ролей: тоді рішення приймав би застосунок, а не автор.
5. **Позначка відмови зберігає набір векторів рейтингу сцен, на яких була відмова.** Наступний виклик блокується, якщо хоча б один збережений вектор за кожною віссю не вищий за рейтинг нової сцени. Відмова на сцені 2/0/0 не блокує сцену 0/2/0. Відмова на сцені 0/0/0 блокує всі сцени, бо модель відмовила навіть на звичайному тексті. Відкинуто блокування всієї пари після першої відмови: тоді одна відмова на рівні 2 зупинила б і звичайні сцени, які модель пише без проблем.

- Розглянуто стандартне: `datalist` браузера з довшим текстом опції — відкинуто, бо він не показує позначок і не фільтрує за кількома ознаками.
- Розглянуто стандартне: автоматичний класифікатор відмов у тексті відповіді — відкинуто для генерації, бо на художньому тексті він дає хибні спрацювання. Лишається відомим обмеженням.

### Що стане гірше

- Звичайну модель можна поставити туди, де вона мовчки «причеше» відверту сцену, не повернувши формальної відмови. Застосунок цього не помітить (п. 9).
- Більше станів, які автор має розуміти: згода, позначка відмови, друга модель письменника.
- Майже жодна модель TEE не підтримує JSON Schema (1 з 13). Для ролей зі структурованою відповіддю вибір найприватніших моделей дуже вузький. `[проба]` (П1)
- Комплекти ролей нової версії не відкриваються в старих версіях застосунку.
- Оцінювач лишається з жорсткою вимогою uncensored. Це непослідовно щодо принципу «відповідальність автора», але виходить за межі зміни.

### Каталог і список (PR 1)

- `ModelOption` отримує поля `privacy: Literal['anonymized','private','unknown']`, `tee: bool`, `uncensored: bool | None` (з каталогу, а не безумовно), `supports_schema: bool | None`, `name: str | None`. Для OpenRouter: `privacy='unknown'`, `tee=False`, `uncensored=None`, `supports_schema = 'structured_outputs' in supported_parameters` (без поля — `None`). Для Venice `supports_schema = capabilities.supportsResponseSchema is True`. Для локального провайдера — `None` («невідомо»).
- Правило JSON Schema у списку: якщо `response_mode == 'json_schema'` у формі, де стоїть список, фільтр JSON Schema увімкнений і заблокований, моделі з `supports_schema` не `True` у списку неактивні з поясненням «Модель не підтримує JSON Schema. Виберіть іншу модель або режим „JSON за промптом“». Зміна режиму відповіді одразу перебудовує список. Якщо вже вибрана модель перестає відповідати режиму, рядок вибраної моделі показує помилку, а збереження форми відхиляється з тим самим поясненням (на клієнті й на сервері під час збереження, коли каталог доступний). Перевірка перед викликом (`validate_model`, `supportsResponseSchema`) лишається остаточним захистом.
- `providers/venice.py` отримує `catalog_models(client)` (усі онлайн-моделі) поруч з `uncensored_models`. `model_options` використовує `catalog_models`.
- Інтерфейс: компонент списку моделей (окремий модуль `static/model-picker.js`) замість `datalist` у формі ролі й у спільному віджеті підключення. Стан фільтрів зберігається лише в сторінці. Типовий фільтр приватності — «Private і вище».
- Порядок рівнів приватності: TEE > Private > Anonymous; «невідомо» поза шкалою. Фільтр приватності діє лише для провайдерів, каталог яких повідомляє рівень (зараз Venice). Для OpenRouter фільтр неактивний з поясненням «OpenRouter не повідомляє рівень приватності», і всі його моделі показуються з позначкою «приватність невідома». Рішення автора специфікації: інакше типовий фільтр сховав би весь каталог OpenRouter.
- Рядок вибраної моделі показує позначки й ціну з `ModelOption.tariff`. Для моделі, якої немає в завантаженому каталозі, — «немає в каталозі».
- У PR 1 правило виклику не змінюється: для Venice модель без Uncensored у списку видно, але вибір блокується з поясненням «доступно після оновлення правил виклику». Так проміжний стан чесний.

### Згода й позначка відмови (PR 2)

- Новий модуль `providers/policy.py`:
  - `is_local(settings)` — `provider=='local'` і loopback-хост Base URL;
  - `request_rating(story, scenes)` — рейтинг запиту: максимум за кожною віссю серед рейтингу твору й ефективних рейтингів сцен, матеріал яких входить у запит (одна сцена для етапів сцени; кілька сцен для impact і review; жодної для `prepare`);
  - `needs_consent(settings, option, rating)` — не локальна, `option.uncensored is not True`, рейтинг запиту має вісь > 0;
  - `check_call(repo, role, settings, story, scenes)` — піднімає `ValueError` з авторським текстом, якщо потрібна згода, а її немає, або якщо хоча б один збережений вектор відмови за кожною віссю не вищий за рейтинг запиту.
- Сховище: `storage/model_policy_store.py`, ключі з ключового рішення 2. Згода: `{role, provider, base_url, model, consented_at}`. Позначка: `{role, provider, base_url, model, refusals:[{rating:[s,v,t], scene_id|null, story_id, attempt_id|null, at, category}]}`. Під час запису нового вектора з набору прибираються вектори, не нижчі за новий за кожною віссю (вони вже покриті), тож набір лишається мінімальним.
- Виклик `check_call` — у тому самому місці, де `enforce_rating` (`make_context`), і в `readiness`, щоб автор побачив блокування до запуску. Інші шляхи, що надсилають матеріал твору від імені ролі, MUST проходити через ту саму перевірку з роллю, чиї налаштування використано: assisted writing — `writer`, editor loop — `editor`, impact і послідовна перевірка — `planner` (за `impact_context.py:14,79`, `review/readiness.py:24`, `editor_loop.py:66`). Повний перелік план складає за пошуком викликів `gateway_factory` / `StreamingGateway`.
- `validate_model` для генераційних ролей перевіряє наявність у каталозі, `offline`, JSON Schema й ліміти, але не `uncensored`. Оцінювач викликає `require_uncensored` (нинішня поведінка).
- Запис позначки: кожен шлях із попереднього пункту, отримавши відмову з категорією `refusal_content` або `refusal_unknown`, записує позначку для пари «роль + модель, з якою відправлено запит» з рейтингом запиту (`request_rating`). Для основного конвеєра це `execute_stage`; для решти шляхів — їхній обробник відповіді. Спільна функція запису живе в `providers/policy.py`, щоб правило було одне.
- API: `GET /api/model-policy?role=&provider=&model=` (згода й позначка), `PUT …/consent`, `DELETE …/consent`, `DELETE …/refusal`. Значень ключів чи тексту твору у відповідях немає.
- Інтерфейс — за прототипом: попередження з галочкою згоди під вибраною моделлю, червоне повідомлення про відмову з кнопками «Зняти позначку» і «Вибрати іншу модель».

- `RoleSettings.low_rating_variant: RoleVariant | None = None`; `RoleVariant` — `provider: ProviderSettings`, `context_tokens`, `max_output_tokens`, `max_input_chars`, `temperature`, `timeout`. Дозволений лише для `writer`; для інших ролей запис відхиляється.

- Згода й позначка відмови діють для пари «writer + модель варіанта» так само, як для основної моделі.
- Відбиток контексту вже включає налаштування запиту, тож зміна маршруту (наприклад, підвищення рейтингу сцени до 2) дає новий відбиток без окремого механізму. `[виведення]`: перевіряє тест PR 3.
- Комплекти ролей: `schema_version` 2 допускає `low_rating_variant`; версія 1 імпортується без змін.

### Сумісність і міграції

- Міграції SQLite немає: нові записи — у `app_settings`, нове поле — у JSON-payload `role_settings` з типовим `None`.
- Наявні налаштування Venice з моделлю uncensored поводяться як раніше; згода для них не потрібна.
- Для наявних налаштувань із моделлю OpenRouter у творі з рейтингом > 0 після PR 2 з'являється вимога згоди. Це навмисна зміна поведінки; повідомлення пояснює, що робити.

### Нові або змінені Scenario (чернетка ID)

- MODEL-003-S01 (змінено) — модель відсутня в каталозі або `offline`: платний запит не надсилається.
- MODEL-003-S02 — модель без Uncensored, твір із рейтингом > 0, згоди немає: виклик блокується з поясненням.
- MODEL-003-S03 — згоду дано для пари «роль + модель»: виклик проходить у будь-якому творі; зміна моделі скидає згоду.
- MODEL-003-S04 — локальна модель на loopback: згода не потрібна; той самий провайдер `local` з не-loopback URL — потрібна; згода для одного Base URL не діє для іншого.
- MODEL-003-S05 — твір 0/0/0, сцена з власним рейтингом 2/0/0, модель без Uncensored без згоди: виклик для цієї сцени блокується, для інших сцен твору — ні.
- MODEL-004-S01 — відмова через зміст записує позначку; сцена з таким самим або вищим рейтингом блокується, нижча за якоюсь віссю — ні; зняття позначки відновлює виклики.
- MODEL-004-S02 — відмови на 2/0/0 і 0/2/0: сцена 1/1/0 не блокується, 2/1/0 і 0/2/2 блокуються; відмова на 0/0/0 блокує всі сцени.
- MODEL-004-S03 — відмова на шляху impact записує позначку для `planner` з максимальним рейтингом сцен запиту.
- MODEL-001-S02 — письменник із варіантом 0–1: сцена 0/1/1 іде до варіанта, сцена 0/2/0 — до основної моделі; без варіанта всі сцени йдуть до основної.
- MODEL-005-S01 — каталог показує позначки й ціну з полів каталогу; відсутнє поле дає «невідомо», а не вигадане значення.
- MODEL-005-S02 — роль у режимі «JSON Schema»: фільтр JSON Schema увімкнений і заблокований, модель без підтримки вибрати й зберегти не можна; перемикання на «JSON за промптом» знімає обмеження; для OpenRouter підтримка береться з `structured_outputs`.

| Заявка | Де записано | Що доводить | Сила |
|---|---|---|---|

## Поправки

- **12.11.2026, правило JSON Schema у списку (розділ «Каталог і список (PR 1)»).** Правило «моделі з `supports_schema` не `True` у списку неактивні» замінено на: неактивні лише моделі з `supports_schema = false`; невідома підтримка (`null`) — вибір і збереження дозволено з підказкою «Підтримка JSON Schema невідома: перевірте модель самостійно.». Причина: локальний провайдер завжди повідомляє невідому підтримку, тож старе правило робило локальні ролі в режимі JSON Schema незбережуваними після завантаження списку (знайдено у фінальному рев'ю PR 1). Твердження про остаточну перевірку перед викликом уточнено: вона є лише для Venice (`validate_model`); для OpenRouter і локальних моделей перевірки JSON Schema перед викликом немає. Сервер (`schema_mismatch`) і раніше відхиляв лише `False`.
