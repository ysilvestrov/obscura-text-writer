# Двомовний сайт інструкцій на GitHub Pages (R-25, #29)

Дата: 2026-11-10
Статус: чернетка

## Для власника

### Мета

Автор, який знайшов Obscura, читає українською або англійською, як встановити застосунок, написати першу сцену й користуватися основними функціями. Інструкції лежать на одній адресі й не змішуються з внутрішніми планами та звітами. Сайт оновлюється сам після злиття в `main`.

### Що зміниться для тебе

- **Адреса сайту**: `https://ysilvestrov.github.io/obscura-text-writer/` (українська) і `…/en/` (англійська), з перемикачем мови на кожній сторінці.
- **Один раз потрібна твоя дія або згода**: увімкнути GitHub Pages у налаштуваннях репозиторію з джерелом «GitHub Actions». Я можу зробити це командою `gh api` після твого «так», або ти робиш це в Settings → Pages.
- **Публікація після злиття.** Кожне злиття в `main`, що змінює інструкції, збирає й публікує сайт без твоєї участі. PR лише збирає й перевіряє сайт, нічого не публікуючи.
- **Нове правило для змін.** Якщо змінено українську сторінку, а англійську ні, перевірка документації падає, доки англійську не оновлено або явно не підтверджено як актуальну.
- **Користувацькі інструкції переїжджають у `docs/site/uk/` і `docs/site/en/`.** Старі файли в `docs/` з інструкціями стають однорядковими посиланнями на нову сторінку, щоб не ламати наявні посилання. Внутрішні плани, звіти й дослідження лишаються в репозиторії, але на сайт не потрапляють.
- Безкоштовно: Pages і Actions для публічного репозиторію не тарифікуються. Cloudflare не потрібен.

### На чому стоїть рішення

1. Двомовний сайт на GitHub Pages з markdown у репозиторії; збірка й публікація на GitHub після push; автоматична перевірка синхронізації мов; знімки лише з нейтральними прикладами; інструкції встановлення готові до появи інсталятора (#30). `[вимога власника]` (#29, R-25)
2. Репозиторій публічний; Pages не ввімкнено (API повертає 404); теки `.github` і жодного workflow немає. `[проба]` (П1)
3. Користувацькі інструкції зараз — 30+ файлів у `docs/` упереміш із внутрішніми звітами (`*-2026-10-*.md`, `research/`, `superpowers/`, `diagnostics/`). Англійською є лише 10 сторінок у `docs/en/`. Українські сторінки — накопичені нотатки за функціями з деталями API й схем; читати їх як інструкцію для нового автора важко. `[проба]` (П2)
4. `markdown-it-py` уже є залежністю застосунку, тож власний збирач не додає залежностей. `[проба]` (П3)
5. Material for MkDocs із листопада 2025 у режимі підтримки; обіцяне вікно виправлень закінчилося 05.11.2026. Наступник Zensical ще в пре-релізі. `[проба]` (П4)
6. Нейтральний приклад для знімків уже є: твір «Маяк на пристані» з seed-скрипту, зробленого для #89. `[проба]` (П5)
7. Спрощення екрана (#89) виконується до цієї зміни, тож знімки знімаються вже з нового інтерфейсу. `[вимога власника]` (порядок беклогу)
8. Хеш української сторінки, записаний в англійській, достатньо ловить «змінили одну мову, забули іншу». Перевірити зміст перекладу автоматично не можна. `[виведення]`

### Ключові рішення

1. **Власний невеликий збирач `scripts/build_site.py` на `markdown-it-py` з одним HTML-шаблоном і CSS.** Відкинуто MkDocs Material: він у режимі підтримки з вичерпаним вікном виправлень, а двомовність потребує стороннього плагіна.
2. **Окреме дерево користувацьких сторінок `docs/site/{uk,en}/` з маніфестом `docs/site/site.json`** (порядок навігації, пари сторінок, заголовки). Відкинуто збірку з наявних файлів `docs/*.md` як є: вони технічні, без структури для нового автора, і внутрішні звіти лежать поруч.
3. **Синхронізація мов через хеш.** Англійська сторінка має front matter `source_sha256` — SHA-256 української сторінки, з якої її перекладено. Перевірка падає, коли хеш не збігається, коли пари немає, коли посилання чи зображення не розв'язується, або коли сторінка посилається на внутрішні матеріали. Відкинуто перевірку лише наявності пари: вона не ловить застарілий переклад.
4. **Workflow GitHub Actions з двома режимами.** На PR: збірка й перевірка без публікації. На push у `main` зі змінами в `docs/site/**`, `docs/images/**` або збирачі: збірка, перевірка, `actions/deploy-pages` і перевірка доступності опублікованої адреси. Права мінімальні: `contents: read`, а `pages: write` і `id-token: write` лише в задачі публікації.
5. **Знімки за мовою інтерфейсу**: `docs/images/site/{uk,en}/`, знімаються відтворюваним скриптом на seed «Маяк на пристані» з інтерфейсом відповідною мовою. Відкинуто українські знімки в англійських сторінках: англомовний автор бачив би не той інтерфейс.

- Розглянуто стандартне: MkDocs + Material з `mkdocs-static-i18n` — відкинуто, бо підтримку Material завершено (П4), а нова залежність збірки потрібна лише для сайту.
- Розглянуто стандартне: Zensical — відкинуто, бо пре-реліз.
- Розглянуто стандартне: Jekyll, вбудований у GitHub Pages — відкинуто, бо Ruby й Liquid поза стеком проєкту, вбудованої двомовності немає, а перевірку синхронізації все одно треба писати окремо.
- Розглянуто стандартне: Docusaurus — відкинуто, бо Node/React-проєкт заради статичних сторінок; i18n у ньому добре, але вага стека непропорційна.

### Що стане гірше

- Власний збирач — ще один код для підтримки (шаблон, навігація, перемикач мов). Пошуку по сайту в першій версії немає.
- Кожна зміна української інструкції тепер вимагає оновити англійську (або підтвердити хеш). Це повільніше для дрібних правок.
- Перенесення інструкцій у нове дерево — великий одноразовий обсяг тексту. Старі посилання на рівні розділів (якорі) можуть вести на сторінку-посилання, а не на потрібний розділ.
- Англійські тексти перекладаю я. Твоя вичитка бажана, але не блокує злиття.

### Оцінка

- Власник: M. Автор: L (на один розмір більше, обов'язкової зупинки немає).
- Розбивка: збирач, шаблон, перемикач мов — 20 %; перевірка синхронізації, посилань і внутрішніх матеріалів, traceability — 15 %; workflow і ввімкнення Pages — 10 %; переписування інструкцій у нове дерево (≈12 тем × 2 мови, з них ≈8 англійських сторінок з нуля) — 40 %; скрипт знімків і самі знімки UA/EN — 15 %.
- Чому L: 2 PR. PR 1 — збирач, перевірка, workflow і перші сторінки («Встановлення й запуск», «Перший твір»). PR 2 — решта тем і знімки. Плюс одноразове ввімкнення Pages поза репозиторієм.
- Дешевший варіант (M, 1 PR): сайт збирається з наявних файлів `docs/*.md` і `docs/en/*.md` за маніфестом, без переписування; англійською лише наявні 10 сторінок і нова «Встановлення». Втрачається читабельність для нового автора, а частина тем лишається без англійської версії.

## Обсяг

### PR 1 — механізм і перші сторінки

- `docs/site/site.json`: `{"languages":["uk","en"],"pages":[{"slug":"install","title":{"uk":"…","en":"…"}}, …]}`. Сторінка `docs/site/<lang>/<slug>.md`. Порядок у маніфесті — порядок навігації.
- `scripts/build_site.py [--out _site]`: читає маніфест, рендерить markdown-it-py (CommonMark + таблиці), обгортає шаблоном `docs/site/template.html` (навігація, перемикач мови на ту саму `slug`, `lang` атрибут), копіює зображення з `docs/images/site/`. Відносні шляхи працюють під підшляхом `/obscura-text-writer/`. Вихід детермінований: однакові джерела дають однакові байти.
- `scripts/check_site.py` (викликається з `scripts/check_docs.py`): кожна сторінка маніфесту існує обома мовами; `source_sha256` англійської дорівнює хешу української; внутрішні посилання й зображення розв'язуються; немає посилань на `docs/superpowers/`, `docs/research/`, `docs/diagnostics/`, `docs/specs/`, `SPEC.MD`, `docs/STATUS.md`; кожне зображення має alt-текст. Помилки зрозумілі: файл, рядок, що робити (`python scripts/check_site.py --rehash en/<slug>` оновлює хеш після перевірки перекладу).
- `.github/workflows/site.yml`: `pull_request` → build + check; `push` у `main` з path-фільтром → build + check + `actions/upload-pages-artifact` + `actions/deploy-pages` + `curl --fail` на адресу сторінки. Версії actions закріплені за мажорною версією від GitHub. Модельних викликів і секретів немає.
- Сторінки «Встановлення й запуск» (Windows, Python, `.env`, ключі провайдерів, порт, резервне копіювання; розділ «Інсталятор» з позначкою «з'явиться в #30») і «Перший твір» обома мовами.
- `.gitignore`: `_site/`.

### PR 2 — решта тем і знімки

- Теми (кожна — сторінка UA/EN): робочий простір і етапи сцени; персонажі; імпорт матеріалів; Ghost Mode; пам'ять; редактура й перевірка впливу; вікові рівні; моделі, ролі й бюджет (зокрема локальні моделі); оцінювач; публікація й експорт; поширені помилки; умови використання й політика назви (посилання на наявні юридичні тексти).
- Старі користувацькі файли в `docs/` стають однорядковими посиланнями на сторінку сайту; README посилається на сайт.
- `scripts/capture_screenshots.py`: seed «Маяк на пристані» в тимчасовому каталозі `C:\tmp\…`, запуск сервера, Playwright (наявна extra `browser`), знімки UA та EN інтерфейсу desktop і mobile у `docs/images/site/{uk,en}/`. Без ключів, особистих шляхів і авторських текстів.

## SPEC.MD

Новий Requirement **DOCS-SITE** — «Двомовний сайт інструкцій»: джерело в `docs/site/`, маніфест, синхронізація хешем, межа внутрішніх матеріалів, збірка без мережі й модельних викликів, публікація лише з `main`. Scenario:

- DOCS-SITE-S01 «Змінено українську сторінку без англійської» → перевірка падає з назвою сторінки й командою `--rehash`.
- DOCS-SITE-S02 «Посилання на внутрішній матеріал» → перевірка падає.
- DOCS-SITE-S03 «Збірка під підшляхом Pages» → усі посилання й зображення відносні й розв'язуються в `_site/`.
- DOCS-SITE-S04 «PR не публікує» → ручна процедура: workflow на PR не має задачі deploy (перевірка файлу workflow тестом).
- DOCS-SITE-S05 «Публікація після злиття» → ручна процедура з причиною: потрібен реальний GitHub; доказ — успішний запуск workflow і HTTP 200 опублікованої адреси.

Розділ про спосіб запуску й пакування згадує сайт як джерело користувацьких інструкцій; правило AGENTS.md про актуальність документації посилається на `docs/site/`.
