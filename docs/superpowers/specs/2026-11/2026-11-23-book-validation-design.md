# R-44 — Валідація книги: зв'язки сцени й роль «Ревізор»

Дата: 2026-11-23
Статус: чернетка

GitHub [#269](https://github.com/ysilvestrov/obscura-text-writer/issues/269). Другий пакет сценарію «редактура книги зовнішнім редактором» (R-43 → **R-44** → R-45 → R-46). Підготовчий PR #278 (єдиний реєстр ролей) уже злито.

## Для власника

**Мета.** Автор може змінити одне слово в прозі, перевірити книгу й продовжувати писати, не перевіряючи всю книгу заново. Нинішня «Перевірка впливу» (R-28), яка не працює, зникає. Її місце займає перевірка зв'язків сцени новою роллю «Ревізор»: перевіряються лише зв'язки, яких торкнулася зміна.

**Що зміниться для тебе.**
- **Позначка «застаріле».** Для завдання, прози й пам'яті вона тепер означає «зв'язок сцени не підтверджено», а не «змінилося щось, від чого залежить текст».
  - Правки канону, стилю й налаштувань твору більше нічого не позначають.
  - Після збереження картки персонажа чи локації Obscura питає, чи позначити залежні сцени неперевіреними.
- **Згенеровані за звичайним шляхом сцени валідні без жодної перевірки.** Звичайний шлях — це завдання від планувальника, проза від письменника й редактора, пам'ять від етапу пам'яті, кожен із поточного матеріалу.
  - Твоя ручна правка завдання чи прози, як і імпорт прози, робить невалідними лише зв'язки цього компонента.
  - Твоя ручна правка пам'яті поточну сцену не зачіпає, лише наступну.
- **Ревізор (англ. Auditor) — п'ята роль** з власними провайдером, моделлю, промптами й лімітами. Поки ти її не налаштуєш, вона бере модель редактора.
- **Валідація книги** в меню твору:
  - перед запуском — кількість зв'язків і орієнтовна вартість;
  - далі перевіряє лише невалідні зв'язки в порядку читання;
  - на першій розбіжності зупиняється й чекає твого рішення.
- **Кнопка «Перевірити сцену»** з'являється в робочому просторі, коли сцена невалідна.
- **«Затвердити всю прозу як авторську» лишається окремим режимом.** Проза стає фінальною (анотація, експорт без поміток), але валідність від цього не змінюється. Кнопка переїжджає в меню твору.
- **Сторінка «Перевірка книги» й усе R-28 зникають.** Збережені звіти лишаються в базі, але ні на що не впливають. На твоїх даних таких записів, що щось змінюють, 0 (див. «Проба 1»).
- **Перший прогін валідації книги на 68 сцен — близько 67 викликів Ревізора.** Далі перевіряються лише змінені зв'язки.

**На чому стоїть рішення.**
- Сцена — ланцюжок: попередня пам'ять → план → завдання → (чернетка, редактура) → проза → пам'ять. Строго пройдений ланцюжок валідний. Зміна компонента, крім пам'яті, інвалідує поточну сцену, зміна пам'яті — наступну. Перевіряються лише невалідні сцени й лише зв'язки зі зміненим компонентом. `[вимога власника]`
- Затвердження прози як авторської не впливає на валідність, а імпорт прози інвалідує сцену. `[вимога власника]`
- Після зміни картки персонажа чи локації Obscura питає автора, чи інвалідувати залежні сцени. Самостійне визначення — поза обсягом. `[вимога власника]`
- Валідність замінює позначку «застаріле» для завдання, прози й пам'яті. `[вимога власника]`
- Ревізор — окрема роль; за замовчуванням модель редактора; ≥90% упевненості без названих розбіжностей — валідно автоматично. `[вимога власника]`
- R-28 / review3/4 прибирається повністю; «Затвердити всю прозу як авторську» лишається окремим режимом. `[вимога власника]`
- З наявних даних видно, з яких версій зроблено кожен компонент. На книзі з 68 сцен перевірки потребують 19 зв'язків «план → завдання», 48 — «завдання → проза» і 0 — «проза → пам'ять». `[проба]` (див. «Проба 2»)
- Пам'ять — накопичувальний журнал із посиланнями на прозу всіх попередніх сцен. Заміна одного слова в прозі сцени 6 нині блокує пам'ять у 63 наступних сценах. `[проба]` (див. «Проба 3»)
- Зараз позначка «застаріле» блокує роботу у 4 із 16 повністю валідних сцен, а застарілими позначено 64 завдання з 68 проти 19 невалідних. `[проба]` (див. «Проба 2»)
- Ревізор на типовій моделі відрізнить справжню розбіжність від «все гаразд» за порогом 90%. `[виведення]`, ще не перевірено (див. «Питання до власника»)
- Власні записи пізніших сцен можна механічно перенести на новий журнал без моделі. `[виведення]`, перевіряється в PR 2
- Зміна чернетки валідність не змінює. Ревізор отримує, крім компонентів зв'язку, картки персонажів і канон як довідку, без стилю. Картки, збережені без автора (MCP, перерахунок складу сцени при збереженні плану), валідність не змінюють. `[виведення]`, рішення автора спеки

**Ключові рішення.**
1. **Три зв'язки зі своєю валідністю й відбитком.**
   - Зв'язки: З1 «попередня пам'ять + план → завдання», З2 «завдання + попередня пам'ять → проза», З3 «проза → пам'ять».
   - Відбиток зв'язку — ідентичність його компонентів. Пам'ять як компонент — це власні записи сцени, а не весь журнал.
   - Зв'язок валідний за побудовою (нижній компонент створено моделлю з поточних верхніх), за висновком Ревізора або за рішенням автора.
   - Відкинуто: окрема вісь із повною першою перевіркою (до 204 викликів) і «перевіряти лише застаріле» — обидва відхилено власником.
2. **Валідність стає позначкою «застаріле» для поточних голів завдання, прози й пам'яті.**
   - Усі читачі (`build_context`, readiness, бейдж сцени, експорт, MCP) отримують її з одного місця.
   - Чернетка й історичні версії працюють як раніше.
   - Відкинуто: залишити обидві системи. Тоді валідна книга однаково блокувала б запуск моделей.
3. **Рівноцінність прози для пам'яті.**
   - Коли зв'язок З3 сцени підтверджено після зміни її прози, стара й нова версії прози вважаються рівноцінними для пам'яті.
   - Журнали пізніших сцен лишаються чинними без жодного виклику моделі.
   - Відкинуто: перебудова пам'яті хвоста після кожної правки прози (десятки викликів за одне слово).
4. **Валідація — звичайний запуск черги з режимом `audit`** (сцена або книга):
   - перед запуском — попередній перегляд і план із відбитком;
   - зупинка зі станом `needs_review`, далі продовження.
   - Відкинуто: окремий протокол на зразок R-28 (саме його громіздкість і зламалася).
5. **Записи висновків — у наявній таблиці `app_settings`, без міграції SQLite.** Відкинуто: нова таблиця — зайва міграція для журналу, який читається разом з іншими записами твору.

Розглянуто стандартне: перевірка узгодженості через ембедінги чи пошук схожості — відкинуто, бо зв'язки сцени семантичні («проза відповідає завданню»), а схожість тексту цього не вимірює. Ще й потрібна окрема модель.

**Що стане гірше.**
- **Правки канону, стилю й налаштувань твору більше не позначають тексти застарілими.** Якщо такі правки й справді суперечать прозі, автор дізнається про це лише сам. Самостійне визначення залежних сцен — окремий пакет у майбутньому.
- **Висновок «валідно» спирається на самооцінку моделі.** Слабка модель може сказати «все гаразд» там, де розбіжність є. Захист: розбіжність з одним названим пунктом не стає валідною автоматично, і ти бачиш, хто підтвердив зв'язок.
- **Механічний перенос пам'яті може не зійтися.** Тоді сцена лишається «не перевірено», і на ній зупиниться валідація книги.
- **Це зміна поведінки, яку видно всюди:** бейдж, блокування запусків, MCP `get_story`, експорт. Старі звіти R-28 зникають з інтерфейсу.
- **Велика зміна:** чотири PR, видаляється близько 3 500 рядків коду й 17 вимог SPEC.

**Оцінка.** Власник: L щонайменше. Автор: L на межі XL — чотири PR в одній специфікації. Розбивка:
- видалення R-28 — 20%;
- ядро валідності (зв'язки, нова позначка «застаріле», рівноцінність прози, перенос пам'яті) — 30%;
- Ревізор і три перевірки — 20%;
- запуски, попередній перегляд і валідація книги — 15%;
- інтерфейс — 5%;
- SPEC, traceability, сайт uk/en — 10%.

Дешевшого варіанта без втрати вимог власника немає. Можна відкласти механічний перенос пам'яті й перебудовувати хвіст моделлю (варіант (б) з питання 1): мінус приблизно 5% роботи, плюс по виклику моделі на кожну пізнішу сцену при новій пам'яті.

**Питання до власника.**
1. **Нова пам'ять сцени k і хвіст книги.** Журнали пізніших сцен містять старі записи сцени k.
   - (а) Рекомендую: механічно переносити власні записи кожної пізнішої сцени на новий журнал. Де перенос не сходиться, сцена стає «не перевірено».
   - (б) Перебудовувати пам'ять хвоста моделлю: по виклику на кожну пізнішу сцену.
2. **Немає пам'яті** попередньої сцени чи самої сцени. Рекомендую зупинку з розбіжністю «немає пам'яті» й варіантом «Створити пам'ять» (платний запуск, лише з твоєї згоди). Альтернатива — пропускати й позначати «не перевірено».
3. **Дозвіл на платну пробу до $0,50 перед PR 3.** Три промпти Ревізора на 5 справжніх зв'язках твоєї книги плюс один із підкинутою розбіжністю, на типовій моделі `gemma-4-uncensored`. Мета — перевірити, чи поріг 90% відрізняє правду від хибного «все гаразд».

## Технічний опис

### 1. Компоненти й зв'язки

Компоненти сцени: попередня пам'ять (П₀), план, завдання, проза, пам'ять сцени (П). Чернетка й редактура — проміжні кроки, не компоненти.

| Зв'язок | Верхні компоненти | Нижній | Перевірка Ревізора |
|---|---|---|---|
| З1 | П₀, план | завдання | `audit_brief` |
| З2 | завдання, П₀ | проза | `audit_prose` |
| З3 | проза | П | `audit_memory` |

- **П₀** визначається через `previous_memory(view, scene, peek=True, require=False)`: остання попередня сцена в лінії книги, злиття або початок серії. Перша сцена книги без початку серії не має П₀; її З1 і З2 перевіряються без пам'яті.
- **Ідентичність пам'яті як компонента** — `memory_digest`: SHA-256 від нормалізованих власних записів сцени в журналі. Це записи, джерелом яких є проза цієї сцени: той самий розріз, що показує вкладка пам'яті. Ідентичність прози, плану й завдання — ID голови.
- **Відбиток зв'язку** — SHA-256 від упорядкованих ідентичностей його компонентів: З1 `(plan_id, p0_digest | None, brief_id)`, З2 `(brief_id, p0_digest | None, prose_id)`, З3 `(prose_id, memory_digest)`.
- Компонента немає — зв'язок `missing` (не невалідний). Валідність сцени рахується лише з наявних зв'язків.

### 2. Валідність зв'язку

Зв'язок валідний, якщо виконується (а), (б) або (в) і не діє (г):

- **(а) За побудовою.** Нижній компонент створено моделлю (`VersionRef.source_run_id` не порожній) з поточних верхніх.
  - **З1.** Знімок залежностей завдання має селектор `head/plan` цієї сцени, що дорівнює поточній голові плану. Селектор `head/memory` П₀ вказує на версію з тим самим `memory_digest`, що й поточна П₀.
  - **З2.** Проза — `edited` від моделі. Її селектор `head/draft` вказує на чернетку від моделі, а знімок цієї чернетки має поточне завдання й П₀ з тим самим `memory_digest`.
  - **З3.** Знімок пам'яті має селектор `head/prose` цієї сцени, що дорівнює поточній голові прози. Ручна правка пам'яті автором (`save_scene_memory`) теж валідна за побудовою: це твердження автора про факти, і вона записує поточну прозу в знімок.
  - Проза `manual` (ручна правка, імпорт R-46) і завдання без `source_run_id` за побудовою не валідні.
- **(б) Висновок Ревізора.** Останній `LinkVerdict` з `source='auditor'`, `outcome='valid'` і поточним відбитком.
- **(в) Рішення автора.** Останній `LinkVerdict` з `source='author'`, `outcome='valid'` і поточним відбитком.
- **(г) Інвалідація за карткою.** `LinkInvalidation` для цього зв'язку з поточним відбитком, новіша за останній валідний висновок, скасовує (а), (б) і (в).

Статуси зв'язку: `valid` (з джерелом `construction` / `auditor` / `author`), `unchecked`, `discrepancy` (останній висновок Ревізора з поточним відбитком — розбіжність), `unavailable` (останній висновок — переповнення входу або відсутня П₀), `missing`. Статус сцени: «Валідна», якщо всі наявні зв'язки `valid`. «Розбіжність», якщо є `discrepancy`. Інакше «Не перевірено».

Зміна чернетки відбитків не змінює. Перестановка сцен змінює П₀ і тому діє як зміна пам'яті.

### 3. Валідність як позначка «застаріле»

`storage/snapshots.py::_compute_freshness` для **поточної голови** `brief`, `prose` або `memory` активної сцени повертає:
- `incomplete` / `integrity_error`, як і раніше;
- інакше `stale=True` з причиною `link_unchecked`, `link_discrepancy` або `link_unavailable`, якщо вхідний зв'язок компонента (`brief` ← З1, `prose` ← З2, `memory` ← З3) невалідний;
- для прози — `stale=False`, якщо голова прийнята автором як авторська (`AcceptanceRecord` для неї), навіть за невалідного З2. Прийнята проза придатна як вхід для наступних сцен, але валідність сцени від цього не змінюється.

Для інших версій (чернетка, історичні версії, не голови) діє чинне порівняння знімка. Хуки R-28 (`review.store`, `impact_validity.valid_overlay`, `review_authority.revision`) вилучаються.

Читачі й те, що вони тепер бачать:

| Читач | Після R-44 |
|---|---|
| `generation/context.py:334` (`add()` у `build_context`) | нова позначка через `freshness` |
| `ContextView.effective_scene` / `Scene.needs_review` | З2 невалідний і проза не прийнята |
| `memory/reuse.py` `_candidate` (`needs_confirmation`) | П₀ придатна, якщо З3 попередньої сцени валідний; пари джерел, рівноцінні за розділом 4, не потребують підтвердження |
| `generation/readiness.py` | через `freshness` |
| Повнота експорту (`publication/book.py::capture`) | проза є і (З2 валідний або проза прийнята) |
| MCP `scene_state` / `get_story` | статус сцени й зв'язків замість `impact_status` |
| Масове затвердження прози (DATA-010-S02) | перелік — голови прози з невалідним З2, не прийняті автором |
| Бейдж сцени (`workspace-status.js`), «застаріла» у версіях | нові статуси |

### 4. Пам'ять: рівноцінність прози й перенос

- **Рівноцінність.** Коли З3 сцени стає валідним через Ревізора чи автора після зміни прози, записується `ProseEquivalence(scene_id, old_prose_id, new_prose_id, verdict_id)`. `old_prose_id` — проза, на яку посилаються журнали пізніших сцен.
  - `_candidate` вважає пару (old, selected) підтвердженою, якщо їх з'єднує ланцюжок рівноцінностей цієї сцени.
  - Журнали не переписуються; цитати й `validate_memory_journal` перевіряються проти старого тексту, як і зараз.
- **Нова пам'ять сцени k** (етап пам'яті або «Створити нову пам'ять»). Змінюється `memory_digest` сцени k, і З1, З2 сцени k+1 стають невалідними.
  - Пізніші журнали містять старі записи сцени k. За варіантом (а) з питання 1: для кожної пізнішої сцени по черзі її власні записи механічно переносяться на новий журнал попередника (`merge_memory_delta` + `validate_memory_journal`).
  - Нова версія отримує той самий `memory_digest`, тому відбитки сцен k+2… не змінюються.
  - Сцена, де перенос не проходить перевірку, лишається з попереднім журналом, і її З3 стає `unchecked` з причиною «перенос пам'яті не зійшовся».
  - За варіантом (б) перенос замінює запуск етапу пам'яті по хвосту з попереднім переглядом вартості.

### 5. Роль «Ревізор»

- **Реєстр** `roles.py`: `ROLES` += `'auditor'`, `ROLE_LABELS['auditor']='Ревізор'`. З'являється `ROLE_STAGES` (роль → етапи її промптів): `planner: ('prepare','brief')`, `auditor: ('audit_brief','audit_prose','audit_memory')`, решта — один етап. `ROLE_STAGE['auditor']='audit_prose'` (основна форма), `STAGE_ROLE` += три етапи → `auditor`. `roles.js` дзеркалить реєстр; MODEL-001-S03 продовжує діяти.
- **Налаштування.** `RoleSettings.stage_prompt_version_ids: dict[str,str]` (лише для ролі `auditor`, ключі `audit_brief` / `audit_memory`). Основний `prompt_version_id` — промпт `audit_prose`.
  - Твір без рядка `role_settings` для `auditor` бере налаштування редактора на льоту: провайдер, модель, timeout, режим відповіді. Ліміти входу й виходу беруться в планувальника, бо в редактора ліміт входу 80 000 символів, а вхід перевірки — як у етапу завдання (`[проба]`, «Проба 4»).
  - Збережені налаштування Ревізора стають власними.
- **Пресети.** `ProfileDocument.schema_version=3`, коли пресет містить Ревізора. Версії 1 і 2 імпортуються без нього, і Ревізор лишається як є. `role_profile_store` приймає набори `ROLE_SET` і `ROLE_SET - {'auditor'}`.
- **Політика** (MODEL-003/004): `STAGE_POLICY_ROLE` += `audit_*` → `auditor`. Окремі ключі згоди й позначки відмови (`model_consent:auditor:…`), шаблони `policy.block.consent.auditor` / `policy.block.refusal.auditor`. Етапи сценові (не `MULTI_SCENE_STAGES`).

- **Інтерфейс налаштувань.** Кнопка й форма Ревізора, три редактори промптів. «Спільний провайдер для всіх ролей» (MODEL-001-S01) охоплює й Ревізора.

### 6. Три перевірки

- **Збирач контексту** `generation/audit_context.py::build_audit_context(view, scene_id, link, settings)` читає застарілі входи, не відмовляє через позначку «застаріле»:
  - **П₀** — проєкція пам'яті для сцени (`memory_projection` з толерантним читанням журналу через `_candidate` без перевірки `needs_confirmation`);
  - **З1** — план сцени, П₀, завдання;
  - **З2** — завдання, П₀, проза;
  - **З3** — проза та власні записи сцени в журналі;
  - **довідка** — проєкція карток персонажів сцени (`project_characters`) і канон.
  - Структурні помилки (немає П₀, злиття без злитої пам'яті, чужі джерела) дають `unavailable` з поясненням.
- **Переповнення.** Якщо оцінка входу перевищує `max_input_chars` Ревізора, виклику немає: зв'язок `unavailable` з поясненням і обсягом. Текст не обрізається.
- **Промпти:** `generation/resources/audit_{brief,prose,memory}_{uk,en}_v1.txt`, мова — як у сцени.
- **Відповідь** (Pydantic, strict JSON schema за `response_mode='json_schema'`):
  - `confidence: int` (0–100);
  - `discrepancies: list[{text: str, quote: str | None}]` (до 20);
  - `summary: str`.
  - Розбирається через `unwrap_model_json`. Неправильна відповідь — збій спроби без висновку й без автоматичного повтору.
- **Поріг.** `outcome='valid'`, лише якщо `confidence >= 90` і `discrepancies == []`. Інакше `discrepancy`.

### 8. Рішення автора

`POST /api/scenes/{id}/links/{link}/decision {action, fingerprint}` — CAS за відбитком. Якщо відбиток змінився — 409.

| Зв'язок | Дія | Наслідок |
|---|---|---|
| З1 | «Затвердити завдання» | `LinkVerdict(source='author', outcome='valid')` |
| З1 | «Редагувати завдання» | відкриває редактор; нове завдання інвалідує З1, З2 |
| З2 | «Затвердити відповідність» | авторський висновок; DATA-010 не викликається (правило «затвердження як авторської не впливає») |
| З2 | «Редагувати прозу» / «Редагувати завдання» | відкриває редактор |
| З3 | «Залишити попередню пам'ять» | авторський висновок + `ProseEquivalence` |
| З3 | «Створити нову пам'ять» | запуск етапу пам'яті сцени з попереднім переглядом; далі розділ 4 |
| будь-який, `unavailable` | «Відкрити налаштування Ревізора» / «Створити пам'ять» (питання 2) | — |

Це нові авторські дії для завдання й пам'яті. DATA-010 досі казав, що для застарілого завдання й пам'яті прийняття немає. `memory_confirmation` (підтвердження ядра пам'яті) лишається окремим і на валідність не впливає.

### 9. Запуски

- **`RunRequest.mode='audit'`**, `audit_scope: 'scene' | 'story'`, `scene_id` для сцени, `audit_plan_fingerprint`.
- **`POST /api/stories/{id}/audit/preview`** (і для сцени) лише читає. Повертає:
  - невалідні зв'язки в порядку читання (сцена: З1 → З2 → З3);
  - кількість викликів;
  - верхню межу вартості `tariff.price(max_input_chars*4+256, max_output_tokens) × виклики` для хмарних моделей, для локальних — без USD;
  - відбиток плану.
  - Хмарний запуск вимагає ліміту твору й запуску, як інші запуски.
  - Попередній перегляд не є верхньою межею, якщо автор під час запуску змінить компонент. Інтерфейс це каже.
- **Виконання.** Worker на кожному кроці бере перший невалідний зв'язок у порядку читання, бо рішення автора змінюють набір.
  - `valid` → далі.
  - `discrepancy` / `unavailable` / немає П₀ → стан `needs_review`, фаза `awaiting_author`, посилання на зв'язок.
  - Продовження — `POST /api/runs/{id}/resume`. Скасування й пауза — між викликами.
- **Автоматично після масових змін:** у R-44 лише точка входу (попередній перегляд + згода). Викликати її буде імпорт R-46.

### 15. Відомі обмеження

- Самостійне визначення впливу правок карток, канону й стилю — поза обсягом.
- Поріг 90% не відкалібровано на моделях. Проба з питання 3 лише виявить, чи типова модель взагалі придатна.
