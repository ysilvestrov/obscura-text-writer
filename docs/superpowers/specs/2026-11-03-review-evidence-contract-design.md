# Перевірка узгодженості: докази, авторські пріоритети та завершеність

Дата: 03.11.2026. Статус: **погоджено користувачем; програмний контракт реалізовано. Модельну кваліфікацію й нові генерації не активовано**.

## Призначення та межі

Зміна стосується послідовної перевірки `storygen.review` (impact protocol3), а не загального оцінювача літературної якості. Мета — зменшити помилки категоризації та хибні зауваження через ігнорування авторських пріоритетів, зберегти придатні знахідки й прибрати залежність технічного прийняття від модельного самозвіту `complete`.

Користувач погодив підготовку специфікації гібридного підходу. Деталі нижче — запропоновані проєктні рішення; наступним прямим запитом користувач дозволив реалізацію. Платні виклики, ескалація та автоматичний допуск моделей залишаються поза цим дозволом. Чинна [SPEC.MD](../../../SPEC.MD) залишається джерелом поточної архітектури. Її розділ REVIEW-NEXT та чинні REVIEW-вимоги фіксують реалізований контракт; повний semantic допуск лишається окремим етапом.

Не входять: переписування сцени, автоматичний вибір правильного канону моделлю, визначення семантичної суперечності звичайним порівнянням рядків, зміна старих benchmark labels, перенесення авторитетності target у передумови, Cloudflare та зміна тарифів. Новий контракт не гарантує відсутності змістових пропусків.

## Підстави з тестувань

- [Авторське рев’ю](../../research/2026-11-01-round2b-owner-review.md): серед 27 secondary L3 сім відхилень через issue замість question, шість — через ігнорування явного пріоритету.
- [Офлайн-експеримент](../../research/2026-11-01-round2b-protocol-sensitivity.md): після прийняття структурно коректних complete=false у L3 valid 116→143/144, miss 24→9/84, але FP 17→23/60. Дев’ять ручних пар дали miss 7/84 і question-ok 12/12; це не автоматична перевірка нового контракту.
- L6: 87/144 відхилень missing_evidence. Послаблення вимоги доказів не доведене як корисне рішення.
- Лише C2 пройшов усі strict пороги на цьому корпусі. Зміна протоколу сама по собі не допускає L3 або інших моделей до автоматичного прийняття.

## Розглянуті підходи

1. Уточнити промпт, залишивши kind/complete моделям: найменша зміна, але не усуває нестабільність службових полів і не робить пріоритет машинним правилом.
2. Гібридний контракт: модель знаходить несумісність і повертає її адресовані докази; код перевіряє структуру, авторські рішення, категорії та виконання плану. **Рекомендований і обраний для цієї специфікації напрям.**
3. Другий модельний суддя для кожної відповіді: додаткові витрати, затримка й ризик залежних помилок; відкладено. Сам цей документ не дозволяє такі виклики.

## Поточна реалізація та точки зміни

`review/planning.py` формує повні інтервали й source-new × target покриття. `review/wire.py` перевіряє aliases, бюджет і complete; `wire_models.py` задає kind/complete. `proofs.py`, `runner.py`, storage `review_store.py` та acceptance прив’язують висновок до exact heads, raw і графа. Наявні механізми покриття, replay, CAS та accounting зберігаються; розширюються новими фазами й версійними правилами.

Додати окремі компоненти: реєстр адресованих тверджень і авторських рішень; перевірку witness; детерміноване розв’язання/класифікацію; незалежний облік task validity/coverage. Імена файлів і внутрішня декомпозиція залишені реалізатору. Storage-транзакції залишаються в Repository.review, UI не отримує права обчислювати authority.

## Дані й авторські рішення

### Адресоване твердження

Реєстр містить незмінний `statement_id`, source version/hash, роль source/target, точні Unicode code-point `start/end`, непорожню `quote`, scene/material та часову область застосування. `quote == original[start:end]`; жодного fuzzy matching або нормалізації переносів. Адреса належить переданому фрагменту, а не довільному місцю всього документа. Однакові байти з різних джерел не зливаються. Модель може запропонувати межі твердження лише всередині переданого інтервалу; код перевіряє їх і формує глобальний ID.

### Пріоритет

Замість числового рейтингу всіх документів — явне авторське рішення `preferred_statement_id`, `superseded_statement_id`, область дії, owner, operation_id, revision та exact hashes. Пріоритет стосується конкретних тверджень; він не підвищує весь документ і не дозволяє ігнорувати інші його твердження. Часова область є авторськими metadata, а не витягнутою моделлю датою. Для першої версії дозволена лише область поточної сцени й матеріалу; глобальні/умовні правила відкладено.

Редактор надає дію «Для цієї перевірки чинне це твердження» з двома цитатами та областю дії; підтвердження атомарне й append-only. Рішення відхиляється для чужого source, порожніх/змінних адрес, target як preferred source, циклу пріоритетів або вже несумісного рішення в тій самій області. Нове рішення явно замінює попереднє операцією, а не редагує його історію. Поточне текстове речення «А важливіше за Б» не стає metadata автоматично: UI дозволяє автору підтвердити таке рішення до запуску.

Реєстр рішень входить у snapshot/fingerprint, preview і task IDs. Зміна або скасування рішення робить попереднє acceptance неактуальним. Наявний run не приймає новий пріоритет потай: потрібен новий preview/план; незмінені докази зберігаються для історії, але не перевикористовуються без нової перевірки сумісності.

Для першої версії пріоритет **прямий, без транзитивного виведення**. У межах одного scope твердження не може одночасно бути preferred і superseded у різних чинних рішеннях. A>B та A>C дозволені; A>B разом із B>C відхиляються з вимогою явно визначити чинні пари. Для одного superseded допускається тільки один preferred; неоднозначні/перетинні області рішень блокуються до явної заміни. Це свідоме обмеження першої версії, а не автоматичний вибір у ланцюжку.

## Новий модельний контракт

Нові запуски явно обирають `impact_protocol=3`, `review_contract_version=4`; відсутність нового поля означає старий контракт3. Модель не повертає kind, aggregate complete, IDs задач, покриття або авторські пріоритети.

Кожна модельна відповідь містить `candidates` і `analysis_status: done | unable`, з коротким `reason` для unable. `done` не доводить повноту розуміння; `unable` блокує позитивне завершення частини. Це явна відмова виконати змістову роботу, а не старий неоднозначний complete=false. Порожні candidates дозволені лише за done; до чистого report усе одно потрібні всі зовнішні gates.

Кандидати — discriminated union:

- `contradiction`: `left` і `right` (локальний ref, start/end, quote), `explanation` конкретної несумісності. Кожен кандидат — одна пара, одна несумісність; не список можливих доказів.
- `information_gap`: `target` із точною цитатою, `source_refs` у доступному scope (можуть бути порожні), `missing_information`, `why_needed`. Відсутність передумови не оголошується суперечністю; без конкретної необхідності для перевірки сцени питання не приймається структурним контрактом. Змістова доречність лишається модельною оцінкою.

Обов’язкові caps рядків, цитат і кількості кандидатів версіонуються в native schema й текстовому fallback. Планувальник вимірює повний запит/схему та результат із цитатами; переповнення не лікується обрізанням. Перед dispatch, якщо мінімальна частина не вміщується, конкретний blocker і новий preview замість збільшення бюджету потай.

Для delta зберігається окремий compact опис before/current з доказами належної old/new сторони, але без aggregate complete. Delta не створює issue для сцени. Підсумок і авторські labels генерує код; synthesis може додавати лише власні валідні кандидати, не видаляти дочірні.

## План перевірки та конфлікти передумов

1. Заморозити target/source snapshot, історичну базу, авторські рішення та налаштування. Підготувати delta за historical_delta; у current_consistency не вигадувати історію.
2. Перевірити передумови окремою фазою `premise_check`: кожен source-new інтервал самостійно для внутрішніх суперечностей та всі неупорядковані пари різних чинних source-new інтервалів, включно з різними інтервалами одного джерела. Формально покриття містить пари інтервалів i≤j; i=j означає один доставлений інтервал із перевіркою всіх тверджень усередині нього. Endpoints одного witness при цьому повинні бути різними твердженнями. Overlap-ідентичні твердження й дублікати нормалізує код; їх не вважають суперечністю самим фактом повтору. План забезпечує доставку кожної пари, але це не доказ її змістового опрацювання.
3. Побудувати граф **повернутих моделлю** суперечностей між твердженнями. Застосувати явні авторські рішення у відповідному scope. Напрям пріоритету не вигадується з порядку документів, ролі моделі або target. Несумісність не є транзитивною: A↔B і B↔C не доводить A↔C. Авторське відкидання B щодо A не відкидає інші твердження документа B.
4. Перевірити всі source-new × target інтервали. Чинні, відкинуті й невирішені твердження передавати з окремими machine-owned позначками. Модель не може переписати ці позначки. Для кожної задачі необхідні релевантні завершені premise proofs; втрата метаданих під час пакування заборонена.
5. Звести збережені валідні кандидати й блокери кодом. Для нових міжфрагментних кандидатів synthesis повинен отримати точні кінці та контекст, потрібний для порівняння; короткий child summary не замінює оригінальні докази.

Кількість пар premise Check — квадратична за інтервалами; усі джерела, що вміщуються разом, пакуються в один виклик з явним premise_pairs, без втрати міжгрупових порівнянь при розбитті. Додаткова межа preflight під час розбиття —100000 пар. Preview показує початкові фази окремо й включає forced synthesis навіть для одного leaf; фактичні докази можуть змінити пакування, тому кількість є початковою оцінкою. Межа викликів однієї сцени —10000; платний preview показує її консервативну вартість окремо від пам’яті й майбутніх сцен; початкова межа — чинні 10000 задач разом з іншими фазами, без прихованого sampling. Якщо план не вміщується в бюджет/контекст/ліміт, він не запускається; користувач отримує причину. Пошук тристоронніх логічних суперечностей без жодної попарної несумісності не гарантується першою версією і явно зазначається серед обмежень.

## Детермінована категоризація

| Підтверджена структурою ситуація | Результат коду |
| --- | --- |
| Source↔source без авторського розв’язання | question / premise_conflict |
| Source↔source із чинним рішенням | resolved_premise_conflict, у журналі; саме по собі не issue |
| Target↔чинне однозначне source-твердження | issue / contradiction |
| Target↔явно відкинуте твердження в тому самому scope | suppressed / superseded_source, не показується як потрібна правка |
| Target↔source-твердження, залучене до невирішеного конфлікту | question / premise_conflict; не вимагати правку target до рішення автора |
| Конкретна необхідна прогалина | question / information_gap |
| Target↔target, невідомі endpoints або недостатні докази | rejected candidate із кодом причини; не clean |

Прив’язка target-кандидата до конфлікту відбувається за statement IDs/точними адресами, а не лише за спільним source document або зв’язністю графа. Якщо модель посилається на ширший перетинний уривок і не можна однозначно визначити чинність твердження, кандидат отримує `authority_ambiguous`; частина не є чистою. Текстове пояснення не може обійти цю перевірку.

Код не встановлює, чи цитати насправді суперечать одна одній, і не перевіряє всю прагматику information_gap. Точний цитатний збіг — доказ походження, не істинності висновку. У UI це модельне зауваження; право остаточного рішення залишається автору.

## Завершеність, часткове збереження та authority

Облік ведеться незалежно для transport (stop/refusal/length/error), envelope/schema, кожного кандидата, запланованого покриття і зведення. Report містить `execution_state: complete | partial | blocked`, accepted candidates, rejected diagnostics та точні unresolved task IDs. `semantic_completeness` не заявляється; повний report означає виконання контрактного плану.

Чистий автоматичний acceptance можливий лише коли: всі заплановані задачі мають completed/stop proof; envelope/schema/caps чинні; analysis_status=done; немає rejected candidates, невирішених задач/питань/issue/authority ambiguity; покриття точне; synthesis зберіг усі знахідки; replay і CAS пройшли. Порожній JSON сам по собі не створює authority. Автоприйняття доступне лише для окремо кваліфікованого профілю нового контракту.

Якщо envelope валідний, кандидати перевіряються незалежно. Валідні зберігаються для перегляду, а невалідні — з причиною; report partial, чисте acceptance заборонено. Невалідний JSON, дубльовані ключі, truncated/refusal/length, перевищений cap або невірна envelope-схема не дають прийняти навіть видимі фрагменти; raw зберігається лише для діагностики. Жодного автоматичного JSON repair або повтору.

Стан сесії при частковому результаті — наявний failure/pause шлях з явним повтором, а не звичайне awaiting_author із правом відхилити все й продовжити. Читання partial findings дозволене. Author rejected/revised acceptance цього report блокується; зміни тексту автором можливі як звичайна редактура, після неї новий preview. Це запобігає обходу incomplete gates через авторську кнопку.

Усі child candidates наслідуються кодом. Synthesis не може перетворити partial/unable на complete або приховати питання. Дедуплікація за нормалізованими парою statement IDs, типом і scope; напрям цитування не створює дубль. Різні пояснення тієї самої пари зберігаються як provenance, але багатофактова пара не зливається автоматично в один доведений факт.

## Збереження, API, відновлення й сумісність

Пропонується review report/acceptance schema4 у відокремленому `review4` namespace `app_settings`, через той самий Repository.review facade; SQL-міграція не потрібна. Records містять contract version, prompt/schema/classifier versions, exact authority decisions, normalized statements/witnesses, diagnostics та proofs. Acceptance4 посилається лише на перевірений report4; authority3 не оголошується authority4 і навпаки. Effective freshness враховує обидві версії за їхніми власними правилами.

Спільний бар’єр authority: для scene/material зберігається монотонний `authority_revision`, початково 0. Кожне створення/заміна/скасування пріоритету атомарно збільшує ревізію. Усі нові report/acceptance фіксують її; legacy без поля означає 0. Чинність acceptance будь-якого походження (включно review3 і native baseline) потребує рівності з поточною ревізією на додачу до своїх наявних gates. Старі записи не змінюються, але не обходять нове авторське рішення. Для ревізії >0 контракт3 не може створювати нову authority: preview/start/decide повертає blocker «Для авторських пріоритетів потрібна перевірка нового формату». Скасування всіх рішень не скидає ревізію й не оживляє історичне прийняття. Нове повне acceptance4 або явна авторська дія за чинним повним report4 відновлює актуальність. Під час rollback сервера з активними review4 metadata запуск старої версії потребує окремої перевірки сумісності; без неї downgrade не підтримується.

API capability: `review_contract_versions: [3,4]` після реалізації. Старий клієнт без поля запускає контракт3. Явний 4 на старому сервері відхиляється як unsupported; UI не надсилає його без capability. Preview повертає contract_version, кількість задач за фазами, bound вартості та blockers; report API — стани, типи, причини й доступні авторські дії. UI не показує службові JSON/aliases як пояснення.

Fingerprint включає контракт, класифікатор, рішення пріоритету, exact target/source heads, basis mode, scopes, граф і налаштування. Resume/backup/fsck відтворюють raw→кандидати→класифікацію→report тим самим версійним кодом. Зміна body, raw, endpoint, рішення, графа чи результату не дозволяє acceptance. Докази завершених частин повторно використовуються тільки за exact identity й dependencies; жодного dispatch під час читання/replay.

Старі protocol1/2, review3 reports/plans, prompts, bindings і frozen research outputs читаються без перезаписування. Новий prompt/schema потребує нової local-counter qualification/binding; відсутність чинної кваліфікації дає явний preflight blocker за правилами чинного token subsystem. Прихований fallback на стару модель/контракт заборонено.

## Користувацька документація й інтерфейс

UA/EN узгоджено пояснюють «Потрібна правка», «Конфлікт передумов», «Бракує даних», «Перевірку не завершено», дві цитати й авторський вибір чинного твердження. Для source conflict користувач обирає пріоритет, а не отримує автоматичну правку сцени. Для partial показуються знайдене і перелік неперевірених частин, без зеленої позначки актуальності. Документація встановлення змінюється лише якщо реалізація додасть залежності; наразі нові залежності не потрібні. Нейтральні знімки UI оновлюються разом із реалізацією, не із цим проєктом документа.

## Приймання та оцінювання

Спочатку offline unit/integration тести класифікатора, scopes, пріоритетів, парного покриття, partial isolation, proof replay, CAS, backup/fsck, legacy і UA/EN UI. Для кожного сценарію REVIEW-NEXT із SPEC під час реалізації потрібен конкретний автоматичний тест у traceability. Наявна ручна процедура нижче перевіряє лише проєкт документа, не працездатність майбутньої функції.

Новий benchmark — окремий версійний контракт і frozen до генерацій план. Включити clean із явним пріоритетом, рівноправні конфлікти, частково суперечливий документ, незалежні твердження в одному джерелі, зміну пріоритету, цикли, неоднозначні адреси, information gaps, порожні/часткові результати, багатофактні й міжфрагментні приклади. Потрібні нові авторськи перевірені приклади поза старими 48; старі 720 — діагностика, не незалежний holdout.

Порівнювати однакові профілі на парних прикладах; не змінювати одночасно модель і контракт. Окремо вимірювати FP, miss по фактах, знайдені суперечності, правильну категорію, структурну придатність, завершений план, пріоритетні помилки, повторюваність та число/вартість викликів. Partial clean не зараховувати як TN; invalid лишаються у знаменниках. Зауваження без доказів не стає TP.

Початкові орієнтири для набору зі знаменниками 60 clean /84 issue-факти /144 відповіді: FP≤7, miss≤10, structural valid≥137; вони не є статистичною гарантією. Додаткові gates: 0 priority violations на явних контрольних прикладах; 0 неповних/пошкоджених proofs, що створили authority. Точний склад нового набору, бюджети та рішення про модель затверджуються окремо до запуску; вони не погоджені цим документом. Нових API-викликів для написання специфікації — 0.

## Порядок поставки та ризики

Пакет 1: адресовані твердження, рішення автора, версії та invalidation. Пакет 2: новий wire, premise-план, парні докази й класифікатор. Пакет 3: partial, authority, replay/backup і UI. Пакет 4: offline qualification, документація та окремо погоджене модельне оцінювання. Це залежності обсягу, не готовий план реалізації; кожен пакет потребує актуалізації відповідних чинних Requirements/Scenario у SPEC тим самим набором змін із кодом.

Основні ризики: квадратична кількість source-пар і нові витрати; ширші цитати можуть не збігатися з межами авторських тверджень; модель може знаходити вигадану несумісність попри правильні адреси; pairwise-пошук не гарантує всіх складних залежностей; дотримання done залишається самозвітом. Протидія — вимірюваний preflight, точні scopes, fail-closed authority, окремий semantic benchmark і авторське рішення.

## Ручна процедура перевірки проєкту

<a id="design-review"></a>

Ця процедура збережена як історія design review і **не є runtime-прийманням**; програмні сценарії вже пов’язані з конкретними тестами traceability, модельне оцінювання не активовано. Для кожного REVIEW-NEXT-S01…S08 прочитати відповідний розділ цього документа та сформувати приклад з очікуваним результатом:

1. S01: два суперечливі твердження та третє незалежне в тому самому документі; пріоритет відкидає тільки явно вибране твердження, stale hash не переносить рішення. A>B і B>C відхиляються, A>B і A>C дозволені.
2. S02: точні endpoints у доставлених фрагментах проходять; цитата поза фрагментом/зі зміненим переносом або target↔target не дає clean.
3. S03: нерозв’язаний source conflict дає question; авторськи розв’язаний не створює issue сам по собі; target проти чинного твердження дає issue, проти відкинутого — suppressed.
4. S04: вилучена source-пара, самостійна перевірка одного інтервалу, target-інтервал або premise proof блокує complete; перевищення задач/бюджету зупиняє preflight. Один фрагмент із двома суперечливими твердженнями не випадає з плану.
5. S05: валідний кандидат зберігається поруч із відхиленим, але partial не дозволяє жодного acceptance; unable/length/invalid JSON також не дають clean.
6. S06: mutation raw/decision/graph змінює replay/authority; старий report3 читається старими правилами й не конвертується. Зміна authority_revision блокує старе acceptance3/native baseline; нова спроба контракт3 не обходить бар’єр, скасування пріоритетів не відновлює старої authority.
7. S07: старий клієнт обирає 3; новий бачить capability, цитати, UA/EN статуси і тільки дозволені дії; reload не запускає inference.
8. S08: старі 720 не оголошуються незалежним тестом нового контракту; нові виклики/допуск не відбуваються без окремої активації.

Зафіксувати питання рев’ю й виправлення до погодження. Під час реалізації замінити/доповнити ручні зв’язки конкретними тестами; фактичні прогони записувати через `scripts/verify.py` у `docs/STATUS.md`. Наявність цієї процедури не означає успішного виконання сценаріїв.


Уточнення реалізації: у delta candidates SHALL бути порожнім (maxItems=0), пошук source-конфліктів виконує premise-фаза. В інших фазах maxItems=4 однаково в native/text schema та runtime; загальний character cap незалежний. Partial report містить unresolved_task_ids та task-tagged diagnostics; explicit repeat повторює лише непридатні задачі й нащадків. У першій поставці автоматична authority4 заблокована для всіх профілів до окремої semantic кваліфікації; автор може прийняти тільки повний перевірений report4.
