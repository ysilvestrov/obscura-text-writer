# R-28b — Перевірка впливу частинами

Статус: погоджено власником 26.10.2026; план та реалізація в поточному чаті. Чинні контракти R-28 у SPEC.MD зберігаються до поставки розширення.

## Проблема та фактичні виміри

Ліміти не збільшують запит: preflight зупиняється на першому перевищенні. На поточному творі дельта сцени9 має80403символи/138612оцінених токенів; після збільшення межі виявляється check сцени5 —167996символів/279642токени. Для сцени5 old/new джерела мають140072символи сумарно, унікальні дослівні тексти —75805. Це виміри локального складання, без API моделей. Ліміт символів незалежний від токенів; виправлення діагностики поставлено окремо,6e048cc.

## Погоджений напрям

Повне покриття частинами, а не заміна джерел конспектом. Планувальник залишається моделлю обох фаз. Автор явно переглядає кількість частин і верхню оцінку витрат, задає ліміт запуску. Автоматичних платних перевірок і повторів після відмови немає. Висновки ніколи не переписують рукопис.

## Запропоноване рішення

### 1. Незмінний маніфест і усунення повторів

Після захоплення вихідних target/source fingerprint формується детермінований manifest. Однаковий дослівний текст передається один раз у словнику документів з SHA; старі/нові посилання кожної передумови збережені окремо. Незмінна пара посилається на один документ. Дедуплікація не зливає різні selector IDs, coverage чи історичні бази. Порожні значення й зміни лише ID лишаються явними.

Manifest містить protocol version, налаштування планування, повний список джерел, діапазони Unicode-символів, primary/overlap діапазони target, стабільні task IDs і порядок. Source text та target зберігаються локально повністю; API отримує лише відповідну частину. Немає майбутньої прози чи обходу часової проєкції персонажів.

### 2. Бюджетований розподіл

Розбиття виконується за фактичним generation_request і чинною оцінкою токенів, з урахуванням system prompt, JSON/schema, метаданих, reserve для відповіді й контексту наступної фази. Окремо дотримується max_input_chars. Число символів не замінює токенну перевірку.

Спочатку розкладаються пакети передумов; цільова сцена залишається цілою, якщо вміщується з пакетом. Якщо один документ чи target сам завеликий — розбиття за абзацами/реченнями з обмеженим перекриттям; fallback усередині довгого абзацу з точними offsets. Усі основні діапазони покривають джерело від0доlen без пропусків. Перекриття не зараховується як нове покриття. Жодного мовчазного обрізання чи збільшення налаштувань.

Діапазони old/new прив’язані до оригіналів, зміщення не видаються за сюжетну відповідність. Модель має контекст меж і знає, що відсутній у частині факт міг переміститися до іншої частини. Розбиття та зведення не змінюють оригінальні цитати.

### 3. Дельта, перевірки та зведення

Спочатку всі частини змінених old/new джерел дають часткові дельти з точними посиланнями й uncertainty. Після цього перевіряються частини цільового матеріалу проти повної змістової дельти та пакетів дослівних джерел/контексту. Маніфест явно перераховує потрібні комбінації й покриття; висновок одного пакета не є висновком усієї сцени.

Окремий завершальний синтез перевіряє взаємодію змін між пакетами й суперечності між частковими результатами. Він отримує зведені дельти/висновки та посилання на збережені докази. Якщо зведення саме завелике — бюджетоване багаторівневе зведення з явним покриттям дочірніх результатів. Модельні конспекти доповнюють перевірку оригінальних джерел; вони не підміняють її. Пропуски, недоступні докази чи unresolved uncertainty блокують позитивне очищення.

Фінальне рішення валідується кодом: changes_required — наявні перевірені findings; no_impact — усі обов’язкові частини/зведення успішні, coverage повне, findings відсутні й uncertainty немає; інакше uncertain/незавершена перевірка. Негативний і позитивний висновки мають окреме пояснення. Знахідки дедуплікуються за точним target range, причиною та джерелами; різні зміни не губляться. Цитати перевіряються проти повного оригіналу й фактично переданого діапазону.

Пам’ять перевіряється окремими частинами; неповне її coverage не стає none_found. Історичні джерела та forwarding не переписуються.

### 4. Черга, бюджет і відновлення

Task IDs залежать від manifest і діапазонів. Кожна модельна спроба має checkpoint, input manifest fingerprint, raw response, coverage та usage. Pause/cancel діють між викликами й через поточний механізм скасування активного. Crash recovery повторно використовує тільки повністю перевірені completed/stop відповіді.

Відмова або технічна помилка зупиняє серію без автоматичного повтору; успішні частини зберігаються для відновлення. Відмова не стає висновком про текст. Незавершений набір не очищує застарілість. Уже завершені звіти інших сцен зберігаються.

Перед початком показуються manifest, кількість/верхня межа викликів і консервативна оцінка вартості включно зі зведеннями. Ціна залежить від запитів частин, не від одного гігантського payload. Run/story cap лишаються жорсткими. Якщо фактичний результат потребує додаткового розбиття понад погоджений manifest/резерв, запуск зупиняється для нового preview, а не збільшує витрати мовчки. Зміна налаштувань не дає dispatch несумісної частини без нового preflight.

### 5. Зберігання й сумісність

Нові manifests/reports мають окремий protocol/schema version і посилання на ВСІ proof attempts. Старі R-28 v1 звіти та їх історія залишаються валідними за старим валідатором; не робиться вигадана міграція старих доказів у частини. Старі незавершені запуски не змішуються з новим протоколом.

Atomic publication і live target/source CAS виконуються лише для цілісного зведеного висновку. Зміна авторського тексту/передумов під час серії залишає спроби для перегляду, але не застосовує результат. Backup/fsck перевіряють повний граф manifest→attempts→coverage→report. За можливості використовується чинний app_settings/blobs без SQL-міграції; остаточно підтвердить план реалізації.

### 6. Інтерфейс

Панель «Редагування книги» зберігається. Preview показує кількість сцен/матеріалів, частин і зведень, модель, ліміти й витрати. Під час виконання — поточна сцена/матеріал, фаза й частина N/M; оцінку/межу позначено явно. Висновок містить цілісні findings із контекстом, а технічні деталі частин доступні в розгортаному блоці. UA/EN, збереження dirty buffers і явний запуск зберігаються.

## Перевірки та критерії приймання

- Детермінізм, Unicode/Markdown offsets, дублікати old=new, довгі абзаци, moved/deleted facts і coverage без прогалин.
- Кожен серіалізований запит вміщується в обидва ліміти; завеликий мінімальний службовий пакет дає конкретну помилку.
- Неповна/підроблена coverage, відсутня спроба, неправильна цитата, output_limit/refusal не очищують сцену.
- Спільний висновок враховує суперечливі часткові звіти й залежності між пакетами; окремі no_impact недостатні.
- Збереження й crash recovery без повторного dispatch; зміна inputs/settings, pause/cancel, жорсткі фінансові межі.
- Roundtrip backup/fsck для нового протоколу, старі v1 звіти й черга без регресій.
- Синтетичний довгий твір і browser UA/EN desktop/mobile. Окремий безкоштовний dry-run на чинному творі: кількість/розміри частин без надсилання текстів провайдеру.
- Реальні платні випробування лише після окремого погодження бюджету й матеріалів; літературна достовірність не оголошується доведеною тестами.

## Обмеження

Повне покриття означає перевірену доставку й обробку всіх потрібних діапазонів, а не математичний доказ модельного розуміння. Розбиття й багаторівневий аналіз можуть пропускати далекі взаємозв’язки; фінальний синтез зменшує, але не усуває цей ризик. Вартість великих серій може бути значною, тому preview і cap обов’язкові. Великі задачі можуть потребувати багатьох викликів; UI не обіцяє постійного малого числа.
