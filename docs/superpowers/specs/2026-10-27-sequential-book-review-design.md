# Послідовна авторська перевірка книги — дизайн

Статус: дизайн погоджено власником27.10.2026, реалізація триває; runtime ще не змінено. Автор погодив27.10.2026 послідовний процес і автоматичне оновлення пам’яті після власних правок. Цей документ визначає запропоновану реалізацію; чинна архітектура лишається у SPEC.MD до implementation commit.

## Мета та погоджені рішення

Автор запускає перевірку, оскільки вважає позначку неактуальності потенційно формальною. Система переглядає сцени за порядком: валідний завершений пошук без зауважень автоматично приймає сцену й переходить далі; на зауваженнях зупиняється для автора. Додаткової кнопки підтвердження чистого результату немає.

Автор відхиляє всі зауваження → авторське прийняття поточних матеріалів → наступна сцена. Автор обирає частину зауважень для роботи → вручну змінює текст або явно запускає наявні AI-assisted/generation можливості → приймає актуальну прозу → «Завершити правки й продовжити» → автоматичне оновлення пам’яті → наступна сцена. Обов’язкового повторного модельного оцінювання виправленої сцени немає. Остаточне рішення автора — окрема підстава актуальності.

Автоматичне оновлення пам’яті погоджене окремо: використовує роль memory, її звичні schema/evidence/chronology/budget gates. Помилка пам’яті не губить авторських правок, але зупиняє перехід до наступної сцени. Незбережений буфер не надсилається моделям.

Рішення автора й моделі залишаються різними записами. Машинний результат позначається «зауважень не знайдено», авторський — «прийнято автором»; жоден не є гарантією літературної безпомилковості. Підвищення якості моделі не є умовою існування цього workflow: автор прямо обрав best-effort автоматичний перехід за відсутності зауважень.

## Підходи та вибір

1. Лишити заморожений book-wide DAG і зупиняти його після сцени. Мінімум змін, але авторські виправлення роблять заздалегідь збудовані наступні inputs застарілими; для нормального продовження потрібні нові плани/запуски. Не відповідає погодженому процесу.
2. Сесія з незмінним порядком scene IDs і окремим свіжим планом поточної сцени. Авторське рішення завершує її; наступний план створюється з актуальних матеріалів і пам’яті. Рекомендований автором документа спосіб реалізації погодженої поведінки.
3. Кілька пошуків + модельний суддя на кожному кроці. Дорожче; R-28i не показав покращення. Не включати в першу реалізацію.

Власник обрав продуктовий процес, а не внутрішній формат storage; підхід2 є технічною пропозицією цього дизайну, що підлягає погодженню разом із ним.

## Межі першої версії

- Наявна роль planner для пошуку, reasoning вимкнено як у перевіреному local-профілі. Немає нової ролі судді, автоматичних повторів або переписування тексту за знайденим зауваженням.
- Зберігаємо чинний матеріальний scope impact: збережені brief/prose, придатні до перевірки. Сцени групуються за порядком. Відсутні draft/prose не генеруються як наслідок перевірки; пропуск відображається як «немає матеріалу», не як позитивний висновок. Актуальні матеріали можна пропускати без модельного виклику. В UI явно вказано, які матеріали сцени розглянуто.
- Плани, канон, доступні на момент сцени персонажі, попередня проза та пам’ять лишаються джерелами за чинними dependency/future-horizon правилами. Майбутня проза/пам’ять не стають минулими подіями.
- Один логічний пошук сцени може мати кілька фізичних викликів для дельти/частин/зведення. Не обіцяємо один API call на сцену або одну фіксовану кількість викликів на всю сесію.
- Зміна тексту/ролі для редактури чи регенерації виконується чинними інструментами, за явним запитом автора і чинним preflight. Сам вибір зауваження «виправити» не запускає генерацію.
- Full story co-editing/concurrency R-15, нові моделі, publish/export і примусова перевірка після авторського прийняття не входять у пакет.

## Оркестрація

Нова сесія використовує чинний Run з mode=impact та окремим impact.protocol=3. Run/scene IDs, events, terminal states, worker exclusivity та cancel/pause семантика зберігаються. Старі protocol1/2 лишаються доступними для читання/відновлення зі своїми frozen inputs; вони не конвертуються непомітно.

Run.impact зберігає scene_order, scene_cursor, phase, перевірені scene checkpoints, current_scene_plan, current_report_id, author_decision_id, pending_memory, settings snapshots та витрати. Підфази: prepare_scene → search → auto_accept або awaiting_author → author_accept → memory_refresh → advance. Для очікування автора використовувати чинний needs_review; для error — failed, для external source conflict — alternative. Відображення subphase не вимагає нових глобальних run states.

scene_order фіксується при старті, але текстові inputs майбутніх сцен не заморожуються наперед. Перед кожною сценою будуються нові dependency snapshot, target hashes, source selectors, поточна memory prefix і bounded subplan. Після авторських правок не намагаємося продовжити старий downstream manifest.

Перестановка/видалення/додавання сцен під час сесії зупиняє її з конкретним поясненням і новим preview порядку. Уже прийняті записи зберігаються й можуть лишатися чинними за точного збігу залежностей. Зміна налаштувань застосовується з наступного етапу; активна спроба завершується зі своїми frozen settings. Новий stage завжди проходить актуальний preflight.

Автоматичний перехід виконується лише якщо всі обов’язкові матеріали/частини сцени завершені, schema/refs/full source-target coverage/CAS перевірені й список зауважень порожній. Немає вимоги ручного підтвердження model-no-concerns. Валідне модельне питання є зауваженням автору. Технічна помилка, output truncation, incomplete або неповний graph не є порожнім успішним результатом.

## Модельний контракт пошуку

Versioned wire3 із phase-specific schemas, без спільного summary/verdict/evidence-list receipt. Код володіє coverage та довгими ID; короткі task-local references прив’язані до конкретних змін/зауважень.

- delta/reduce_delta: complete, короткі changes old→new з exact proof references, конкретні unresolved_questions. Роль дельти — зміни передумов, не вердикт про сцену. Зіставлення сторін через chunks не робить відсутність фрагмента доказом видалення факту.
- check: чинні current rules/передумови + original target passages; результат complete, concerns, carry_refs. concern має kind=issue|question, change_refs, target_refs, source_refs, коротке message. Немає required_change із порадами змінити канон, global uncertainty prose або обов’язкового «усе добре» summary. Модель не формує URL/offsets.
- synthesis: нові міжфрагментні concerns та потрібні carry_refs; старі concerns/їхні proofs успадковує код. Root не втрачає локальні concerns, не перетворює unresolved question на clean. У root carry далі не потрібний.

Пошук current-only не отримує скасовані before як чинні правила; old/provenance лишаються у delta/history. Проміжний carry містить лише addresses до точних оригінальних тверджень, не довільний переказ. Відбір моделей все ще може помилятися; code coverage не видається за гарантію семантичної повноти.

Межі масивів/рядків визначаються output та input packing, не універсальним maxItems100. Якщо модель не може вмістити необхідний результат, incomplete зберігає partial concerns і зупиняє сцену. Code-owned registry/DAG не розгортається в копії цитат у кожному model output. Перед кожним наступним dispatch рахується фактичний вхід з потрібними цитатами/schema; непоміщення не обрізається. Усі джерела/target діапазони доставляються за чинним full-coverage принципом, але в рамках поточної сцени.

Нове system/schema binding tokenizer кваліфікується окремо. Доти допустимий тільки явний conservative fallback із правдивими preview-числами. Старі qualified profiles не переписуються.

## Авторське рішення

Concerns отримують code IDs і власний immutable report. Для кожного автор обирає «Відхилити» або «Врахувати в правках». Поки є невирішені concerns, авторський checkpoint не завершується; пакетне «Відхилити всі й далі» є явною дією, а не неявним трактуванням незнятої галочки.

Відхилення всіх concerns на незмінених heads створює author_acceptance й одразу дозволяє перехід, якщо memory prefix чинний. Після вибору concerns для правок лишаємося на сцені; автор користується звичними вкладками/інструментами й явно завершує роботу. Частковий Save не переводить на наступну сцену.

Завершення правок приймає поточні збережені heads. Новий draft/proposal сам по собі не є чинною прозою: потрібен звичний вибір/прийняття prose. Конкурентна зміна heads або dependencies після показаного author acceptance preview дає409 і зберігає буфер/історію. Автор може прийняти поточний текст як є навіть коли спочатку планував правку: це має бути явно названою авторською дією, а не фальшивою позначкою «виправлено».

Рішення зберігає оригінальні report/concern IDs, per-concern dispositions, exact accepted brief/prose versions/hashes, актуальний source snapshot, спосіб прийняття model_no_concerns|author_rejected|author_revised, час і operation ID. Відхилені concerns не пропонуються знову для того самого accepted snapshot; нові dependencies не успадковують старе рішення автоматично.

Model proof не переписується на no_impact після авторського відхилення. Author acceptance — окремий authority record, достатній для відповідних material freshness resolvers, але не для автоматичного прийняття пам’яті або evaluator result. Прийняття brief у цьому потоці окреме від наявного R-05 accept_draft/accept_prose; не розширювати старий record так, щоб старі readers почали неправильно трактувати матеріал.

## Пам’ять та префікс

Для сцени n використовуємо тільки чинний префікс1…n-1; memory n будують із цього префіксу та обраної prose n. Нові авторські правки стають джерелом наступної сцени після успішного checkpoint memory, не після модельного припущення.

Після зміни prose n автоматичний memory stage обов’язковий перед advance. За незмінної прози й чинної own memory нового виклику немає. Прийняття прози не дорівнює прийняттю історичних цитат пам’яті.

Через cumulative journal зміна ранньої сцени може робити memory наступних сцен застарілою, навіть якщо їхня проза коректна. Сесія підтримує memory prerequisites по порядку: використовує exact validated current checkpoint без виклику, коли це дозволяє чинний контракт; інакше автоматично перебудовує потрібну пам’ять роллю memory. Не реалізовувати новий fuzzy rebase старих update/retire або семантичне перенесення claim IDs у цьому пакеті. За потреби model-free reuse дозволений лише чинним точним правилам, не за припущенням «текст приблизно той самий».

Перед поточною сценою можуть знадобитися memory-only кроки попереднього префіксу, а після її прийняття — її own memory для наступної. Preview і budget зобов’язані показати цю можливість: до одного memory-call на відповідну сцену кожного нового snapshot без автоматичних повторів. Якщо material/context memory не вміщується, потрібна окрема явна конфігурація; прозу не обрізати.

Некоректна/історична пам’ять не використовується як поточна потай. Звичний механізм авторського погодження historical evidence зберігається окремо; загальний старт review не є згодою на конкретний ризик. Помилка schema/evidence/refusal/timeout/budget зберігає author acceptance/prose й pending_memory checkpoint; після відновлення не повторює вже завершені stages. Прапорці «передавати далі», ручні записи й їхні provenance не губляться при rebuild; якщо штатний rebuild не може їх зберегти валідно, сесія повідомляє конкретний blocker для автора.

## Persistence та транзакції

Пропозиція: використати runs/run_events та versioned JSON records у app_settings, як чинні impact/acceptance stores; новий SQL schema не потрібний, доки у плані реалізації не доведена інша необхідність. Нові prefixes не повинні потрапляти в legacy readers. Окремі typed records: scene review report, concern disposition bundle, scene acceptance, memory checkpoint. Поточні model-no-concerns proofs і author acceptances відокремлені.

Атомарні storage commands для прийняття й переходу перевіряють run/cursor/scene ownership, heads/source CAS, весь proof graph для automatic acceptance, operation ID та payload identity. Report + acceptance + checkpoint/event публікуються узгоджено. Немає транзакції SQLite на час LLM або авторського редагування. Повтор того самого operation ID з тим самим payload повертає результат; інший payload не переписує рішення.

Падіння між saved attempt і advance повторно використовує verified attempt. Падіння після author acceptance до memory починає з pending_memory, а не просить повторити рішення автора чи генерувати прозу знову. Новий counter/prompt/provider не робить чужі saved responses придатними. Власні прийняття цієї сесії можуть оновлювати наступні baseline лише після нових live snapshots.

Після завершення показуємо scope та фактичний стан усіх сцен. Пізня зміна може знову інвалідувати вже переглянуту сцену через дозволені future-plan dependencies; сесія не називає весь твір актуальним усупереч resolver. У першій версії не стрибаємо назад автоматично: показуємо такі сцени у підсумку для наступного проходу.

## API, UI та витрати

Новий preview послідовної review-сесії: порядок/scene IDs, наявні target materials, потрібні prefix memory maintenance, обрані ролі, bounded current-scene call estimate, paid upper limit/reservation semantics. Точні calls усього майбутнього циклу невідомі до авторських змін; не показувати фіктивне точне число. Для платного запуску потрібен явний ліміт та чинний/ручний тариф за існуючими правилами. Перед кожним stage актуальний reserve; якщо коштів бракує, пауза з прозою/рішеннями, без прихованої генерації. Загальний ліміт сесії діє на всі наступні кроки; ручна регенерація через інший Run використовує власні чинні limits і не обходить story cap.

Start створює protocol3 сесію явно; нічого не запускається від перегляду/оновлення сторінки. Decision preview дає exact report/heads/source fingerprint; decision/finish commands перевіряють CAS/idempotency. Події SSE показують сцену/матеріал/subphase, реальні completed steps поточної сцени та витрати останнього виклику. У needs_review відкривається поточна сцена, список concerns з точними source/target цитатами; незбережений буфер іншої сцени не підміняється.

Resume/repeat лишаються видимими з причиною disabled. Відновлення з needs_review не запускає модель замість рішення автора. Після reload/settings navigation завантажуються durable checkpoint, dispositions та current phase, не лише остання ephemeral подія. UA/EN для всіх нових повідомлень. Поточний імпорт/експорт і літературні тексти/промпти лишаються українськими.

## Перевірки перед поставкою

- Порожній валідний результат автоматично приймає матеріали й переходить без confirm; failed/length/empty/incomplete/invalid refs/full-coverage gap не очищують їх.
- Concern/question зупиняє перед наступною сценою. Reject-all приймає exact snapshot, не змінює model proof. Partial decisions не переходять далі.
- Правки/регенерація зберігають текст і історію; author finish приймає обрану прозу, оновлює memory і переходить без обов’язкового re-search тієї самої сцени.
- Memory failure/refusal/overflow зберігає author acceptance і checkpoint; resume не дублює prose generation/завершені paid calls. Prefix rebuild для unchanged downstream prose не губить зміни ранньої сцени, forwarding choices або chronology.
- Наступна сцена бачить нові sources/heads; непогоджені external changes, reorder/trash й інший story ID не обходять CAS/ownership.
- Crash до/після кожного durable boundary; повторні POST, cancellation, settings change, source change під час search та після review preview. Stored terminal result replay/legacy wire1/2/backup/fsck.
- Bounded output refs-only, відсутність expanded evidence inflation; фактичний input gate, qualified counter або правдивий fallback. Багато concerns не обрізаються для fake clean.
- Browser desktop/mobile: auto advance, author pause/reject/finish, buffers, reload/settings return, budget/error messages/UA-EN. Нейтральні screenshot за потреби.
- Нейтральний end-to-end local smoke перед робочим запуском. Випробування літературної якості окреме від correctness транспорту. Paid calls/авторський bookrun не запускати як побічний ефект поставки.
