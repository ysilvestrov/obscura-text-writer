# Другий раунд локального планувальника — покроковий план реалізації

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Виконання в поточному чаті; цей документ сам по собі не дозволяє inference, платні виклики чи завантаження ваг.

**Goal:** Отримати відтворюване порівняння L1–L6, C1–C2 та K1–K2 на синтетичному українському holdout без зміни продукту.

**Architecture:** Окремий дослідницький CLI перевикористовує незмінні protocol3 request builder і validator. Дані, транспорт, оцінювання, черга й звіт розділено всередині `docs/research/round2/`; сирі відповіді та відновлення — лише в ignored `artifacts/round-2/`. Жодних змін `src/**`, production-ролей чи tokenizer bindings.

**Tech Stack:** Чинна Python `.venv`, `httpx`, `pydantic`, стандартна бібліотека; окреме середовище конвертації HF→GGUF із зафіксованими залежностями та llama.cpp. Нативний Anthropic Messages API через HTTP, без додавання SDK у залежності продукту.

**Актуальні доповнення:** [хмарні учасники/бюджет](../../research/2026-10-29-round-2-cloud-amendment.md), [підготовка й dev](../../research/2026-10-29-round-2-dev-results.md).

**Spec:** [бріф](../../research/2026-10-28-round-2-codex-brief.md), [дизайн дослідження](../../research/2026-10-28-local-planner-round-2-plan.md), [перший раунд](../../research/2026-10-27-local-planner-round-1-summary.md). Дизайн дослідження не редагується заднім числом. Цей документ деталізує виконання; непогоджені уточнення нижче не замінюють його контракт.

## Global Constraints

- Лише `check`, `current_consistency`, protocol3, синтетична українська; `delta`/`synthesis` не входять у раунд.
- 12 шаблонів × 4 варіанти = 48: 20 clean, 24 issue, 28 очікуваних суперечностей, 4 question; 24 нейтральні й 24 дорослі приклади. У дорослих явно задані повнолітні віки.
- Локальні: temperature 0,1, `reasoning_effort=none`, max output 4096; native strict JSON Schema із щонайменше трьома concerns. Значення reasoning перевіряється за фактичними даними, не лише запитом.
- Базовий load: 131072, batch 512, flash attention, KV GPU; для L3/L4 — 32K та однакове число GPU/offload-шарів. Фактичні відхилення записуються.
- L1–L4: власна Q4_K_M, та сама версія llama.cpp; пропозиція виконавця — без imatrix для обох пар, щоб не вводити додатковий калібрувальний корпус. Вибір записати до конвертації.
- Сирі результати ignored; ключі лише `.env`/environment. Локальні коміти по етапах, без push. Початковий стан LM Studio відновлюється після роботи й після аварійної зупинки, коли це технічно можливо.
- Пороги: FP ≤7/60, miss ≤10/84, valid ≥137/144. Invalid/refusal не вилучаються зі знаменників.
- Змістовий результат не повторюється. Транспортний збій зберігається як спроба та повторюється з журналом; нескінченний цикл повторів не допускається.
- Holdout не використовується для налаштування; після заморожування зміна harness потребує рішення власника й повного нового порівняння.

## Review Focus

1. У типі E знайдена одна з двох суперечностей: call-level TP не приховує другу FN — тести етапу 0.
2. Неправильне пояснення з правильними S/T-посиланнями: структурна валідність не видається за семантичну — ручне сліпе зіставлення етапу 5.
3. Збій між отриманням відповіді та записом результату: resume не повторює вже збережений змістовий виклик — тести етапу 0.
4. Немає usage/reasoning поля: unknown не перетворюється на 0 — тести етапу 0 та gate етапу 3.
5. Витрати, gated-ваги чи збій відновлення GPU: зупинка з причиною, без підстановки іншої конфігурації — етапи 2–3 та fake-тести preflight/restore.

## Уточнення, які потрібні до заморожування

Це виявлені прогалини контракту, а не вже погоджені зміни.

1. **Семантичний scoring.** Пропоную дві таблиці: один взаємовиключний результат на виклик і окремі TP/FN по кожній очікуваній суперечності. Для issue на call-level: TP за наявності хоча б одного правильно зіставленого issue, інакше FN; часткове знаходження видно у fact-level miss. Зайві хибні concerns на issue рахувати окремо, вони не повинні зникнути за TP. Question на clean окремо показувати як необґрунтоване зауваження й консервативно включати у FP; question замість issue — пропуск; issue замість очікуваного question — question-missed. Ці правила власник погоджує до holdout.
2. **Зіставлення concerns з gold.** S/T aliases не доводять правильність пояснення. Код готує кандидати за доказами, людина підтверджує семантичне зіставлення й content-refusal у сліпій формі без назви моделі. Для E потрібні окремі gold contradiction IDs; дублі не збільшують TP. Окремі 20% TP — поглиблена оцінка достатності доказів/пояснень, а не заміна основного зіставлення. Без такого рішення автоматичні метрики мають статус попередніх.
3. **Спільні 20% TP.** У різних моделей різні TP. Пропозиція: один seeded порядок gold case/contradiction IDs; єдина спільна панель, у якій для кожної конфігурації позначені TP/не-TP, із добором за тим самим порядком, щоб покрити щонайменше 20% її TP. Не оголошувати різні добірки одним парним порівнянням.
4. **Транспортні повтори.** Пропозиція: максимум дві додаткові спроби одного logical call, потім зупинка конфігурації з рішенням власника. Не обирати «найкращу» відповідь: перша змістова відповідь остаточна. Показувати всі transport attempts і окремо підсумкові 144 slots; спосіб обліку незавершених slots погодити до старту.
5. **Unknown reasoning / недоступна schema.** Якщо сервер не віддає лічильник, треба отримати еквівалентну перевірювану телеметрію або зупинитися; відсутність reasoning-тексту сама по собі недостатня. Якщо C1/C2 не підтримують той самий контракт structured output, не підміняти його непомітно tools чи ремонтом JSON.
6. **Моделі й автор набору.** Точні API IDs C1/C2, доступність, structured output, reasoning defaults і тарифи перевірити за офіційними джерелами перед реалізацією адаптерів. Не вважати desktop Codex ID доступним OpenAI API ID. Точний ID автора holdout брати з доступних достовірних метаданих; якщо його немає, не вигадувати — власник визначає іншого відомого автора/процес до написання набору.
7. **Негативний контроль.** «L5 гірша за найкращу L1–L4» не має правила для змішаного виграшу FP/miss/valid. До запуску визначити критерій; пропозиція — порівнювати весь вектор метрик, а суперечливий результат називати невизначеним, без довільного зведеного бала.

## Усі дії власника

| Коли | Дія | Що надає/готує виконавець |
|---|---|---|
| До реалізації scoring | Погодити уточнення щодо часткового E, question/FP, семантичного зіставлення, retry, unknown reasoning, контролю L5 і спільних 20% TP | Конкретні правила з початку цього плану та приклади їх роботи |
| До написання holdout | Підтвердити автора чернеток із достовірним model ID, який не є C1/C2 | Доступні метадані автора; якщо ID недоступний — чесне повідомлення |
| Після підготовки набору | Прочитати всі 48 прикладів та gold; виправити/погодити кожний | Читабельна форма й автоматичний structural audit |
| До платних API | Вибрати точні C1/C2 із перевірених доступних IDs; надати ключі через `.env`; погодити окремий загальний бюджет | Перелік доступних моделей, параметри, офіційні тарифи та верхній розрахунок, без inference |
| До великих завантажень | Погодити розташування ваг і необхідний обсяг завантажень/диска | Розрахунок peak storage та список точних repositories/revisions |
| Лише якщо gated | Увійти в HF, прийняти ліцензії моделей, надати read-доступ через environment | Точні посилання та назва змінної, без прохання надсилати секрет у чат |
| Перед GPU-перемиканням | Завершити активні генерації; дозволити тимчасову зайнятість локального API | Snapshot чинного load і процедура restore; ручне завантаження моделей не потрібне |
| Лише якщо dev не проходить | Вирішити зміну/заміну/виключення конфігурації або зупинку | Фактичні помилки, latency/VRAM/reasoning та варіанти, до holdout |
| Перед quality | Погодити остаточний manifest, правила й бюджет; виділити період без використання production API | Freeze hashes, кількість викликів, ресурсний прогноз і перелік відкритих питань (має бути порожнім) |
| Після quality | Розмітити сліпу форму concerns/refusal самостійно або призначити погодженого розмітника; виконати поглиблені 20% TP | Форми без назв моделей, evidence поруч, автоматичні підказки без автоматичного семантичного verdict |
| Для timing | Підключити ноутбук до мережі, вибрати performance mode, закрити важкі програми й не користуватися GPU протягом вимірів | Точне узгоджене вікно й telemetry; звіт про неконтрольовані чинники |
| Після звіту | Перевірити висновки/відхилення та вирішити, чи потрібні бонуси/публікація | Окремий звіт і пакет матеріалів; push/публікація лише за новим прямим запитом |

**Власнику не потрібно:** писати harness, запускати команди конвертації, вручну рахувати метрики, встановлювати всі моделі через UI, передавати ключі в чат чи підтримувати вкладку браузера відкритою. Ці дії бере на себе виконавець після відповідних дозволів і в межах доступних інструментів.
