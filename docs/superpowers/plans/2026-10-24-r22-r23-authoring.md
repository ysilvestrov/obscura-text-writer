# R-22/R-23 — план реалізації візуального редактора й AI-assisted writing

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Власник раніше обрав реалізацію в цьому чаті; не створювати worktree/окремі чати без нового рішення.

**Goal:** візуальне форматування, непересічні коментарі та один виклик письменника з переглядом змін і прийняттям у чернетку.

**Architecture:** ProseMirror забезпечує документ, транзакції, undo/redo й декорації; окремий Markdown bridge зберігає авторитетний source та координати. Python зберігає immutable текстові версії й окремі ревізії коментарів; новий queued rewrite створює пропозицію, яку автор приймає в draft через CAS. Спільними з редактором є чистий diff/групування й компонент перегляду, але не hardcoded публікація у prose.

**Tech Stack:** Python 3.10+, FastAPI/SQLite; ProseMirror, mdast-util-from-markdown/to-markdown, esbuild; markdown-it-py для безпечної структурної проєкції й експорту. Браузерні ресурси поставляються локально у Python-пакеті; Node потрібний лише розробнику для відтворення bundle.

**Spec:** [спільний дизайн](../../specs/changes/R-22-R-23-authoring-design.md), [R-22](../../specs/changes/R-22-markdown-editing.md), [R-23](../../specs/changes/R-23-ai-assisted-writing.md). UX погоджено власником 24.10.2026 («Ок»). Технічний план погоджено власником 24.10.2026 («ОК, продовжуй»); чинну архітектуру визначає SPEC.MD.

## Global Constraints

- Один виклик письменника з окремим промптом; повний текст, усі коментарі; без evaluator/classifier/авторетрай/нової модельної ролі.
- AI-assisted MVP працює з draft. Проза підтримує візуальне форматування; AI-assisted для prose/структурованого brief лишається майбутнім розширенням.
- Основний режим візуальний, без Markdown source mode. Toolbar: жирний, курсив, undo/redo та коментар; не додавати непогоджені меню шрифтів/кольорів.
- Загальний коментар — під текстом, фрагментні — popover і фон; права панель не перебудовується. Діапазони не перетинаються, вкладення заборонені, сусідні дозволені.
- Підсвічування/коментарі не потрапляють у Markdown/книги. Unicode/CRLF не нормалізуються під час відкриття/Save без змін.
- Вихідний текст — конкретна збережена версія. Dirty перед викликом: «Зберегти й переписати» / «Скасувати»; save failure або несправна прив’язка не запускає модель.
- Результат не змінює head до явного прийняття. Перегляд без ручного редагування; початково жодної вибраної правки, реченнєве групування як у поточного protocol2.
- Root SPEC, traceability й користувацькі інструкції оновлюються в кожному архітектурному коміті; це не дозвіл міняти реальні журнали/запускати платні моделі.

## Технічні рішення

### 1. Поставка й Markdown bridge

Прямий ProseMirror без React/Tiptap/платного comment plugin. Джерела — `frontend/src/`, lockfile — `frontend/pnpm-lock.yaml`; deterministic ESM bundle — `src/storygen/web/static/rich-editor-engine.js`, ліцензії — `static/licenses/`. Ресурси включаються у wheel; CDN/Node/мережа під час користування не потрібні. Не замінювати весь frontend на SPA.

Версії-кандидати перевірено через офіційний npm registry 24.10.2026, пакети ще не встановлені: prosemirror-model1.25.12, state1.4.4, view1.42.8, transform1.12.4, commands1.7.2, history1.5.1, keymap1.2.3; mdast-util-from-markdown2.1.0, to-markdown2.2.0; esbuild0.28.2. Це MIT-пакети; dev browser runner @playwright/test1.64.1 — Apache-2.0, Node>=20. Python markdown-it-py4.2.0 підтримує Python>=3.10. На реалізації фіксувати exact версії/цілісність у lockfiles і ліцензійному manifest; не виконувати автоматичний latest upgrade.

mdast дає структурний source з позиціями; bridge будує відповідність до ProseMirror. Після редагування зберігаються дослівні source slices незмінених блоків і роздільників; змінені блоки серіалізуються зі збереженням тексту/семантичного форматування. Повторний parse має відтворювати очікуваний документ, а відображення anchors визначається цим деревом/транзакціями, не пошуком схожої цитати. Entity/escape/UTF-16→codepoint mapping перевіряється окремими fixtures. Проста повна parse→serialize нормалізація всього рукопису заборонена.

Редаговані конструкції MVP — абзаци, переноси, strong/em. Інші CommonMark-вузли зберігаються як source-backed opaque вузли з безпечним текстовим представленням; їхній вміст не зникає й не перетворюється у випадково редагований HTML. Toolbar не редагує внутрішню структуру opaque-вузла; спроба коментувати його пояснює обмеження. Сам текст звичайної прози лишається повністю редагованим. HTML відображається буквально, зовнішні зображення не завантажуються. Підтримка інших конструкцій як повністю редагованих не входить у перший пакет.

### 2. Старі тексти й формат версії

Додати `VersionRef.content_format: Literal['plain','markdown']='plain'`, окремо від чинного storage `format=text|json`. Не backfill-ити старі версії: їхні зірочки/підкреслення є літеральним текстом. Відкриття старого plain не створює нової версії. Після реальної візуальної правки зберігається markdown із правильним escaping; збереження без змін повертає старий plain/ref.

`AuthorTextChange(ProseChange).content_format` optional лише для draft/prose endpoints; brief/memory лишаються на чинному ProseChange. старі клієнти без поля зберігають формат вибраного head, а не перетлумачують markdown як plain. No-op перевіряє і source, і content_format. Новий model draft та результати редактора/AI-assisted мають зафіксований формат; metadata не вгадується за наявністю `**`. Prompt/request/schema та token estimate враховують Markdown-preservation правила без зміни мови твору. Пам’ять та evidence зберігають точні фрагменти raw source.

### 3. Коментарі й збереження

Домен `authoring/comments.py`: `CommentSet{id,scene_id,material_kind:'draft',revision,source_version_id,source_sha256,general,comments[]}`, `Comment{id,instruction,anchor}`, `Anchor{start,end,source_quote,display_quote,state:'valid'|'needs_review',reason?}`. `[start,end)` — Unicode codepoints у збереженому raw source; JS явно конвертує UTF-16. Для valid anchor сервер перевіряє exact slice, owner/source/format, непорожність та непересічність. Для needs_review старе джерело/цитата зберігаються, але виклик заборонений. Не використовувати DOM positions або fuzzy rebinding як серверний доказ.

Захисні межі:100 фрагментних коментарів,8000 символів на вказівку,12000 на загальний коментар і50000 сумарно; перевищення — явна помилка до enqueue, без обрізання. Ці межі не замінюють чинний token budget.

Одна SQL-міграція `004_authoring_comments.sql`: append-only таблиця `authoring_comment_sets` з FK story/scene/source version і unique `(scene_id,material_kind,revision)`. Це історія наборів, не дублювання рукопису в HTML. Поточний набір — найбільша revision. Приватний SQL лише у `storage/comment_store.py`; Repository дає публічні методи. Збереження тексту й нового набору — одна транзакція publication/CAS після immutable blob write. Якщо текст не змінився, ID/head/revision тексту й наступні сцени не інвалідуються; змінюється лише revision набору.

Popover «Зберегти» фіксує коментар у робочому буфері й явно позначає незбережені зміни; загальне Save зберігає текст+коментарі на сервері. До Save діють чинні unsaved/navigation guards; не видавати локальний буфер за вже записаний на сервер. Під час короткого atomic Save блокуються текст і коментарі, після помилки введене зберігається. Після reload відновлюється останній явно збережений набір; автоматичне відновлення ще не збереженого тексту після аварії не обіцяється.

API: `GET /api/scenes/{id}/comments?material=draft`; `POST /api/scenes/{id}/draft` приймає optional `comment_set`/`expected_comments_revision` разом із text/content_format/expected_revision. Draft endpoint використовує DraftChange(AuthorTextChange) із optional comment payload. Старий endpoint без comments не переприв’язує їх мовчки: mismatch source version показується як потреба перевірки. Зовнішня заміна draft або нова генерація не переносить старі anchors автоматично.

### 4. Rewrite й прийняття

`RunRequest.mode='rewrite'`, поля `scene_id`, `source_version_id`, `comment_set_id`, `comment_fingerprint`; сцена й draft джерела фіксуються до enqueue. Один task/stage `rewrite`, роль `writer`; автоматична послідовність STAGES=brief/draft/edit/memory не розширюється. окремий ресурс `assisted_writer_uk_v1.txt`. Звичайний writer prompt/custom prompt не підставляється замість цього контракту. Provider/модель/temperature/reasoning/ліміти беруться з writer; response — plain text, без JSON Schema. Контекст: source draft, усі коментарі, writer horizon/плани, стиль/канон, учасники сцени й попередня пам’ять; готовий brief не є обов’язковим входом цього окремого сценарію. Явні author-provided джерела проходять чинні guards. Без прихованого зменшення контексту.

До API-виклику перевіряються exact source/current draft, notes revision/fingerprint, context/budget/cancel. Attempt зберігає повний snapshot коментарів, source ID/hash/content_format, промпт і provider settings. Complete stop/nonempty створює proposal із `rewrite_diff.py` і станом needs_review; incomplete/refusal/порожній/тотожно незмінений результат не замінює draft. Зміни під час виконання дають alternative, без перезапису ручних правок.

Окремий snapshot scope `author_rewrite`: зовнішні залежності як у writer context; immutable source draft — frozen hash/provenance, а не селектор його майбутнього head. Поле `frozen_author_source_id` має вузьку перевірку scope/kind/owner й не обходить hash/complete/cycle. Актуальність самого історичного source не перевіряється повторно після публікації результату; поточний source head контролюється TargetCAS до застосування. Так результат не стає stale сам від заміни draft і не втрачає provenance. Без загального послаблення freshness інших refs. Comment-set revision/fingerprint — guard початку й publication, а не постійний селектор latest comments: очищення робочих коментарів після apply не робить прийнятий draft stale.

API: `GET /api/scenes/{id}/rewrites`; `GET .../rewrites/{attempt}`; `POST .../rewrites/{attempt}/selection-preview`; `POST .../rewrites/{attempt}/apply`. Preview/apply перевіряють source/head revision, comment-set revision/fingerprint, proposal fingerprint і цілі групи правок. Store публікує `kind='draft'` у head draft, інвалідує реальні похідні матеріали та записує рішення атомарно; prose не змінюється. Не викликати чинний copyedit_store напряму: він hardcoded для edited/prose/editor_loop.

Після часткового/повного прийняття новий робочий набір коментарів порожній; оригінальний лишається в attempt і comment-set history. Відхилення всіх змін не створює ідентичного draft і не стирає робочі коментарі. Вставка на самій межі виділення позначається «через межу», а не довільно inside/outside. Геометрія обчислюється за source offsets, не за поясненнями моделі.
