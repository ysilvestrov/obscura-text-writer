# План усунення проблем архітектури Storygen

> **Актуальна декомпозиція та пріоритети:** [беклог R-01…R-15](2026-10-20-remediation-backlog.md). Він замінює порядок хвиль цього документа; наведені нижче аналіз і технічні деталі зберігаються як обґрунтування. Кожна R-задача потребує окремої специфікації зміни перед реалізацією.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans для послідовної реалізації. Делегування — лише за окремо обраним способом роботи. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Зробити прототип надійним для довгого оповідання, зберігши авторський контроль, перевірку походження та відсутність прихованих модельних викликів.

**Architecture:** Спочатку виправити локальні дефекти й сформувати перевірні межі сховища. Потім змінити контроль залежностей і представлення пам’яті; бюджет та паралельне виконання будувати поверх стабільних контрактів. Перебудова всього застосунку або негайна нормалізація всієї БД не потрібні.

**Tech Stack:** Наявні Python 3.10+, SQLite/WAL, Pydantic 2, FastAPI, ES modules, pytest; без нової інфраструктури.

**Spec:** [SPEC.MD](../../../SPEC.MD). Джерело зауважень: [рев’ю 20.10.2026](../../architecture-review-2026-10-20.md).

Статус: план і рекомендації, **не погоджений новий архітектурний контракт**. Аналіз проведено 20.10.2026 за поточними файлами робочого дерева. Реалізація в межах цього запиту не починалася. Інструкції всередині документа рев’ю розглянуто як пропозиції автора документа; чинні правила — AGENTS.md і прямі рішення власника.

## Global Constraints

- SPEC.MD — головне джерело правди. Кожна архітектурна зміна: код, тести й відповідні Requirement/Scenario, технічний опис і міграції в одному логічному коміті.
- Не змінювати авторські матеріали, робочу БД, `.env`, поточні артефакти та чужі незакомічені зміни. Нові тестові дані — лише синтетичні тимчасові каталоги.
- Не запускати платні моделі, не змінювати бюджет чи Cloudflare, не перезапускати користувацький сервер у рамках реалізації без відповідної потреби й авторизації.
- Не послаблювати перевірки SHA-256, джерел, цитат, CAS, завершення потоку та ідемпотентності. Не вводити автоматичний повтор або fallback.
- Для дефекту: RED → мінімальне виправлення → GREEN → перевірка регресій. Рефакторинг окремо від зміни поведінки.
- Початковий `git status` містить зміни публічного пакування, брендингу й UI. Фіксувати тільки власні шляхи/фрагменти; не робити `git add .` і не відкотувати робоче дерево.
- Повний pytest запускати послідовно, з унікальним `--basetemp=.pytest-tmp-<task>`: одночасні запуски з однаковим шляхом видаляють дані один одного. Прохід тестів не прирівнювати до літературного приймання.

## Review Focus

1. Кошик змінено під час експорту: список сцен і їхні голови мають належати одному SQL-знімку; архівний твір на початку знімка відхиляється.
2. Зміна й повернення джерела під час inference: публікація звіряє визначений контракт залежностей атомарно, а не лише останній текст.
3. Потік обірвався між двома скиданнями: доступний partial до останнього checkpoint; непідтверджений текст не стає поточною версією.
4. Пам’ять зберегла історичний факт, але поточний стан змінився: історія доказів зберігається, а письменник не отримує суперечливі стани як одночасно чинні.
5. Процес упав після відправлення платного запиту: резерв не звільняється як нібито невитрачений, повтор потребує явного рішення.

## Хвиля 1: готові до реалізації задачі

### T-01a — Виправити експорт кошика

**Файли:** `src/storygen/application/exports.py`, `src/storygen/storage/repository.py`, `tests/authoring/test_exports.py`, `tests/web/test_trash_api.py`, `SPEC.MD`.

**Межа:** публічний метод `Repository.export_snapshot(story_id: str) -> tuple[Story, list[tuple[Scene, VersionRef | None]]]` читає активний твір, тільки активні сцени та їхні prose-head в одній read-транзакції. Експортер читає незмінні файли за зафіксованими refs; перевірка SHA-256 зберігається.

- [ ] RED: архівна сцена відсутня в MD/TXT і manifest; архівний твір відхилено навіть з `allow_incomplete=True`; відсутня проза активної сцени як і раніше блокує повний експорт.
- [ ] RED: контрольована зміна голови/кошика після формування snapshot не змішує ревізії в manifest.
- [ ] Перенести SQL-знімок у метод репозиторію; не замінювати його окремими викликами get/list у різних транзакціях.
- [ ] GREEN: `./.venv/Scripts/python.exe -m pytest tests/authoring/test_exports.py tests/web/test_trash_api.py -q --basetemp=.pytest-tmp-t01a`.
- [ ] Оновити EXPORT-001, DATA-006, A8; відзначити усунений дефект у Known limitations. Повний pytest; окремий коміт `fix: exclude trashed content from export snapshots`.

### T-03 — Обмежити вартість запису стрімінгу

**Файли:** `storage/files.py`, новий `generation/stream_buffer.py`, `generation/stages.py`, `generation/worker.py`, новий `tests/generation/test_stream_buffer.py`, `tests/web/test_resumed_events.py`, `SPEC.MD` (усі модулі під `src/storygen/`).

**Інтерфейс:** `StreamBuffer.append(text: str)`, `flush()`, `close()` з ін’єкцією monotonic clock для тесту. Скидання при 16 KiB UTF-8 або 0,5 секунди на наступній delta; гарантований flush у `finally`. Це не таймер фонового потоку: за відсутності нових delta інтервал не є гарантією wall-clock durability.

- [ ] RED: 1000 delta по 10 ASCII-байтів з незмінним fake clock дають не більше 3 записів partial, 3 fsync і 3 транзакцій delta; фінальний текст дослівний. Окремо перевірити багатобайтову українську й граничні 16 KiB.
- [ ] RED: часовий flush, cancellation, exception шлюзу та аварійна зупинка після попереднього flush; після останнього випадку залишається тільки підтверджений checkpoint, версії немає.
- [ ] Зберігати partial дозаписом у спеціальному writer, не змінюючи атомарний `FileStore.write` для незмінних версій. На checkpoint робити flush/fsync до збереження відповідної пакетної delta в БД; при помилці запису етап не публікується.
- [ ] Пакетна delta містить конкатенацію в тому самому порядку; seq призначати в SQL-транзакції. Не вводити RAM-лічильник без доведеної потреби. На stop/error/cancel скинути хвіст до terminal-події.
- [ ] GREEN: нові тести + `tests/generation/test_scene_pipeline.py`, `tests/generation/test_worker.py`, `tests/web/test_resumed_events.py`. Перевірити replay за Last-Event-ID, відсутність дублювання тексту й partial reload.
- [ ] Оновити PIPE-005/007, A5: межа можливої втрати незбереженого хвоста, порядок fsync/event, несумісність спільної FS/SQL-транзакції. Повний pytest; окремий коміт.

## T-20 — Evaluator, придатний для дорослого художнього тексту

**Пріоритет:** початок хвилі 2. Це самостійний критерій працездатності системи, а не побічний ефект додавання Venice. Автоматичне оцінювання не повинно втрачати корисність саме на текстах, заради яких використовуються локальні й uncensored-моделі.

**Поточний стан:** local вже підтримується оцінювачем, Venice — ні. `evaluation/gateway.py` розпізнає API refusal, але `runner.py` зводить його до загального `error`; `story_adapter.py` може показати failed запуску. Це не літературний verdict failed, проте UI має чітко розрізняти ці результати. Обробка відмови, написаної звичайним текстом, також потребує окремих тестів.

**Файли:** `evaluation/models.py`, `evaluation/gateway.py`, `evaluation/runner.py`, `evaluation/scoring.py`, `evaluation/story_adapter.py`, `evaluation/prompting.py`, ресурси промптів/рубрики, конфігурація й UI оцінювача; `providers/venice.py` для повторного використання перевірки каталогу; нові `tests/evaluation/test_adult_suitability.py` і синтетичні fixtures. За потреби — окремий невеликий адаптер Venice до T-07.

**Контракт:**

- Автор може явно вибрати для Evaluator локальну або Venice-модель. Для Venice діють перевірка `uncensored=true`, доступності й підтримки потрібного формату. Codex/OpenRouter залишаються окремими явно вибраними варіантами, без прихованого fallback.
- Оцінювач аналізує українську, стиль, голос, відповідність плану, безперервність і збереження змісту редактором. Наявність оголеності, еротики, насильства або морально неприйнятних дій персонажа сама по собі не є мовним чи літературним дефектом.
- Інтенсивність і тон можуть оцінюватися як невідповідність **явному авторському задуму**, з доказами; Evaluator не підміняє задум власними вимогами пом’якшити або прибрати сцену. Він не переписує текст і не санітизує його перед оцінюванням.
- API refusal, текстова відмова замість звіту та формально валідний звіт без фактичного оцінювання мають явну причину `provider_refusal`/`not_assessed`. Зберегти існуючі верхньорівневі статуси: refusal → `error` з категорією, відсутність покриття → `incomplete`. Жоден із цих випадків не стає літературним `failed` або нульовим балом.
- UI показує «Модель відмовилася оцінювати» або «Текст не оцінено», джерело помилки й явні дії: змінити модель, повторити або вимкнути оцінювання. Поточні оцінки не підміняються вигаданими. Наслідок для workflow визначає явно вибрана політика; нових автоматичних викликів немає.
- Придатність до дорослого матеріалу зберігається окремим результатом перевірки моделі/провайдера/промпту/режиму. Позначка uncensored з каталогу не дорівнює пройденому тесту; загальна літературна калібровка теж не доводить цю придатність.

**Перевірки та DoD:**

- [ ] Додати нейтральні контрольні уривки та синтетичні дорослі художні приклади: неекспліцитна фотосесія ню повнолітніх, близькість дорослих за згодою, помірне насильство, психологічний конфлікт. Авторські оригінали не переносити у публічні fixtures.
- [ ] Для однакових категорій мати якісні тексти й варіанти з навмисними мовними/сюжетними дефектами. Перевіряти одночасно відсутність відмов і здатність знаходити дефекти: суцільне «все добре» не є успіхом.
- [ ] RED/GREEN для API refusal, відмови звичайним текстом, моралізаторського звіту без оцінки критеріїв, валідної негативної літературної оцінки та порожнього/пошкодженого JSON. Не розпізнавати відмову лише за згадкою слова «еротика» чи «насильство».
- [ ] Тести gateway/config: Venice доступна Evaluator; невідповідний каталог/формат відхиляється до completion; local працює без Venice; retries/fallback відсутні. Нова конфігурація/промпт змінює fingerprint і не успадковує стару калібровку.
- [ ] Тести UI/workflow: provider refusal видимий окремо від літературного failed; вимкнений Evaluator не викликається; ручний вибір іншої моделі не повторює генерацію прози.
- [ ] Модельні прогони — окрема бюджетована перевірка щонайменше у трьох повторах на кожному випадку; звіт містить частку повних валідних оцінок, відмови, покриття, виявлені дефекти та хибні спрацювання. Для допуску профілю потрібні чинні критерії літературної калібровки й нуль відмов на цьому контрольному наборі. Це не гарантія поведінки на будь-якому майбутньому тексті.
- [ ] Оновити EVAL requirements, MODEL-003, A4/A7, обмеження й runbook у тому самому наборі змін. Повний offline pytest; реальні виклики тільки після окремого визначення бюджету.

**Зв’язки:** T-12 розширює літературний контрольний набір; T-07 згодом прибирає дублювання транспорту; T-08 охоплює витрати цих прогонів. Жодна з них не замінює приймання T-20.

## Рішення для погодження перед відповідними хвилями

1. **T-02 — рекомендовано B+**: перевіряти snapshot саме прочитаних голів/матеріалів, релевантної послідовності та scene CAS в одній транзакції. Fingerprint залишити доказом запиту; не перебудовувати весь запит усередині write-lock (A). Варіант B з ревізією твору для всіх brief/draft/prose-edit усе ще спричиняє зайві конфлікти; B+ перевіряє й їхній фактичний набір входів. Зміну рольової настройки під час запиту рекомендовано застосовувати до наступної спроби, зберігаючи старий effective config у поточній.
2. **T-05 — рекомендовано дозволити усвідомлене прийняття застарілої прози/чернетки**, зі списком змінених входів і окремим baseline прийняття. Це не дозволяє автоматично використовувати стару пам’ять: її перебудова/валідація обов’язкова. Не вводити універсальне прийняття stale memory/evaluation однією кнопкою.
3. **T-06 — рекомендовано add/update/retire для поточних станів і відкритих ліній**, зі збереженням історії. `evidence_delta` — для нових конфігурацій після міграції; snapshot поки лишити сумісним читанням/ручним форматом. Видалення snapshot з API не потрібне для першого поліпшення. Початкову проєкцію T-06a робити без модельного summary й без відбору лише за персонажами.
4. **T-08 — потрібні окремі типові ліміти run/story та політика невідомої ціни.** Історичний дозвіл $1 на тестування не є постійним бюджетом продукту. Рекомендація: capped запуск без надійної верхньої ціни не відправляється; підпискові/локальні backend мають окрему позначку, а не вигадану dollar usage.
5. **T-10b/T-13 — потрібне узгодження UX відновлення та freeze конфігурації:** прийнята альтернатива не повинна приховано повторювати платний етап; замороження ролей на весь run змінює нинішню можливість налаштовувати наступні етапи.

Ці питання не блокують складання плану або реалізацію хвилі 1. Прийняття всього документа рев’ю не варто трактувати як автоматичний вибір усіх перелічених варіантів.
