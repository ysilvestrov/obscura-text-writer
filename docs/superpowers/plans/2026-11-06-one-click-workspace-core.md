# План реалізації: основні дії одним натисканням

> Для виконавця: застосувати `superpowers:executing-plans`, виконуючи задачі послідовно. Після ядра провести огляд усієї гілки; наступний план доведення будувати за фактичним результатом ядра.

**Мета:** без модального підтвердження запускати основні модельні дії робочого простору, завчасно показуючи їхні параметри й надаючи дієву зупинку.

**Архітектура:** наявний readiness надає попередню телеметрію; перед enqueue виконується повторна перевірка. Браузерний стан керує скасуванням підготовки, а після створення запуску використовує серверний cancel; у фазі невизначеного POST ідентичність запиту зберігається для звірки без повторного inference. Дані в sidebar позначаються як заплановані або фактичні відповідно до джерела.

**Технології:** Python/FastAPI, Pydantic, JavaScript modules, Playwright, чинні CSS та UA/EN i18n.

**Специфікація:** `docs/specs/changes/editor-one-click-telemetry-2026-11-06.md` (погоджена власником 06.11.2026).

## Обмеження

- Зміни стосуються лише основної кнопки режимів plan, brief, draft, prose; режим memory — навігація без модельної телеметрії. Інші кнопки й підтвердження не змінюються.
- Зберегти CAS, перевірки буфера і бюджету, fingerprint та окрему згоду для застарілої пам’яті; не запускати модель на приватних даних під час тестування.
- Не заявляти миттєве серверне завершення чи відсутність витрат; не повторювати невизначений POST без гарантії ідемпотентності.
- Не зберігати приватний текст у телеметрії. Старі записи з відсутніми метаданими відображати як невідомі.
- Специфікація, traceability, журнал, UA/EN інструкції й `docs/STATUS.md` оновлюються разом із кодом; незв’язаний research-файл не включати в коміт.

## Ризики для рев’ю

1. Скасування під час збереження: завершений save зберігається, enqueue не починається (задача 2).
2. Втрата відповіді enqueue: сервер міг створити run; не створити другий і не повідомити хибно про успішне скасування (задача 2).
3. Зміна сцени, налаштувань або readiness між показом і запуском: повторна перевірка, без підміни джерела (задачі 1–2).
4. Застаріла пам’ять: без окремої згоди fingerprint не передається; після зміни джерела старий fingerprint не працює (задача 2).
5. Reload, стара історія або зміна мови/налаштувань: sidebar не видає поточну модель за модель старого запуску (задача 3).

## Задача 2: запуск і зупинка без гонки

**Файли:** `src/storygen/web/static/workspace-route.js`, `workspace-state.js`, `runs.js`, `api.js`; за потреби `src/storygen/web/routes_runs.py` та `src/storygen/generation/worker.py`; тести `tests/web/browser/save-and-run.spec.mjs`, новий `tests/web/browser/workspace-cancel.spec.mjs`, `tests/web/` API тести.

**Інтерфейс:** нова команда `cancel-primary` у workspace registry зупиняє поточну основну дію; `run` приймає ознаку основної дії та `AbortSignal`. Поточні дії інших callers зберігають confirmation. Для reconciliation створення run використовувати наявний `request_id` і read-only пошук за ним, обмежений поточним story; відсутність результату під час невизначеного POST не вважати доказом завершення сервера.

- [ ] Додати тести, що для всіх чотирьох режимів один click зберігає dirty буфер і виконує один enqueue без dialog; CAS або зміна сцени зупиняє enqueue. Інші виклики `run` зберігають confirmation.
- [ ] Додати керовані затримки на save, readiness, POST і cancel. Перевірити stop до POST, stop під час POST із пізньою відповіддю, втрату відповіді, reload/reconciliation за `request_id`, stop queued/running, повторне натискання та неможливість другого run. Кнопка активна для cancel, доки стан справді дозволяє дію; серверний статус показує `cancellation_requested` до підтвердження.
- [ ] Додати окремі тести для `memory_review`: згода видається лише після явної авторської дії з описом ризику; старий fingerprint не дозволяє запуск після зміни джерел. Звичайна дія не передає fingerprint автоматично.
- [ ] Запустити нові browser/API тести й зафіксувати RED. Реалізувати переривання preflight сигналом; save та enqueue не переривати сліпо: після save перевірити cancel flag, а POST довести до відомого результату або звіряти за `request_id`. Після отримання ID надіслати cancel; при помилці зв’язку зберегти невизначений стан і можливість повторити лише звірку/скасування.
- [ ] Повторити тести до GREEN; перевірити, що завершення/помилка відновлюють кнопку й що локальне скасування не показується як серверне завершення.

## Задача 3: достовірний підсумок запуску
