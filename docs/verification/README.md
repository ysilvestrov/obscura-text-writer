# Перевірність архітектури

Контракт — [SPEC.MD](../../SPEC.MD), стан конкретного запуску — [STATUS](../STATUS.md).

```powershell
./.venv/Scripts/python.exe scripts/check_docs.py
./.venv/Scripts/python.exe scripts/verify.py
```

Перша команда перевіряє структуру документа, [матрицю](traceability.json), AST-наявність конкретних тестів, точкові `pytest.mark.req` та локальні посилання актуальних документів. Вона не запускає тести, не звертається до моделей і не змінює дані. Пропуск у матриці або зламане посилання є помилкою цієї команди, а не блокуванням застосунку.

Друга команда виконує pytest і формує STATUS зі свіжого JUnit XML. Не запускайте її одночасно з іншим повним suite. Можна задати конкретні тести:

```powershell
./.venv/Scripts/python.exe scripts/verify.py -- tests/test_spec_traceability.py -q
```

Такий результат стосується лише зазначеної команди. Collection не означає passed, skip не означає passed, синтетичні gateway не доводять роботу реальних моделей. Звіт містить базовий commit і hash вихідних файлів, оскільки документація результату створюється після тестів. Зміна файлів робить попереднє свідчення історичним. Зміна hash/commit під час прогону дає unconfirmed.

## Додавання сценарію

1. У SPEC додайте унікальний ID: `REQ-ID-S01` або змістовний суфікс. Не змінюйте його після перейменування заголовка.
2. У traceability.json додайте `id`, `requirement`, `scope` і `tests`: точні `tests/path.py::test_name` або `tests/path.py::TestClass::test_name`. Посилання на функцію охоплює її параметризовані варіанти, не означає, що всі вони виконалися успішно. Wildcard і module-only не допускаються.
3. Для неавтоматизованої частини додайте `manual.procedure` — локальне посилання з anchor, та `manual.reason` — конкретну причину. Процедура описує кроки й очікуваний результат, а не вигаданий звіт виконання.
4. За потреби поставте `@pytest.mark.req("REQ-ID")` на конкретну test-функцію. Marker має відповідати матриці. Загальні module/class markers не підтримуються й не є покриттям.
5. Оновіть зміст SPEC і запустіть обидві команди. Якщо виявлена розбіжність коду та вимоги, дослідіть її; не змінюйте контракт для узаконення дефекту.

`scope` вказує межу перевірки. Наявність тесту не гарантує, що він доводить кожне речення вимоги; це перевіряє рев’ю. Ручні процедури [описано окремо](manual.md); їх результати треба записувати з датою, ревізією та фактичними доказами.

Покриття матрицею не є числом пройдених тестів. Реальне калібрування Evaluator та літературна оцінка мають власний набір і окремий дозволений бюджет.

Межа AST-перевірки: явно вимкнені через __test__=False або fixture визначення відхиляються; довільна динаміка pytest plugins не виконується валідатором. Фактичну collection і результат визначає pytest у verify.py.
