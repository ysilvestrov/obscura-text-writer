# Ревю архітектури Storygen — завдання для Codex

Дата: 20 жовтня 2026 року. Гілка: `feat/working-prototype`. Джерела ревю: `README.MD`, `SPEC.MD`, усі файли `docs/`, вибірково код (`storage/`, `generation/`, `application/exports.py`).

Статус документа: ревю й беклог пропозицій. Документ **не є** архітектурною специфікацією й не має переваги над `SPEC.MD`. Пропозиції стають контрактом лише після погодження власником і одночасної зміни коду, тестів і `SPEC.MD`.

## 0. Правила виконання для агента

1. Перед будь-якою зміною прочитайте `AGENTS.md` і відповідні розділи `SPEC.MD`.
2. Архітектурна зміна коду MUST оновлювати `SPEC.MD` (Requirement/Scenario, технічний опис, інваріанти, міграції, обмеження) у тому самому коміті.
3. Задачі з позначкою **[ПОТРІБНЕ РІШЕННЯ]** не виконувати, доки власник не обере варіант. Підготуйте короткий опис варіантів і зупиніться.
4. Кожне виправлення дефекту: спочатку RED-тест, що відтворює дефект, потім GREEN. Повний `pytest` має проходити.
5. Жодних платних модельних викликів, Cloudflare-операцій чи змін бюджету без окремої явної згоди користувача.
6. Не змінювати авторські оригінали, `data/`, `artifacts/`. Не послаблювати перевірки походження, цитат і ревізій.
7. Одна задача — один логічний коміт. Не змішувати рефакторинг із зміною поведінки.

Команда перевірки:

```powershell
./.venv/Scripts/python.exe -m pytest -q
```

## 1. Короткий висновок

Сильні сторони, які треба зберегти: незмінні версії з SHA-256, CAS-публікація, ідемпотентний `request_id`, відсутність прихованих повторів і fallback, явний слід спроби до виклику моделі, чесне розмежування технічного й літературного приймання.

Головні слабкості: груба незворотна модель застарілості; глобальна ревізія твору як замок; пам’ять, що лише накопичується; розмиті межі шарів; неефективний запис стрімінгу; контроль витрат поза продуктом; найменш розвинений контур якості (редактор і оцінювач).

## 2. Знахідки

Формат: ID — суть — докази — наслідок.

### Дані й консистентність

**F-01. Застарілість — незворотний булевий прапорець.**
- Докази: `src/storygen/generation/dependencies.py` (`invalidate_story_materials`, `invalidate_in_transaction` ставлять `stale=True`); `src/storygen/storage/repository.py` `set_head` відхиляє stale; SPEC A5: «жоден stale-статус не скидається автоматично».
- `invalidate_story_materials` позначає всі brief/draft/edited/memory/evaluation твору без урахування графа залежностей.
- Наслідок: після правки канону/стилю жодну наявну альтернативу не можна прийняти навіть свідомо; виняток `accepted_stale_prose_ids` (CONTEXT-003) — обхід цієї моделі.

**F-02. Ревізія твору як глобальний замок — хибні конфлікти.** [ПОТРІБНЕ РІШЕННЯ]
- Докази: `repository.py` `commit_stage_result` — `changed=story.revision!=attempt.context['story_revision']` для всіх етапів; `_touch_story` викликається майже всіма авторськими операціями та збереженням ролей (`authoring/blueprints.py`).
- Контексти memory та edit/patches (`generation/context.py`, гілки `stage=='memory'` і `edit_mode=='patches'`) не залежать від інших сцен, але зміна плану будь-якої сцени або налаштувань будь-якої ролі робить результат `alternative` і зупиняє багатосценовий запуск.
- Розбіжність із DATA-004 («матеріали, від яких залежав запит»): код суворіший за контракт. Згідно з AGENTS.md розбіжність треба явно дослідити, а не узаконити.

**F-03. SQLite використовується як документне сховище JSON.**
- Докази: `storage/migrations/001_initial.sql` — heads, stale, complete, trashed_at лише в `payload`; міграція 002 змінює JSON.
- Наслідок: FK не гарантують коректності голів; масові операції — повні скани з розбором JSON (`invalidate_story_materials`, `list_versions`, `list_runs` кожні 0,5 с у `worker.py` `_loop`).

**F-04. Порушення інкапсуляції репозиторію й інверсія шарів.**
- Докази: `repo._get`/`repo.db` використовуються в `authoring/trash.py`, `authoring/service.py`, `authoring/imports.py`, `authoring/blueprints.py`, `application/exports.py`, `evaluation/story_adapter.py` (рядок із прямим `UPDATE versions`), `generation/worker.py`; `storage/repository.py` імпортує `generation.dependencies`.
- Наслідок: правило «лише активні об’єкти» не централізоване. Відомий дефект SPEC Known limitations №1 підтверджено: `application/exports.py` читає твір через `_get` і сцени SQL-запитом без фільтра `trashed_at`.

**F-05. Немає інструмента цілісності.** FS/SQL без спільної транзакції задокументовано, але немає перевірки сиріт, висячих голів і хешів усього каталогу та штатного резервного копіювання.

### Пам’ять і контекст

**F-06. Пам’ять лише накопичується.**
- Немає операцій update/retire; `character_states` накопичують суперечності.
- Семисценовий прогін: 11 → 74 записів, оцінка входу пам’яті 5393 → 31382 токенів на 5426 слів. Екстраполяція на 15 тис. слів — порядку 85 тис. токенів.
- Режим `snapshot` вимагає дослівного повтору всієї пам’яті моделлю — причина інциденту `finish_reason=length` (docs/usability-and-seven-scenes.md).

**F-07. Письменник/планувальник отримують сирий JSON пам’яті з цитатами й UUID.**
- Доказ: `generation/context.py` — `'ЗДІЙСНЕНІ ПОДІЇ — ПЕРЕВІРЕНА ПАМ’ЯТЬ\n'+past.model_dump_json()`.
- Цитати потрібні для валідації, а не для письма; це головне джерело роздування контексту.

**F-08. Оцінка токенів сильно завищена для кирилиці.**
- Доказ: `context.py` `make_context` — `ceil(len(utf8)/2)+64` ≈ 1 токен на кириличний символ.
- Факт: 32716 оцінка проти 14702 prompt_tokens провайдера (×2,2). Відсікає локальні моделі з 8k контекстом — цільове обладнання з початкового дизайну.

**F-09. Письменник бачить плани всіх наступних сцен, включно з фіналом**, без налаштування горизонту (`context.py`, цикл «МАЙБУТНІ ПОДІЇ»).

### Виконання

**F-10. Квадратичний і синхронний запис стрімінгу.**
- Доказ: `generation/stages.py` — на кожну delta `repo.files.write(partial, весь текст)`; `storage/files.py` `write` робить fsync + replace; `worker.py` `event()` — окрема `BEGIN IMMEDIATE` транзакція з `MAX(seq)` на кожну delta.
- Наслідок: O(n²) запис, тисячі fsync на відповідь, конкуренція за write-lock SQLite з UI.

**F-11. Одна черга для всіх ресурсів.** Локальний GPU, хмарні провайдери й Codex CLI (timeout 300 с) серіалізовані разом. Для VRAM виправдано, для хмари — ні.

**F-12. Неформалізований автомат станів запуску.**
- `TERMINAL` у `worker.py` змішує завершення й зупинки (paused, interrupted, needs_review, alternative).
- `cancel` переводить failed/alternative у cancelled (перевіряється лише `completed`).
- Один `alternative` завершує весь `remaining`-запуск без вибору для автора.

**F-13. Контроль витрат поза продуктом.** Резерви, ledger і стоп-ліміти існують лише в приватних скриптах `artifacts/*/run.py`. У продукті немає бюджету запуску/твору (SPEC A4, Known limitations №5).

### Провайдери й оцінювач

**F-14. Два паралельні шари провайдерів.** `providers/` (local/openrouter/venice) і `evaluation/gateway.py` + `evaluation/codex_gateway.py` (local/openrouter/codex) з окремими конфігураціями й timeout. Venice недоступна оцінювачу — ризик відмов саме на дорослому матеріалі, для якого підключено uncensored-моделі.

**F-15. Слабкий контур якості.** Захист `patches` лексичний і не ловить граматичних регресів (Qwen: «відбиваючи»); підтверджені автором дефекти не стають fixtures; контрольний набір — 10 прикладів; сумісність промпту з режимом — ручна вказівка «очистіть власний промпт».

**F-16. Налаштування ролей прив’язані до твору**, без профілів. Кожен новий твір вимагає ручного налаштування 4 ролей (context 131072, output 6144 тощо).

### Специфікація й документація

**F-17. Нормативні правила в прозі.** Багато інваріантів SPEC.MD (ліміти CopyEdits, критерії калібрування, правила reuse) є лише в розділі Architecture, не в Requirement/Scenario; переважно один Scenario на Requirement; немає зв’язку Requirement ↔ тест.

**F-18. Документи — журнали з розбіжними числами.** Кількість тестів: 130/145/151/182/186/189/205; README — 205, `docs/prototype-acceptance.md` — 182. Розділ «Запуск» README починається нерелевантним реченням. Немає ADR: рішення (evidence_delta, patches, no fallback, Venice лише uncensored) розкидані по звітах.

**F-19. Надщільний стиль коду** (крапки з комою, багато логіки в рядку) ускладнює супровід системи з тонкими інваріантами.

## 3. Беклог задач

Пріоритети: **P0** — дешево й великий ефект; **P1** — наступний етап; **P2** — далі. Кожна задача має критерії готовності (DoD).

### P0

**T-01. Централізувати правило активних об’єктів; виправити експорт кошика.** (F-04, SPEC Known limitations №1)
- Експорт використовує `_active_story` і лише активні сцени; архівний твір не експортується.
- Прямий `UPDATE versions` з `evaluation/story_adapter.py` перенести в метод `Repository`.
- Додати перевірку (тест або import-linter), що `repo._get`/`repo.db` не використовуються поза `src/storygen/storage/`; існуючі звертання перенести в публічні методи репозиторію поетапно.
- DoD: RED/GREEN-тести «архівна сцена не входить в експорт» і «експорт архівного твору → 404/400»; пункт №1 Known limitations у SPEC.MD замінено описом усунутого відхилення; EXPORT-001 і DATA-006 доповнено сценарієм.

**T-02. Конфлікти публікації за залежностями.** [ПОТРІБНЕ РІШЕННЯ] (F-02)
- Варіант A: під час commit перераховувати fingerprint контексту на поточному стані й порівнювати з fingerprint спроби.
- Варіант B: перевіряти голови й stale для `input_refs` + ревізію сцени; ревізію твору — лише для етапів із матеріалами всього твору (brief/draft/prose-edit).
- В обох варіантах зміна налаштувань ролі не збільшує ревізію твору (вона вже у fingerprint).
- DoD: тест «правка плану сцени 6 під час memory сцени 2 → completed, не alternative»; тест «зміна вхідної прози → alternative»; оновлено DATA-004, A2, A5 SPEC.MD.

**T-03. Буферизований стрімінг.** (F-10)
- partial: дозапис без fsync під час потоку, скидання раз на 0,5–1 с або N КБ, fsync і атомарна фіксація в кінці.
- Події delta групувати; `seq` — лічильник у пам’яті під `condition` з ініціалізацією з БД.
- Збереження інваріантів PIPE-005/PIPE-007: partial після збою містить текст до останнього скидання; частковий текст ніколи не стає версією.
- DoD: тест на кількість записів/транзакцій на 1000 delta (верхня межа); тест відновлення partial після переривання; SSE replay працює; оновлено PIPE-007 і A5.

**T-04. Калібрована оцінка токенів.** (F-08)
- Зберігати для ролі коефіцієнт `chars_per_token`, оновлюваний з `usage.prompt_tokens` (якщо провайдер повертає); типовий — поточна консервативна формула.
- Запас безпеки (напр. +15%) обов’язковий; приховане обрізання заборонене.
- DoD: тести оцінки з коефіцієнтом і без; `estimate_method` у ContextBundle відображає метод; оновлено CONTEXT-001 і A5.

### P1

**T-05. Похідна застарілість.** [ПОТРІБНЕ РІШЕННЯ] (F-01)
- Версія зберігає відбиток входів; статус fresh/outdated обчислюється з поточного стану.
- Окремий запис авторського рішення «прийнято попри зміни» (хто/коли/які входи).
- Масова інвалідація лише за графом залежностей.
- Прибрати `accepted_stale_prose_ids` або звести до похідного правила.
- DoD: міграція схеми з тестом на старій БД; сценарії DATA-005, DATA-008, CONTEXT-003 переписані; прийняття застарілої альтернативи — лише з явним підтвердженням.

**T-06. Пам’ять v2.** [ПОТРІБНЕ РІШЕННЯ] (F-06, F-07)
- Операції `add` / `update` / `retire` з `evidence_id`; повний журнал для валідації.
- Проєкція «поточний стан» для письменника/планувальника: без цитат і UUID, відбір за персонажами сцени.
- `evidence_delta` — типовий режим; `snapshot` позначити застарілим.
- DoD: тест росту контексту на синтетичних 15 сценах (обмежений); тести retire/update із перевіркою джерела; оновлено MEMORY-001/002, CONTEXT-002, A6.

**T-07. Єдиний реєстр провайдерів.** (F-14)
- Спільний модуль підключень, перевірок можливостей, timeout і обліку вартості для генерації й оцінювача; Codex CLI — окремий адаптер того ж інтерфейсу.
- Venice і local доступні оцінювачу (каталожна перевірка uncensored зберігається).
- DoD: наявні тести оцінювача й генерації зелені; оновлено MODEL-*, A4, A7.

**T-08. Бюджет у продукті.** (F-13)
- Таблиця ledger: резерв перед викликом (ціна з каталогу × max_tokens + вхід), заміна фактичною вартістю, повний резерв для невідомої.
- Ліміти на запуск і на твір; перевищення — відмова до відправлення.
- DoD: тести резерву, заміни й відмови; UI показує резерв і фактичні витрати; новий Requirement у SPEC.MD; Known limitations №5 оновлено.

**T-09. Черги за ресурсами.** (F-11)
- Лейни `local-gpu`, `openrouter`, `venice`, `codex`, кожна з паралельністю 1; порядок у межах твору зберігається.
- DoD: тест «хмарний оцінювач не блокує локальну генерацію іншого твору»; оновлено PIPE-002 і A5.

**T-10. Явний автомат станів запуску.** (F-12)
- Таблиця дозволених переходів + тест на кожен перехід; розділити `finished` (completed/failed/cancelled) і `stopped` (paused/interrupted/needs_review/alternative).
- `cancel` не змінює finished-стани.
- `alternative` у `remaining` → пауза з вибором автора.
- DoD: оновлено A5, PIPE-004/005, DATA-006 (умова архівації).
