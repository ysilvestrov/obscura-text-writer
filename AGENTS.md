# Правила проєкту

## Архітектурна специфікація

- Коренева [SPEC.MD](SPEC.MD) є головним джерелом правди щодо архітектури проєкту. Перед архітектурними змінами прочитайте відповідні розділи.
- Будь-яка архітектурна зміна коду MUST бути відображена у SPEC.MD в тому самому наборі змін і коміті. Робота не завершена без актуальної специфікації.
- Архітектурні зміни включають компоненти та їхні межі, домен/схему даних, збереження й версії, залежності та інвалідацію, чергу/відновлення/стани, контекст і пам’ять, провайдерів, API й контракт UI/сервера, конфігурацію/секрети, оцінювання, експорт, безпеку та спосіб запуску/пакування.
- Оновлюйте відповідні OpenSpec Requirement/Scenario, технічний опис, інваріанти, сумісність/міграції та відомі обмеження. Для виправлення дефекту вкажіть усунене відхилення; не залишайте опис відомого дефекту як чинний факт.
- Розбіжність між кодом і специфікацією треба явно дослідити. Не переписуйте вимогу лише для узаконення регресії; навмисна зміна архітектури змінює і код, і контракт. Відомі дефекти відокремлюйте від бажаної поведінки.
- Старі плани, бріфи, чати й звіти не мають переваги над чинною SPEC.MD щодо архітектури. Специфікація не скасовує інструкцій вищого пріоритету та прямих актуальних рішень користувача.
- Мова документації — українська; структурні маркери OpenSpec (`Requirement`, `Scenario`, `GIVEN`, `WHEN`, `THEN`, `SHALL`, `MUST`) залишаються англійськими.
- Кожен Scenario має сталий унікальний ID та запис у `docs/verification/traceability.json` із конкретним тестом або явною ручною процедурою й причиною. Зміну перевіряйте `python scripts/check_docs.py`; відсутній зв’язок є помилкою цієї команди. Наявність тесту/процедури не оголошуйте успішним виконанням; фактичний запуск документуйте через `python scripts/verify.py` у `docs/STATUS.md`.

## Актуальність користувацької документації

- Кожна зміна коду, що входить у коміт, MUST бути розглянута на необхідність оновлення користувацької документації, включно з інструкціями встановлення, користування й зображеннями інтерфейсу. Це правило діє також для неархітектурних змін.
- У повідомленні коміту або описі PR зазначайте оновлені інструкції/мовні версії або конкретну причину, чому зміна документації не потрібна. Сам факт проходження тестів не замінює таку перевірку.
- Користувацькі інструкції сайту лежать у `docs/site/{uk,en}/` (маніфест `docs/site/site.json`). Змінивши одну мовну версію сторінки, оновіть іншу й підтвердіть пару `python scripts/check_site.py --rehash <slug>`; інакше `scripts/check_docs.py` падає. Підтримуйте українську й англійську документацію узгодженими; знімки редактора й налаштувань використовуйте лише з нейтральними прикладами без приватних матеріалів. Архітектурна SPEC.MD і її traceability залишаються обов’язковими незалежно від сайту.

- Активний порядок розробки: [беклог R-01…R-15](docs/superpowers/plans/2026-10-20-remediation-backlog.md), погоджений власником 20.10.2026. Продовжуйте з першої незавершеної задачі, враховуючи залежності.
- Стан, перевірки та рішення записуйте в [журнал виконання](docs/superpowers/plans/2026-10-20-remediation-progress.md). Перед реалізацією кожного пакета оформлюйте окрему специфікацію зміни; нові відкриті продуктові рішення не вважайте автоматично погодженими разом із порядком робіт.

## Завершення задачі та збереження результатів

- Після завершення погодженої задачі MUST зафіксувати перевірені зміни комітом, відправити гілку в GitHub і створити або оновити PR. Посилання на PR навести у відповіді користувачу.
- MUST оновити основну робочу теку `C:\Projects\text-generator` до перевіреного результату. Не залишати єдину копію змін у тимчасовому worktree або лише в локальному коміті.
- Перед оновленням основної теки перевірити її локальні зміни. Зберегти резервну копію правок, що перетинаються з оновленням, та узгодити їх без втрати авторських позначок, конфігурації, даних і сторонніх незавершених файлів. Не використовувати `reset --hard` або `clean` для такого оновлення.
- Після оновлення перевірити ревізію основної теки та наявність потрібних файлів. У підсумку вказати PR, коміт і стан основної теки; явно повідомити про перешкоду, якщо збереження в GitHub або синхронізацію не вдалося завершити.

## Cloudflare: бюджет

- Користувач використовує Cloudflare Free і хоче залишатися на Free.
- Перед конфігурацією або операцією Cloudflare, яка ймовірно збільшить щомісячний рахунок, потрібна окрема явна згода користувача з поясненням можливих платежів: підписка, ставки використання та відповідні ліміти.
- Операції, які безкоштовні за умовами сервісу або очевидно малим обсягом лишаються в безкоштовному ліміті, можна виконувати в межах уже погодженого проєкту без повторного погодження бюджету.
- Перевіряйте актуальні ціни та ліміти конкретної зміни. Малий трафік не робить обов’язкову платну мінімальну підписку безкоштовною.

- Усі PR MUST відкриватися виключно на `main`, ніколи на побічні гілки.
